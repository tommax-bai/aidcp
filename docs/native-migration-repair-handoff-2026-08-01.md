### 1.2 修掉的九条「说成功、实际没发生」

| 缺陷 | 改前 | 改后 |
| --- | --- | --- |
| **重连认错浏览器**（整批唯一会张冠李戴） | 只按端口 + 平台域名挑目标，同机多开时端口被回收复用 → 可能附着到别人的分身，之后动作全记到别人账下 | 重连时实读浏览器自报身份并比对准入基线；对不上拒绝，**没基线在碰端点之前就拒绝** |

| **设为封面** | 往上找容器停在轮播「当前显示」层 → 判据恒真 → 连按钮都不点 | 有界回溯只认真正的图片项容器，证据须封面专属 |
| **搜索筛选** | 误判后既不点、也进不了未确认分支 → 把**未筛选**结果当筛过的返回 | 有界轮询确认，确认不上如实报未确认且**不返回卡片** |
| **评论输入框** | 判据里硬写「或者是评论框」＝ 无条件回成功 | 改读焦点落位 |
| **评论点赞 / 兼容步骤** | 类名宽松子串，否定形（`not-selected` / `unliked`）也被读成正证据 | 改读图标状态位 + 有界轮询等翻转 |
| **同意闸** | 「点过接受但复探读不回来」与「压根没探到」回执上一模一样 | 两者可分；不确定就停手，不拿「不知道」冒充「已清掉」 |

## 5. 别再踩的坑（★ 是本轮新踩的）

- ★ **别让三个 Rust 编译同时跑。** 本轮开三条并行线，三个 agent **全部被看门狗判定卡死**——
  机器资源被 cargo 挤爆。工作没丢（改动都在，只是没提交），但要人接手补格式化、补验证、补提交。
  **并行的粒度放在「写代码」上，编译与测试串行。**
- ★ **控制仓提交必须精确到路径。** 本仓长期有 5–8 个 session 并发编辑，
  **`git add -A` / `git add openspec/` 会把别人正在编辑、还没写完的文件一起提交走**。
  本轮实际发生过：我 6 个文件的改动被另一个 session 的全量暂存提交带走，内容没坏但提交说明彻底丢了。
  **救回损失的习惯**：把「为什么」写进**文件本身的注释**（`<!-- 2026-08-01 用户裁定… -->`），不要只写在提交说明里。
- ★ **`scripts/land-change` 认不出带 `codex/` 前缀的分支。** 早先由其他工具建的 worktree 分支名是
  `codex/<change-name>`，集成脚本按不带前缀的名字找，会报「分支不存在」。
  **但它此时已经做完 rebase 了** —— 手动收尾即可：确认 `git merge-base --is-ancestor origin/master HEAD`，
  再 `git push origin HEAD:master`，然后同步主 checkout。
- ★ **全量 `npm test` 很慢（本机十几分钟起），但 MUST NOT 因此跳过。**
  本轮它抓到**两条**只有它能抓到的失败，而类型检查 + `gate:native` + `test:acceptance`
  三道网**合起来也漏掉了这两条**。做 3.2 的子代理没跑全量，所以两条都没被发现。
  1. 假引擎还在发那个已从线路上删掉的预算字段，用例还在断言旧的 `min(请求, 事实源)` 语义。
  2. **3.1 建的机械对账用例失去了对账对象** —— 它从引擎源码正则抓预算数字、断言与宿主表逐字相等，
     而 3.2 把引擎侧的数字删光了。
     **⚠️ 这条的正确处置不是删用例。** 它守着两件事，3.2 只让其中一件过期：
     「两边数字不漂移」确实无从谈起了，但「**引擎新增窗口却漏进宿主表**」仍然要守 ——
     宿主表同时是**准入白名单**，标签认不出就否决这次窗口，那条不可逆写入就此失去写保护、
     且**运行期才现形**。已改写成两条新断言（引擎源码里不得再出现预算数字 + 每个标签必须在白名单里），
     并逐条做了变异验证证明它们真会红。
  **教训**：删一条红掉的守护用例之前，先问它到底在守几件事。只让其中一件过期时，
  删掉等于把剩下那件静默放生 —— 而它看起来仍然「有测试覆盖」。
  - **诊断姿势**：别用 `npm test | tail`——管道要等进程结束才吐，看着像卡死。
    `npm test > /tmp/x.log 2>&1` 落盘再看，能实时看到跑到哪、有没有 `✖`。
  - 单文件跑很快（十几秒到一分钟），定位到嫌疑文件后直接点名跑。
- ★ **有一条会拦下集成的既有 flake，别以为是自己改红的。** 会话恢复那条
  （「缓存会话的传输已死时走重建」）在满负载并行跑全量时偶发管道断裂，单跑必过。
  2026-08-01 当日出现两次，两次都用基线对照证明**非当批引入**。
  **⚠️ 但它不只是测试偶发**：同一个竞态在生产上会让「传输已死」被判成「还活着」，
  于是去写一个已死的管道、拿到异常，而不是走进已经写好的重建路径 —— 一个结构性事实被表达成了异常。
  完整登记与建议修法在运行时契约 change 的 §12。**MUST NOT 给它加重试或标成允许失败**，

## 10.1 它不是「打字方式」的问题，是一条活的假成功

原以为这条只是「把整段赋值换成逐字打」。实读之后发现判据本身在说谎：

注入路由的做法是——把整段正文 `before + ' #话题'` **一次性重新赋值**，点完候选之后，
拿「正文里搜得到这几个字」当确认。**而它读回的正是自己刚写进去的那串。**
候选点没点上、平台受没受理，判据都为真。

- **后果不是「没贴上就报错」，是「没贴上也报成功」**：稿子发出去时话题只是一串普通文字，
  拿不到话题带来的分发，回执上一切正常，云端也看不出来。
- **这条路径是活的**：云端对每条稿子的**每一个 tag** 都下发一条这样的指令。

★ **可复用的判断法**：一个后置判据，先问它读的那份东西**是不是我们自己刚写进去的**。
是的话，它证明的是「输入发生了」，不是「平台受理了」——这两件事在写动作上永远要分开。
本轮 §9 的 H.1（评论到达确认）与这一条是**同一种病的两个实例**，都在同一天被找出来。

## 10.2 修法：整套移植退役实现，不自创

退役 TS 实现早就解决过，而且是**实机校准**的：逐字打触发串 → 轮询建议下拉 →
**只点**「文本精确匹配的候选」或「新建话题」那一项 → 真实鼠标事件（页面侧 `.click()`
实测**不提交**那个待定 span）→ 要求正文里出现真 token `a.tiptap-topic[data-topic]`，
剔掉隐藏后缀，**精确相等**而非子串（子串会让已存在的 `#考研数学` 替 `考研` 顶包）。

选择器、两个 4s 窗口、判据，一律照搬，**没有一处是在桩上现编的**。

**三条值得记住的设计约束**（都写进了代码注释）：

1. **认不出目标候选就不点。** 随便点一个的代价是**不可逆**——稿子上贴了一个无关话题，
   之后没有任何一步会去撤它。诚实的做法是不点、如实回未确认，正文里留一串裸 `#关键词`
   （与退役实现同行为），云端算尽力而为、**稿子照发**。
2. **打字之后没有安全取消点，这是有意的。** 本路径唯一的清场原语是**整字段清空**，
   而那一刻正文里躺着整篇稿子，清它等于毁稿。所以取消只在打字**之前**生效；
   之后把两个有界窗口跑完再让位（≤8s），且**每个出口都回「不确定」、绝不回「未开始」**。
3. **只截 `topic` 一种。** `mention` / `location` / `collection` 仍走注入路由——
   它们**没有任何实机校准过的 token 判据可移植**（退役实现对这三支用的也是通用锚点 + 页面子串，
   同样自证）。只把打字搬进引擎、判据仍留自证，**等于把同一个谎言搬进更新的代码**。
   ★ 这条取舍值得单独记：**做一半比不做更坏的场合，就是「判据仍会说谎」的场合。**

④ 候选放宽成「取下拉第一项」→ 「全是无关词时不许点」红。Rust 两次输出里都有 `Compiling`。

## 11.1 ★★ 最重要的一件：spec delta 与实装大面积对不上

按 §8.1 那条纪律（「归档前把每条具名偏离对着 delta 读一遍」）实做了一遍，**结果比预期严重**：

**`specs/` 里有 8 条 MUST 与实装相反。** 照原样归档就会把它们并进主 spec。

原因是系统性的，不是本 change 独有：**delta 是 propose 当时按「意图」写的**，
而实装期跨了好几轮裁定 —— 验证码协助拟人化（2.9）、注入路由点击助手（3.7）、
锚点暂存与晋升（5.4 / 5.5）、定时设置、遗留步骤路径，**先后被显式弃守或收窄，
而 delta 一次都没跟着改**。

**没有任何东西会拦**：`openspec validate --strict` 只校验 delta 的内部结构、从不比对实现；
归档流程也不问。逐条清单与建议改法已写进 `tasks.md` 的
**「归档前置 — spec delta 与实装的逐条对账」**一节（含两条尚未读完、需要收口时补的）。

- **改法不是把 MUST 删掉。** 弃守的是「本 change 交付这件事」，不是「这件事不该做」。
  正确形态照迁移主线 3.2 的口径：**规格只能写「已实现」那一列** ——
  未交付的部分要么从 delta 摘出去另立，要么把要求收窄到实际成立的范围，并留下承接方。
- ★ **同批其余几个 change 归档前都该做一遍同样的对账**（它们的 delta 也都是 propose 期写的）。
  这条建议的成本很低、漏掉的代价是主 spec 长期失真。

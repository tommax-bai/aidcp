# 决策记录：跨库锁与服务间异步总线**不引入 Redis**

> 提问（用户，2026-07-25）：「跨库锁和队列，我们是否可以引入 redis 来进行」，随后澄清「队列指服务间通信的异步队列」。
> 结论：**两个问题都是「不引入」，但理由完全不同**——锁是**技术上不能**，总线是**这套部署下代价远大于收益**。
> 产出方法 = 本仓 CLAUDE.md §3 的「业界方案」四步：① 代码里坐实现状 → ② 多角度业界模式 → ③ 综合成案 → ④ 对抗性评审。
> 两轮多 agent 论证（8 + 9 个 agent，含各自的最强辩护人与对抗性评审员），基线 cloud `7c2f6e3`。
> **本文已把对抗性评审推翻 / 更正的部分逐条折进去了**（见 §6），不是综合稿的原样转录。

---

## 1. 一页结论

| 问题 | 结论 | 一句话理由 |
|---|---|---|
| **跨库锁** 用 Redis？ | **不能** | 围栏令牌必须由资源侧校验，而让 PostgreSQL 校验它本身就已经是互斥；且锁的生命周期必须与事务是同一个对象。Redis 的最强辩护人自己算出「能帮 0 处」。 |
| **服务间异步总线** 用 Redis？ | **不引入** | 事务型入队做不到（业务写在 PG、入队在 Redis = 双写裂缝），所以 Redis 只能加在 outbox **之后**，净增一跳；而它独有的收益有两个**零新组件**的先手可以吃掉。叠加这套机器的实测形态（见 §4），代价远大于收益。 |

**真正的缺口是「传输」，不是「队列」。** 今天 `event_outbox` 一个组件干了两件事：**事务型入队**（业务写与"我要发这条消息"同一笔提交）与**传输**（消费者直接连库读那张表）。库一分开，第二件事就不合法了——跨服务消费等于跨库直读。
**推荐答案**：入队留在 outbox（它已经做得比 Redis 好），传输改为「生产方进程内中继 → 经内部 HTTP 推给消费方 → 消费方在自己库里 inbox 去重」。零新基础设施，零新运行时依赖，全程没有任何域读另一个域的库。

## 2. 锁：为什么是「不能」而不是「不推荐」

### 2.1 五条独立理由（任一条单独足以否决）

1. **围栏令牌的技术必然性。** Kleppmann ↔ antirez 之争在本项目收敛到同一结论：不带围栏的分布式锁在**正确性**场景不安全；带围栏，则围栏**必须由被保护的资源**校验。而让 PostgreSQL 校验一个围栏号 = 版本列 + 条件 `UPDATE` + 零行诚实拒绝——**那本身就是互斥**。于是 Redis 退化成纯开销 + 一个新故障域 + 一套新凭据面。仓里已有两处成熟实例在这么做（互动运行控制的 version CAS、`publish_log.content_version`）。

2. **锁的生命周期必须与事务的生命周期是同一个对象。**
   - PG 行锁：后端进程死 → 锁释放**并且**未提交工作原子回滚。两件事**不可拆**。
   - Redis 锁：解锁点由**每个调用点的代码顺序**决定，而四种顺序全部有害——提交前解锁 = 互斥消失；提交后崩 = 自死锁到 TTL；回滚了锁还在 = 幻影互斥；TTL 早于临界区 = 静默双写。**且写错顺序没有任何机械手段会告警。**
   - 叠加本项目的部署形态被钉死为「先停再起」，而其中一处临界区必须容纳 180 秒的模型调用 ⇒ **每一次部署都可能留下一具死锁尸体，而恢复逻辑本身需要那把锁**。

3. **它会降级一条现有的机械保护。** 自动化写者锁的键里带着 `dev`/`ol` 标识、且挂在**共享**库上 ⇒ 一个 `.env` 里标识配反的进程去抢的是**同一把锁**、当场被抓住。换成「每台机器一个 Redis」，配错的线上进程会在**自己机器的** Redis 上顺利拿到 `dev` 那把锁。而「标识配反」在这套部署里**有前科**。

4. **本仓准入条款直接排除它**（不用走类比）：跨服务的授权、互斥与业务事实 MUST 落成数据库持久记录或持久消息；业务副作用的唯一性 MUST 落在唯一约束、条件 `UPDATE` 或 claim/lease 上。Redis 三项皆不是。

5. **绝大多数处收口后就不需要跨域互斥了。** 把「由错误一方发起的事务」搬回属主之后，剩下的多数只是「两笔提交谁先 + 幂等键」，而**幂等键已经在表结构里**（`(platform, env_key) WHERE state<>'purged'` 之类的部分唯一索引、`UNIQUE(env_key)`、审计表主键），重试驱动**已经在跑**（人工请求的调用方 + 60 秒对账循环）。
   > **互斥解决「同时」，幂等 + 排序解决「重来」。把后者当成前者，才会得出「需要一个外部协调存储」。**

### 2.2 ⚠️ 一处必须更正的原始结论：**不是「0 处需要跨域互斥」**

综合稿曾断言「收口后需要跨域互斥的处数 = 0」。**对抗性评审推翻了这一条，且仓里已有文档写着它错**：

- 那份 8 处清单**只有 api → automation 一个方向**。反方向真实存在，且属主收口消不掉：
  - `interaction-store.ts` 的 `upsertAuthStatus`（**automation** 属主事务）去锁 `client_environments`（**api** 属主），命中 0 行时回落锁 `client_env_scope`（同样 api 属主）；
  - 同文件 `assertAccountScope` 在 automation 事务内对 `client_env_revocation_holds`（api）与 `accounts`（api）取 `FOR SHARE`。
- 互斥对手写得很清楚（`src/db/environment-row-lock.ts` 文件头）：「写侧（客户解绑 / 批量改派 / 撤销对账）拆分后属 api，边缘上报的环境登录态首写属 automation」。
- `docs/cross-service-shared-state-inventory.md` 早已把 `upsertAuthStatus` 登记为跨服务，并在「残留缺口」写明「把写点收敛到数据所有者服务的窄内部端点仍待做」。

⇒ **这是一处真正的跨属主互斥**：api 的归属撤销/改派 ⟷ automation 的授权首写。两个对手**按定义在两个域**，所以「属主本地行锁 + 幂等键」这条公式在这里落空。

**但这不改变结论**，只改变理由的形状：这一处的正解是**把写点搬进属主域**（automation 侧变成一次 RPC，互斥落回 api 侧一张表上的条件写），**不是**加一个锁服务。RPC 本身不持锁——这正是「要么条件写、要么分布式锁」的分叉点，而本项目的答案一贯是前者。

另：**「8 处」这个分母本身不完整**，反向至少再加 3 个取锁点。

### 2.3 唯一的窄口子（有条件的「能」）

**只有写者选举（leader election）**，且不承载授权 / 业务事实 / 准入闸。必须同时满足：

1. 属主收口已完成，且仍剩 ≥1 处**经证明**无法收进单一属主的互斥；
2. 它跨的是**进程 / 服务**，而**不是** dev ↔ ol 两个 target（跨 target 一律留共享 PG）；
3. 只是选举，不做别的；
4. 生产上真的分出了 ≥2 个进程，且有**实测数据**证明属主库内的行锁做不到。

当前一处都不满足。而且即便满足，正解仍不是 Redis——是让锁住进属主自己的库（automation 库仍是**一个**库、同时服务两个 target ⇒ 键里那个标识哈希原封不动继续有效，跨 target 互斥免费保住）。

## 3. 总线：为什么是「不引入」

### 3.1 硬阻断：事务型入队做不到

业务写在 PG、入队在 Redis = 两次提交 = 双写裂缝，**两个方向都是第一红线形态**：
- PG 成功 / Redis 失败 ⇒ **静默漏投**；
- Redis 成功 / PG 失败 ⇒ 下游为**没发生的事**行动，并写自己的审计说做完了。

修它的标准答案就是「在 PG 里放 outbox，再中继到 Redis」⇒ **Redis 不取代 outbox，它是 outbox 之后多加的一跳。**

### 3.2 Redis 独有且真实的收益只剩两项——而两项都有零新组件的先手

| Redis 独有 | 零新组件的先手 |
|---|---|
| 逐条 ack + 待处理表 ⇒ 单条毒消息不堵队头 | **消费游标的键从 `(consumer, target)` 扩到 `(consumer, target, topic)`** ⇒ 毒消息只堵它自己那条主题 |
| 唤醒流量完全不碰生产 PG | **接上已预留的 `LISTEN`/`NOTIFY` 唤醒**——`wake()` 方法就在原语里、**生产代码零调用者** ⇒ 毫秒级唤醒 |

两项都必须**先用掉**，再谈 broker。配套纪律：专用连接 + 有界重连 + 监控通知队列占用，且**绝不因为接了通知就放宽轮询周期**（原语已把这条写成 MUST NOT）。

### 3.3 真实流量清点（决定性的一节）

| 流 | 方向 | 消费者 | 触发 | 量级 |
|---|---|---|---|---|
| 风控命令 | api → automation | 1 | **人工点按钮** | 每天个位数，< 1 条/秒，约 100–300 字节 |
| 面板事件 | automation → api | 1 | 编排事件 tee | 推导 ≈ 4 条/秒（15 并发）/ ≈ 12 条/秒（45 并发） |
| 账号删除级联 | api → {content, automation} | **2（唯一扇出）** | 删账号 | **0，且结构上不可能非 0**（全仓零 `DELETE FROM accounts`）|
| 稿件审批 outbox | automation ↔ api | 1 | 审批 | **今天唯一真在生产跑的跨服务异步流** |

三个改变结论的事实：
1. **全仓只有 2 个已定义的通用 outbox 主题**（面板事件、风控命令）。
2. **这两条流从未在生产运行过**——都被运行模式门控，而 dev/ol 都跑单体 ⇒ 零遥测，上面的量级是从平台配额与事件链**推导**的，不是实测。
3. **唯一的扇出流是一条永远不会触发的流。** 扇出是 broker 相对点对点 HTTP 的核心优势，而这里分子是 0。

⇒ 在「2 个主题、1 个消费者、每天个位数到十几条/秒、唯一扇出永不触发」的规模上，broker 的主要收益（削峰、消费者组、高吞吐、扇出）**一项都用不上**。

## 4. 这套机器的实测形态（支持「不引入」的决定性证据）

> 2026-07-25 只读探测两台机器。**注意：下面第 1 条推翻了「本项目零 Redis」这个说法。**

1. **dev 上已经跑着一个 Redis**（`127.0.0.1:6379`，v6.2.20），但它是 **isales 的**——3 个 isales 进程共 6 条活连接，`redis.service` 这个 unit 名也被它占着。红线是「绝不碰 isales」⇒ aidcp **既不能用它、也不能改它的绑定**，只能起**第二个** Redis：第二个端口、第二份配置、第二个数据目录、第二个 unit、第二个密码。此后 dev 上每一次「Redis 挂了」的排查，第一步都得先回答「哪个 Redis，我刚才有没有踩红线」。
2. **监控为零**：node_exporter / prometheus / grafana / zabbix / telegraf / filebeat **全部未运行**。running 的只有云厂商的安全与助手 agent。**机械上无人在看监控**；唯一告警通道是应用自己写告警表 + 推飞书卡。
3. **自动备份为零**：root 无 crontab，PG 备份目录为空，WAL 归档关闭，复制槽 0。所谓备份 = 部署 session 手工丢下的一次性压缩包。
4. **但 PG 的单条提交耐久性是真的**：`fsync=on`、`synchronous_commit=on` ⇒ COMMIT 返回 = 字节已进磁盘 WAL。
5. **两台都没有容器编排**；部署 = rsync 源码 + systemd，无 build 步。
6. **ol 那台内存 3560 MB、没有本地 PG**（跨公网连 dev 那台的 PG，RTT ≈ 9.4 ms）。当前 aidcp 进程树已占 ~480 MB，而**拆完是三个 node 进程、各带一套编译壳** ⇒ 这在 3.5 GB 的盒子上本身就已经是个真问题，broker 是加在它之上。
7. **两端 Node 大版本不同**（dev v20 / ol v22）。
8. **ol 几乎空转**：24 小时 7 行日志、8787 零连接、委托任务全生命周期 5 条、标识为 ol 的账号 0 个。⇒ 「规模」这一项的分子也是 0。

**所以支持 PG 的论点不是「PG 运维得好」**（§4.2/4.3 说明它并不）。而是：**PG 是这套 fleet 上唯一一个已经进了部署清单、唯一一个失败方向被设计成 fail-closed、唯一一个能用团队真在用的工具（SQL）翻查的有状态组件。给一个连第一个有状态组件都运维不好的车队加第二个，是在放大已知缺口。**

### 4.1 拓扑题的答案（两种都否）

- **一个实例（放 dev 机）**：ol 生产的异步链路可用性从 `P(PG)` 变成 `P(PG) × P(broker)`，严格更差、无补偿；而 dev 按章程就是**不稳定那台**（主干高频部署位）。且 PG 挂 = 响亮 fail-closed，Redis 挂 = 按其配置**重启本身就是一次丢数据事件**。两种失败方向不是一个量级。另需公网暴露，而 Redis 没有 `pg_hba` 等价物。
- **两个实例（各机一个）**：唯一真收益是 target 物理隔离（承认这比列过滤好）。但**版本漂移会更糟，不是更好**——共用一张表时，格式漂移会被这套 fleet **唯一已有的机械闸**（迁移账本 + schema 契约门，且放行通道必须填具体版本 id）撞破；两个 broker 没有账本、没有版本、没有门，两端**永不对话**，于是漂移会攒到下次切发布分支才现形。

## 5. 什么情况下应该回头重开这个话题（可判定触发条件）

**锁**：仅当 §2.3 四条同时成立。届时先做的仍是「把锁搬进属主自己的库」，Redis 只在那之后仍不达标时才谈。

**总线**：以下**全部**满足才重开——
1. §3.2 两个先手（`LISTEN` 唤醒、游标加主题维）**已落地**，且有**实测数据**证明仍不达标；
2. 保留 PG outbox 做事务型入队，Redis 只做中继之后的一跳；
3. 双游标（outbox 游标 + 待处理表）的对账口径与「这条到底进流了没有」的第三态处置已写清；
4. 备份 / 回滚语义已重建，或**明示这条流的数据可丢**；
5. 数值门槛任一突破：主题数 > 10、扇出度 > 3、峰值 > 500 条/秒、或出现真实的跨服务重放需求。

## 6. 对抗性评审对上述结论的更正（已折进正文，此处留痕）

1. **「0 处需要跨域互斥」被推翻** → 见 §2.2。结论不变，理由形状变了。
2. **「8 处跨库锁」分母不完整** → 反向至少再加 3 个取锁点。
3. **一条错误的修法处方被拦下**：曾建议把自动化写者锁的连接改成 `resolveOwnerPgConfig('automation')`。**那会引入 bug**——该锁的连接配置结构只有 host/port/database/user/password、**没有连接串字段**，而 owner resolver 在 URL 已设时返回的正是连接串 ⇒ 五个字段全空 → 回落到内置默认（本机 + 明文口令兜底）→ **在错的库上取锁而且会成功**，正是它要防的形态。且它今天认 `AIDCP_PG_*` 家族、owner resolver 不认 ⇒ 也不是字节等价。且失败后果是**整个云端拒绝启动**。⇒ 正确修法必须先给它的连接配置结构加上连接串支持，或另写一个 owner→writer-lock 的专用解析。**已同步更正 `cloud-block3-l3-cutover-plan.md`。**
4. **「否决 broker 因为写者锁在结构上禁止多消费者」这条论证不成立** → 那把锁本身在拆库当天静默失效、且已排期被替换。该理由降级为「今天不需要扇出」（这一条成立）。
5. **两处措辞更正**：① 集成测试的 gate 环境变量**不是**「全仓零命中」（有 2 处命中 = 测试自己读它）；实质对——**无任何脚本设置它 ⇒ 常规 `npm test` 下永久 skip**。② 「今天唯一在跑的锁保障是一次 SQL 子串匹配」**已不成立**——`test/acceptance/advisory-lock-ownership.test.ts` 的 AC-LOCK-01/02 在跑，**但只扫咨询锁、不覆盖行锁**，这才是真缺口；且 `7c2f6e3` 已为授权票据路径补了 4 条事务边界用例。
6. **「加一条 `npm run test:pg` 让集成测试好跑」必须带守卫**：那些测试会 `TRUNCATE` 客户身份 / 环境归属 / 离场台账，而 dev 与 ol 连**同一台物理 PG、那台就是生产库**，内置默认还兜底本机 `aidcp` 库 ⇒ 必须拒绝已知生产 host + 强制专用库名前缀 + 仅 CI。
7. **三条现存链路今天就违反「一个域绝不直连另一个域的库」**（api 写 automation 的 outbox、api 读 automation 的 outbox 并写其游标、automation 读写 api 的审批 outbox）⇒ 传输层方案的定价要算上「三次已落地缝的重做」，不是「加一层中继」。

## 7. 一句话给非工程视角

我们不引入 Redis。**锁**这件事上它技术上做不到我们要的保证——它的失效是无声的，而我们现在的做法失效时会响亮报错，这个差别正是这套系统一贯的取舍。**队列**这件事上我们真正缺的那一段（服务之间怎么把消息递过去）有一个更便宜、更诚实、而且代码里已经有零件的做法；而 Redis 能额外带来的那两点好处，用两个不新增任何组件的小改就能拿到。另外实测发现：这两台机器**没有任何监控、没有自动备份**，给一个连现有数据库都还没运维好的环境再加一个有状态组件，只会放大已经存在的缺口。

## 1. `publish-claim-reject-defer-not-fail`（0/14）

**「资源暂时被占」被判成失败，而且是 2 秒内烧光预算的那种失败。**

链路（提案作者已逐行坐实）：

1. 同账号已有一轮发帖在跑 / 在途待审草稿到上限 / 全局生成并发已满 → `tryClaim` 拒绝
   （`publish-scheduler.ts:504-514`），被包成 `{result:'triggered', status:'skipped', failureReason:'…already_running'}`。
2. `executors.ts:133` 有一条判断**想**把这三类归为「稍后重试」，但它要求 `result === 'blocked'`
   —— 而这三者**从来不是 blocked**（blocked 只由人设未绑 / 风控产出）。
   **该正则的后三个分支永不可达。**
3. 于是落到 `{kind:'failed', retryable:true}` → 以 `now + 1000ms` **热重试**。
4. 自然语言发帖默认只有 2 次机会 → **约 2 秒烧光** → 用户看到「发帖失败」。

**修法倾向**（提案已给）：让 scheduler 给出**结构化拒因**，而不是让委托层对中文文案做子串匹配；
顺带清掉那条死条件，免得下一个人照着它推理。

**关联**：这是 `delegated-terminal-failure-reason` 排查「发帖失败卡不说原因」时挖出的**第一放大器**
——那条 change 让卡说出了原因，没修「为什么会走到这张卡」。

## 2. `captcha-assist-base-url-self-proof`（0/37）

**验证码协助链接的公开基址是一条进程内无法验证的声明**，它的真假由 DNS / nginx 决定。

2026-07-16 事故坐实代价：dev 的基址在 07-07 配置时是对的，07-11 域名割接给 OL 后
**那条配置一字未动就腐烂成了跨环境指针**——dev 签发的链接把运营送到 OL，
而 OL 既没有该事故、也够不着那个分身，鉴权之前就回 503。

**腐烂潜伏了 5 天，因为没有任何东西在喊。** 系统当时已经「知道」链接会失败
（它自己就是那个 503 的作者），却仍然发出一个长得像正常按钮的链接。

**修法倾向**：周期性匿名探针，判据 = 「那个地址上回的是我方自己的 `captcha_assist_unavailable`
⇒ 它铁定不是我」，连续 2 次才判死；判死后卡照发、**只是没有按钮** + 说明原因。
其余一切结局（401/404/200/超时/非 JSON）→ `unknown` → 不行动。
**零对端依赖，dev 单边部署当天生效。**

## 3. `bound-facebook-comment-migration-latch`（0/31）

**评论迁移闩有三个生命周期缺口，三个都会让一条已批准的评论消失**，其中两个还会把消失归因到错的地方。

迁移是两步：先发「导航用途开帖」，等回执确认落在目标详情页，才发评论。中间那段等待由
`role-dispatcher.ts` 里的 `pendingMigration` 持有**一条已经批准过的评论**。

已点名的第一个缺口：消费准入**没有相关性判据**——进分支的条件只有「闩存在 + 动作是开帖」，
且**第一件事就是清闩**，之后才判是否落地。

**为什么值得记**：本仓档案里最贵的三次重复对外写入，根因全是一次停手；
而这里是反过来的一类——**一条已批准的评论静默消失**。两者都属「三态压成一态」。

## 4. `unify-facebook-comment-budget-source`（0/31）

**评论提交的时间预算，两个仓各写了一份同样的公式**：下限 42s / 基数 27s / 每字符 330ms / 上限 180s
——四个常量逐位相同，一份在云端 `comment-agent/facebook-edge-steps.ts`，
一份在边缘 `native-page-engine/browse-session.ts`。

**两份实现各自编译通过、各自测试通过，漂开的那天没有任何东西会说出来**
（同族判例见 [[second-implementation-needs-reference-assert]]）。

**修法倾向**：计算方留云端，把算出的预算随命令带下去；协议字段两端逐字一致。

## 5. `facebook-consent-structural-detect`（0/20）

同意浮层的自动接受**靠逐语言的按钮文案正则**。提案里有一处**对自己立论的订正**，比结论更值得读：

> 原稿称未覆盖语种下同意条「认得出但点不动 → 诚实 `no_target`」——**不成立**。
> 存在性判定要求「政策文案命中 **且** 至少一个按钮词表命中」，
> 未覆盖语种两条都 miss ⇒ 判定为「没有浮层」⇒ **静默当没有浮层一样继续**。

也就是说：**覆盖缺口从「是不是同意条」这一步就开始了，只改按钮选取扩不了任何覆盖。**

**两轮对抗评审后收敛为「安全优先」**：放宽按钮选取被证不安全（带 cookie 细则的登录/「继续」墙
会被误点成真门），所以交付的是**对既有路径的加固**（容器隔离 + 语言无关的登录门负向护栏），
**语种覆盖扩展显式 deferred**，未能正向识别的非英同意条退化为诚实 `no_target`。

## 6. `wechat-store-and-circuit`（0/23）

**视频号云端存储把四处「暂时做不到」实现成了「永远做不到」，且没有任何机制把它们拨回来。**

最严重的是**账号写熔断闭环死锁**：跳闸后全仓唯一的清除语句只在「发送成功确认」时执行，
而门禁在熔断态拒绝一切发送——没有发送就没有确认。运营唯一的写入口不碰熔断字段，
**关掉写暂停也解不开**：接口回 200、后台显示「允许写入」，实际每次发送仍失败
——**界面与真实行为相反**。

同源另三处：收件箱摄取把已处理会话无条件打回待审；卡在分类中的 job 只在进程启动时恢复一次；
解绑后正文的清理硬等边缘回执（边缘永不回来则正文永久留存，spec 明写的 30 天 purge 形同虚设）。

**它违反的是已成文的不变量**：「熔断清除 MUST 接通人工确认路径且不得死锁」
（`publish-dispatch-resilience`）——发布侧早就写下了，视频号侧复刻了同一个错误。

### 2.1 `fb-publish-fill-deadline` —— 三条遗留里只有两条是真的

## 3. 别再踩的坑（★ 是本轮新踩或新证实的）

- ★ **★★ 在 ECS 上跑 `npm ci` 会把 `node_modules` 清空，而且救不回来。**
  三个派生仓的 kernel / transport 是 `git+ssh` 依赖，**ECS 上没有 GitHub 部署密钥** ⇒ 安装必失败；
  而 `npm ci` 先删后装 ⇒ 失败后目录是空的。**服务不会当场报警**（进程已加载在内存里，仍显示 active），
  **下一次重启才起不来**。历来的备份 tar **全部排除 node_modules**，恢复不了。
  也**不能整份从本机拷** —— `@resvg/resvg-js` 与 tsx 依赖的 esbuild 是平台原生件。
  正解见记忆 `derived-repo-npm-ci-wipes-node-modules`。本轮在 dev 上踩过一次，已完整恢复。
- ★ **dev 加一条迁移＝给 OL 装一颗「下次重启就停机」的雷，且重启前零症状。**
  共库共账本，契约门只在启动期跑。**OL 部署的健康检查 MUST 包含「重启后真的起来了」**，
  撞上时**不要回滚**（旧构建认识的迁移只会更少），只能按精确豁免口径向前放行，
  且放行前先读那条迁移的文件头有没有回滚安全论证。见记忆 `shared-ledger-arms-ol-restart-outage`。
- ★ **发布分支是按小时新建的，台账里的分支名必然滞后。**
  认定 OL 跑哪一支 MUST 用「候选分支之间真有差异的文件」实测比对，MUST NOT 照抄台账。
  本轮 automation 与 api 各错一次。
- ★ **派生服务之间没有启动顺序约束，谁先起来是运气。**
  自动化侧的**厂商密钥与角色模型镜像只在启动期读一次**：那次读若撞上接口进程还没监听，
  就锁在 env 回退 / 保守默认上，**不会自愈**。本轮 OL 上火山那家因此无密钥可用（env 里没有），
  重启自动化后恢复（「命中 2 项，无读失败」）。整机重启会原样重演，**尚未修**。
- ★ **看到 `WHERE execution_target=$1` 不等于「按部署目标分行」** —— 传进去的可能是合并哨兵。
  判据是参数值。
- ★ **派生仓的 `test/` 不在 `sync-split-repos` 覆盖范围内**，且那些副本是**手工适配过的**
  （kernel 走包路径、可能少几条用例）。同步测试改动 MUST 逐条改，**整份覆盖会静默还原它的适配**。
- **登记的根因可能是错的**（前一份已列，本轮又添两条：5.1 早已实装、5.2 根因不对）。
  动手前先自己量一遍。
- **canonical checkout 里有并发 session 的未提交改动是常态**：`git add` 只写自己那几个路径，绝不 `-A`。

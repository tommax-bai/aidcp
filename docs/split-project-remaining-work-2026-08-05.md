## 一、线上有风险的两条（今天发现，都未解）

### 1. 接口服务「一重启就再也起不来」—— 已临时恢复，结构问题还在

**现象**：OL 的接口服务今天部署时起不来。启动契约门（enforce）判「库比代码新」：
库内账本最高 `0110_facebook_global_policy_single_scope`，构建只认到 `0109`。

**要害**：**回滚救不了**。备份里的旧构建同样不认识 0110。它此前一直在跑，
只是因为它在 0110 落库**之前**就启动了、之后没被重启过 —— 而契约门只在启动时跑，
所以这台机器**从 0110 应用那一刻起就处于「一重启即死」状态，全程零告警**。

**根因**：DEV/OL **共库**，而 0110 来自 `unify-facebook-global-policy-across-targets` ——
一个**尚未完成**的 change。未完成 change 的迁移一旦应用，
**所有不含该迁移的构建当场失去启动能力**。

**当前处置**：OL 的 api `.env` 追加了 `AIDCP_ALLOW_SCHEMA_AHEAD=0110_…`（单值放行、会打日志与告警）。
**这不是解决**，是让服务能起来。

**要做的**：
- [ ] 该 change 上线后**撤回**那行放行位（已在 .env 里就地注明）。
- [ ] 定一条规则：**未完成 change 的迁移 MUST NOT 应用到共库**，或者反过来 ——
      迁移一旦应用，同批必须把「认识它的构建」推到所有环境。二选一，现在两头都没做。

### 2. 消息表有一个主题只进不出

`event_outbox`（automation 属主库，**DEV/OL 共用同一张**）：

| 主题 | 行数 | 最老 |
| --- | --- | --- |
| `sync_read.changed` | **141,351** | 2026-07-27 |
| `config_mirror.bump` | 17 | 2026-07-27 |

实测增速约 **1.6 万行/天**。剪裁器**是接了**的（随风控记账一起构造并启动），
但它的主题名单 `automationOutboxRetentionTopics` **只有 `panel.event` 与 `risk.command` 两条**。

**别顺手按年龄裸剪**：该主题的消费方是带游标的同步读中继，剪早了会删掉尚未投递的行，
本仓已因「同游标不同载荷」栽过（拒收永久 + 启动期 fail-closed → 整机起不来）。
正确形态是「等消费者游标推进」，与 `risk.command` 同款。

## 二、今天新发现、需要独立立项的缺陷

### 3. 13 条迁移没有属主头 ⇒ 全新环境根本建不起来

**这是「全新空库拉起」验证跑出来的，一跑就断。**
本机真 PostgreSQL 16 空库，第 30 条整批停止：`relation "risk_counters" does not exist`。

`0030_panel_hardening_indexes` 一条横跨两个属主库 ——
`risk_counters` / `interaction_feed` 归 **automation**，`llm_token_usage` 归 **content**
⇒ **物理上不可能在任何单一属主库里跑通**。

`migrate status` 自报「残留迁移（头声明为空、计入全部属主）**13 条**」，
每一条都会在不该跑它的库里撞墙。停在：content 1/20、automation 13/57、api 20/70。

**为什么现在的库没事**：它们的表是**共库时期**建的，那时三张表在同一个库里。
今天的库结构是历史遗留物，不是这套迁移的产物。

**要做的**：逐条补属主头；跨属主的**拆成按属主分文件**（`0030` 至少拆成 automation / content 两条）。
粗归位清单（api 9 / automation 3 / 1 条待读正文）在 `cloud-schema-migration-executor` 的 5.9 批注里，
**只作起点、MUST 逐条实读** —— `0030` 正是粗归位会看漏的那种。

### 4. 三个派生仓的迁移命令一条都跑不起来

`scripts/migrate.ts` 仍 `import ... from '../src/kernel/pg-owner-connection-resolver.js'`，
而该文件在派生仓里**不存在**（已搬进 `aidcp-kernel` 包）—— 本机与 ECS 上都不存在，三仓各 2 处引用。

**后果**：今天唯一能跑迁移的仍是 `aidcp-cloud`，也就是刚被定为**永不部署**的那个仓（`CLAUDE.md` §8.0）。
部署流程要求的「上线前先跑一次 migrate status/up」在派生形态下**物理上做不到**。

### 5. 委托任务执行泵起了但一句话都不说

单体启动打 `DelegatedTaskWorker 已启动（…并发=N）`；派生**只在被 env 显式关掉时**才打一句。
⇒ 「起了」与「没起」在日志上**完全同形**，下次真没起时没人会发现。
（今天是靠查 `delegated_tasks` 表反推它在跑的。）

**要做的**：补一条启动自述，与「已按配置禁用」那条对称。

### 6. Facebook Reels 换页确认不上（真剩余缺陷，但不是「浏览停摆」）

**先纠正一条已被推翻的判断**：交接文档原先把「OL scroll 两天 100% 失败、账号空转」列为最高优先级，
**那是误报**。同一 6 小时窗口，风控账本记了 **1703 次真实浏览**、193 点赞、14 关注；
当时在睡的账号是**今日浏览额度用满**，不是滚不动。误报根因是按回执的**布尔** `ok` 做汇总，
把三态里的「没能确认」压成了「失败」。

**真剩下的问题**：确认窗口 15s（`aidcp-edge/native/page-engine/src/facebook/reels.rs` 的
`FACEBOOK_REEL_IDENTITY_HYDRATION_TIMEOUT`）内始终看不到换页，可换页确实发生了。

**别急着再抬窗口**（08-02 刚抬过一次）：1703 view / 658 scroll = **2.6**，
说明换页多半**不是那次按键驱动的**，先弄清是谁在推进。
用户已确认 OL 运营机跑的是 0.3.26（08-04 最新），08-02~08-04 那 6 个 Reels 修复都在机器上
⇒ 这是真剩余缺陷，不是旧包。

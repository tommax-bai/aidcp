## 1. 用户在本轮定下的编址分层（**别再重新讨论，尤其别再提"上收云端"**）

| 层 | 编址单位 | 权威 | 例子 |
| --- | --- | --- | --- |
| 宿主层 | 机器 | **本地** | 槽位调度、内存推算、启动队列、等待门槛 |
| 环境层 | 分身 | **本地** | 浏览器开关、登录协调、指纹、代理、阻断浮层 |
| 翻译层 | 环境 → 账号 | **本地** | 身份确立、身份守卫、身份翻转 |
| 账号层 | 账号 | **云端** | 浏览、互动、发布、风控、配额、审批 |

由此推出的、**本轮已经拿来做决定**的几条：

- **槽位调度权在宿主层，不上收云端。** 车队跨机器，**槽位不跨机器**，且环境绑死本机分身、
  不可迁移 ⇒ 不存在任何"云端能做而宿主做不了"的槽位决策。
  > 本轮我（助手）先前推过"把判断权上收云端"，**那是错的，已当场收回**。新 session 别再走回去。
- **今天的病根是云端下发的字段名叫 `eligible`——那是个决策词。** 两层各出一个决策 ⇒ 必然漂移。
  云端在这件事上只该给账号层**事实**（这个账号到 T 之前没有活干）。
- **验证码按"翻译层是否完成"分类，不按"浏览期 / 登录期"**：
  - 身份确立**之前**（登录验证码 / 首登 checkpoint）＝环境层。此时账号还不存在，
    账号层**结构上没有可裁决的对象**——这是最硬的论据。
  - 身份确立**之后**（浏览期风控浮层）＝账号层，属风控事实，云端单写。
  - 运行期掉登录 / checkpoint ＝翻译层事件：检测与恢复在本地，"该账号当前不可操作"归云端。
  - **三类共有：检测与上报永远在本地**（云端看不见页面）；分歧只在分类与后果。
- **让位决策 = 宿主层拿两条事实做的判断**：云端的"没活干到 T" + 本地的"这个浏览器此刻是不是人机接口"。
- 宿主层拥有决策权的**代价是必须向上可见**——否则就退化成本次故障。可见性是遥测，**不是审批权**。

分层表与推论已写进 change `admit-browser-standby-on-live-facts` 的 `design.md`，
归档后会随 delta 并入 `browser-cold-standby` 规格。

## 2. 触发本轮的真机故障（已定位、已修，未出包）

**现象**：2026-08-05 18:18，账号 `Lê Thảo Hân`（`ads-k1fd38qw`，Facebook，Native 引擎）
小时浏览配额跑满。云端每 60 秒推一次 `eligible=true`（等待约 33 分钟 ≫ 门槛 5 分钟）。
客户端**连续 32 分钟每次都拒绝**，浏览器一直占着两个槽位之一，界面与日志**零痕迹**。
同机另两个账号 18:08 收到同类提示后**在同一毫秒内**让位——机制与配置本身正常。

**根因两半**：

1. **准入读了一个已无写入方的标签。** 准入要求会话轴 ∈ {running, resting}，
   而写会话轴的那几句中文只有**已退役的 TypeScript 浏览循环**会打印
   （`src/browse/browse-session.ts`）。Facebook 与现役小红书都跑 Native 引擎，
   发的是结构化会话事件，外壳**零处理分支**。实测本机全部日志历史里那几句话出现 **0 次**。
   该轴自核心 spawn 被写下一次之后再无人维护，只会被各种失败路径单向改坏、永不复原。
2. **拒绝完全无痕。** 除"最短持有时长未满"外的所有拒绝理由都是直接 return——
   不写状态、不写日志、不计次数。于是锁死半小时在磁盘上零证据，
   连"是哪一次写把会话轴改坏的"都**无法回溯**（我确实没查出来，也不必了，见 §3 的 D1）。

**顺带挖出的、更急的一个坑**（原属 `browser-slot-scheduling` §5.6，本轮接管）：
核心侧"进入待机被拒"原本复用无参的 `onCloseFailed`，外壳当成"运营要关浏览器但没关成"，
于是收敛自动化意图、把环境写成暂停态 = **永久占槽且被踢出等槽位队列的砖**。
而 `enterStandby()` 的五个失败出口里，**三个是拆除动作之前的无害拒绝**
（最常见的是 `task_lease_active`＝正在发帖 / 评论），两个才是 `session.detach()` 之后的真失败。
本次改动的全部目的就是让待机尝试频繁发生 ⇒ 不修这条等于把低频隐患放大成高频故障。

改动四处：

1. **准入换活事实** —— 移除对 `status.edge` / `status.session` 的依赖，改读：核心子进程在、
   云端连接 connected、运营自动化意图不是暂停/停止。三条不可逆互锁（发布在途 / 关闭暂停重启在途 /
   阻断浮层与登录态）**逐字未动**。
2. **每次拒绝留痕** —— 具名原因 + **连续拒绝次数** + 首次拒绝时刻；写进环境待机状态、
   开发者详情新增「浏览器让位 / 让位诊断」两行；日志按"首次 + 每 5 次"节流。
   *单次拒绝正常，连续拒绝才是故障——此前两者长得一模一样。*
3. **待机被拒不再复用关闭失败回执** —— 新增本地 IPC `lifecycle.standby_refused{reason, browserIntact}`。
   `browserIntact` 的判据是**物理的**：拒绝发生在任何拆除动作之前 ⇒ true（外壳原样不动、下次提示重判）；
   已 detach/kill 过 ⇒ false（如实标真态未确认）。**两支都不动运营意图。**
   用户主动关闭 / 暂停那条路径**一行未改**。
4. **开发者详情**新增两行呈现。

**设计取舍（写在 `design.md`，别重新推一遍）**：

- **D1 做减法，不给坏标签补来源。** 补来源要动核心 + 外壳两侧，且补完闸门依然无痕。
  减法还有一个额外好处：它让"哪一次写改坏了会话轴"这个**从磁盘上查不出来的问题变得无关紧要**。
- **D2 云端连接轴保留，但钉死写入方。** 它与会话轴的本质区别是**写入方还活着**
  （握手与断连由现役客户端连接层打印，各平台通用）。回归断言：从 `main.cjs` 抽出匹配串，
  逐个到核心源码里找发射点。**这条断言就是本次事故的机械化教训。**
- **D5 §5.6 必须同批修**，理由见 §2 末段。

**测试里最该保住的两条**（改这块前先跑它们）：

- `陈旧的日志推断轴不再阻挡让位（本次故障的定向回归）`
- `准入 MUST NOT 再读日志推断轴`（结构断言）

**变异自查做过**：把旧判据加回准入，恰好由上面两条抓住，不是恒真断言。

## 4. 未做 —— 第三步（尚未 propose，方向已定）

按 §1 的分层，第三步的方向与我最早说的**相反**：不是把判断权上收云端，
而是**把云端那侧的决策词降级成事实、槽位决策明确留在宿主层、同时补上可见性**。五条：

1. 云端 `eligible` 降级成事实（"这个账号到 T 之前没活干"），停止在账号层出决策。
2. **等待门槛的权威从云端还给宿主层。** 要翻已归档规格 `browser-cold-standby` 里那条
   `Cloud SHALL be the single standby wait-threshold authority`——该门槛的推导全部是本地成本
   （热身 90s、串行启动队列约 40s、盈亏平衡约 2m10s），云端一个都不知道也不该知道。
3. **撤掉云端 `needsBrowserToUnblock` 那个一票否决**：它在账号层回答一个环境层问题，
   数据还是边缘上报的，往返一趟只增加漂移面、不增加信息。
4. 会话轴接结构化会话事件（Native 引擎的 `session_ready` / `session_stopped`），让它重新有写入方。
   注意：**这不是让它回到准入闸**，只是让界面上"在不在跑"这件事别继续错。
5. 宿主层的槽位决策**向上回执**（遥测）。**现成通道不可复用**：边缘→云端那条浏览器真态上报
   只接受 `absent`/`ready` 两个值，且云端 `onBrowserStatus` 第一行就是"状态没变直接返回"，
   诊断字段跟着一起被丢弃。所以这一步要新增一条协议消息，**四~五处同步**（CLAUDE.md §2）。

第 3 步开工前建议先看 §1 的分层表，别再从"两个决策者"这个错误框架出发。

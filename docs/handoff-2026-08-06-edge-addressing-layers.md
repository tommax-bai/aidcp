## 3. 已定口径（用户裁定，别再重议）

### 决策一 · 视频号定时同步后置
理由：尚无真实应用。**副作用**：失去一条低风险的「上移形态」练手路径，
故步骤 5 建议**先只搬一个最小子集**（如只搬「未知遮挡的二次确认判定」）再搬其余。

### 决策二 · 「确认不了」＝ 按发了算

**这是记账口径，不是报告口径。** 已核实与今天的实装一致：

- 评论去重：「确认成功 ∪ 已派发未确认 = 提交已派发 → **必写去重**」
- 配额：「确认成功或已派发未确认**都扣额**」
- 发布：「已派发但未拿到确认——页面态 submitted、**绝不重投**」

**MUST 保留的分法（今天已如此，不要合并）**：

```
内部（防重复用的账）  按「发了算」  → 扣配额、写去重、绝不重投、记风控
对外报告              按「不确定」  → ok=false，明写「已提交未确认」
```

一旦对外也报成功，就是把三态压回两态——正是整个设计要拆开的那个问题。

**三个附加项（不阻塞，建议一并做）**：确认不了的比例上升要有计数告警；
浏览闭环会再看到那些帖子，**保留一条事后回填真相的通道**（发布链已有先例：原生定时发布"到期才对账计数"）；
漏发一条评论与漏发一篇排期稿件代价不同，发帖可能要特殊对待。

## 7. 设计要点速查（详见 §1 的规格与设计文档）

**动作与检查分离**——默认拆开，例外只有「瞬时证据」（编辑器清空 / 提交键变灰这类，一个往返后就没了，
几乎只出现在不可逆提交上）。

**动作命令根本不许说「成功」**：

```
act ...    → 只能回：未开始 ／ 已派发 ／（现场就确定做不到）
check ...  → 才能回：确认成功 ／ 确认未发生 ／ 确认不了
```

这样静默假成功在结构上不可能——动作命令说不出「成功」这个词。红线的实质保住了：
「函数返回了不算数」仍成立，只是改由「事件真的发出去了」来兑现，不必靠读回业务状态。

**取证是三件事**：目标对不对（动作**前**判，搬不走）／ 动作落没落地（**现场**判，搬不走）／
平台认没认（**能搬走**，且往往更准，因为很多平台异步生效）。

# 从 Native 迁移修复批里摘出的云端编排缺陷（2026-07-31 用户裁定）

> **这份文档只承接「被摘出的立论」，不对任何工作线下指令。** 它不是 openspec change，
> 里面的条目**当前不在任何 change 的账上**，需要时由用户或属主正式立项。

## 为什么摘

Native 迁移修复那七条工作线的主体是**纯边缘**（把 JS 页面智能搬进 Rust 引擎时丢掉的行为）。
但两条线里各混进了一节云端任务，用户 2026-07-31 复核时提出质疑并裁定摘出。

判据是**「Rust 迁移碰过它没有」**：

| 类别 | 处置 | 例子 |
| --- | --- | --- |
| 边缘改了、云端不跟就白改 | **留在原 change** | 边缘新增「反应计数未观测」标记，云端不接就仍旧塌成 0 |
| 迁移一行没碰过、是云端自己的老毛病 | **摘出（本文档）** | 迁移闩的超时清理只覆盖免审强制评论那一支 |

**摘出的直接理由不是「不该做」，是**：混在「迁移修复」里会让那批永远收不了口——
你以为在修迁移遗留，实际在修云端编排层的独立缺陷，两者的优先级、验证方式、以及**谁该排期**都不一样。

**摘出不改变任何生产行为**：这 7 项零开工，摘的只是账本归属。缺陷仍然存在、立论仍然成立。

## A. Facebook 迁移闩的生命周期（原 `restore-native-facebook-residual-parity` §6 的 6.2–6.4）

**落点**：`aidcp-cloud/src/orchestrator/role-dispatcher.ts`（行号为 2026-07-28 快照，**必然已漂，按符号定位**）。

**先读这段现状再动手**（已逐行核对过，勿重复实现已有行为）：

- **落地判据已经守住红线**：进入条件**已经**要求回执的 noteId 等于闩记录的 noteId、且观测面为详情页
  （原 `:3567`）⇒ 无关回执**不会**把已批准的评论发到未经证实的页面。
  **下面 6.3 补的是「消费准入」，不是「落地判据」**——别把已有的保护再实现一遍。
- **超时清理已经存在，但只武装了一支**：`armMandatoryCommentOutcomeTimer` 在无审批 trace 时直接 return
  （原 `:1550-1551`），所以只有免审强制评论有超时清闩。

### A.1（原 6.2）超时清理扩到每一次已批准交付

把 `pendingMigration` 的有界超时清理扩到**每一次已批准交付**（今天只对免审强制评论武装）：
无审批 trace 的普通交付也必须有超时清闩 + 「已批准未送达」上报 + emit 终局事件
（与原 `:3064-3079` 的抑制路径同口径）。

**验收**：断言普通交付武装后，在超时预算内不给回执 → 闩被清、操作员收到「已批准未送达」、评论支线时钟解冻。

### A.2（原 6.3）闩的消费准入加相关性判据

原 `:3557` 的进入条件除「有闩 + 动作是开帖」外，**还须该回执与武装它的那次迁移相关联**（至少 noteId 匹配）。
不相关的开帖回执 MUST NOT 进入该分支、MUST NOT 清闩、MUST NOT 触发本次迁移的失败归因。

**今天的实际后果**：它会走原 `:3600` 的 else 分支，**把失败归到不相干的回执上**。

### A.3（原 6.4）支线超时与闩不再各清一半

让评论支线硬超时（`expireCommentSubline`，原 `:1311-1326`）在清飞行中评论标记时**同时清迁移闩并回报操作员**，
二者不再各清一半。

### A.4 用例（原 6.5 拆分而来）

原 6.5 是**混合条目**，其中「迁移指令带规范目标」那一句属于**留在原 change 的 6.1**（边缘对侧已就绪），
已在原清单保留。本文档承接的是其余部分：

- **普通（无审批 trace）交付**超时 / 会话结束 / 断连三路各清闩并回报操作员
- 异 noteId 的开帖回执**既不解除闩、不发评论、也不产生本次迁移的失败归因**
- 同 noteId + 详情观测的回执正常解除并发评论（**回归断言原 `:3567` 的既有落地判据未被削弱**）

## B. 评论提交预算的两份公式（原 `harden-native-engine-runtime-contracts` §8）

**危害方向是诚实的**（错报失败：长评论被判超时），**不是静默假成功**——这也是它此前被反复延后的原因。

**注意一个容易搞混的点**：这跟原 §3「提交窗口预算单一事实源」**不是同一个预算**。
原台账写「留待下一轮连同 3.2 一起做」只是因为主题相近，物理上是**不同的常量、不同的文件**：

- 原 §3 = **提交窗口**（引擎向宿主请求写窗口的时长），纯边缘内部，**留在原 change**
  （且其危害已消除，剩下是把线路上那个失效字段物理删掉的整洁工作）
- 本节 = **评论提交预算**（云端判定方的等待窗口 vs 边缘执行方的命令预算），跨仓

### B.1（原 8.1）确定计算方

确定评论提交预算的计算方（云端下发或边缘回报），并在该侧按**「实际会被打进编辑器的完整串」**计算，
另一侧改为据传输值派生。

> 「完整串」这个限定是要害：评论正文与联系方式/群聊码后缀是**拼成一串一次打完**的，
> 按正文长度算预算会短算。

### B.2（原 8.2）删除非计算方的常量副本

两份之一：`aidcp-cloud/src/comment-agent/facebook-edge-steps.ts:46-57` 与
`aidcp-edge/src/native-page-engine/browse-session.ts:65-71`。**必须同批处置**，单删一侧会让两边对不上。

### B.3（原 8.3）回归：判定方窗口不短于执行方预算

带群聊码后缀的评论上，判定方的等待窗口**不短于**执行方的命令预算；慢但成功的提交不会被判超时。

### B.4（原 8.4）回归：只有一处声明会变

改动预算常量时**只有一处声明变化**，不存在第二份公式可以保留旧值。

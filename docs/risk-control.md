# AIDCP 风控模型设计

> 适用范围：aidcp 在小红书（XHS）场景下的 AI Agent 自动浏览 / 点赞 / 收藏 / 评论 /
> 发布。当前实现为**单机单账号、Chrome + CDP 原生**，操作延迟仅有简单均匀随机等待，
> 无频率限制、无时间窗口管理。本文给出一套可落地的风控模型，目标是：**在不被平台
> 风控系统标记的前提下，让自动化账号长期存活**。
>
> 配套文档：[反检测与登录态维持方案](anti-detection.md)。两者关系：本文管"做什么、
> 做多少、什么时候做"（行为节奏 / 频率 / 风险状态），反检测文档管"怎么做才不被识别为
> 机器"（指纹 / 网络 / 行为拟人化的技术实现）。

---

## 0. 设计原则与威胁模型

### 0.1 平台风控在看什么

小红书的风控不是单点规则，而是**多维行为画像 + 实时频率 + 设备/网络指纹**的综合
评分。对自动化账号最致命的不是"某一次操作太快"，而是**行为分布过于规整**：

1. **频率维度**：单位时间操作次数、操作总量是否超过真人合理范围。
2. **时间维度**：是否 7×24 不间断、是否有真人作息（睡眠 / 三餐 / 通勤）。
3. **节奏维度**：操作间隔是否服从真人分布（长尾、有疲劳曲线），还是机械均匀。
4. **内容维度**：互动对象是否高度同质、发布内容是否模板化、搜索词是否异常重复。
5. **设备/网络维度**：指纹是否稳定且可信、IP 是否纯净、设备与账号是否一对一绑定
   （见反检测文档）。

> 公开经验（知乎/woshipm 等运营社区，2024–2025）反复印证两个关键信号：
> **"每天浏览时长 ÷ 近期发布数量 = 账号质量指数"**——发得多、看得少的账号会被直接
> 归类为营销号；以及**"新号需连续养号 5–7 天再发布"**。这两点构成本文冷启动与
> 频率模型的事实基础。

### 0.2 核心原则

| 原则 | 含义 | 反例（当前实现的问题） |
| --- | --- | --- |
| **真人优先于效率** | 宁可少做，不可做得"太像机器" | 4–8s 均匀随机间隔，方差小、无长尾 |
| **分布优于固定值** | 一切延迟/数量都从分布采样，不用常数 | 固定区间 `random(4,8)` |
| **有作息** | 不是 24h 跑，有活跃窗口、睡眠、波动 | 无时间窗口管理 |
| **可降级** | 检测到风控信号自动降速，而非硬闯 | 无风控状态机 |
| **保守起步** | 新号/新环境从最低档开始，逐步放量 | 无冷启动概念 |

## 1. 操作频率限制

### 1.1 每日操作上限（按动作类型分别限制）

不同动作的风险权重差异巨大：浏览风险最低（真人也大量浏览），发布/评论风险最高
（带引流嫌疑）。因此**必须按动作类型分别设限**，而非一个总数。

| 动作 | 保守档 | 正常档 | 激进档 | 说明 |
| --- | --- | --- | --- | --- |
| 浏览笔记（打开详情） | 80 / 天 | 150 / 天 | 300 / 天 | 风险最低，是"养号质量指数"的分母，应保证充足 |
| 点赞（like） | **20 / 天** | **50 / 天** | **100 / 天** | 高频点赞是最典型的机器特征 |
| 收藏（collect） | 10 / 天 | 25 / 天 | 50 / 天 | 收藏比点赞更"重"，真人收藏率远低于点赞 |
| 评论（comment） | 3 / 天 | 8 / 天 | 15 / 天 | 评论带引流风险，平台严查；务必 ≥15 字、带情绪词 |
| 关注（follow） | 5 / 天 | 15 / 天 | 30 / 天 | 关注/取关波动是封号高发区 |
| 发布笔记（publish） | 0–1 / 天 | 1 / 天 | 2 / 天 | 发布是最高风险动作；同一天多篇极易触发营销号判定 |

> **比例约束（比绝对值更重要）**：点赞率（点赞数 / 浏览数）应落在 **15%–35%**，
> 收藏率 < 点赞率，关注率 < 5%。真人不会"看一篇赞一篇"。aidcp 应在运行时实时
> 计算这些比率，超出区间则跳过本次互动而非强行执行。

### 1.2 单次会话时长上限 + 冷却时间

一次"会话"= 一次连续上线的操作流。真人不会连续操作几小时不停。

| 维度 | 保守档 | 正常档 | 激进档 |
| --- | --- | --- | --- |
| 单次会话时长 | **15 min** | **30 min** | **60 min** |
| 单次会话内动作数（含浏览） | ≤ 30 | ≤ 60 | ≤ 120 |
| 会话间冷却 | ≥ 90 min | ≥ 45 min | ≥ 20 min |
| 每日会话数 | 2–3 | 3–4 | 4–6 |

会话结束条件（满足任一即结束）：
- 达到会话时长上限（时长本身从对数正态分布采样，见 §3.4）；
- 达到会话动作数上限；
- 命中"自然离开"概率（每个动作后以小概率 p≈0.02–0.05 主动结束，模拟真人随手关掉）。

### 1.3 小时级频率衰减（不能连续高频 3 小时）

即使总量不超标，**连续多个小时维持同一高强度**也是机器特征。引入**小时配额 +
衰减因子**：

```
hourly_quota(h) = base_quota × decay(consecutive_active_hours)
decay(n) = max(0.3, 1.0 - 0.25 × (n - 1))   // 第1小时 1.0，第2小时 0.75，第3小时 0.5，第4小时起 0.3 封顶
```

含义：连续活跃越久，单位时间允许的操作越少；模拟真人"越用越累、越刷越慢"。
当 `consecutive_active_hours ≥ 3` 时，强制插入一次长休息（≥ 1 个会话冷却周期），
计数清零。

### 1.4 频率阈值的工程实现

用**滑动窗口计数器**（内存 + 持久化到本地/PG，进程重启不丢）：

```
counters = {
  day:    { like, collect, comment, follow, publish, view },   // 跨自然日重置
  hour:   { ... },                                             // 滑动 60min
  minute: { ... }                                              // 滑动 60s，防爆发
}
```

每次动作前调用 `canDo(action)`：任一窗口超限 → 拒绝并触发"跳过/改为浏览/结束会话"
的降级策略，而不是等待后重试（等待重试会形成可识别的"卡点"特征）。

## 2. 操作时间模型（作息）

### 2.1 活跃时间窗口

绝不 24h 运行。按真人作息把一天划分为活跃概率不同的时段：

| 时段 | 工作日活跃概率 | 周末活跃概率 | 说明 |
| --- | --- | --- | --- |
| 00:00–06:30（凌晨） | **0.02** | 0.05 | 极低频，仅偶发；连续凌晨活跃是强机器信号 |
| 06:30–09:00（早间） | 0.35 | 0.20 | 通勤/起床刷一会 |
| 09:00–12:00（上午） | 0.30 | 0.45 | 工作日偏低，周末偏高 |
| 12:00–14:00（午休） | 0.55 | 0.50 | 午休高峰 |
| 14:00–18:00（下午） | 0.30 | 0.55 | — |
| 18:00–20:00（晚饭） | 0.40 | 0.45 | — |
| **20:00–23:30（黄金）** | **0.85** | **0.90** | XHS 真实流量高峰，互动集中于此 |
| 23:30–00:00 | 0.30 | 0.45 | 睡前刷 |

调度器每到一个候选启动时刻，按当前时段概率决定是否真正上线；并保证一天的会话
**主要集中在高活跃时段**，凌晨即使采样命中也只做纯浏览、不做互动。

### 2.2 工作日 vs 周末节奏差异

- 工作日：会话更碎片化（午休 + 通勤 + 晚间），单会话偏短。
- 周末：会话更长、更集中，上午/下午活跃度上升，总操作量可比工作日高 20–40%。
- 引入"**今天是否高强度**"的日级随机（约 1/5 概率为低强度日，模拟懒散/忙碌），
  避免每天总量都一样（每天数量完全相同本身就是机器特征）。

### 2.3 随机化每日启动时间

每日首个会话的启动时刻 = 该时段名义起点 + **±30 min 高斯抖动**（σ≈12min，截断在
±30min）。后续会话启动时刻同样抖动，避免出现"每天 20:00:00 准时上线"。

```
start = scheduled_slot_start + clamp(gauss(0, 12min), -30min, +30min)
```

## 3. 操作速度与加速度（重点）

> 这是把"机械脚本"变成"真人"的核心。当前实现用均匀随机分布，方差小、无长尾、
> 无趋势，是最容易被行为分析模型识别的特征。以下全部改为**有分布、有趋势、有相关性**。

### 3.1 停顿时间：对数正态分布（而非均匀）

真人停顿是"大量短停顿 + 少量长停顿"的长尾结构，天然服从**对数正态分布**。

```
pause = exp(gauss(μ, σ))            // 单位：秒
卡片间切换:  μ=ln(5),  σ=0.5   →   中位数≈5s，少数到 15s+
操作间隔:    μ=ln(2.5), σ=0.45  →   中位数≈2.5s
```

对比当前 `random(4,8)`：对数正态能产生 1s 的快速划过，也能产生 20s 的"被某条
笔记吸引"，这种**跨数量级的长尾**是均匀分布永远做不到的。

> 实现提示：用 Box–Muller 生成高斯，再取 `exp`；对结果做下限截断（如 ≥0.4s）防止
> 出现非真人的瞬时操作。

### 3.2 阅读时间与内容长度相关

阅读时间不能是固定区间，应与笔记内容量正相关：

```
read_time = base + k_text × text_len + k_img × image_count + noise
base = 1.5s
k_text ≈ 0.18s / 100字            // 真人阅读速度约 300–500 字/分钟
k_img  ≈ 0.8s / 图
noise  = lognormal 抖动（见 §3.1）
上限截断: 长文最多停留 ~90s，避免异常长
```

长文/多图笔记停留久、短笔记一扫而过——这种**停留时长与内容的相关性**，是真人
最自然的指纹，机器脚本通常完全忽略。

### 3.3 滚动：ease-in-out 加速度曲线 + 惯性

真人滚动不是匀速，而是"加速 → 巡航 → 减速"，且鼠标滚轮/触控板有惯性。

- 单次滚动的位移随时间服从 **ease-in-out**（如三次贝塞尔 `cubic-bezier(.25,.1,.25,1)`）；
- 一次"滑动手势"拆成多个小 wheel 事件，步长先增后减；
- 偶发**回滚**（向上滚一点再继续向下，模拟"刚才那条想再看看"），概率 ≈ 5–10%；
- 滚动结束后有短暂停顿（注视）再开始下一次。

```
为每次滚动采样: distance, duration
按 ease-in-out 把 distance 切成 N 个 wheel delta（N≈duration/16ms 帧）
逐帧 dispatch Input.dispatchMouseEvent(type=mouseWheel)   // 见反检测文档行为指纹章节
```

### 3.4 会话节奏：热身 → 自然 → 疲劳曲线

一次会话内的操作速度不是恒定的，而有**疲劳曲线**：

```
开始（前 ~15%）：热身——节奏偏慢、互动少（刚打开 App 在"逛"）
中段（~15%–70%）：自然——节奏稳定，互动集中在此
后段（~70%+）：疲劳——停顿变长、滚动变快但互动减少（快速划过，准备离开）
```

实现为对 §3.1 的 `μ`（停顿尺度）施加一个随会话进度变化的**乘子曲线**：

```
fatigue(progress) = 1.0                       progress < 0.15  → ×1.2 (热身,略慢)
                  = 1.0                       0.15–0.70        → ×1.0
                  = 1.0 + 0.6×(progress-0.7)  progress > 0.70  → 停顿放大、互动概率衰减
```

并对互动触发概率乘以 `(1 - 0.5×max(0, progress-0.7))`，让后段互动自然减少。

### 3.5 鼠标移动：贝塞尔曲线轨迹（非瞬移）

绝不直接 `click(x,y)`。从当前光标位置到目标，沿**二/三阶贝塞尔曲线**生成中间点，
逐帧 `Input.dispatchMouseEvent(type=mouseMoved)`，再 `mousePressed/mouseReleased`：

```
P0 = 当前位置, P3 = 目标(带 ±3px 落点抖动)
控制点 P1,P2 = 在 P0→P3 连线两侧加随机垂直偏移（产生自然弧线）
点数 N ∝ 距离（远则多点）, 速度服从 ease-in-out（fitts 定律：先快后慢逼近）
偶发: 轻微 overshoot 后回拉（真人常越过目标再修正）
```

> 贝塞尔参数与实现细节统一放在[反检测文档 §5 行为指纹](anti-detection.md)，本文只规定
> "必须用曲线轨迹"这一行为约束。

## 4. 内容去重

### 4.1 不重复互动同一内容

维护**已互动集合**（持久化）：以笔记 ID（note_id）为键，记录是否已点赞/收藏/评论。

- 点赞前查重：已赞过 → 跳过（绝不重复点赞，重复点赞=机器在"扫库"）。
- explore 流里遇到已互动笔记 → 可正常浏览但不再互动。
- 集合需持久化（本地 SQLite / PG），跨会话、跨重启有效，**避免重启后又把昨天赞过的
  再赞一遍**。

### 4.2 发布内容相似度检测（避免模板化）

模板化文案是营销号判定的直接证据。发布前做相似度自检：

- 维护近 N 篇（建议 N≥30）已发布内容的指纹：标题/正文做 **MinHash / SimHash** 或
  TF-IDF 向量；
- 新内容与历史任一篇相似度 > 阈值（建议 Jaccard 0.7 / 余弦 0.85）→ 拒绝发布，要求
  重新生成；
- 同时检测**结构模板化**：开头句式、emoji 使用模式、话题标签集合是否高度雷同。
- 标题不重复；正文长度、配图数量也应有自然波动，不要每篇都一样长。

### 4.3 同一关键词搜索频率限制

短时间反复搜同一词是典型爬虫特征。

- 单关键词搜索：每会话 ≤ 1 次，每日 ≤ 3 次；
- 维护"近期搜索词"队列，避免高频重复；
- 搜索词应有主题相关性聚类（围绕账号人设垂类），而非随机/跳跃，模拟真人兴趣。

## 5. 冷启动策略（养号）

> 依据运营社区共识：**新号需连续养号 5–7 天**，期间以浏览为主、极低频互动、**不发布**。
> aidcp 应内置"账号年龄 → 行为档位"的自动映射。

### 5.1 新账号前 7 天行为规划

| 天数 | 浏览 | 点赞 | 收藏 | 评论 | 关注 | 发布 | 目标 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Day 1–2 | 30–50 | 0–3 | 0–1 | 0 | 0–1 | 0 | 纯浏览，建立"看得多"的质量指数；完善资料 |
| Day 3–4 | 50–80 | 5–10 | 1–3 | 0–1 | 1–2 | 0 | 开始轻互动，仍以浏览为主 |
| Day 5–7 | 80–120 | 10–20 | 3–5 | 1–3 | 2–3 | 0–1 | 互动趋于正常；Day7 后可试发首篇 |
| Day 8+ | 进入"保守档"，再逐步过渡到"正常档" | | | | | | 放量 |

每日浏览时长建议 ≥ 30 min（分早晚两段），呼应"质量指数"公式。

### 5.2 养号阶段操作模式

- **真实人设垂类**：浏览/互动围绕一个或少数兴趣垂类，建立稳定画像，别什么都看。
- **认真互动**：点赞前必有阅读时间（§3.2）；评论 ≥15 字且带情绪词，绝不机械短评。
- **完善账号资料**：头像/昵称/简介/背景图合规（不涉政/涉黄/不露微信号），资料一次
  填好后保持稳定。

### 5.3 从纯浏览转为互动 / 开始发布的判据

| 转换 | 触发条件 |
| --- | --- |
| 浏览 → 轻互动 | 账号年龄 ≥ 3 天 且 累计浏览 ≥ 80 且 无任何风控信号 |
| 轻互动 → 正常互动 | 账号年龄 ≥ 7 天 且 连续 3 天点赞率落在 15–35% 且 状态=normal |
| 开始发布 | 账号年龄 ≥ 7 天 且 已有稳定浏览历史 且 首篇通过相似度自检 |
| 提档（保守→正常→激进） | 当前档位连续运行 ≥ 7 天 且 全程 state=normal 且 无限流信号 |

任意阶段一旦命中风控信号（§7），立即**回退一档并暂停发布**。

## 6. 具体数值建议汇总（保守 / 正常 / 激进）

> 三档定位：**保守**=新号/新环境/出现过风控；**正常**=稳定运行的成熟号；
> **激进**=已长期存活、指纹/IP 干净、可承受一定风险时的上限（不建议长期使用）。

| 维度 | 保守 | 正常 | 激进 |
| --- | --- | --- | --- |
| 每日浏览 | 80 | 150 | 300 |
| 每日点赞 | 20 | 50 | 100 |
| 每日收藏 | 10 | 25 | 50 |
| 每日评论 | 3 | 8 | 15 |
| 每日关注 | 5 | 15 | 30 |
| 每日发布 | 0–1 | 1 | 2 |
| 单次会话时长 | 15 min | 30 min | 60 min |
| 每日会话数 | 2–3 | 3–4 | 4–6 |
| 会话间冷却 | ≥90 min | ≥45 min | ≥20 min |
| 卡片间停顿(中位) | 6s | 5s | 3.5s |
| 操作间停顿(中位) | 3s | 2.5s | 1.8s |
| 点赞率区间 | 15–25% | 15–35% | 15–40% |
| 连续活跃上限 | 2 h | 3 h | 3 h |
| 凌晨(0–6:30)活跃 | 几乎不 | 极低频纯浏览 | 极低频 |

## 7. 风控状态机

> 统一事件模型引用：本章状态迁移输入统一受 `./design-gaps-and-models.md` 的事件模型约束。风控域只消费统一事件，不单独定义另一套事件契约。

- 账号最终风控状态只由云端 `RiskController` 单写；异常系统、任务系统、飞书与 Web 只能提交事件或读取投影，不能直接改写账号最终状态。
- 风控相关输入事件至少应携带统一事件类型、`severity`、主体账号/任务标识、来源层级与幂等键，避免重复告警导致重复迁移。
- 是否触发 `normal / warned / restricted / frozen` 的迁移，以云端 `RiskController` 对统一事件的判定结果为准。

账号在四个风控等级间迁移。状态由**信号检测器**驱动，并直接控制 §6 的档位。

### 7.1 状态定义与档位映射

| 状态 | 含义 | 行为档位 | 发布 |
| --- | --- | --- | --- |
| `normal` | 健康 | 当前设定档（保守/正常/激进） | 允许 |
| `warned` | 出现疑似限流信号 | 强制降到**保守档** ×0.7 | 暂停 24h |
| `restricted` | 确认被限流 | 仅**纯浏览**（停止一切互动） | 禁止 |
| `frozen` | 功能受限/疑似封禁 | **完全停手**，告警人工介入 | 禁止 |

```
       信号轻       信号确认        登录失败/封禁提示
normal ───────► warned ───────► restricted ───────► frozen
  ▲               │ 24h无新信号      │ 持续 ≥72h 无好转
  │ 连续7天        ▼                 ▼          人工解封/申诉成功
  └──────────── normal ◄──────── (观察恢复) ◄────────────┘
```

### 7.2 触发条件（降级）

| 目标状态 | 触发信号（任一） |
| --- | --- |
| → `warned` | 单篇笔记搜索屏蔽（标题搜不到）；近 3 篇平均阅读量较基线**断崖下跌 >60%**；互动接口偶发失败/异常弹窗增多；操作被要求验证码/滑块 |
| → `restricted` | warned 状态下信号未消失且新增；多篇连续限流；关注/点赞操作明确报错或被静默吞掉（后置校验连续失败，呼应架构"三道闸"） |
| → `frozen` | 登录态失效无法续期；出现"账号异常/封禁/申诉"提示；CDP 后置校验长期系统性失败（疑似账号级封锁） |

> 信号采集复用现有 LocatingEngine 的**后置校验（第一道闸）**与**重试升级（第二道闸）**：
> 互动后业务结果未发生 / 连续失败升级 `systemic_revision`，既可能是页面改版，也可能
> 是被限流——风控状态机据此联合判断。

### 7.3 恢复条件（升级回迁）

| 迁移 | 条件 |
| --- | --- |
| `warned` → `normal` | 进入保守档运行后，连续 **7 天** 无新信号、阅读量回到基线 70% 以上 |
| `restricted` → `warned` | 纯浏览观察 ≥ 3 天，无新增限流信号，搜索屏蔽解除 |
| `frozen` → `restricted` | 人工介入（重新登录/申诉成功）后，先以最低档纯浏览观察 |

### 7.4 降级操作（被限流后自动降速）

进入 `warned`/`restricted` 时，调度器自动执行：

1. **限频**：所有每日上限 ×0.7（warned）或互动归零（restricted）；
2. **降速**：停顿分布 `μ` ×1.3，会话时长上限 ×0.6，会话数 −1；
3. **停发**：暂停发布；
4. **拉长冷却**：会话间冷却翻倍；
5. **告警**：`frozen` 时输出告警事件，停止自动操作，等待人工。

降级是**自动且即时**的——不依赖人工发现，这正是当前实现完全缺失、却最关键的一环。

## 8. 与 aidcp 现有架构的集成建议

| 风控能力 | 建议落点 | 说明 |
| --- | --- | --- |
| 频率计数器 / 档位 / 状态机 | 云端（aidcp-cloud），新增 `RiskController` | 跨会话、跨节点共享状态，复用 PG 持久化 |
| 时间窗口调度 | 云端调度器，决定"是否上线 / 启动哪个会话" | 由云端下发"本次会话预算"（时长/动作数/档位） |
| 停顿/滚动/鼠标分布采样 | 边缘端（aidcp-edge），新增 `HumanizedTiming` 模块 | 替换现有 `random(4,8)`；与执行层 CdpActionExecutor 协作 |
| 内容去重 / 相似度 | 互动去重在边缘内存+云端持久化；发布相似度在云端发布前 | 复用现有 PG |
| 信号采集 | 复用 LocatingEngine 后置校验 / 重试升级结果，上报云端状态机 | 不新增检测，只接线 |

> 设计上与现有"边轻云重"一致：**策略/状态/预算在云端，节奏/拟人化执行在边缘**。
> 行为指纹的具体技术实现（贝塞尔参数、wheel 事件序列、按键节奏）见
> [反检测与登录态维持方案](anti-detection.md)。

补充约束：本节涉及的风控控制器、计数器与状态机落点，均应以 `./design-gaps-and-models.md` 中“统一事件模型 + RiskController 单写原则”为上位约束。实现上建议由云端统一接收 `action.result`、`anchor.report`、`error` 等底层信号，归一化为事件后再驱动状态迁移，而不是由多个模块分别写状态。

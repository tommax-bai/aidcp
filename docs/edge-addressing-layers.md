## 1. 为什么需要这份文件

边缘长期被描述为「重、不好理解」。逐条盘点后，这是**两个**问题：

| | 症状 | 真相 |
| --- | --- | --- |
| **重** | 代码量大、状态多 | **大部分是结构必然**——边缘同时承载四类按不同编址单位运转的东西，而云端只对其中一类有话语权 |
| **不好理解** | 行为难预测、改动不敢下手 | **这才是真问题**——四类今天全挤在同一个约 1870 行的 `main()` 闭包里，中间没有边界 |

那个闭包的代码注释自己承认过：「留在这个无导出的 `main()` 闭包里的判据，用例一行都驱动不了」。

**边缘不缺归属表**（既有台账已把 82 条运行时通道全部归属、230 块行段覆盖无空洞），
**缺的是裁决依据**——而且已经出现过用错判据的实例（见 §4 判例二）。

## 2. 四层：按「编址单位」划分

| 层 | 编址单位 | 权威 | 典型内容 |
| --- | --- | --- | --- |
| **宿主层** | 机器 | **本地** | 槽位调度、可用内存推算、有界串行启动队列、进程生死与回收 |
| **环境层** | 分身 | **本地** | 浏览器开关与待机、Facebook 启动登录协调、指纹、代理、阻断检测 |
| **翻译层** | 环境 → 账号 | **本地** | 身份首读与确立、身份守卫复核、身份翻转后重立 |
| **账号层** | 账号 | **云端** | 浏览、互动、发布、风控、配额、人审、记账 |

### 2.1 核心论据：云端的权威全部按账号编址

边缘主进程的实际启动顺序（`aidcp-edge` @ `00fda89`）：

```
① 浏览器起来（环境）
② 引擎建立
③ Facebook 启动登录协调        ← 进度与失败只报桌面外壳，不报云端
④ 读登录态 → 账号身份确立       src/main.ts:671
⑤ 才 new EdgeClient({ accountId })   src/main.ts:683   ← accountId 是构造参数
⑥ 才 connect()                       src/main.ts:1419
```

**登录协调执行时，云端客户端对象尚不存在。** 它的进度与失败出口都是桌面外壳 IPC
（`src/main.ts:414` 进度 / `:426` 失败），该函数体内零 `client.send`。

而且**一条云端连接绑死一个账号**：身份翻转时的处理是「断开 → 换账号 → 重连」，两条路径同形——
守卫重立（`src/main.ts:1566` 断开 / `:1577` 换 accountId）、唤醒发现账号变了
（`:1839` 断开 → `:1840` 换 accountId → `:1843` 重连）。

**因此：云端不是「来不及说话」，是「没有可说的对象」。** 它的整套权威——额度、风控、审批、归属——
全部按账号编址；一个还没有账号的环境，在它的概念体系里不存在。

这是一条**编址体系的缺席**，不是时序上的先后。两者的区别决定了处置：时序问题可以靠"等一等"解决，
编址缺席不能。

### 2.2 为什么不用其他分法

- **按「观测 / 动作」分**：会把周期阻断观测整块判错——它跨层（§4 判例三）。
- **按「读 / 写」分**：解释不了槽位调度为什么必须本地——它既不读页面也不写平台。

编址分法是唯一能同时正确裁决 §4 三个判例的。

## 3. 四条判据

| # | 判据 | 问什么 |
| --- | --- | --- |
| **①** | **事实归属** | 决策依赖的事实**只有谁知道**？（本机可用内存 vs 账号级额度） |
| **②** | **时序** | 它是否发生在**云端到场之前**？**断连时是否仍须工作**？ |
| **③** | **后果** | 判错了会不会**在平台上留痕**？（可逆 vs 不可逆对外写入） |
| **④** | **性质** | 决定「**何时能开始**」还是「**开始之后做什么**」？ |

### 3.1 四条 MUST 合并使用

四条全中 ⇒ 归本地；全不中 ⇒ 归账号层；**中间态按 §4 判例三的方式拆开处理，而不是整块二选一**。

**单独使用任何一条都可能得出错误结论：**

- 单用 ①：会把登录协调判错——页面信号确实只有本机知道，但那不足以说明它该**自主决策**。
- 单用 ③：会把登录协调判成「混合体」——这正是 §4 判例二记录的那次误判。

四条一起用，才能定位到「它是环境层」这个结论。

## 4. 三个已裁决判例

### 判例一 · 浏览器槽位调度 ⇒ 宿主层，铁定本地

| 判据 | 结论 |
| --- | --- |
| ① 事实归属 | 容量按**本机启动时可用内存**推算（`src/electron/main.cjs:2799`）——云端问都问不到 ✓ |
| ② 时序 | 浏览器得先开起来才能连云端；**断连时仍须工作**，否则本机连自救都做不了 ✓ |
| ③ 后果 | 判错了最坏是本机卡住，**平台上一个字都不会多发** ✓ |
| ④ 性质 | 有界串行启动队列（`:2507`）＝**准入排队**，不决定行为 ✓ |

**四条全中。** 这也解释了它为什么天然不需要人审、额度、以及「已派发未确认」那一整套账号层机制——
它的错误后果不落在平台上。

### 判例二 · Facebook 启动登录协调 ⇒ 环境层，留本地

**⚠ 本判例同时是一次误判的记录，作为反面示范保留。**

**曾经的错误结论**：「它是混合体（四条判据只中两条），建议先别碰。」

**错在哪**：拿「登录失败会打到账号头上（触发风控、安全检查点）」当归属判据。

> **那是后果，不是归属。** 执行的时候账号还不存在（见 §2.1 的启动顺序）。
>
> **用后果去定归属，方向反了。**

**正确结论**：按编址它是**干净的环境层**——它服务的对象是「这个分身」，产出是「这个分身现在登着谁」，
整个过程与云端无交互。该留本地。

**这类错误容易再犯**，因为「后果严重」的直觉压过「归属清晰」的事实。裁决时先问编址，再看后果。

### 判例三 · 周期阻断观测 ⇒ 跨层，拆开处理

它是三例中唯一跨层的：

| 面 | 内容 | 层 | 处置 |
| --- | --- | --- | --- |
| **能力面** | 探页面有没有被拦住（`browse-session.ts:1483` 发 `page_probe` 给引擎） | 环境层 | **留本地** |
| **决策面** | 判类 + 二次确认 + 置风控态 + 停发命令 + 通知人（`:1523` → `:1552` → `:1656` → `:1659` 发往云端） | 账号层 | **可上移** |

**正解不是整块搬走，而是「能力留下、决策上移」。**

**但 MUST 保留一条环境层的自我保护兜底**：「发现被平台拦住即就地停手」。
理由：断连期间没人做决策，而此时继续瞎点是所有情况里最坏的一种——这条兜底本身就是环境层的职责，
不因决策上移而转移。

## 5. 禁令：MUST NOT 派生第二张归属表

**本判据 MUST NOT 派生任何新的边缘归属表、归属清单、目录规则文件或归属门禁。**

**理由**：边缘一旦出现两张互不校验的归属表，就构成本设计从头到尾要治理的那个失败形态——
同一份知识多处手抄、没有一处是权威、漂移无人察觉。

这套系统已就同类形态付过代价并留下明文教训。`aidcp-cloud/boundaries/ownership-rules.json` 里写着：

> 逐文件裁定名册 **MUST NOT 改用生成物顶替**——那会让判据退化成「是否已经在生成物里」，
> 手工往生成物塞一条新文件 + 目录默认层就能全绿、refresh 随后永久洗白。

**分工写死**：

| | 回答什么 |
| --- | --- |
| 既有归属台账 | **这块归谁** |
| 本判据 | **凭什么** |

台账是本判据的**消费方**。判据不产出台账，台账不内嵌判据。

| | 那条 change | 本判据 |
| --- | --- | --- |

本判据把这个已被局部发现的结构**命名并补全**，特别是补上**环境层与账号层的分界**——
那是既有拆分未回答、而后续每一次上移决策都必须回答的。

**本文不修改那条 change 的任何产物。** 它是否引用本判据，由其 owner 决定。

### 6.2 不适用于云端拆仓归属

云端按另一套编址单位划分（`api` / `content` / `automation` / `kernel`，事实源见
`docs/cloud-service-decomposition-proposal.md` §4.7）。

**本判据 MUST NOT 被用于裁决云端模块归属。** 两者编址单位不同、适用范围不重叠。

## 8. 用法速查

面对边缘里任意一件事：

1. **先问编址**：它服务的对象是一台机器、一个分身、一次环境→账号的翻译，还是一个账号？
2. **再用四条判据交叉验证**：事实只有谁知道 / 是否云端到场前就得干 / 判错了平台上留不留痕 / 管开始还是管做什么。
3. **四条全中 ⇒ 本地；全不中 ⇒ 账号层；中间态 ⇒ 拆开**（能力与决策分属不同层时，按判例三处理）。
4. **裁决结论写进既有归属台账，不要新开一张表。**

## 一、结论

**改后批准，且必须分级批准。**

- **批准并可立即启动**：阶段 0–2（单仓内建立边界、独立入口与进程、Schema 与迁移唯一所有者、Outbox/Inbox、导入与数据所有权检查）。方向正确，绝大部分收益在这里。
- **不批准为既定终局**：阶段 3–5 的 Git 仓拆分。降级为「以可判定门槛为准入的待触发选项」。理由不是方向错，是准入论据不成立：§15 自己立了四条门槛，实测只有「隔离要求」一条成立，而它由阶段 2 的**进程**隔离即可兑现，不需要 Git 边界；方案未解释顶层三分法为何豁免自己立的门槛。
- 现在批准阶段 0–2 **不会**关闭拆仓这个选项——无论采信哪一版结论，第一批工作完全相同。

## 二、必须修的问题（按严重度排序，已去重合并）

### 1. 拆仓的增量收益未被论证，且论据被现状证伪（major｜§12 阶段3、§14、§15、§16）

- §14 的 18 条红线中，17 条在阶段 1+2 即可拿到；唯一必须拆仓的红线 5「三个仓可独立构建/部署/回滚」是把手段写成目的，且其六个词里五个已被阶段 2 自己承诺（:506-508）。
- 阶段 3「先提 content」的四条理由：①「AI/FFmpeg/ASR/Python/GPU 依赖不同」——cloud 运行时依赖只有 6 个包，全 src grep `ffmpeg|whisper|transcode|child_process` 零命中，edge 同样零命中，**今天完全不存在**；②「创作和评估输入输出清晰」——14 个 LLM 角色中 9 个构造参数直接要预算/当日配额/冷却/风控解释；③「高负载影响心跳」由阶段 2 进程隔离兑现，非仓库理由；④「发布节奏独立」是纯断言。
- §15 门槛实测：四仓提交邮箱只有同一人的两个地址、仓龄 7 周、近 30 天 2847 次提交、dev/ol 各 2 vCPU 且单进程 RSS 仅 243/267 MB、CI 为 0。
- 摩擦成本未测算：近 30 天 cloud 428 个可分类提交中 34% 跨两域、11% 跨三域；53% 的提交要动 4649→4804 行的组合根。

**改法**：①§14 加一列「兑现阶段」，红线 5 改写为实质属性（各单元可独立构建/部署/健康检查/回滚，且回滚不牵动其他单元）；②§12 阶段 3 补可判定的进入条件（内容侧已引入异构运行时依赖 / 内容负载实测打断心跳 / 出现独立发布节奏，三者皆不成立则停在阶段 2）；③显式声明「阶段 2 形态是合法终局，停在此处不算未完成」；④§16 拆成两段批准；⑤重写阶段 3 的四条理由，把①标为条件式未来、②改为「发布链已有现成接缝」（生成候审段与下发段已被既有 change 切开）。

### 2. 「RiskController 单写」是进程内单写，不是服务单写（major｜§14.9、§5.1、§12 阶段2）

风险状态在 controller 创建时读一次库，此后纯内存变更 + 全列盲 upsert（无版本、无 CAS，`risk/pg-risk-store.ts:191-203`），controller Map 永不驱逐；配额计数只在创建时回放一天窗口。dev 与 ol 今天已是两个进程共写同一张 `risk_state`。方案把它提为服务级单写，却没有一句说明 automation 对同一 executionTarget 必须单实例。后果不是性能问题，是配额合计翻倍地放行**真实平台动作**，以及 `restricted` 被陈旧的 `normal` 静默盖回。

**改法**：§14.9 改成「对任一账号，任一时刻风险状态写入者唯一，且配额判定所依据的计数与库内事实一致」，并二选一写死：(A) 单实例路线（每 target 单实例 + 禁止滚动/蓝绿，现状 stop→start 已满足）；(B) 去单实例路线（状态加版本列 + 条件写、准入判定改按需聚合、controller 缓存加失效）。两者成本差一个数量级，**必须在阶段 2 之前拍板**。同时阶段 2 补一张「单实例 / 可多实例」分类表：委托任务 worker 与小时格认领是可照抄的正例（认领令牌 + 租约 + 跳锁 + target 过滤）；发布下发器、验证码协助、连接运行时注册表属前者。

### 3. api 停机时 automation 会全停，且配置变更跨进程后永久不可见（major｜§11、§5.1）

「按合同安全收敛」无定义。实况：人设闸、慢启动锚点、四类限频配置今天都是**每次判定同步读进程内镜像**，读不到即 fail-closed；其契约被代码写死为「同步、零 IO、永不抛」，内部 HTTP 形态上满足不了。更硬的是：13 个配置镜像只在启动和本进程写入时刷新，全仓无 watch、无轮询、无 LISTEN/NOTIFY——拆进程当天，写方改了读方永远看不到。

**改法**：①把配额、节奏、单场、恢复四个配置存储**随消费方一并归 automation**（今天依赖方向已单向倒置，零代码成本，一次消除四条跨服务同步读）；②人设与环境养号事实改为 automation 本地只读副本 + 版本 + 失效通知 + 有界陈旧度，超期才收敛停手；③§11 那一行改写为三态（在跑会话 / 已领取未开始的持久任务 / 新会话启动）；④把客户端已有的「已绑 / 未绑 / 未知」三态延伸到服务契约：只有权威「未绑」才允许触发人设向导，「未知」必须映射成独立不可用态。

### 4. 审批授权链靠本机临时文件，方案零字（major｜§4.2、§5.2、§6.4、§12 阶段4）

发布与评论的「已授权」这一位不在数据库里，而在一个本机文件上：写方是飞书回调、后台、客户端内审批（未来归 api），读删方是发布下发与评论审批闸（未来归 automation），同时还是与 edge 的两端契约路径。api 与 automation 一分进程即断，失败方向是 fail-closed 的静默停滞。同类还有第二处：环境级串行用的库级 advisory lock 被客户鉴权与互动两个模块共用，拆库即静默失效。

**改法**：①§6.4 禁止清单补一条「不得用共享文件系统、本机路径或数据库 advisory lock 传递跨服务的授权、锁或业务事实」；②§12 阶段 0 的盘点清单从「进程内状态/事件/Store/每张表」扩为「+ 本机文件信号、本地锁、库级 advisory lock、常驻定时任务」——现清单结构上盘不到这四类；③阶段 4 把授权改为 api 拥有的持久记录（含候选版本、决策人、时间、目标环境与 target），automation 经持久命令获知。

### 5. 可观测性整段缺失，且最需要关联的那条路径恰恰没要求关联（major｜§6.1、§6.3、§11）

方案定义了「降级后什么样」，没定义「怎么知道已经降级了」。§6.3 为持久消息定义了关联标识，§6.1 的内部 HTTP 只要求超时/预算/熔断/诚实错误——而按 §7.2，热路径走的是内部 HTTP，一次完整互动新增约 9–11 次往返。现状：无日志/指标库、无贯穿标识、无指标端点、276 处裸 console、ECS 无监控 agent、告警写入者与被监控进程同源（进程死即无告警）。

**改法**：①§6.1 补一句：内部 HTTP 必须透传关联标识、因果标识、执行目标，被调方必须写进日志，缺失时生成并回填、禁止静默丢弃；②新增一节「降级的可检测性」，与 §11 表一一对应——每有一行「允许受影响」，就必须有一个检测信号；③§14 补两条：故障类跳过（评估超时/报错/解析失败/内部调用失败）与设计内克制（模型判过、预算耗尽、冷却未过）必须分别计数并持久化、超阈告警；任一服务不可用必须在 N 分钟内产生可路由告警，且告警链路不得与被监控服务同进程。

### 6. 服务间身份与秘钥分发整段缺失（major｜§6.1、§5.1、§14）

现有四套认证全是「外部主体→云端」，无一是服务间模型；内部服务调用今天为 0 次，拆分创造的是全新信任类。而将要暴露的内部接口能一次启停所有连接的浏览会话、能读全量客户数据。秘钥同样无解：厂商密钥加密落库、主密钥来自环境变量，写入面在 api、解密使用方在 content 与 automation，而 §6.4 禁止跨服务读表——按方案已有规则，这一类数据**无解**（「引用版本或快照」对秘钥无意义）。§14 的 18 条红线里安全类为 0。DB 口令还以明文常量兜底在源码，独立数据库账号会把它放大成三份。

**改法**：①新增 §6.5：指定单一服务身份机制、内部监听器默认只绑回环、控制类与只读类凭据分离；②§5.1 补一行「模型与对象存储厂商凭据」，并二选一（api 提供短期取值接口 / content 只读该表并在 §6.4 写成显式例外），同时记录「启动期一次性解密」现状会让轮换从重启 1 个进程变成协调重启 N 个；③§14 补一条安全红线；④新增任何数据库角色之前，先把 DB 口令从源码兜底改为纯配置读取。

### 7. 数据侧地基不存在，且没有可逆性约束（major｜§5.1、§12 阶段2、§14.5）

没有迁移执行器、没有迁移账本：唯一工具接一个文件路径跑完即退，编号已四组碰撞、缺一号；真实 schema 由 32 个存储各自建表（组合根 37 处初始化调用）；零 CREATE SCHEMA、零 CREATE ROLE，唯一一条授权语句还是管理员误跑后的事故补丁。在这个地基上要求「三条独立迁移目录」，等于把 1 条无序线变成 3 条无序线。更危险的是：由于存储会自建表，「回滚到旧版本代码」在表已迁走时会**静默重建空表并分叉写入**——回滚动作本身成了一次静默假成功。§10 的兼容规则只覆盖合同，完全没延伸到数据库。

**改法**：①阶段 2 的「唯一所有者」前置一条硬前提：先建带账本的有序迁移执行器、取消存储自建表、清理编号碰撞——这一条**不依赖拆分、可立即做**；②§5.1 与阶段 2 补可逆性约束：迁移期只做扩张（新增 + 双写 + 影子读比对），收缩必须是独立、可单独回滚的变更；③把 §5.1 的 MUST 拆成两个可独立验收的子目标——「迁移目录与所有权归属」（阶段 2 可完成）与「Schema/角色物理分离 + 授权屏障」（依赖 ol 拆库，排在其后），并**显式承认中间存在一段红线 6 无机械强制的窗口**；④写明「迁移期共用同一 PostgreSQL **数据库**」（非仅同实例）——跨 schema 外键与库级 advisory lock 都是库级作用域，跨库即静默失效。

### 8. 合同防漂移选错了机制，而现有保护正在被拆掉（major｜§10、§14.16、§12、§13）

§10 全是构建期机制，防不住本项目已发生的两次血案：客户 API 五段路由与云端四段实现不一致，主路径 100% 返 404 而测试全绿；枚举扩宽导致管理后台整页白屏而类型检查全绿。更要命的是 **§10 的兼容规则把「枚举扩宽」默认为兼容**，等于为白屏事故背书。同时：今天唯一有效的跨边界机械手段是同源类型穷举，拆仓即失效；而 §13 把 CI 列为跨仓一致性三大承重件之一，§12 六个阶段却没有任何一条产出它——CI 现状为 0（只有 edge 一个手动触发的打包流程，不跑测试）。

**改法**：①改 §10 兼容规则——新增枚举成员对穷举型消费者是破坏性变更，必须走版本；并新增消费者义务：遇未知枚举值必须走渲染/逻辑兜底并告警，禁止裸索引、禁止退化为白屏或静默丢弃（这是唯一与机制无关、无条件生效的防线）；②§10 增一条运行时自证：每个服务暴露版本端点，返回合同版本 + 受控枚举运行时全集 + 关键字段清单，真值取自唯一运行时源，消费方必须有对活端点的对拍测试且在部署闸里非跳过执行（仓内已有可直接照抄的实现）；③增清单驱动的路径级契约测试（对运行中的服务真拼 URL 打真 HTTP，冻结路径退化为「接口不存在」即失败）；④阶段 2 补明确交付物「各仓 CI 跑通类型检查 + 验收测试 + 合同夹具」，并作为阶段 3 的准入。

### 9. 其余需要一句话级修补的（minor，合并）

- **§4 归属缺口**：三条边界只覆盖 252/315 文件（78% LOC），63 个文件 18630 行无人认领；微信收件箱域 20 张表（占全库四分之一）在三仓职责表零落点；飞书 15 文件 2686 行同时是审批出口与第二运营控制入口，也无归属。→ §4 补 interactions 与飞书归属；把 §7.2 末段的逃生条款（临时微判断可留 automation）**提升为阶段 3 的显式首批范围**，点名 4 个资产型评估角色 + 发布生成段，并写明浏览闭环判断本阶段不迁。
- **§6.3 信封精度**：关联标识与幂等键悬空——「幂等键」在 §8.5 被点名却全文无定义；`tenantId` 未定义且与仓内既有「tenant=账号」用法撞车，而 `accountId` 全文 0 次；`personaVersion` 无载体（人设表无版本列）；「能力版本」全文仅出现一次未定义；`aggregateVersion` 未规定分配者，且发布台账上已有一个同名易混的内容编辑版本列，误用即假闸。→ 集中补一段，模板照抄视觉参考分析的「schemaVersion + 供应商/模型 + 内容哈希复合键 + 诚实失败态」。
- **§11 表缺两行**：PostgreSQL 不可用/连接耗尽（真正的共因故障域，且拆分后该实例还兼任服务间消息总线，爆炸半径**变大**）、跨服务消息积压/死信。同时 api 停止那一行要补全：管理后台全部读写不可用，且 automation 必须保留一条不经 api 的紧急停手入口。
- **§14.2 与 §14.5 无法验收**：同机三进程在 CPU 与内存两维零隔离（systemd 无任何资源限额），进程拆分只解决「同步栅格化阻塞事件循环」这一条；健康检查现为无条件返回成功，红线 5 可被空洞通过。→ §14.2 补验收前提；红线 5 补「自有依赖不可达必须返回不健康，且不得把下游不可达转化为自身不健康」。
- **§12 阶段 2 补运维工件**：部署前置检查器现为「单目录 + 单服务」模型，必须改造为「目标 × 服务」二维（3 服务 × 2 target = 6 个部署单元，备份/rsync/重启/健康检查/回滚各一份）；fleet 脚本仓清单参数化（真正有行为的只有 4 处）。
- **§12 阶段 1 顺序**：把「模块导入与数据所有权检查」从末位提到首位，并注明先于任何边界重构落地。
- **§16 文档同步清单**补：受影响的已合并 spec 的 delta（至少后台面板 API 那份要求「进程内挂载、复用组合根单例、面板 WS 订阅进程内总线」的 SHALL 会被本方案取代）、验证与验收策略文档、并行开发手册。

## 三、方案做对的地方

1. **§12 的阶段顺序是对的**，且把最便宜、收益最高的一步放在最前；阶段 1 自陈「目标是先消除源码和状态耦合，不是假装已经完成微服务化」——这份自我限定很清醒。
2. **明令「不要在同一次改动中拆服务、迁数据并改名」**，并把改名隔离到阶段 5、写明「aidcp-cloud 是迁移来源，不创建一个重复实现的新仓」——直接排除了「并行重写 + 某天切换」这个最致命的迁移失败模式，是绞杀者而非重写。
3. **§15 显式反过度设计**：拒绝 7 种进一步拆分（中央合同仓、媒体仓、风控仓、每平台一仓、每 Worker 一仓、Kafka、服务网格、分布式事务），并主张优先用同仓 Worker 解决扩容。方向完全正确，问题只在于这把尺子没有量它自己。
4. **§9 不按平台拆服务或仓库**，平台差异走适配器，并要求能力缺失返回明确错误、不得回落——避开了本项目最容易踩的切分陷阱。
5. **§11 把降级语义写成可验收契约**，而不是含糊的「解耦」；末句禁止把「已接收/已创建/已投递/已派发/结果未知」显示为业务成功，与本仓第一红线同轴。
6. **§6.2 把互动的五个阶段显式区分**，写死「Edge 回执已返回不能冒充平台动作已发生」——这是分布式下最容易被伪装成成功的一处。
7. **§6.4 的五条禁令全部对应仓内真实存在的耦合**，尤其「进程内事件总线不承诺跨进程可靠性」直接点中现役实现（同步 fire-and-forget、异常只打日志）。
8. **§8 对执行目标的六条规定**精确命中 dev/ol 共库这一真实竞态，且委托任务与小时格认领已按此实现，是现成范式。

## 五、对三个替代方案的取舍判断

三个替代方案都主张「单仓多进程、不拆仓」，但判据与第一刀不同，不应等量齐观。

**我的推荐是组合，而不是三选一：用方案三的判据 + 方案一的内核层 + 方案二的第一刀顺序。**

- **判据取方案三（三平面：请求面 / 作业面 / 在线运行面）**。它的判据是机械可判定的——「干活时需不需要碰只存在于本进程内存里的活对象（连接注册表、事件总线、会话上下文、风控实例、在途租约）」，315 个文件全部自动落位，且可直接写成导入检查当场执行。原方案的判据是语义的（属于内容还是自动化），实测在 9/14 个角色、发布链 15093 行、互动域 6832 行上判不出来，才有了 78% 覆盖率这个后果。
- **内核层取方案一**。原方案 §6.4 禁止共享业务包，但实测有 16 个文件被三边共同导入（角色基类 43 个导入方、协议 40、数据库配置 30、角色名枚举 49），按 §6.4 要复制三份——而角色名枚举那 43 个成员的联合类型今天正是靠同源类型检查兜底的。承认它、命名它、给它单写者纪律，比假装它不存在好。这一步还有直接收益：反方向 79 条跨边界导入里 69 条会当场归零。
- **第一刀取方案二（客户数据面）**，不取原方案的 content。理由三条：①它兑现的是 18 条红线里唯一有外部用户可感知价值的一条，而且今天的不对称是反的——边云 WS 启动排在两个 HTTP 服务之前且不可跳过，自动化侧任何崩溃都拖垮客户数据面，反之不然；②九成工作已由既有 change 做完，真正要改的只有三处（活体绑定闸、三个风控实例直读、配置镜像失效）；③它可以做到「零内部服务间调用」，于是内部 HTTP 熔断、Outbox、消息信封、合同工具链在这一刀下**一条都不需要建**。相比之下 content 是最难切的一刀（9 个角色结构性横跨、选卡角色把打分与下发焊在一个对象里、发布链横跨三侧、创作触发今天只遍历在线账号，直接违反 §11 首行）。
- **§14.2（内容负载不影响心跳）不必靠切 content 买**。今天唯一的真实落点是文字卡的同步栅格化，用工作线程把它挪出主线程是改一个文件；切一个服务边界是造一条边界。同样的红线，成本差两个数量级。作业面（方案三的第二刀）排在其后，触发条件是「实测观测到内容负载打断心跳」或「真的引入了 ffmpeg/ASR/GPU」。

**三者的共同缺陷要诚实说**：它们都换不来物理边界。逻辑门禁可以靠改豁免清单绕过，Git 边界不能。如果决策目标就是「要一道过不去的墙」，那应该直接走原方案——但那时必须同时接受：先失去同源类型检查、后建成 CI 合同测试之间那段真空期；以及 fleet 全局门禁触发面随仓数线性放大（已有 canonical 子仓被切到发布分支停留 24h 的先例，而两道漂移守卫只看控制仓）。

**方案二单独看最保守**：它明确不买 §14.2、不动面板直读运行时。作为「只允许切一刀」的答案它是对的，但作为终局不够。**方案一单独看最完整但第一刀选择与它自己的收益论证略有张力**（它承认门禁可绕过，却把最强的收益压在门禁上）。**方案三工作量最大**（创作触发要改成数据库队列驱动），但那笔工作恰好顺手修掉 §11 首行的既存违例，不算白付。

## 附录二：三个替代方案原文摘要

### 一仓四层：aidcp-cloud 内部边界固化（不新增任何 Git 仓库）

- **一句话**：在 aidcp-cloud 一个仓里做四件事——把「谁属于哪个域」写成一张机器可校验的归属表并用 acceptance test 做棘轮式依赖门禁、把组合根切成两个进程入口（客户数据面 vs 自动化面，内容仍留在自动化进程）、补一个最小迁移器并给表标所有权、只为一个真实存在的丢账洞建一张 outbox；明确不承诺拆仓、不建合同工具链、不切第三个进程。
- **边界**：## A. 域划分：四层而不是三域，且按文件归属而不是按目录

原方案的三域切法在代码里不成立：三条边界只覆盖 252/315 文件（78% LOC），漏了 63 个文件 18630 行；`interactions/`（20 文件 6832 行）横跨三边（`interaction-customer-api.ts` 挂客户 HTTP、`interaction-internal-api.ts` 挂面板、`reply-ai.ts` 调 LLM、`send-orchestrator.ts` 才是自动化）；`publish-agent/` 15093 行同样横跨三边（生成 ~7000 / 下发 ~2680 / 台账 ~1940）。所以本方案划四层：

1. **kernel（共享内核，允许被任何层导入）**——把实测的 16 个三边共导文件正式命名并冻结：`comm/protocol.ts`(40 个导入方)、`event-bus/types.ts`(49，全仓第一)、`agents/base-role.ts`(43)、`cache/pg-anchor-cache.ts`(30，13 个 config/panel store 从它拿 `DEFAULT_PG_CONFIG`)、`soul/types.ts`、`platform/index.ts`、`panel/types.ts`、`time/shanghai-day.ts`、`deployment-target.ts` 等。**这是与原方案最大的分歧点**：§6.4 明令禁止「共享包含业务逻辑的公共包」，等于要把这 16 个文件按仓复制三份，而 `event-bus/types.ts` 里那 43 个成员的 `RoleName` 联合类型今天正是靠同源 typecheck 兜底的。本方案反向操作：承认它、命名它、给它单写者纪律（改动串行、必须过 acceptance）。
2. **api**：`client-auth/`、`panel/`、`config/`（除下述 5 个 store）、`interactions/{interaction-customer-api, interaction-internal-api, interaction-scope-internal-api, reply-config-*}`、`publish-agent/{publish-log-store, client-publish-approval, draft-image-remove}`。
3. **content**：`agents/{curated-note-evaluator, curated-comment-evaluator, concept-extractor-role, comment-de-ai-flavor}`、`publish-agent/` 生成段（prompts / image-generator / cover-card-writer / visual-reference-analyzer / image-prompt-composer）、`render/`、`llm/`、`cache/curated-content-store.ts`。
4. **automation**：`comm/`、`orchestrator/`、`event-bus/`、`risk/`、`delegated-task/`、`comment-agent/`、`agents/` 其余 46 个、`publish-agent/` 下发段（publish-dispatcher / publish-scheduler / command-sequencer）、`interactions/send-orchestrator.ts` 等。

归属产物是一张 315 行的 `src/module-ownership.json`（路径→层），**新增文件未归类即测试失败**——这条让归属表不会腐化，是它相对「写在文档里的边界」的唯一实质差别。

## B. 依赖门禁：一个 acceptance test + 棘轮 allowlist

仓里零 lint 工具链（package.json 只有 build/typecheck/test/test:acceptance/start，无 eslint、无 dependency-cruiser），但已有「用测试当机械门禁」的现成范式（`test/acceptance/protocol-contract.test.ts` 靠 `Record<MessageType,true>` 穷举）。新增 `test/acceptance/module-boundary.test.ts`：解析 src 全量 import，按允许方向（任何层→kernel；api→content/automation 仅经指定 facade；content 不得导入 automation 除 kernel 外任何文件）判定。

**起手不修，先冻结**：把实测现存的 215 条跨边界 import 全量写进 allowlist，测试只保证「不新增」。分批削减时按方向优先级：`automation→content` 53 条里 43 条集中在 `orchestrator/role-dispatcher.ts` 一个文件（它 import 并 new 出 40 个 agents 角色类），这一处是全仓最纠缠的单点，也是收益最集中的一处。反方向 `content→automation` 79 条中 46 条指向 `event-bus/types.ts`、13 条 `platform/index.ts`、10 条 `comm/protocol.ts`——划进 kernel 后**这 69 条当场归零**，不需要写一行代码。这是四层划法相对三域划法的直接收益。

## C. 进程：只切一刀（api ↔ automation+content），不切三刀

今天一个 node 进程同时持有 8787(Edge WS) / 8090(panel) / 8091(client-auth)。切成两个 systemd 单元：`aidcp-api.service`（8090+8091）与 `aidcp-cloud.service`（8787，含 content）。实施形态是把 `src/server.ts` 拆成 `src/main-api.ts` / `src/main-automation.ts` 两个入口 + `src/composition/` 下分组装配函数。

**明确砍掉 content 独立进程**。原方案 §12 阶段 3 把 content 排在第一刀，理由是「AI / FFmpeg / ASR / Python / GPU 依赖与自动化明显不同」——这条今天完全不成立：cloud 运行时依赖只有 6 个包（lark-sdk / resvg / ali-oss / pg / satori / ws），全 src grep `ffmpeg|whisper|transcode|child_process|spawn` 零命中，所有「AI」都是远程 HTTP。§14.2（内容负载不影响 WS 心跳）今天唯一的真实落点是文字卡的 `resvg.render()` 同步栅格化（`src/render/text-card.ts:639-652`，lazy import，只在封面场景）。**用 `worker_threads` 把 resvg 挪出主线程 = 改一个文件；切一个 content 进程 = 造一条服务边界。**同样的红线，成本差两个数量级。等真接 TikTok/抖音视频、真引入 ffmpeg 时再切，那时理由才是真的。

**这一刀必须捆绑的前置（原方案通篇未提，但两条路都躲不掉）**：评论/发布审批今天靠本机 `/tmp/aidcp-publish-approve-<requestId>.json` 在飞书回调、面板、server.ts 读方与 edge 之间共享（写方 `feishu/ws-receiver.ts:123`、`panel/panel-server.ts:1179`；读方 `server.ts:1980,1995`）。api 与 automation 一分进程，这条链当场断。必须先把审批信号迁到 DB 一列——且 CLAUDE.md §4 记明这是与 edge 的**两端契约路径**，迁移要连 edge 侧 `buildPublishApprovalSignalPath` 一起改。这是本方案第一个必须完成的硬前置。

## D. schema：补迁移器 + 表所有权标注，**不做**独立 Schema / 独立数据库账号

明确放弃原方案 §5.1 的「独立 Schema、数据库账号、迁移目录」。三条理由都是实测：①今天**根本没有迁移执行器**——`scripts/run-migration.ts` 接一个文件路径建一次性 Client 执行，不记账本、不排序，migrations/ 编号已四组碰撞（0002/0030/0037/0038 各两份）且缺 0012；真实 schema 由 32 个 store 各自 `CREATE TABLE IF NOT EXISTS` 自愈建出（server.ts 里 37 处 `.init()`）。②dev/ol 共库、已被迫冻结破坏性 DDL（`docs/deployment-environments.md:64-70`）；三服务 × 两 target 会把今天 1 条迁移线膨胀成 6 次可错序施加。③`interactions/` 有一条跨 12 张表的单事务离场清理（`interaction-store.ts:1640-1678`），还有 `interaction-env:<envKey>` advisory lock 被 ClientUserStore 与 InteractionStore 共用——分库即静默失效。

改做三件：
1. **最小迁移器**：一张 `schema_migrations` 账本 + 有序施加 + 编号唯一性检查。这是所有下游动作的前置。
2. **表所有权表**（79 张表 → 层），配一个 acceptance test 解析 SQL 字面量，非属主出现 INSERT/UPDATE/DELETE 即失败，同样起手 allowlist 冻结现存 10 处多写。
3. **只修真正有害的少数**：ClientUserStore 直写 4 张 `interaction_*` 表（两个模块两个独立 Pool 写同一批表）、面板 retention-sweeper 直删 `risk_counters`/`interaction_feed`/`llm_token_usage`（跨三域）、`first_post_onboarding` 双写、Edge 握手回调直写 `client_environments`。**明确不动**：`publish_log`（一张表七态跨三段是发布领域本来的形状，拆开只会造跨服务 join）、`curated_content.bot_liked`（拆开同理）、`llm_token_usage`（所有域的模型出口都在写，按域拆它没有意义）。

## E. outbox：只建一张表，只治一个洞

不建通用 Outbox/Inbox 框架。实测跨重启丢失的洞只有一个：`interaction.occurred`（边缘确认真发生了平台动作）通向持久风控记账，全靠内存总线上一句 `.then(c => c.record(...)).catch(warn)`（`server.ts:1499-1531`）——进程在边缘回执与异步 PG 写之间崩溃，平台已经看见的那一下静默丢账。做法：边缘回执落地的同一事务写一张 `risk_interaction_outbox`（带 `execution_target`），消费者照抄 `delegated_tasks` 现成范式（claim/lease/version/dedupe + target 隔离 + 启动 `recoverInterruptedClaims` 回收僵尸）。

**明确不迁的**：浏览闭环本身不是跨重启工作——会话绑在活 WS 连接上，云端重启后边缘重连即 `restartSession` 重开一场，`SessionContext` 全部字段都是进程内私有态。把它迁 Outbox 既无必要也不合语义，原方案 §12 阶段 1 的字面范围比实际大得多。§6.2 的「至少一次 + Inbox 去重 + 聚合版本乱序 + 死信重放」在单进程内多数不需要。

- `assetId` 抽象与短期授权地址：今天跨模块传裸 URL、OSS 公读永久 URL，没暴露出问题。

- 改名、动仓名、动 `scripts/` 四仓白名单。
- **买到什么**：**能拿到的（按确定性排序）**

1. **代码耦合止血，且大头是白拿的**。四层划法把 `content→automation` 的 79 条里 69 条（46 条 event-bus/types.ts + 13 条 platform/index.ts + 10 条 comm/protocol.ts）一次性划进 kernel 归零，不写一行代码。剩余削减集中在 `role-dispatcher.ts` 一个文件（automation→content 53 条里的 43 条）。棘轮门禁保证「今天的 215 条是上限」——这一条今天完全没有任何机械手段，纯靠人记。

2. **§14.1 红线（Automation/Edge/浏览器全挂时客户数据 HTTP 仍可用）真拿得到**，且这是 18 条红线里唯一有直接用户可见价值的。切 api 进程后 automation 崩溃/重启不影响 8091。现状是反向的：`await server.start()`（server.ts:3199）在两个 HTTP 服务之前且不可跳过，WS 起不来整进程起不来。注意这条红线的另一半今天已经免费到手——客户数据链路只剩一处硬违反（`POST /delegated-tasks/draft` 的 `attestLiveBinding`，`client-auth-server.ts:432/1766`），且它带明确注释说明是被评估过的例外；其余路由已被历次 change 去边缘化。

3. **§14.2（内容负载不影响 WS 心跳）以远低于原方案的成本拿到**：resvg 进 worker_threads，一个文件 vs 一条服务边界。

4. **§14.3 的实际缺口被真正堵上**。一张 outbox 表精确对准唯一确证的丢账点，而不是把整个浏览闭环搬进持久队列。

**3. 新增一条机制：配置镜像失效通道。** 这是全案唯一的新造物，也是唯一必须补测试的地方。做不好的后果很具体：客户在 App 里改了人设、点了暂停，自动化侧要等到下次重启才看见——这类「改了没生效」的故障排查成本很高。

**4. 双写与共享 DB 的耦合一条不减。** `interaction_*` 四张表仍被两个进程的两个独立 Pool 写、`first_post_onboarding` 仍双写、面板保留清理器仍跨域删 `risk_counters`/`interaction_feed`/`llm_token_usage`。也就是说方案 §14.6「不存在跨服务业务表写入」这条红线，这一刀**明确不兑现**，而且是有意不兑现（见下）。同理必须写死一条约束：**两个进程永远指向同一个 PG 实例**，否则 `interaction-env:<envKey>` advisory lock 静默失效。

**5. 不兑现的红线要说清楚，别自欺。** §14.2（媒体/内容高负载不影响 Edge WS 心跳）这一刀**不买**——`resvg` 的同步栅格化、面板 WS 扇出、浏览编排仍在同一条事件循环上，只是客户 HTTP 离开了。§14.5（三仓独立构建部署回滚）不买。§14.6 不买。真正买到的是 1、17、18 三条。

**6. 排查跨进程问题会稍微变难。** 一个客户动作可能横跨两份日志，而全仓没有 correlationId 传播。因为客户面不调用老进程，实际影响有限，但「客户改了配置→自动化行为变化」这类链路的时间线要靠两边日志对齐。
- **何时该选它**：**在下列条件成立时选本案（今天全部成立）**：开发是单人、无 CI、无数据库迁移执行器、两台 2 vCPU 的 ECS（ol 仅 3.5 GB 内存、与 dev 共库）、迭代节奏是每天多次 dev 部署、且唯一有外部用户可感知 SLA 的面是客户 App 的数据面。此时把「可用性隔离」和「代码/数据所有权隔离」解耦、只买前者，收益/代价比最好。

**什么时候该转向原方案（触发条件，任一成立就重估）**：
1. 出现第二个长期开发者或两条独立发布节奏——这正是方案 §15 自己写的门槛；
2. 迁移器 + 迁移账本 + 每仓 CI（至少 typecheck/test/合同测试）已经建成——在此之前谈独立 Schema、独立数据库账号、跨仓合同版本都是空转；
3. 内容侧真的引入 ffmpeg / ASR / GPU 依赖（TikTok、抖音扩展）。注意即便到那一天，**第一步也应是在 `aidcp-cloud` 仓内拆一个独立 worker 进程，而不是拆仓**——原方案 §15 末句自己也是这个立场；
4. 出现实测的资源互挤证据（客户面 QPS 或内容负载把边-云心跳打断、把事件循环压垮）。今天没有：RSS 250 MB 上下，resvg 是 lazy import 且只用于封面文字卡，面板 WS 的 OOM 风险已由跳帧/断连背压兜住。

**为什么不是「在线交互面 vs 离线创作面」那条缝**：它其实有**最干净的现成接缝**——change `decouple-publish-generation-from-dispatch` 已把「生成候审段（不碰边缘、不让位浏览）」与「下发段（唯一碰边缘）」切开，`delegated_tasks` 已提供完整的 claim / lease / version / dedupe + `execution_target` 隔离，照抄即可，几乎不用造 Outbox。所以如果目标是保护事件循环与 WS 心跳（§14.2），**这一刀比切客户面更该做**。本案不选它，只因为一件事：**这个问题今天没有证据发生过**，而客户面被自动化重启连累是每天都在发生的既成事实。YAGNI 的判据是「已发生 vs 可能发生」，不是「缝干净不干净」。一旦第 4 条触发条件出现（真的观测到心跳被内容负载打断），就应该切这一刀，且同样按「同仓多进程、不拆仓」的方式做。

**什么时候本案会失效/不该做**：如果客户面与自动化最终被判定必须写不同数据库实例（例如合规或多租户隔离要求），那 `interaction-env:<envKey>` 这类库级 advisory lock 会静默失效，本案「同实例同 schema」的前提破裂，届时必须先补真正的单写者改造——那已经是原方案的路线，本案就该退场。

### 三平面单仓拆分（Request / Job / Runtime）——按重启语义切，不按业务领域切

- **一句话**：不新增任何 Git 仓库，在 aidcp-cloud 内按「这段代码干活时需不需要碰只存在于本进程内存里的活对象」这条机械可判定的判据，切成请求面 / 作业面 / 在线运行面三个部署单元（三入口、三 systemd、同库同 schema），把浏览闭环 37 角色整体留在运行面不做任何角色手术。
- **边界**：## 判据（唯一一条，机械可判定）

**这段代码服务一个请求 / 一个作业时，是否必须访问「只存在于当前进程内存里的活对象」？**
活对象只有五类，全部可枚举：边缘 WS 连接注册表（`src/comm/ws-server.ts:324`）、进程内事件总线（`src/event-bus/index.ts:17-19`，每连接一份）、会话上下文（`src/agents/session-context.ts:17-69`，全部 `private _` 内存字段）、风控控制器实例与其按账号串行链（`src/risk/risk-controller.ts:225-289`）、在途租约/在途审批等内存 Map（`src/comm/captcha-assist.ts:152-161`）。

- **不需要**（只碰 PG / OSS / 外部供应商 HTTP）→ 归 **请求面** 或 **作业面**；
- **需要** → 归 **在线运行面**。

请求面 vs 作业面再切一刀：**能否在一次 HTTP 请求的时限内做完**。做不完（模型链、栅格化、未来 ffmpeg/ASR）→ 作业面，且必须由 PG 队列 claim/lease 驱动。

这条判据可以直接落成 import lint：请求面模块**禁止** import `comm/`、`orchestrator/`、`event-bus/`、`risk/risk-controller`；作业面模块同样禁止。违规即 CI 红。对照之下，原方案的判据（这段代码属于「内容」还是「自动化」）在实测中判不出来——9/14 个 LLM 角色的构造参数里同时要预算、当日配额、冷却、风控解释（`src/agents/comment-appraiser.ts` / `interaction-appraiser-role.ts` / `comment-like-appraiser.ts` / `follow-agent.ts` 的 Options）；`publish-agent/` 15093 行横跨三仓；`interactions/` 横跨三仓（`src/server.ts:4568` 挂客户 HTTP、`:4117` 挂面板、`reply-ai.ts:1` 调 LLM、`send-orchestrator.ts` 碰边缘）；还有 63 个文件 18630 行三条边界一个都不认领。

## 数据层：不拆 schema，改拆「写入者收口」

原方案要求每服务独立 Schema + 独立账号 + 独立迁移目录。实测这一步会同时打断：`interaction-env:<envKey>` advisory lock 的跨模块互斥（`interactions/interaction-store.ts:337-339` 注释明写与 `ClientUserStore.beginEnvironmentOffboard` 同锁）、跨 12 张表的单事务离场清理（`interaction-store.ts:1640-1678`）、24 条指向 `accounts` 的外键、以及 `curated_content.listForClient` 打 `delegated_tasks` 的 EXISTS 子查询（`cache/curated-content-store.ts:1343-1361`）。而且「3 条独立迁移线 × 2 target」在 DEV/OL 共库且破坏性 DDL 已被冻结的前提下（`docs/deployment-environments.md:64-70`）是纯增负债。

本方案改为：**同库、同 schema、同角色不动**；把「单一写入者」的粒度从「服务」降到「Store 类」——一张表的所有写路径必须收口到唯一一个 store 类，用一个枚举 `表 → 属主 store` 的机械测试守住。今天已基本成立（`publish_log` 的全部写方法都在 `publish-log-store.ts`）；已知需要先修的是 `interaction_runtime_controls` / `interaction_auth_state` / `interaction_offboards` / `interaction_offboard_audit` 四张表的双写（`client-user-store.ts:453,470,528,572,687,763` vs `interaction-store.ts:378,1253,1358,1388,1394,1663）和 `first_post_onboarding`（`config/persona-store.ts:196-215` vs `onboarding/first-post-onboarding-store.ts:26`）。

允许一张表被多个平面写（`publish_log` 会被三个平面写），但要求每条跨平面写路径有 CAS 或天然列不相交。`publish_log` 的编辑路径已有真列版本闸（`publish-log-store.ts:73-78`、`publish-dispatcher.ts:461-471`）；`accounts` 是列不相交（面板写 group_label/contact_info、握手写 nickname、暂停写 status）。其余状态迁移路径的幂等性**未逐条核实**，是准入清单里必须补的一项。

## 三件必须先做的前置（与要不要拆无关，但拆之前必须做）

1. **建迁移执行器 + 账本**。现在没有账本表，唯一工具是接单文件路径的一次性 Client（`scripts/run-migration.ts:20-47`），编号已四组碰撞（0002/0030/0037/0038 各两份）、缺 0012，真实 schema 由 32 个 store 的 `CREATE TABLE IF NOT EXISTS` 自建（`src/server.ts` 37 处 `.init()`）。三进程各自自建表 = 启动竞态，必须先收口。
2. **审批信号从本机文件迁 PG**。今天写方是飞书回调（`feishu/ws-receiver.ts:123-124,158`）与面板（`panel/panel-server.ts:1179`），读方在 `server.ts:1980,1995` 与评论闸角色。拆完后写方分裂在两个进程，本机文件直接断。原方案对此完全未提。
3. **配置内存镜像加跨进程失效通道**（LISTEN/NOTIFY 或轮询）。13 个 store 的镜像只在启动和本进程写入时刷新，全仓无 watch/无 setInterval（`src/server.ts:1361` 注释自己写死了这条）。人设闸、慢启动起点、暂停态的写方在请求面、读方在运行面（`risk/risk-controller.ts:328` ← `client-auth-server.ts:1098`）。**这一条两个方案都要付，不是本方案独有。**
- **买到什么**：**1. 热路径上新增 0 次跨进程往返。** 浏览闭环整条留在运行面。原方案把内容评估切到跨进程 HTTP，实测一次完整互动要走 13–16 次角色接力、9 次串行模型判定，切完每篇帖新增约 9–11 次内部往返；延迟不是问题（模型天花板 180s），但每个评估点的失败模式从 1 个变 2 个，而其 §11 规定评估失败即跳过本次互动——等于用 9–11 个新增故障点去买「内容能力可独立扩容」，而今天 47/50 个角色的产物根本不落库、会话结束即丢。

**2. 零角色手术。** 43 个角色（`event-bus/types.ts:535-582`）一个不拆。原方案要在 9/14 个 LLM 角色中间切一刀，还要把 `content_evaluator` 从「打分」和「选中并下发 open_note」焊死的一个对象里劈开（`orchestrator/role-dispatcher.ts:1285-1287,2748`）。

**3. 真正买到 §14.1 和 §14.2 两条红线。** 客户 HTTP 与在线闭环进不同进程 → 运行面崩溃/重启不影响客户数据面；文字卡同步栅格化（`render/text-card.ts:639-652`）与面板 WS 的无界发送缓冲（`panel/panel-ws.ts:37-40` 注释自陈「会 OOM 连累整个云端」）离开边-云心跳所在的事件循环（`comm/ws-server.ts:177-178`，30s ping / 75s 判 stale）。这两条是今天唯一有真实物证的故障耦合，本方案和原方案买到的是同一份。

**4. 顺手修掉 §11 首行的既存违例。** 把创作触发改成 PG 队列后，`ContentScheduler` 就不再只遍历在线账号（`src/server.ts:3578` 的 `onlineAccounts: () => runtimes?.onlineAccountIdentities() ?? []`）。今天 automation 停 ⇒ 在线账号为空 ⇒ 零创作被触发，直接违反原方案自己写的「automation 停止时创作应保持可用」。原方案要靠拆仓 + 持久消息才顺带解决，本方案在阶段一就解决。

**5. 保住今天唯一有效的防漂移机械手段。** 同仓 typecheck 穷举（两份 protocol.ts 的 `Record<MessageType,true>`）继续有效。CLAUDE.md 已记录两处 typecheck 抓不到的漂移代价：命令被静默丢弃、角色永远等不到回执。拆仓会把这层保护整体换成「版本化合同包 + CI 合同测试」，而三个代码仓今天连 `.github` 目录都没有（只有 edge 一个手动触发的 Electron 打包 workflow）。

**6. 保住同库的三样东西**：advisory lock 跨模块互斥、跨 12 表单事务清理、跨 owner 的 EXISTS 子查询与 24 条外键。

**7. 留了干净的扩展缝，而且是对的那条缝。** 作业面是三者中唯一天然可远程化的（无长连接、无低延迟同步依赖，合同就是 PG 队列 + OSS）。真出现 GPU / Python 运行时 / 非 Node 依赖时，**先拆作业面**成独立部署甚至独立仓，代价局部可控。内容资产的真身也只有 4 处（`curated_note_evaluator` / `curated_comment_evaluator` / `concept_extractor` 三个落库角色 + 已有 schemaVersion+sha256 内容哈希模板的视觉分析 `publish-agent/visual-reference-types.ts:150-163`），可以一次搬一个到作业面，每次独立验收——不需要先建一个 `aidcp-content` 仓再往里填。
- **代价**：**1. 不解决「代码耦合」这一类。** 三个平面同仓、物理上仍可互相 import，只有 import lint 拦，靠纪律和 CI。原方案用 Git 边界物理隔离，这一点它确实更硬——但前提是有 CI，而现在 CI 为 0，跨仓漂移反而没有任何机械手段（同仓 typecheck 会失效）。这是我的方案接受的最大取舍：**用「弱但今天就能跑的 lint」换「强但今天不存在的合同 CI」。**

**2. 运行面仍然是个约 25k 行的大块**（agents 7143 + comm 5958 + orchestrator 3944 + risk + interactions 下发 + publish 下发 2680）。本方案不假装解决了它，只承诺它不再和客户数据面共命运。`role-dispatcher` 的 53 个构造注入点（`orchestrator/role-dispatcher.ts` 的 RoleDispatcherOptions）原样保留。

**3. 面板实时看板要退化或加一条中继。** 今天面板 WS 直接 `onAny` 订阅进程内总线扇出（`panel/panel-ws.ts:135`、`orchestrator/connection-runtime.ts:171` 的 tee）。拆开后只有两条路：降级为「失效通知 + HTTP 重拉」（与 §2.2 对客户端的口径一致），或者运行面暴露一条只读 SSE、请求面订阅后再扇出给浏览器。后者是本方案唯一新增的跨进程长连接，是最脏的一处。

**4. 约 10 个注入点要改成 loopback 内部 HTTP。** 面板侧 7 处：连接在线数（`panel/panel-server.ts:734`）、风控控制器三处（`:712,1505,1532`）、启停全部会话（`src/server.ts:4167-4180` 的 `runtimes.startAll()/endAll()`）、发布下发器与验证码协助、以及最极端的角色 prompt 只读预览——它今天靠启动时再造一整套编排图实现（`src/server.ts:3098-3111` 新建私有总线 + `accountId='__preview__'` 的风控器 + 完整 dispatcher，只为渲染 prompt 文本）。客户侧 3 处：`resolveEdgeIdForAccount`（`src/server.ts:4567`）、慢启动视图里的风控器（`:4452`）、环境风控真态（`:4583,4591`）。而这套内部 HTTP 要从零建——今天云端内部服务间 HTTP 调用是 0 次，7 个 outbound 全是供应商方向，其中 3 个连超时都没有（`feishu/token.ts:57`、`wanxiang-client.ts:94-96`、`billing-price-refresh.ts:78`），全仓无传输层熔断、无调用预算、无 deadline/correlationId 传播。

**5. 创作触发要从进程内调度改成 PG 队列 claim/lease + execution_target。** 这是本方案第二大工作量块。范式现成（`delegated-task/store.ts:29,87-94,480-522` + `worker.ts:69,81-93` 的僵尸 claim 回收），但要新写一条。

**6. 内存预算要显式核算，ol 是硬约束。** ol 只有 2 vCPU / 3560 MB / 无 swap；今天单进程实测 node RSS 267 MB + tsx 包装 95 MB + esbuild 25 MB。拆三进程后 tsx 包装 ×3 是纯浪费，必须先改成先 build 再 `node dist`（现在 ExecStart 是 `npx tsx src/server.ts`）。作业面在 2 vCPU 上跑同步栅格化必须设并发上限 1–2。**三进程在 ol 上的实际内存未实测。**

**7. 不给「客户面 / 运营面」分家。** 面板与客户 HTTP 共进程。它们读同一批投影表和同一批配置 store，分家会立刻制造两份投影和两套 store 复制，而重启语义完全相同（都是无状态 HTTP）——分家买不到任何故障隔离。这是我明确放弃的一条缝。

**8. 三份部署工件。** `scripts/deploy-target` 现在把目标建模成「单目录 + 单服务」（`scripts/deploy-target:41-44,73-76,86-89`），要改成三服务模型（目录/服务/端口/healthcheck 各三份）。这一项原方案同样要付，且它还要再加 Git 远端与 CI。
- **何时该选它**：## 什么条件下应该选本方案（今天全部成立）

1. **只有一个人在写代码。** 四仓提交邮箱只有两个、且是同一人；仓龄 7 周；近 30 天 2847 次提交。原方案 §15 自设的门槛是「只有出现独立团队、独立发布节奏、明确扩容瓶颈或隔离要求时才继续拆分」——按它自己的标准，今天一条都不成立。
2. **CI 为 0。** 只有 edge 有一个手动触发的 Electron 打包 workflow，cloud/console/控制仓连 `.github` 都没有。跨仓合同的唯一执行机制是 CI；没有 CI 的多仓 = 只有边界的形式、没有边界的执行力，同时还丢掉了今天唯一有效的同仓 typecheck 穷举。
3. **领域边界本身还没稳定。** 同一份方案文档一天之内（b9f31cc → 879206f）从「明确不建议拆多仓」翻成「拆三仓」，两版之间无新增实测证据；`publish-agent` / `interactions` / 63 个无归属文件说明领域切分现在还是一道待解的题，不是一个已知答案。沿未稳定的领域边界建 Git 仓，等于把一次误判固化成六仓运维成本。
4. **ol 是 2 vCPU / 3.5G / 无 swap 的单机。** 六个进程 + 六份 node_modules + 六条部署流水，在这个规格上是纯负担。

## 什么条件下应该改选原方案（触发器，逐条可判定）

1. **出现第二个稳定投入的开发者**，且两人的改动集中在不同平面（比如一人只做客户面与后台、一人只做浏览闭环）——此时 Git 边界开始买到真东西（独立发布节奏、独立回滚）。
2. **作业面需要非 Node 运行时或 GPU**（真的接了 ffmpeg / ASR / Python 模型）——此时**先只拆作业面**为独立部署单元甚至独立仓，因为它的合同是 PG 队列 + OSS，没有长连接、没有低延迟同步依赖，是三者中唯一能干净远程化的。不要因此顺带拆另外两个。
3. **内容评估出现第二个消费者**（另一条产品线、外部调用方）——此时「可复用、可版本化的内容能力」才第一次有真实需求，`ContentFacts` / `AccountFitAssessment` / `AuthorAssessment` 那三个对象才值得建。今天这三个对象在代码里一个都不存在，最接近的两个角色产的是一次性事件载荷、不落库，置信度还有默认填 0.7 和 prompt 要了却被丢弃两处伪精度（`agents/content-evaluator.ts:261`、`agents/author-evaluator.ts:185 vs 206-212`）。
4. **单仓 CI 时长或 typecheck 时长成为交付瓶颈**——这要求 CI 先存在。
5. **出现强合规隔离要求**（客户数据必须与自动化执行物理隔离、不同数据库账号可审计）。

## 无论选哪个方案，都应该先做的（不构成拆分依据，但拆分前必须完成）

建迁移执行器与账本（编号已四组碰撞、无账本表、schema 靠 32 个 store 自建）；审批信号从本机文件迁 PG；配置内存镜像加跨进程失效通道；补上 `interaction.occurred → 风控记账` 那条跨重启洞。这四件事在两个方案下的工作量相同，且都是今天就该修的——建议先把它们做完，再回头判断到底需不需要 Git 边界。

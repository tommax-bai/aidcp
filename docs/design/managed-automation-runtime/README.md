## 撤出时同步撤掉的授权（**这条最重要**）

原 change 带着一条 2026-07-25 的用户裁定「**重叠处以本方案为准**」，并且写进了控制仓 `CLAUDE.md` §3，
要求任何人动 publish / comment / browse / 排期 / 风控配额 / 仲裁 / 客户投影 类规格**之前先来查它的 §24 映射表**。

**该授权随本次撤出一并失效**，`CLAUDE.md` 的对应段落已改写。含义是：

- **已上线规格重新成为唯一权威**，不再有「以本方案为准」的上位声明。
- 动上述几类规格**不再需要**先来查本目录，也不必担心与它冲突或重复劳动。
- 本目录里所有「取代」「收编」的表述，**现在都只是设计意图，对生产与验收零约束力**。

原 change 自己的规则本来就写了「取代不得先于对应 delta 生效，delta 未落地前旧 spec 仍是权威」——
而它零开工、一条 delta 都没落，所以**撤出不改变任何生产行为，也不丢任何已上线保证**。

## 重新立项时值得直接复用的

1. **§24 的处置映射表**：那约 60 份能力的逐条对照是实读规格得出的，重做一遍成本很高。
   注意其中早先提的 72 条「取代」主张，评审后有 63 条被推翻、改判为「收编若干条、其余保留」——
   **表里已是修正后的口径，不要照最初那版重做**。
2. **§24.2 的四条待裁决冲突**（一条「已提交、结果未知」可否长期占住账号 lane 及其上限；
   协议字段滚动兼容 vs 能力版本锁步的分面边界；运营手动指令是否算「全托管」从而适用两段占用；
   确定性命中可否跳过会话软预算与冷却）。这四条是判断题不是工程量，重新立项前先裁掉能省很多返工。
3. **§24.4 记着两条已具名放弃的已上线保证**（取消能力级审批下限、取消操作员越权档）。
   那是用户的决定、不是遗漏 —— 重新立项时若要恢复，需要显式重新决定。
4. **边缘侧的分工口径**：设计里把「跨步骤编排放在边缘」显式列为**被否决的备选**
   （理由：策略与长期状态随客户端离线消失，且扩大本地权限）。整条运行模型分层全在云端，
   边缘只增加**版本化能力声明**与**原子命令适配**两类东西。这条口径与仓内既有铁律一致，可直接沿用。

## 与边缘侧诚实性工作的关系（**不随本次撤出而取消**）

设计里给边缘定的职责是：本机生命周期、平台原子能力、**页面身份复核、动作后验证、诚实回执**。
后三项正是 Native 迁移修复那批工作在补的东西，**用户已裁定继续做**，与本方案是否立项无关 ——
它们本身就是边缘侧该有的行为，不是为这套运行模型服务的前置件。

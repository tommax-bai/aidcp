# aidcp-cloud 退役：实测出来的障碍与结论（2026-08-05）

> **一句话**：代码和迁移已经零遗留，但**测试搬不走**——实测下来 134 个只活在 cloud 的用例里，
> 真正搬得动的只有 7 个。所以正确的终局不是「退役 cloud」，而是**把它降级成不可部署的整图验证仓**。

---

「OL 也切过去了，aidcp-cloud 可以退役了么？」当时我给的答复是「差 128 个孤儿测试要分家，
估 3-5 个 session」。**那个估计是错的**，本文件是实测之后的更正。

## 2. 真正的障碍：测试的 90% 离不开整张图

134 个只活在 cloud 的用例，先按 import 图分类，**再逐个真跑**验证：

| 桶 | 分类阶段 | 真跑之后 |
| --- | --- | --- |
| 单一属主、可搬 | 18 | **7** |
| 跨 2+ 业务属主 | 97 | 97 |
| 整图扫描 / 迁移 | 14 | 14 + 10（分类看错的） |
| 只测单体组装 | 5 | 5 |

**分类阶段看错的那 10 个，错法值得记**：它们的 **import 只碰一个属主**，
但正文**把别的属主的源文件当数据读**（`readFile(join(ROOT,'src/config',name))` 这类），
基于 import 的分类器天生看不见。搬过去当场 `ENOENT`。

失败的另一类是 schema 用例：迁移编号 / 顺序 / DDL 对齐这些，需要**全部 108 条迁移**在一处，
而单仓只有自己那一份（api 69 / automation 57 / content 20）。

**所以「跨属主」不是分类偏差，是这套测试的本质属性。**
它们测的是「多个域摆在一起时成不成立」——那正是拆仓要拆开的东西。

---

## 3. 结论：cloud 不该退役，该**降级**

**终局形态**：`aidcp-cloud` 不再是可部署单体，而是

- **事实源**：派生仓的 `src/` 与 `migrations/` 仍从它重放（现状不变）
- **整图验证仓**：那 ~120 个跨属主 / 整图用例留在这里跑，它是唯一跑得动的地方
- **永不部署**：三个 systemd unit 已在两个环境 disabled；这一条要写死成规则，不是习惯

这不是妥协。**「拆进程」与「拆代码仓」是两件事**，前者已经做完并在生产上生效；
后者对这套测试来说没有收益——把 120 个跨属主用例硬拆到三个仓，
只会得到三份各自看不全的检查，外加一堆重复的 fixture。

---

## 4. 若仍要走到「删掉 cloud 仓」，还差什么

按代价排（这才是真实清单，不是「3-5 个 session」）：

1. **那 ~120 个用例要有新家。** 唯一现实的落点是一个能同时 checkout 多仓的地方
   ——控制仓已经在做这件事（`sync-split-repos` / `boundary-census`），但它**没有构建链**
   （CLAUDE §0），跑 TypeScript 用例要先解决这个。
2. **共享包的测试归位**：kernel 13 / transport 8 已各有自己的用例，但 cloud 里还有
   kernel 10 / transport 10 的份额没归位（本批未动）。
3. **两份边界扫描器要合并**：cloud 与 automation 那两份 1000 行的 `boundary-scan.ts`
   **2026-08-05 实测已经漂开**。
4. **事实源要改指**：控制仓 9 个脚本引用 aidcp-cloud，`CLAUDE.md` 里 15 处。
5. **OL 的回滚路要先不需要它**（今天它是唯一回滚路）。

**第 1 条是承重的，其余都是收尾。** 在第 1 条有答案之前，别把「退役」排进计划。

## 5. 本批实际落地的

- `scripts/boundary-census`：跨仓边界普查，补上两处结构性盲区
  （cloud 看不见派生仓私有件；单仓看不见跨仓边）。四轮变异测试，含两轮**抓出闸自身恒真**。
- 顺手修掉三件它报出来的真问题：api 的边界规则比事实源少 1 条目录规则 + 77 条裁定；
  一个私有组装根两处名单都没登记（`--prune` 会删掉它，而删掉的现形方式是慢启动 clamp 静默失效）；
  普查自己最初 11 条「悬空引用」全是没剥注释造成的假阳性。
- 7 个单属主用例搬回属主仓（api 3 / automation 4），并从 cloud 移除。

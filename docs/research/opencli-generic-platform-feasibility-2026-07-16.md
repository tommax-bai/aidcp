# OpenCLI 做「通用平台」能力 — 可行性结论

**面向 aidcp（云端 LLM 决策 + edge 真机 / AdsPower 指纹执行 · 跨平台拟人养号）工程负责人**

---

## 结论（一眼看完）

| 用途 | 用 OpenCLI？ | 一句话原因 |
|---|---|---|
| **养号级新平台**（写：发帖 / 评论 / 关注 / 浏览） | ❌ 不用 | 零反检测 + 无操作后校验 + 绕过统一闸，撞三条铁律 |
| **轻量情报级（Tier B）** | 🟡 窄象限可试 | 只读、不登录业务号、封了不心疼的场景；它有 100+ 现成站、跑起来不烧 token |

Tier B 里 OpenCLI 也**不是默认赢**——真正的对手是「自己写几个匿名抓取脚本」（拿 80%、零依赖）。OpenCLI 要赢，必须赢在它独有的地方（第三节）。

---

## 一、OpenCLI 是两套东西（先分清）

- **A 确定性 adapter 层**（`opencli <站点>`）：一次性逆向后确定性重放，**运行时零 token**，100+ 现成站（含小红书、B 站、知乎）。
- **B 通用浏览器原语层**（`opencli browser`）：看一眼页面再动，**运行时 LLM 在环、非零 token**。

**一条实测修正（推翻了直觉）**：对**请求签名硬化的站（小红书）**，连 A 层都退化成**人工维护的 DOM 自动化**——它的签名头「无法从外部可靠重放」，连读带写都只能驱动页面。所以「零 token 确定性」这个招牌，**恰恰在你最在意的站上打折、且靠人工修**。真·零 token 只在签名可重放的站（B 站那类）成立。

底座、许可等事实：Chrome 扩展 + 本地守护进程，也支持接外部 CDP 端口；多 profile；Apache-2.0；**全链零反检测 / 零拟人 / 零限频**；adapter 破裂靠**手动** autofix。

---

## 二、为什么养号级不能用（对着三条铁律逐条看）

**① 隐蔽（反检测）— 命门，结构性冲突。** 不管走哪条路都零指纹隔离、零拟人、零限频。无浏览器直发 = 完全不过指纹环境、机械时序；浏览器内合成事件 = 一步到位的合成点击（正是 Facebook 上「被当悬停、不提交」那种点法），且无鼠标轨迹 / 停顿 / 时序抖动。等于把「我是机器」写在每个动作上。

**② 诚实回执 — 只做了一半。** 它证明「元素找对了」，但**不证明「业务结果真发生」**（点赞真加了没）。你们的定位引擎有三道闸（操作后校验 / 连续失败停手升级 / 坏锚点隔离回滚），OpenCLI 只有操作前的「先看清楚」。原样接 = 静默假成功。

**③ 状态单写 / 统一闸 — 它是一条旁路。** 它作为外部命令行子进程执行动作，你们的风控 / 配额 / 软暂停统一出口**管不到它**，风控对它做的动作失明。（纠正一个常见误判：它不是「第二个写风控状态的人」，而是「绕过统一闸、风控看不见的执行面」——性质是可观测性 / 闸控缺口。）

架构上：底座能接（它支持外部 CDP 端口），但只是「多挂一个客户端」，不是替代；编排层硬冲突（它假设「一个人一个浏览器、每步现场找元素」，你们是「云端选完元素、边缘哑执行、多环境并行」），塞进来要么让边缘长出第二个决策脑、要么阉成更弱的执行器，没有中间态。

---

## 三、Tier B：赢面 / 陷阱 / 焊死规则

**赢面（三条同时成立才用它）**
1. **广度**：对一个**没覆盖过的新平台**临时做抽取，当天能起，不用自己逆向。
2. **签名可重放的站** = 真·零 token 确定性重放（B 站那类）。
3. 配套逆向流水线成熟，是有价值的离线工程脚手架。

**陷阱**
- **签名硬化的站退化成人工维护**：小红书就是——你们本来就能读，OpenCLI 反而更差（双输）。→ **它只在「你们不养号、也还没覆盖」的平台上有价值**（把知乎 / B 站等热点当喂给小红书内容的**上位选题信号**）。
- **「复用你已登录真 Chrome」是默认行为、是 foot-gun**：一步就可能把业务号暴露进抓取，必须工程上焊死。

**焊死规则（Tier B 落地前提，不可协商）**
1. 只读、不写。
2. 身份物理隔离：只用匿名 / 一次性可弃 cookie，绝不指向登录业务号的浏览器。
3. 旁路：独立进程 / 独立机器，不进 edge / 协议 / 风控；产物只作内容决策的上游数据。
4. 平台限定：只对「不养号 + 未覆盖 + 合作 / 签名可重放」的站用；小红书这类不用它。

---

## 四、成本账：它省的不是你缺的那块

加平台真正贵的地方，是对付**主动反自动化的平台**（Facebook 的执行器约 8000+ 行手写坐标级代码，因为通用选择器路线在其敌意页面上成功率塌了）。OpenCLI 的通用原语建立在「页面配合」前提上、且零反检测，会**因为和当年一模一样的原因**在这种平台上碎掉。它补的是「又一套通用点击 / 输入原语」——这层你们本来就不缺（自家定位引擎 + deepdive 已推荐的 Stagehand 都是）。所以对养号级新平台，ROI ≈ 0，甚至为负（多养一套栈）。

---

## 五、两个更上游、必须先验的假设（评审揪出的盲点）

1. **「扩自家引擎加新平台很便宜」未被证实。** 小红书 driver 只有 25 行，是因为背后 7000+ 行的浏览流程本来就照小红书形状建的。你们只有两个数据点：小红书（为它而建）、Facebook（通用路碎、手写 8000+ 行）。**「用现成通用路廉价加一个真·新平台」一次都没验过**——它比「OpenCLI 值不值」更上游。
2. **敌意平台的第三条路被四个视角集体漏掉。** 对 Facebook 这种 DOM 混淆的敌意平台，手写坐标和 Stagehand 都脆；deepdive 自己的答案是**视觉像素级定位**（看截图点坐标、不依赖 DOM，如 UI-TARS-1.5 / Qwen3-VL），应正式进候选。

---

## 六、下一步（不急着开 change，YAGNI）

openspec 里零个 generic-platform change、无第 4/5 平台实需，只有「未来可能要」——**此刻不开 change**，先用 PoC 拿数据：

- **PoC-2（验 Tier B 价值）**：选 1 个签名可重放的合作站（B 站）+ 1 个你实际想要选题信号但不养号的站，用 OpenCLI 现成 adapter **纯匿名只读**抽取，子进程旁路，不接任何养号资产。**必须有对照基线**（同任务用几十行 fetch+解析脚本实现一遍）。验收两问：① 相对基线净省多少（起步 + 运行 token）；② 触发一次站点改版 breakage，量手动修复人力。
- **决策门**：净省显著 + 维护可接受 → `openspec explore` 落成**限定只读的情报采集旁路能力**；基线脚本就够 80% / 维护跑步机太重 → 弃。

---

## 说人话总结

OpenCLI 看着能「让新平台不用手写」，但它省的是你们本来就不缺的那层（通用点击 / 输入）；加平台真正贵的是「对付像 Facebook 那种主动反自动化的平台」，这块它一样搞不定，还完全没有反封号能力——拿它养号等于自己把账号送去被识别。它唯一真香的角落，是「只读地扒公开数据做选题 / 竞品调研」这种不登录业务号、不怕封的场景。建议：养号别碰它；只读调研可以拿它做个可弃的小试点；真要加养号平台，还是走你们自己那套已经付过成本的通用定位引擎（必要时叠 Stagehand，敌意平台再考虑视觉定位）。

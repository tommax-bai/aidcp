## 贯穿全程的判断准则（共库期 dev 改动三层）

dev 与 ol 长期共用同一个 PostgreSQL 库、跑不同版本代码。据此，dev 上的改动分三层：

| 改动类型 | dev 能否大胆改 | 依据 |
| --- | --- | --- |
| 改代码逻辑、改不落库的行为、**加**新表/新列 | 能，ol 完全无感 | 只增不减，ol 旧代码读不到新东西也不依赖它 |
| **删共享数据的行** | 能，只要 ol 不再需要那些行 | 影响经"共享数据"而非"代码"传导；删前核对 ol 是否还读 |
| **删/改共享数据的结构**（删列、删表、拆表） | **必须押后到不共库** | ol 旧代码引用那个列/表，读不到直接崩 |

**唯一卡死、必须等到拆库才能做的，只有第三行。**

## 阶段 2 · 跑稳期（观察 + 决策，不写不可逆代码）

让新模式在 dev、随后在 ol 上都跑稳、验证过，再进下一阶段。

- [ ] **dev 观察**：风控单写、配置副本失效、发布授权持久化、迁移工具、归属跟随会话，跑稳
- [ ] **决定 ol 何时上新模式**（用户拍板；从发布分支走，走部署安全序列）
- [ ] **ol 观察**：同上，跑稳
- [ ] **契约门 warn → enforce**：落账之后，把 schema 契约门从"只告警"切成"库落后于代码即拒绝启动"（回滚保护真正生效）——等跑稳再切
- [ ] **风控 enforce 开关**：返工后"拒绝握手"已删，需确认这个开关返工后还剩什么语义（大概率只剩"条件写止血是抛错还是告警"），再决定要不要动

**「跑稳到什么程度才算可以进阶段 3」的判据**（待细化成清单）：观察期无异常告警、门禁豁免降到约定阈值、真机验收项通过。

## 2. 为什么 automation 不能跟单体并存（这条决定了切换只能是原子的）

自动化写者锁**按 target 单实例**，且在**构造期**就抢（远早于业务放行），抢不到就 fail-closed
退出。dev 那把锁在单体手里 ⇒ 派生 automation 起不来。这是设计，不是缺陷：两个实例同时持写权，
合计放行的真实平台动作会翻倍。

⇒ **不存在「先让 automation 陪跑一阵子」这个选项**。要么不动，要么切。

## 4. 几条会让人白花时间的（都实测过）

- **`npm install <包名>` 会把 pin 规格从 `git+ssh://` 重写成 `github:`**，对账脚本从此报「未 pin」；
  且本机实测跑了 **37 分钟**。要刷新装机用 `rm -rf node_modules/<包> && npm install`（17 秒）。
- **ECS 上没有 GitHub 私钥**，但 `ssh -A` 转发可用 ⇒ 服务器上不留钥匙也能装私有共享包。
  ECS 的 npm registry 是公网 npmjs，**没有本机那个 @types 劫持问题**。
- **systemd unit 用未加引号的 heredoc 写时，正文里不能出现反引号**——会被 shell 当命令替换执行，
  实测把 `systemctl status` 的输出写进了 unit 文件，systemd 报 `Missing '='`。
- **新加的派生仓私有文件要登记进 `scripts/sync-split-repos` 的私有清单**，否则对账报「多出」、
  `--prune` 会**删掉它们**。
- **门禁写完要变异测试**：本批那道 AC-OWN-07 第一版恒绿（把数组当对象读、表全集为空），
  注入违规仍然全绿，只有变异测试才发现。

### 16.4 第三批：今日进展 + 慢启动（17:00 部署 dev）—— **原定方案被实测推翻**

**先说被推翻的那部分**（这是本节最有价值的一条）：

原判是「`slowStart` 要把两个纯函数提进共享包」。**实测不成立** —— 其中的平台能力投影
传递依赖到整张平台能力注册表，而那张表在控制仓 §4.7 **已被终局裁定「不析出、整体维持
automation」**，并写进了 kernel 拒入名册，边界门禁会当场拦，**且无豁免通道**。

⇒ 沿着「把数据搬过来」这条路走到底是死的。**正解是反过来：让属主域算完了给。**

**而属主域早就有一份现成的装配器**（在给边缘陪伴界面供数）。于是原计划的
「4 条新路由 + 7 个纯函数提共享包」塌成 **1 条路由**，且 `slowStart` 与「今日进展」
**一并解掉**（那块载荷里本来就带着慢启动真态与已过平台投影的配额）。

| 落点 | 内容 |
| --- | --- |
| `aidcp-cloud@be0b24a` | 新增 `src/transport/client-usage-http.ts` + 刷新归属清单（目录 inherit 规则自动认领，无需改规则） |
| `aidcp-transport@47ede10` | 同步；三仓 pin 随之抬升 |
| `aidcp-automation@4f6a2fc` | 注册路由（**本进程零新增取数逻辑**）+ 进路由清单闸 |
| `aidcp-api@51f741d` | 接 `environmentOverview` 与 `slowStart`，**同一次取数** |

**这个设计里有三条刻意为之，别当成可以简化的地方**：

1. **传输层对载荷形状无知**（做成类型参数）。载荷类型被终局裁定不得进 kernel，
   传输层要拿到它只能再抄第三份，而定稿 §10.9 明写**同步点数量 MUST NOT 增加**。
   管子不需要知道里面流的是什么，两端各用自己已被管着的那份声明。
2. **粒度是「装配好的整块」，不是几项原料。** 递原料等于逼接口进程做最后那步平台投影，
   而它永远拿不到注册表；唯一能编译的写法是给投影传空值 —— **那不报错**，
   只会让 Facebook 账号重新看到「收藏 0/N」，即已被除掉的那个谎。
3. **两项从同一次取数拿。** 分两次会多出「真态取自刷新后、上限取自刷新前」这种错配，
   而两边都不报错。

**失败语义三段，一段没塌**：属主域内部对首帖段 / 配额段各自 catch 成**字段缺席**（诚实的「未知」）；
四项风控计数与会话快照**不 catch、直接抛**；接口侧只在最外层 catch 一次 → 503。
日志带跨进程错误码——「对面没这条路由」（跑的是旧版本）与「对面挂了」是两件事。

**验到哪一步**：属主域那条新路由在 dev 上**实测答出了真实装配数据**（各时间窗计数 + 配额 + 饱和集）；
三个服务重启后全 active、零错、端口齐。**客户端那条真实请求仍未走通**（没有可用的客户登录凭据），
需用户在客户端上确认。

**接线口 18/23**，剩 5 个（`draftRefinements` / `interactionApi` / `onOffboardCreated` /
`personaAutoFill` / `operatorAlias`）在闸的缺席表里具名。

**另需知道**：`aidcp-automation` 仓有 **5 条既有测试失败**（发布填充预算 / 命令序列器 / 边界记录），
在干净树上同样红、与本批无关，**未修、如实登记**。

#### ⚠ 本批最有价值的发现：互动能力自物理拆库起就整体关着

给离场那条路由写的**具名错误**当场把它喊了出来。顺下去查到根因：

- 自动化的互动能力探测里断言了 `interaction_reply_configs` 这张表；
- 但那张表按 §5.1 **归 api 属主**，物理拆库后住在 api 库里；
- 而探测跑在 automation 属主池上 ⇒ **拆库之后它永远为假** ⇒ 互动域整体不组装。
- 而本进程**从不读写那张表**（全仓引用只有这一处断言）。
- 与 §1 第 1 条修掉的那个坑**同型、方向相反**（那次是 api 池上的存储断言了 automation 的列）。

**第二层问题：错误名把排查方向带偏了。** 它报 `interaction_schema_missing_run_0042`，
而 0042 **早就应用了、列也在**；真正缺的是另一张表。基础形状是好几个对象的**与**，
只报其中一个迁移号，等于让查的人先去翻迁移账本、再去比对列，**全程走错方向**。
已改成逐项探测 + 缺什么报什么；采集不到时**说自己没采集到**，不装作「什么都不缺」。
两条用例守着（含「错误里不许再出现迁移号」）。

**修完实测**：互动能力已组装，离场路由从「能力不可用」变成 `{"ok":true,"result":0}`
（0 = 边缘不在线，一个事实）。三服务 active、零重启、六端口、就绪度 ready、isales 未碰。

**这条也是 §10 第 6 条那笔根债的又一次现形**：启动日志每次都明说「互动能力未接入」，
只是没有人在看。

**`interactionApi` 的前置因此变了**：原以为要新开 2 个端口 8 个方法，但在这条修掉之前
建多少通道都没用（能力整体不组装）。现在能力起来了，剩下的通道工作可以真正开工 ——
另有一条调查结论要一并处理：**互动域的错误类跨进程后 `instanceof` 恒 false**，
会把「已发出但核不到」（409 不可重试）退化成 500 + 可重试，
**那正是「重投一条可能已上墙的命令」**，必须先修错误保真再点亮写通道。

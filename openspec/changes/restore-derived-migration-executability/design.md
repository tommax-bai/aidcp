## Context

拆仓后每个属主库各持一份迁移账本，「一条迁移属于哪个属主」由 `aidcp-cloud/src/schema/migration-owners.ts` 单一判据给出：**看它文件头 `-- aidcp:objects=` 声明的对象落在谁的表上**。两类边角被显式处置：跨属主迁移在每个相关属主的账本里各记一条；**「残留迁移」（头里没有任何能定位到表的对象声明）计入全部属主**。

残留规则给自己写了理由：这类迁移「不持有任何存活对象，因此没有哪个属主库的 schema 正确性依赖它」，多记是安全方向。**2026-08-05 的空库实跑证明该前提为假。** 本仓 13 条残留迁移里 12 条仍在对真实的表执行 DDL/DML；实跑停在 `0030_panel_hardening_indexes`（`relation "risk_counters" does not exist`），进度 content 1/20、automation 13/57、api 20/70。

同一次实跑还先撞上一个独立缺陷：三个派生仓的 `scripts/migrate.ts` 相对引用 `../src/kernel/pg-owner-connection-resolver.js` 与 `../src/kernel/schema-name.js`，而派生仓**没有 `src/kernel/` 目录**（kernel 已是 npm 包）。三仓迁移 CLI 全断，今天唯一能跑迁移的是按 §8.0 永不部署的 `aidcp-cloud`。

**两个硬约束框住了全部解法空间：**

1. **已应用迁移的字节不可改。** 校验和是整文件 sha256，账本行与磁盘不一致时**整批拒绝**（`migration_checksum_mismatch`，且明写「绝不重跑、绝不覆盖账本校验和」）。13 条残留迁移全部 ≤ `0069`，**在 dev / ol 的账本里都已入账**。⇒ **往它们文件里加任何一行头声明，都会让 dev 与 ol 的迁移命令当场全停。**
2. **归属判据不得由 SQL 文本反推。** 现有判据明写「MUST NOT 由 SQL 文本反推表名 —— 那会造出第二套口径」。

## Goals / Non-Goals

**Goals:**

- 三个派生仓能真的执行迁移，且该文件不再靠手工维护。
- 每条迁移的属主归属**由显式声明给出**，缺声明即失败，不再有「推断为全属主」这条静默路径。
- 有一道**静态闸**能在空库实跑之前抓住同类缺陷 —— 没有它，这次修完下次照样漂。
- 全部动作对 dev / ol 是**零 DDL、零校验和变更**。

**Non-Goals:**

- 不解决「跨属主迁移会在每个属主库里建出外域的表」这个既有性质（`0000_baseline` 在三个库各建一套）。它今天可执行、不阻塞任何事，属独立议题。
- 不改账本行语义、不改复合序、不改乱序闸。
- 不做真库验收 —— 那是 `cloud-schema-migration-executor` 的 5.9 / backlog 簇 111.6，本 change 只负责让它**第一次具备执行条件**。

## Decisions

### D1：把「执行范围」与「账本范围」拆成两个概念

**今天它们是同一个东西**，这正是缺陷的根：一条迁移被计入属主 O，就意味着「在 O 的库里跑它」。

改为：

- **账本范围 = 全部属主**（不变）。两条既有理由仍然成立：否则拆库后执行器会把外域迁移当 pending 重放，且乱序闸会在每个库里把它判成失序整批拒绝。账本行的语义本来就是「**这个版本在这个库里已经处置过**」，从不声称某张表存在。
- **执行范围 = 显式声明给出**（新）。声明缺失即失败。

拆开之后，12 条单属主残留迁移**自动就对了**：在属主库里执行，在另两个库里只记账不执行。

**否决的替代**：让残留迁移在所有库里都执行、失败就跳过 —— 那是「静默假成功」，且会把真正的 schema 缺失一起吞掉。

### D2：归属声明分两条路径 —— 历史用封闭名册，新迁移用文件内头

约束 1 直接排除了「给 13 条已应用迁移加头」。故：

- **历史（本 change 落地前已存在的迁移）**：`migrations/legacy-owner-overrides.json`，逐条 `{ version, owners[], basis, supersededBy? }`。**封闭名册、只减不增** —— 范式与仓内既有的 `boundaries/adjudicated-files.json` 一致（人工判过的集合，生成物不得回喂顶替）。
- **新迁移**：文件内 `-- aidcp:owner=<owner>[,<owner>]` 头。新文件尚未入账本，加头无成本。

**归属解析顺序（唯一，MUST NOT 另立）**：① 文件内 `owner` 头 → ② 名册条目 → ③ `objects` 声明能定位到表 → ④ **失败**。第 ④ 步取代今天的残留分支，是本 change 的核心红线：**MUST NOT 静默计入全部属主**。

**否决的替代**：往 13 条的 `objects=` 里补声明。那会撞坏 `migrate verify` 赖以成立的对象→版本映射（同一对象被两个版本声明），且同样改字节、同样触发校验和拒绝 —— 两头都不通。

**为什么不统一成一种机制**：统一到文件内头需要改字节（约束 1 否决）；统一到名册则会让名册成为常规路径、逐年膨胀成第二事实源。用「封闭名册 + 机械断言它不增长」把历史与未来切开，是这里唯一诚实的形态。

### D3：`0030_panel_hardening_indexes` 用「记账不执行 + 两条新迁移接替」拆分

它在 `risk_counters` / `interaction_feed`（automation）与 `llm_token_usage`（content）上各建索引，**在任何单一属主库里都不可能跑通**；而按约束 1 又不能改它。

- 名册里给它 `owners: []` + `supersededBy: [<新 automation 迁移>, <新 content 迁移>]` —— 每个库都记账，**哪个库都不执行**。
- 追加两条新迁移（新版本 id、排在目录尾部），各自 `CREATE INDEX IF NOT EXISTS` 建本属主那部分。
- **dev / ol**：`0030` 已入账、文件未动 → 无校验和冲突；两条新迁移跑到时索引已存在 → 幂等空转。
- **全新空库**：`0030` 记账不执行；索引由两条新迁移在正确的库里建出。

**硬要求**：`owners: []` **MUST** 同时给出 `supersededBy`，且被点名的迁移合起来 MUST 覆盖它建过的全部对象。空 `owners` 不带接替声明 = 悄悄丢掉一批索引，这是本 change 最容易犯的错。

### D4：静态可执行性闸 —— 判据是「触及的每张表，都由同样在该库执行的迁移创建」

没有这道闸，这次修完只是把 13 条排好，下一条同形态的迁移照样漂进来，而且**照样要等到有人真的建一个新库才会发现**。

- 判据：对每个属主 O、每条执行范围含 O 的迁移 M，M 引用的每张表都必须由某条执行范围也含 O 的迁移创建。
- 表引用集合由 SQL 文本扫描得出。**这不违反约束 2，因为它 MUST NOT 参与归属判定 —— 它只有否决权，永远不能给任何迁移分配属主。** 这条限制要写进扫描器文件头，否则它迟早被当成第二套归属口径。
- 口径复用仓内既有扫描器（`src/schema/ddl-scan.ts` 与边界门禁那套 SQL 扫描），**不写第三份**；解析不了的语句 MUST 失败并指名，MUST NOT 静默跳过。
- 落成验收用例，进 `npm run test:acceptance`。

### D5：`scripts/` 纳入拆仓同步覆盖

`scripts/sync-split-repos` 覆盖 `src/` 与 `test/`、对 `migrations/` 只报不改，**完全不覆盖 `scripts/`**。`scripts/migrate.ts` 自拆仓当日手工搬过去后即无人管 —— 这是根因，不是表象。

能修它的说明符改写器 `rewrite_kernel_imports` **早就存在且对这条路径解析正确**（`scripts/migrate.ts` + `../src/kernel/x.js` → `aidcp-kernel/kernel/x.js`），只是从未作用到该目录。因此 D5 主要是**接线**，不是新造。

同步覆盖按**逐文件点名**（范式同 `aidcp-transport` 那份点名清单），不整目录搬 —— `scripts/` 下多数脚本是控制仓 / 单体自用的，整目录同步会把一堆无关脚本推进派生仓。

## Risks / Trade-offs

- **[名册变成新的事实源]** → 机械断言其条目数只减不增，且 version 必须属于「本 change 落地前已存在」的冻结集合；新迁移写进名册即失败。
- **[头声明生成器回头重写已应用迁移]** → `scripts/generate-migration-headers.ts` 按「每个对象归最后创建它的那个文件」重算头声明；D3 的两条新迁移会创建 `0030` 已声明的同名索引，若生成器重跑就会去改 `0030` 的头 → 校验和冲突。**MUST 给生成器加「已应用 / 冻结集合内的迁移不重写」的守卫**，并在实施时实测一次「重跑生成器后 `git status` 为空」。
- **[「记账不执行」被误用成万能豁免]** → 只允许出现在封闭名册里，且 `owners: []` 必须带 `supersededBy`；新迁移无此形态。
- **[SQL 扫描器漏判]** → 它只有否决权。漏判的后果是「闸没抓住」（退回今天的状态），不是「错误地放行了一条本可执行的迁移」。真正的兜底仍是空库实跑（5.9 / 簇 111.6）。
- **[派生仓 `migrations/` 分发随执行范围变化]** → 12 条单属主迁移的分发范围会收窄。**MUST NOT 从派生仓删除已应用的迁移文件**（删了账本行就成了 `ledgerOnly` 噪声）；分发范围以「账本范围」为准，执行范围只控制跑不跑。这条容易做反。

## Migration Plan

1. 先修派生仓 CLI（D5）—— 独立、可单独验证、不依赖其余任何一项。
2. 再落归属机制（D1 / D2）与名册，`aidcp-cloud` 内先跑通全部静态用例。
3. 再做 `0030` 拆分（D3）与可执行性闸（D4）。
4. 同步分发到三个派生仓，逐仓 `migrate status` 自证 CLI 可跑、无 pending 异常。
5. 空库实跑（属 `cloud-schema-migration-executor` 5.9，本 change 只负责让它可执行）。

**回滚**：全部改动是新增文件 + 新增闸 + 两条幂等新迁移，无破坏性 DDL；回滚即还原提交，dev / ol 的库与账本不受影响。

## Open Questions

- `migrate verify` 是否接受「同一对象被两个版本声明」（`0030` 与接替它的新迁移）？实施时 MUST 实读 verify 代码确认，不得凭推测；若不接受，退路是让新迁移用新索引名并在名册 basis 里写明。
- 名册的「冻结集合」用什么表达：显式 version 清单，还是「文件 mtime / git 首次出现时间」？倾向显式清单 —— 前者可审、后者不可重放。

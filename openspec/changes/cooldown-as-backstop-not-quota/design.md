# Design — cooldown-as-backstop-not-quota

## 1. 语义改判（核心）

冷却＝**兜底**，只防**意外**爆发；主闸＝**风控配额**，单独负责数量。**兜底必须比主闸松。**

这一条是本 change 的宪法，其余全是推论。

## 2. 判据（可机械验算）

「`3600 / 冷却 > 该动作小时配额`」这个口径**必要但不充分**——它只量小时窗，按它量只有 `comment` 违规。本病主要活在**分钟窗**。补全成逐窗口形式：

> **对每个动作、每个可达档位、每个窗口 W（分/时/日）：冷却 `c` MUST ≤ 窗口长度 `L_W` ÷ 该窗口配额 `q_W`。**

**等号合格的证明**（见 proposal「15 不是拍的」）：冷却取等放行 ＋ 配额半开窗 ＋ `count >= quota` 才拒 ⇒ 以 `c = L/q` 等间隔跑，窗内恒 `q-1 < q` ⇒ 配额可跑满 ⇒ 不削主闸。

**等价的运营口径**（也写进 spec，因为人能测）：

> **主闸的每一个旋钮都必须真的能拧动。** 冷却若在窗口 W 上比主闸紧，那个旋钮就被焊死了。

## 3. 为什么一刀切 15，而不是按动作给值

- 上界由各动作的分钟爆发上限定死：like 15 / collect 20 / follow 60 / comment 60。**四个都能取 15，且 15 是唯一的最大统一值。**
- 给 follow / comment 单配更大的值（30s / 60s）在它们身上**行为完全等价**：两次 follow 必须跨场（一场只准 1 次、一场 15-20 分钟），两次 comment 同理。15 到 60 之间任何值都落在一个**算术上不存在的窗口**里。差异化只增认知负担、零收益；取到 60 反而与分钟格并列 binding，等于又变回半个主闸。
- 给 comment 单配「因为评论更敏感所以留 5 分钟」**正是本次要根除的思路**——那是把策略重新编码进硬编码常量。评论的敏感性已经表达在面板上（8/日、2/时，远紧于点赞的 50/13）。
- like 在 aggressive 档余量 1.00×（压线）。但压线合格（§2），且 like 的分钟 cap=4 只可能以**爆发**形式出现（4/min = 240/h ≫ 小时配额 13 或 20）——**挡爆发正是兜底的本职**。

## 4. 为什么不是删

兜底还有一件**主闸干不了**的活：**同账号并行（N:1）**。

单场预算是每会话各一份；配额按账号持久化但**只数数量、不管间距**；冷却是**全局单例按账号分桶**（`server.ts:2548` 构造、`:2714` 注入）——它是唯一一道给出「最小间距」的机制。两个并行会话可以在同一刻各发一个赞，只有冷却拦得住。同理挡秒级重入。

删了这道保护就没了；留 15s，它平时完全隐形、只在异常里说话。**这正是兜底该有的样子。**

## 5. 为什么不动「拦截即丢弃」

它是「兜底比主闸严」造成实际损失的**传导机制**，不是根因。`c=15` 可证明不 binding ⇒ 损失趋零。改成排队/补发是新机制、新失败模式（钉页、过期意图重放），YAGNI。

但 spec MUST 写死**条件式**不变量：

> 拦截即丢是可接受代价，**当且仅当**冷却值可证明不削主闸的任一窗口配额。

否则下一个人把冷却调回大值，这个病会一字不差复发。

## 6. mandatory 例外：保留，但改写理由

- 保留的理由**不是**「零成本」，是**冷却丢弃而不排队**：mandatory 是运营对指定内容类别的显式授权，且是每帖一次性机会，被 15s 兜底丢掉＝**永久损失一次已授权动作**。
- 爆炸半径由主闸兜死：mandatory **不绕主闸**（dispatcher 仍调 `canInteract`；`CommentAppraiser` 仍调 `explain('comment')` 预检、下发前再判一次）。
- **spec 里那条例外的理由句必须改写**：现文「该规则是运营员对指定内容类别的显式确定性动作授权」隐含「冷却是数量约束、授权动作不该被数量约束挡」。新语义下的正确理由是「兜底丢弃不排队，MUST NOT destroy 已授权的一次性机会」。
- 若未来要删这个例外，**前置条件是冷却改成排队而非丢弃**。登记 backlog，不在本 change。

## 7. 重启静默期一并降到 15s

- 现状：默认 180s（`server.ts:2547`），判定在 `canAct` 内部（`action-cooldown.ts:65-68`）——静默窗内「该账号该动作本进程无成功记录 → 拒」。
- 它的原始立论「冷却内存态、重启清零 ⇒ burst」**在新语义下被抽空**：配额是 PG 持久化 ＋ 启动回灌（`risk-controller.ts:126`）⇒ 重启后主闸完好，分钟窗地板照旧。
- 但机制本身还有一件真活：重启后冷却无历史 ⇒ **兜底对「每账号每动作的第一发」是瞎的**。15s 静默恰好补上这一发。
- ⇒ **保留机制、改默认值 180→15s**，同受 §2 不变量约束。留 180s ＝ 病灶从冷却搬到静默期（严 12×，且严于 follow/comment 的 60s 主闸地板）。
- 附带：静默期拒绝时日志打印「还需 0s」（`action-cooldown.ts:76-78` 无历史时返回 0），与真冷却在日志里无法区分。**本 change 不修**，登记 backlog。

## 8. 主闸取值路径夹 cap（把不变量变成算术）

- 现状：**派生路径夹** `MINUTE_BURST_CAP`（`quotas.ts:68`），**覆盖路径不夹**（`quota-config-store.ts:145` 的 `validInt(row?.perMinute) ?? derived.minute`；facade 只校验 `0..QUOTA_MAX`）。
- **实证（非推测）**：面板浏览行 `perHour=80` > `HOUR_BURST_CAP.view=60`，且这一行今天正在生效 ⇒ 覆盖确实不夹。
- 后果：运营给 like 的 `perMinute` 填 6 ⇒ 上界 10s < 15s ⇒ **兜底反超主闸、病一字不差复发，无日志无告警**。
- 修法：在 `windowQuotasFor` **单点**夹 `perMinute`（不是 facade 写路径）——它同时是 `canDo` 的取值口**和**面板 catalog 的取值口 ⇒ 天然「显示的＝生效的」，且覆盖已落库老行。这正是仓内 `risk-controller.ts:227-229` 自己写下的原则：「两处各写一份就是『显示的 ≠ 生效的』的经典入口」。
- 🔴 **红线：只夹 `perMinute`，MUST NOT 夹 `perHour` / `daily`。** 浏览行 `perHour=80` 正在生效，夹了会当场把浏览量从 80 砍到 60 —— **这是本 change 最容易被「对称性」诱发的回归**。
- 本仓已被「不变量靠文档维持」烧过两次（协议主动命令白名单、`action.completed` 动作名口径，两处 typecheck 都抓不到、都出过事）。这一行是把纪律换成算术。

## 9. 自动评论旁路：不并进本 change

**事实（已复核）**：`triggerGatedAutoComment`（`aidcp-cloud/src/comment-agent/gated-auto-comment.ts:76`）依次查单场评论预算 → `canDo('comment')`（主闸）→ 联系评论日上限；**不查冷却**。记账走 `interaction.occurred → RiskController.record`，与 dispatcher 的 `action.completed → markCooldown` **不同源** ⇒ **也不落戳**。

**为什么不并**：

1. **语义改判后它不是洞，是对的架构**。兜底防意外爆发；主闸负责数量。这条路已经过了主闸（评论配额 ＋ 日上限），不需要兜底再上一道数量枷锁。给它补冷却＝**把兜底重新升格成主闸**，正是本 change 要根除的方向。
2. **「不落戳」这条残留不一致，被主闸堵死**。老场景（t=0 排期评论不留戳 → t=70s 浏览闭环评论 → 70 秒内两条）在**今天 30 分钟冷却下逐字同样成立**（旁路从不留戳，冷却对它没有历史可依据）⇒ **冷却值对它完全无关，改 15s 既没造出它也没让它更坏**。而分钟配额 1 给了 60s 硬地板 ⇒ 结构上跑不出 <60s 的两条评论。
3. **补「落戳」（1 行）也不做**：唯一能改善的是「跨路径两条评论 <15s 连发」，而分钟配额 1 已把这个区间清空。零收益，YAGNI。

**但必须写进 spec 的（零代码，纯澄清）**——四条评论路径的真实闸门表：

| 路径 | 主闸（配额） | 冷却 |
|---|---|---|
| 浏览闭环普通评论 | 查 | **查（本 change 唯一真正影响的路径）** |
| mandatory 强制评论 | 查（`explain` 预检 ＋ 下发前二次判） | 不查（例外，保留） |
| 排期 / 联系 / 引流自动评论 | 查 | 不查 |
| 手动 `/comment` | **不查**（用户 2026-07-10 定案：操作员全权） | 不查 |

今天这张表没人写下来过，**「评论有 30 分钟冷却」是个集体误解**。写明它本身就是本 change 的一半价值——也解释了为什么 comment 的「翻一倍」只发生在第一行那一条路上。

⚠️ **MUST NOT 在提案里写「跨路径共享的主闸已经就位且工作正常」**。真相是「主闸覆盖四条路中的三条；手动路按用户定案豁免」。别把一个已知的、用户定案的豁免写成完好。

## 10. 已证伪 / 不要写进提案的说法

| 说法 | 为什么错 |
|---|---|
| ❌「读一篇帖 ~60s 是结构性下界，所以 15s 恒不触发」 | 60s 是 LLM 往返的涌现值，无任何闸保证。真下界是详情停留地板 2.5-5s ＋ 动作间隔；FB feed 就地读是 glance 模式、秒级，而它正是 dev 上在跑的生产路径。安全论证必须挂在**分钟配额 ＋ 单场预算** |
| ❌「量会涨 60%」/「利用率 60%→100%」 | 无测量。决定性参数是「一场里冒出几个互动意图」，没人测过。方向对，数字别写 |
| ❌「日格＝滑动 24h」 | day 窗是**上海自然日**，跨零点硬清零 |
| ❌「任何评论路径都必过 `canDo('comment')`」 | 手动 `/comment` 明文跳过风控状态 ＋ 速率配额 ＋ 日上限（`comment-scheduler.ts:821-824`） |
| ❌「mandatory 只绕 like 的冷却」 | comment 侧也绕（`comment-appraiser.ts:97-121` 在冷却检查之前就 return） |
| ❌「follow 的分钟格恒为 1 是结构保证」 | `MINUTE_BURST_CAP` 只夹派生路径，夹不住面板覆盖（见 §8）。它是**当前 DB 的一行**，不是不变量——除非 §8 落地 |

## 11. 风险与回滚

**风险**

1. **面板日额第一次被真的摸到**（点赞 50/日、收藏 25/日）。不是 bug，是判据落地的必然。**涨幅无法预估**。**最大单点风险，且不是冷却的错。**
2. **点赞形状在极尾部变差**：最坏序列从 0/120/240s 变成 0/15/30s。但：(a) 需 3 篇过质量闸的帖在 30s 内读完；(b) **分钟配额 3 今天就允许 3 个赞瞬时连发**（滑动窗只数量、不管间距）⇒ **15s 让最坏形状比「只有配额」更好，不更差**；(c) mandatory 旁路今天就绕冷却 ⇒ 0 秒连发今天已上膛（**须在 dev 上核实是否真有账号配了强制点赞规则**，别当假设）。
3. **重试旁路**（`role-dispatcher.ts:2637-2652`）：like/collect 失败原地重发一次，**不过 `canInteract`、也不过冷却**。与取值无关，但它证伪「冷却是最坏形状唯一守门人」。**仅登记，不修。**
4. **收藏/点赞比例向上漂**：收藏永远与点赞同数组下发（`interaction-appraiser-role.ts:264-272`），今天两个长短不一的冷却把「both」决策拆成「只点赞不收藏」。统一 15s 后赞藏恢复同刻共发 ⇒ 平台侧若对 save/like 有画像，这是一个**可观测的行为口径阶跃**（更像人，但要盯）。系统内**无任何闸**在管 save/like 比。
5. **日初出现新的静默拒绝**：点赞/浏览比例闸（日窗、views ≥ 10 才检、`(likes+1)/views ≤ 0.35`）。冷却不再吃意图后，日初 views=10 / likes=3 时第 4 赞被 `ratio:like_view` 拒。长期无碍（50/150=0.33）。**别在改完后把它误判成「冷却没生效」。**
6. **「收藏了但没点赞」暴露频次上升**：like 被拦时 collect 仍会发（循环对每个 action 独立判闸、无联动）。今天就有、与本 change 正交。**登记 backlog。**

**回滚**

- **冷却值**：改回四常量（一次 rsync ＋ restart）。冷却是进程内内存态 ⇒ **重启即彻底回到旧行为，零残留状态**。
- **静默期**：`AIDCP_RESTART_QUIET_MS=180000` **秒级回滚，不改代码、不发版**。
- **perMinute 夹 cap**：唯一有持久化关联的一项——但它今天**零行为变化**（四行未覆盖；浏览行 perMinute=4 ≤ cap 8）；回滚只需去掉那一行夹，**已落库的行本 change 从不改写**。
- ⇒ **整个 change 的回滚面积 ＝ 一次云端 restart。无边缘、无协议、无 DB 迁移。**

## Context

Facebook 慢启动的曲线（总天数 + 每日动作上限）在 2026-07 之后已经变成**后台可编辑的运行时配置**：管理后台「环境」页的 Facebook 全局运行策略编辑器逐格写，云端配额 clamp 现读同一份策略（`aidcp-cloud/src/risk/risk-controller.ts:491-499`，Facebook 走配置、其他平台才走编译期曲线）。

桌面客户端展示侧没有跟上：

- 曲线表写死在页面结构里（`aidcp-edge/src/electron/renderer/index.html:525-536`），7 行 6 列，注释承诺「与云端冷启动常量逐格同步」——这个承诺已无人可守，因为 Facebook 的生效来源早已不是那个常量。
- 表内 42 个数字恰好等于后台**出厂默认值**（`aidcp-cloud/src/config/facebook-operation-policy-store.ts:93-101`），所以运营没改过配置时看不出问题。
- 未绑定账号 / 绑定冲突的环境走的那条组装分支把总天数写死成 7（`aidcp-cloud/src/client-auth/client-auth-server.ts:370-388`）。

已有的通道足够用：env-scoped 慢启动读（`GET /environments/:envKey/slow-start`）已经在绑定账号时回传当日生效上限 `dayQuotas`，客户端也已消费它。缺的只是**整条曲线**。

## Goals / Non-Goals

**Goals:**

- 客户端展示的曲线与云端 clamp 生效的曲线同源：同一份运行时全局策略。
- 总天数在所有分支（绑定 / 未绑定 / 冲突）都取权威值。
- 曲线读不到时如实说明，绝不回落写死数字。
- 客户端补上后台早已有、界面一直没显示的「搜索」一项。

**Non-Goals:**

- 不改后台的配置页面、写入路径、边界与校验。
- 不改小红书曲线（仍是编译期常量，本次不动）。
- 不动协议 v2 与两份 `protocol.ts`：这条读走客户 HTTP API，不经边缘 WebSocket。
- 不在客户端做任何本地推算（第几天、还能做多少、是否更严），一律用云端给的数。

## Decisions

### D1：曲线走已有的 env-scoped 慢启动读，不新开端点、不进 WebSocket

该读已经是客户端渲染这一行的**唯一权威来源**（离线可读、未绑账号可读、写后回执同形）。曲线跟着它走，天然获得同一次 ownership 校验、同一条降级路径、同一个「按 envKey 隔离、晚到响应丢弃」的既有逻辑。

**放弃的选项**：跟 `ui.snapshot` 走。快照要边缘在线，而这一行的既定要求就是边缘离线也照常显示——曲线跟着快照走等于给它加了一个它本来没有的前置。

### D2：曲线取用口加在既有的 Facebook 运行策略端口上，且是**必填方法**

客户鉴权服务已经注入了 Facebook 运行策略端口（operation-policy 路由在用）。曲线取用作为该端口的新方法，而**不是**新加一个可选 deps。

理由是机械保证：本仓已经吃过「拆进程后组装根漏接可选参数 → 能力静默消失」的亏。必填方法让两个组装根（单体 `aidcp-cloud/src/server.ts` 与派生 `aidcp-api/src/server.ts` 的手写 `main()`）在**编译期**就必须补上，漏接线当场编译失败，而不是上线后安静地少一个字段。

### D3：曲线缺席只有一种表达——字段整个不出现

回包里 `curve` 要么是一份完整曲线，要么整个字段不在。

- **MUST NOT** 用编译期默认曲线冒充：那份默认值很可能比运营配的更松，而且它正是本次要消灭的那张假表。
- **MUST NOT** 下发空数组或零值曲线：那等于宣称「这个号没有逐日上限」。
- 非 Facebook 环境不带曲线（那一行本来就只在 Facebook 环境显示）。

客户端对缺席的处置是**就地说明读不到**，不是显示旧数字。理由与本仓的红线一致：把「不知道」编成一个看起来确定的「是」，比不显示危险得多——运营会照着一张不会再变的表决策。

### D4：总天数一处取值，两个分支共用

未绑定 / 冲突分支不再自带常量 7，改为由调用点把当前生效总天数传进去。绑定分支本来就走风控投影（已经用配置值），两条路径从此同源。

非 Facebook 平台维持 7（小红书曲线仍是编译期常量，改它属于另一件事）。

### D5：客户端表格「表头静态、表体动态」

列集合是稳定的（浏览 / 点赞 / 评论 / 关注 / 发布 / 搜索 / 加组，恰是后台配置的 7 项），表头保持静态结构；行数与数字全部来自回包，行数跟随总天数（后台可配 1–30 天）。

客户端 **MUST NOT** 对不在回包里的动作自造一列或补零——收藏、评论点赞、私信回复这三项 Facebook 结构上做不了，云端本就不该给、客户端也不该编。

## Risks / Trade-offs

- **[派生仓组装根漏接]** → 用必填方法把它变成编译期错误（D2）。另外任务里显式列出两个组装根，并要求两侧都跑 `typecheck`。
- **[dev 已切三服务，客户口在 api 进程]** → 部署时必须重启承载客户 API 的那个服务，而不是只重启单体；验收要从客户端真实读一次，不能只看单体日志。
- **[后台把总天数改大后表格变长]** → 表格容器已有独立滚动，最长 30 行；渲染前按总天数裁剪 / 对齐，行数以回包数组长度为准，不额外补空行。
- **[曲线读取增加一次策略取用]** → 该取用是内存态只读（策略已在进程内缓存），无额外 IO。
- **[老版本客户端收到新字段]** → 多一个字段被忽略，行为与今天完全一致（仍显示写死的表）。这不是回归，但也说明**只有出包并更新到运营机后，这个修复才真正到达运营**。

## Migration Plan

1. 云端先落地：新字段是纯增量，老客户端忽略即可，无需协调发布顺序。
2. 客户端随后落地，出包后才到运营机（本仓默认不自动打包，需用户显式要求）。
3. 回滚：云端回滚即字段消失，新客户端进入「读不到曲线」的诚实降级态，不会显示错误数字。

## Why

管理后台已经可以逐格编辑 Facebook 慢启动曲线（总天数 1–30 天 + 每一天的动作上限），云端配额计算也已按后台配置执行。但桌面客户端给运营看的那张「慢启动曲线限额」表，是当年手抄进页面结构的一张静态表：永远 7 行、永远是出厂默认那 42 个数字。今天两边数字碰巧一致（客户端表 = 后台出厂默认），所以没人发现；运营只要在后台改过一格，客户端展示的就是一份**再也不会变的假曲线**，而运营正是拿它来判断「这个新号今天还能做多少」。

同一处还有第二条漂移：环境尚未绑定账号（或绑定冲突）时，云端组装慢启动状态走的是另一条分支，总天数在那里被写死成 7。后台把周期改成 10 天，这类环境的客户端徽章仍会显示「第 3/7 天」。

「显示的 ≠ 生效的」在本仓已被反复判为红线（配额面板可热编辑、曲线不可热编辑，两者之间没有任何不变量保证一致）。这次把展示侧接到与 clamp 同一个事实源上。

## What Changes

- 云端 env-scoped 慢启动读（`GET /environments/:envKey/slow-start`）回包新增**当前生效曲线**：总天数 + 逐日动作上限表。来源与配额 clamp 逐字同源（同一份运行时全局策略），仅 Facebook 环境提供；非 Facebook 或曲线读不到时**整个字段不出现**，MUST NOT 用编译期默认值冒充。
- 云端未绑定账号 / 绑定冲突分支的总天数改为读运行时策略，不再写死 7。
- 客户端那张曲线表改为**按回包数据渲染**：行数跟随总天数，列跟随回包字段（补上后台已有、客户端一直没显示的「搜索」）；说明文案里的「头 7 天」改为按真实总天数表述。
- 客户端拿不到曲线时**如实说明读不到**，MUST NOT 回落到旧的写死数字——回落一次就是把「不知道」重新编成一个看起来确定的假表。
- 客户端删除写死的曲线数字与「与云端常量逐格同步」的注释承诺（该承诺已无人可守：Facebook 的生效来源早已不是那个常量）。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `client-customer-auth`: env-scoped 慢启动读的回包契约新增当前生效曲线；未绑定账号分支的总天数改为权威来源，不再是常量。
- `edge-companion-ui`: 客户端曲线说明的内容来源由「客户端内置静态表」改为「云端回包」；新增读不到曲线时的诚实降级要求。

## Impact

- `aidcp-cloud`：`src/client-auth/client-auth-server.ts`（慢启动读回包组装、未绑账号视图）、慢启动读依赖的 controller 视图出口（`src/server.ts` 注入处）、Facebook 全局运行策略取用（`src/config/facebook-operation-policy-store.ts` 已有运行时策略读，只新增取用点）。
- `aidcp-edge`：`src/electron/renderer/index.html`（静态表格结构）、`src/electron/renderer/renderer.js` 与 `ui-logic.js`（曲线渲染与降级文案）。
- 无协议 v2 消息变更（不走边缘 WebSocket，只走客户 HTTP API），因此不触碰两份 `protocol.ts`。
- 无数据库结构变更。后台配置页面与写入路径不变。

## Context

评论提交有两个时间量，方向相反、必须保序：

- **判定方窗口**（云端）：等多久还没收到回执就判 `timeout`。
- **执行方预算**（边缘）：命令内部自掐表，超了就诚实回 `comment_deadline_exceeded` 并清空编辑框。

保序关系是 **判定方窗口 ≥ 执行方预算**。反过来的后果不是"慢一点"，是**一条真评论被发两次**：云端先判超时 ⇒ 不打去重标记 ⇒ 下一轮同帖再发。

今天这个保序由**两份各自维护、取值恰好相等的公式**保证。边缘那份还额外减了一个 2s 的传输余量，所以实际是 `边缘预算 = 云端窗口 − 2s`，关系成立 —— 但成立的原因是两边的四个常量恰好一样，而不是结构上必然。

**已上线规格自己也承认这个形态是脆的**：`facebook-comment-idempotency` 的最后一条场景把「边缘确认预算变大时回头核算云端超时」写成了一条**人工义务**。人工义务加两份可漂移的公式，等于没有义务。

**注意别与另一个预算搞混**（摘出文档专门订正过）：这跟「提交窗口」不是一回事。提交窗口是引擎向宿主请求写窗口的时长，纯边缘内部；本 change 是跨仓的判定方窗口 vs 执行方预算。不同常量、不同文件。

## Goals / Non-Goals

**Goals:**

- 让「判定方窗口 ≥ 执行方预算」由**结构**保证，而不是由两个常量表恰好相等保证。
- 删掉边缘那份公式副本，让预算只有一处声明会变。
- 兜底路径（字段缺席）**响亮**，且不重新引入第二份公式。

**Non-Goals:**

- 不改预算的取值。四个数字都是 2026-07-29 按真机实测定的（约 277 字符越南语长文撞 deadline 后整体 ×1.5、上限单独抬到 180s），本 change 只改「谁算、怎么传」，**一个数字都不动**。
- 不改评论提交的验证语义、去重台账、回执原因码词表。
- 不引入跨仓共享包。边缘与云端不共享包体系（云端的 kernel 只服务云端三仓），为四个数字建一条跨仓依赖是不成比例的。
- 不新增协议消息类型、不动动作↔消息映射。

## Decisions

### D1. 计算方定为云端

两个候选：云端算了下发，或边缘算了回报。

**选云端**，两条理由：

- **判定方必须先知道自己要等多久**。若由边缘算了回报，云端在收到回报之前就已经开始等了 —— 它得先用一个默认值等着，那个默认值就是第二份公式，问题原样还在。
- **云端已经是计算方**。公式与常量今天就在云端那份里完整存在且被用着；改动是「把已经算出来的数带上」，不是搬家。

### D2. 边缘只保留传输余量，不保留公式

边缘删掉四个常量与公式，改为 `预算 = 收到的值 − 传输余量`。

**传输余量为什么可以留在边缘**：它表达的不是「这条评论要打多久」，而是「边缘要比云端早一点收口，好让诚实回执赶在云端判超时之前到」。这是边缘对自己回执时序的判断，与长度无关，**不是那份公式的第二份**。它今天也已经带着这个理由写在注释里。

### D3. 兜底必须响亮，且必须是「与长度无关的常量」

字段缺席时（老云端、手工命令路径、或将来某条没带上的路径），边缘回落到既有的默认 Native 命令超时，并在回执上标出「本次预算未由云端下发」。

**为什么不能保留一份按长度算的兜底**：那正好把删掉的东西原样加回来，而且更隐蔽 —— 它只在字段缺席时生效，平时测不到，等到真的分叉那天它就是那份漂移的副本。

**为什么不能 fail-closed 拒绝命令**：字段是可选新增，两个方向的部署顺序都会短暂出现缺席；拒绝会把一次部署时序问题变成评论全线停摆。回落 + 响亮标注是正确的量级。

### D4. 协议改动的范围要说清，免得被当成"协议大改"

新增一个**可选字段**到既有载荷：

- 两份 `protocol.ts` 逐字一致（`npm run typecheck` 会抓到不一致——两份用穷举表互相约束）；
- `docs/protocol.md` 同步字段说明；
- **不新增消息类型** ⇒ `MessageType` 穷举与头部计数不变；
- **不动动作↔消息映射** ⇒ command-bridge 不改；
- **不进主动命令路由白名单** ⇒ 它是既有命令 `interaction.comment` 的一个字段，不是云端独立下发的新命令。白名单只对「独立下发、非应答」的命令生效。

### D5. 不做 drift-guard 测试，做结构消除

本仓有跨仓漂移守卫的先例（加群词表）。实读那条守卫：它是行为测试 + 手抄夹具，能发现「云端不再认某语种」，发现不了「边缘加了云端不认的语种」。

**数字的情况更糟**：两个常量取值不同不产生任何可观测的行为差异，直到真机上一条长评论超时。**行为测试原理上看不见第二份实现。** 所以这里不加守卫，直接把第二份删掉。

## Risks / Trade-offs

- **[边缘出包滞后]** 边缘是桌面客户端，靠重新打包分发 → 云端先上线只是「多带一个字段」，边缘拿到之前保证不成立。**如实记为「效果要等下一次出包才完整」**，不在验收里假装已生效。
- **[兜底路径长期常驻]** 若边缘长期收不到字段，兜底会长期生效而没人注意 → 回执标注让它可见；且兜底值与长度无关，长评论在兜底下会更早失败（诚实失败，不是重复评论），方向是安全的。
- **[改了传输值就等于改了两边]** 单一事实源的另一面是：改错一次，两边一起错 → 但这正是想要的形态。今天改错一次是**两边不一致**，那比一起错更难发现。
- **[热点文件]** 两份 `protocol.ts` 是并行开发点名的单写热点 → 本 change 期间与任何动协议的流串行；开工前 `openspec list` 核对。

## Migration Plan

1. **云端先上**：加字段 + 带上算出的值。老边缘忽略未知字段，行为完全不变。可独立部署 dev。
2. **边缘随后**：删公式、改为派生、加兜底标注。边缘先上也安全（走兜底）。
3. 两边都上之后保证才完整。**这一步依赖出包**，按 handoff §2.2 的口径不为此专门打包，随下一次出包自然生效。

回滚：两侧独立可回滚。云端回滚 = 不再带字段 ⇒ 边缘走兜底；边缘回滚 = 恢复自己的公式 ⇒ 回到今天的两份形态。**任一侧单独回滚都不会造成不一致的危险态**，因为兜底与旧公式都满足「不超过云端窗口」。

## Open Questions

- 传输的到底是「云端的等待窗口」还是「边缘应当使用的预算」（即减不减余量、谁来减）？倾向传窗口、由边缘减余量（余量是边缘自己的判断，D2）。实装时若发现云端也需要知道边缘的实际预算（例如为了日志对账），再考虑两个字段。
- 手工 `/comment` 路径是否走同一个计算方。实读后确认；若它另有一条不经过该计算方的下发路径，那条路径要么接上，要么明确记为走兜底。

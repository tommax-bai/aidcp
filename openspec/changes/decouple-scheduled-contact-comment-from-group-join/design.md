## Context

Facebook 上的排期联系评论今天是一个复合动作：加入一个新群 → 加入被平台确认后，在同一轮、无任何小时或天级等待，就在那个刚加入的群里发评论。

它带来的问题不是「做了两件事」，而是**评论容器被外部钉死**。评论路径里有两种取容器的方式：外部传入的固定容器，或调用账本选群口。选群口是预热期与单群冷却唯一被检查的地方。容器被钉死时选群口根本不会被调用——这两道闸不是被绕过一次，而是永远不参与判定。

还有一条今天不显眼、拆分后才暴露的耦合：带「先加群」的那条调用直连加群调度器的排期入口，**完全不读每账号的加群配置**（开关、日上限、动作时段三道闸只写在排期器自己的独立加群分支里）。所以今天只要联系评论开着，账号就会加新群，哪怕自动加群开关是关的、日上限是 0。

## Goals / Non-Goals

**Goals:**

- 让排期联系评论回到账本选群，从而真实受预热期与单群冷却约束。
- 把「加群」这件事收回它自己的开关下：排期链路上加群只有一个来源。
- 显示名与实际行为对齐。

**Non-Goals:**

- **不拆手动命令、委托任务与固定规则模式**。用户 2026-07-29 决定规则模式按定死的规则跑，后续要调再单独改规则。这意味着「加完群立刻评论」在规则模式下仍会发生——这是被明说的取舍，不是遗漏。
- 不改复合动作本体（它继续为上述三条路径服务）。
- 不改预热期与冷却的取值（那是环境变量，另行调整）。
- 不改边缘端。

## Decisions

**D1. 改点是选项构造，不是复合动作本体。**

排期联系评论的选项由一个专用函数构造，且该函数**只有排期触发口一个调用方**。把 Facebook 分支上的「先加群」标记去掉，改动就精确落在排期这一条路径上，其余三个入口各自独立传参、完全不受影响。

替代方案是在复合动作内部按来源分支。否决理由：那会把「谁该加群」的判断塞进一个执行体，四个来源的差异从调用点转移到实现里，之后每加一个来源都要回去改它。

**D2. 拆分后不为排期链路补任何「加群兜底」。**

一个自然的顾虑是：账本里没有合规群时，联系评论会空转。这里刻意不补「那就去加一个新群」——那等于把刚拆掉的耦合原样装回来。空转是诚实结果，处置方式是开自动加群，让它按自己的闸去补充群源。

**D3. 显示名改回联系评论，但规则模式面板的文案不动。**

排期表里那个动作拆分后不再加群，旧名会误导。规则模式面板里描述其轮次的文案仍然准确，因为规则模式确实还先加群。两处文案分别判断，不做统一替换。

**D4. 那 1 个受影响账号交给运营配置，不做数据修补。**

拆分后会停止加群的账号，dev 实测只有 1 个（联系评论开着但没有自动加群配置行）。正确处置是给它配一行自动加群，属运营侧动作。**不在本 change 里替它写数据**：那会重新引入「系统替存量账号做配置决定」，与刚落地的种入范围铁律相反。

## Risks / Trade-offs

- **规则模式仍会加完就评** → 用户明确决定不拆。**缓解**：写进规格与本设计，使它是一个被记录的取舍而非被遗忘的缺口；后续若要处置，改的是规则定义本身。

- **拆分后联系评论可能长期空转** → 账号已加入的群若全部处在冷却或预热中，每轮都无目标。**缓解**：这是诚实空转、有可诊断结果；真正的解法是开自动加群补充群源。另需注意「放开时限兜底」当前默认开着——它会在无合规群时丢掉预热与冷却，反而让拆分的收益打折。关掉它是另一件事（环境变量），本 change 不动，但必须在交接里点明。

- **1 个存量账号停止加群** → 见 D4，交运营配置。**缓解**：数字已实测、账号已具名，不是一个模糊的「可能有影响」。

- **结果回执形态变化** → 从一张「加群 + 评论」合并卡变成普通评论结果卡。**缓解**：属预期变化，回执本身仍然诚实；测试需同步。

## Migration Plan

无数据库改动。部署即生效，只影响此后触发的排期联系评论槽位。

**回滚**：把选项构造里那一处标记加回即可，复合动作本体从未改动。

## Open Questions

- 「放开时限兜底」默认开着，会在无合规群时丢掉预热与冷却三道闸。本 change 让预热与冷却终于对排期联系评论生效，但那个兜底会削弱这一收益。关掉它只需改环境变量，属运营侧决定，记在交接里。

## Context

新登记的 Facebook 账号在自动化侧完全空白：排期侧表与自动加群配置表都没有行，两处读取端对「无行」都判为不自动。现网 40 个 Facebook 账号里只有 3 个有排期行。

范围经用户 2026-07-29 明确收窄：**只管新账号，存量一个不碰**。这条约束是本设计的主要形状来源——它排除了所有基于「谁没有配置行」的实现路径。

三张涉及的表（账号主表、排期侧表、自动加群配置表）经边界清单确认**同属 api 属主**，无跨域写入。

### 为什么「绑定环境时」不能作为挂载点

绑定观察在**每次客户端环境连上来**时都会重新发生一次（登记环境的入口带着握手声明的账号与平台，且以「来了新值就覆盖」的语义写入）。

这个反复性对「顺带覆盖存量账号」是优点，但对本次范围是致命的：绑定这一刻**无法区分**「刚新建的账号」与「早已存在、只是没配过的账号」，它看到的都是「这个账号没有配置行」。挂在这里必然把 37 个存量账号一并种上，与范围相反。

账号登记则天然带这个区分：主表插入用的是「冲突就什么都不做」的写法并回带插入结果，**有回带即真的新建**。

## Goals / Non-Goals

**Goals:**

- 真正新登记的 Facebook 账号自动获得一份可用的默认自动化配置。
- 存量账号零影响，且这一点由**结构**保证，而不是靠一个可以被绕过的开关。
- 不引入数据迁移、不引入回填脚本。
- 保持所有既有闸门语义不变——种入只移除「运营尚未配置」这一道。

**Non-Goals:**

- 不处理存量账号（用户明确决定，后续若要处理另起 change）。
- 不种入联系评论。
- 不种入小红书与视频号。
- 不改生效值的计算规则，不改风控配额，不改时段周历。
- 不为种入失败提供自动补种。

## Decisions

**D1. 用注入式回调，不让账号存储直接依赖两个配置存储。**

账号主表存储今天不认识排期与加群配置。让它 import 两个配置存储会新增两条依赖边，且在拆仓纪律下要额外论证。改为在它上面开一个可选回调注入点，由组装根把回调接到两个配置存储的既有写入方法上。

替代方案是把登记方法的返回值从「无」改成「是否新建」，由调用方去种。否决理由：该方法是一个**跨进程端口**，改返回类型会连带改端口契约与其 HTTP 传输实现，波及面远大于收益；而且它有两个调用入口，改返回值意味着两处都要各自实现一遍种入，逻辑会分叉。

**D2. 触发判据是「真的插入了新行」，不是「配置侧表没有行」。**

这是本设计最重要的一条。后者对存量账号同样成立，用它做判据会让种入扩散到 37 个存量账号——与范围相反。主表插入本就用「冲突则什么都不做 + 回带插入结果」的写法，回带非空即真的新建，判据现成、无需新增状态。

**D3. 平台未显式声明时不种。**

登记方法的平台参数是可选的，缺省会回落成小红书。走握手那条路时平台由客户端声明并已校验，可靠；但另一个内部接口入口可以不带平台。在「没说平台」时按回落值种配置，等于给一个可能是 Facebook 的账号种一份小红书默认值。选择不种并留下具名日志——这与本仓「读不到就说读不到、绝不猜」的一贯方向一致。

**D4. 种入走两个配置存储的既有写入方法，不另写 SQL。**

两个写入方法都自带写前校验（账号行存在、平台匹配、取值边界）与镜像版本推进。复用它们意味着：种入的取值必然满足与后台写入完全相同的约束；跨进程缓存失效无需另行处理。代价是两次独立写入、不在同一事务里——可接受，因为两行相互独立，任一行缺失都只是「该动作不自动」这一保守方向。

**D5. 联系评论不种。**

除了「用户列举的三项不含它」之外，还有一条独立理由：带「先加群再评论」标记的复合动作**只挂在联系评论上**（已核：独立加群动作不带该标记）。不种入联系评论，新账号就不会出现「加入新群后同一轮立即在该群评论」这一已知风险形态。这条理由要写进规格，防止后续有人「顺手把它也打开」。

**D6. 发帖需人审、评论免审，两者刻意不同值。**

发帖没有选择：Facebook 排期发帖在既有要求里就必须走需人审，免审对它保持禁用。

评论取免审是**用户 2026-07-29 的决定**，推翻了本设计初稿的需人审。初稿的理由是「与保守失败同向、出问题好收」；用户的取舍是让新账号真正能自动跑起来，不需要逐条点审批。

可达性已核：环境级评论审批策略只能把来源模式**升**成免审——策略为缺省值时逐字沿用来源模式，只有读取失败才回落需人审。所以种一个免审的来源模式就足够，不需要也**不允许**去绕过那条策略。

后果如实记录：新账号绑上人设并通过其余各闸后，自动评论会直接发到平台、无人过目；发帖不受影响，仍逐条待人审。

两个模式取不同值本身也是一道防线——测试里有一条断言专挡「把两个模式一起改掉」的误编辑。

## Risks / Trade-offs

- **种入失败后该账号永久不会被自动种入** → 回调只在真正新建那一次触发。**缓解**：具名日志 + 后台手工补配。**刻意不做自动补种**：任何补种都要扫描「已存在但无配置行」的集合，而那正是 37 个存量账号所在的集合，做了就等于违背范围。这一点写进规格，避免后来人当缺陷去"修"。

- **误把判据写成「配置侧表没有行」** → 会静默把 37 个存量账号全部种上，且这个错误在单账号测试里完全看不出来。**缓解**：规格与设计各写一条明确禁止；测试里放一条「已存在账号 + 无配置行 → 不种入」的断言专门挡它。

- **种入让新账号的自动加群数量增长** → 新账号是逐个进来的，且每个仍受风控日额度与会话预算取小。**缓解**：本次不含存量，增长天然渐进；且联系评论不种，复合动作不会被激活。

- **两次写入非原子** → 排期行成功、加群行失败时，该账号会发帖评论但不自动加群。**缓解**：方向保守（少做而非多做），且两行相互独立、各自的读取端都能正确处理对方缺失；日志需分别标明哪一行失败。

- **组装根改动与两个停滞中的 change 有文件重叠** → 相关 change 已停滞 2–6 天，且这几个文件不在「热点文件单写者」名单上。**缓解**：改动做窄（一个可选注入点 + 组装根接线），冲突面最小。

## Migration Plan

无数据库迁移，无回填。部署即生效，且**只对部署之后新登记的账号生效**。

**回滚**：把组装根那处接线摘掉即可——回调不注入时登记行为逐字回到今天。已种入的行保留（它们是合法配置，与运营手工配出来的行无法也不需要区分）。

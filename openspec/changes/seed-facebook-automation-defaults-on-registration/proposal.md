## Why

新登记的 Facebook 账号今天在自动化侧是**完全空白**的：排期侧表和自动加群配置表都没有行，而两处的读取端对「无行」都判为不自动。结果是每个新账号都要运营手工点开后台、逐项配一遍才会开始跑，而这些配置的取值在运营实践中是固定的。

现网数据印证了这个负担：40 个 Facebook 账号里只有 3 个有排期行，37 个从未被配过、因而一条自动化都不跑。

本 change 只解决**新账号**这一半：账号首次登记时按平台种入一份默认配置。**存量账号一个不碰**（用户 2026-07-29 决定），因此不含任何回填脚本与数据迁移。

## What Changes

- 账号主表登记流程新增一个**注入式回调**，仅在该次登记**真的插入了新行**时触发。已存在的账号走不到这个分支，天然被排除。
- 回调按平台种入默认配置，**只针对 Facebook**：
  - 排期侧表：总开关开；自动发帖开、需人审、日上限 5；自动评论开、需人审、日上限 20。
  - 自动加群配置表：开、日上限 20。
- 小红书与视频号**不种**。用户的诉求是 Facebook；视频号四个动作在平台目录里全部不支持，给它写任何正上限都会被写前校验拒绝。
- **联系评论刻意不种**（保持关闭）。用户列举的三项是发帖、评论、加群，不含联系评论；而且带「先加群再评论」标记的复合动作正是由联系评论驱动的，不种它，新账号就不会出现「加完群立刻在新群评论」这个已知风险形态。
- 平台未由调用方显式声明时**不种**。账号登记的平台参数是可选的，缺省会回落成小红书；在「没说平台」的情况下按回落值种配置，等于给一个可能是 Facebook 的账号种错默认值。
- 种入失败**不阻断登记**，但 MUST 留下可检索的具名日志。

**不做的事**：无数据迁移、无回填脚本、不改存量账号、不改生效值的计算规则。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `content-schedule`: 新增一条要求，规定新登记 Facebook 账号种入自动化默认配置的完整契约（触发条件、取值、平台过滤、失败语义）；同时修改「Facebook 自动加群按账号独立配置且默认关闭」——该要求标题所承载的「默认关闭」意图对**新登记**账号不再成立，但「无配置行即完全不触发」这一条对仍然没有行的账号逐字保留。
- `accounts-master-data`: 修改「握手时自动登记新账号」，写明真正新建一行时会连带种入平台对应的自动化默认配置，且该动作 MUST NOT 对已存在的账号触发。

## Impact

**aidcp-cloud**

- 账号主表存储：登记方法新增一个可选回调注入点。**不新增对配置存储的 import**——回调由组装根接线，存储本身不认识排期与加群配置。
- 组装根：把回调接到排期存储与自动加群存储的既有写入方法上。两者都自带镜像版本推进，因此种入后跨进程缓存失效无需另行处理。
- 涉及的三张表（账号主表、排期侧表、自动加群配置表）**同属 api 属主**，无跨域写入。

**不受影响**

- aidcp-edge：零改动。
- aidcp-console：零改动。种出来的行经既有面板接口正常读写。
- 数据库：无迁移。
- 存量账号：零改动。

## 一条必须写明的安全性质

种入默认配置**不等于该账号立刻开始跑**。它仍要逐一通过人设绑定、环境绑定、边缘在线、风控状态正常、以及活跃与内容两张时段周历的交集。种入只是把「运营还没配过」这一道闸移开，其余各闸原样保留。

## 已知不做补救的一处缺口

回调只在「真的插入了新行」时触发一次。若那一次种入因数据库瞬时故障失败，该账号此后不会再被自动种入——因为它已经不是新账号了。这是为满足「存量账号一个不碰」必然付出的代价：任何补救路径都必须去扫描「已存在但没有配置行的账号」，而那正是 37 个存量账号所在的集合。因此失败只做具名日志 + 后台手工补配，MUST NOT 加自动补种。

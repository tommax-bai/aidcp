## Context

FB 评论「发没发出去」的判定，历史上迭代过两轮，每轮都是在**没有真机形态**的情况下用代理指标猜的：

- 2026-07-11 `facebook-comment-inplace-ack-verify`：真机探针实测「comment_id 是乐观先给的」（68ms 出 client 占位 id，3.5s 才升级为服务器 id），据此把判据收窄为「服务器正式 id **或** 交互控件出现」，并把 reload 从「唯一判据」降级为「有界轮询兜底」。**但**该轮探针只存 `nodeTextLen` 不存原文、时间戳选择器写死 `abbr/time`（作者当时就在结论里写了「需再调」，没调），导致「发布中」这一态**结构上测不到**，方案里被提出后在结论中蒸发。
- 2026-07-16 `facebook-comment-participation-gate`：补了群参与审批的「待审核」徽章否决，堵住押审假绿。

2026-07-17 用补丁版探针（每帧存该行 `nodeText`；时间戳选择器回落到 `<a>`）两跑一致，**首次拿到 FB 评论行的完整三态**：

```
t=  31ms   'Tianxing Bai [标记] 发布中...'         btns=0  opacity=1   ← 在飞（client 占位 id）
t=2807ms   服务器点头（GraphQL 响应）
t=2906ms   'Tianxing Bai [标记] 1 分钟 赞 回复'     btns=4  opacity=1   ← 上墙（服务器 base64 id）
（被拒真机样本 comment_id=4134110716722371）
           'Tianxing Bai [越南语正文] 16小时 已拒绝 查看反馈'  btns=2  opacity=1  ← 被拒
```

两条既有 spec 要求当场被推翻：①「交互控件出现」用**按钮计数**实现，被拒行也有 2 个按钮 → 假绿；②「reload 是权威兜底」，探针当场制造假阴性（报 `reloadPersisted:false`，评论实际都在）。

约束：`aidcp-edge` 单文件改动为主；页内 JS 判别是 FakeCdp 桩测盲区；车队实跑越南群（文案须留 i18n 缝）；边缘轮询须按迭代次数限界 + 注入 sleep（不用 wall-clock，见既有纪律）。

## Goals / Non-Goals

**Goals:**
- 堵掉「被拒评论判成发布成功」这个活的假绿（最高优先级，红线）。
- 把判定基座从**代理指标**（数按钮）换成**真机坐实的状态机**（在飞 / 上墙 / 被拒）。
- 删掉刷新腿这个假阴性产地，预算内部重分配。
- 让「已拒绝」自成一档诚实终态，运营可分诊、目标帖不被烧掉。

**Non-Goals:**
- **不改任何超时常量**（云端提交步超时、边缘 20 秒提交保护窗一律不动）。点头 2.8 秒，现有窗口余量充足。
- 不碰协议（复用既有 reason 字符串通道）、不碰 console。
- 不改「报错浮层不当失败」这条既有要求——行内「已拒绝」与提交后报错浮层是**两个不同 DOM 物件**。
- 不试图用样式（透明度/颜色）判别——真机实测被拒行与正常行样式零差异。
- 不做「已拒绝」的自动申诉/重发。被拒即终态，交人工。

## Decisions

### D1：成功判据 = 服务器正式 id **或**「具名赞/回复控件」，撤销按钮计数

按钮计数（`reactions>=2`）是「赞和回复出现了」的代理，真机证伪：被拒行的 2 个按钮是「编辑或删除此项」+「查看反馈」。改为在该行内**具名识别**赞/回复控件（`aria-label` / 文本匹配，中英覆盖 + 越南语缝）。

*备选*：只认服务器 base64 id、彻底放弃控件判据。**否**——真机两跑里控件与 id 几乎同时出现（点头后 99ms 内），双判据互为冗余，砍掉会牺牲慢渲染下的确认率；且上轮 spec 已把双判据写死，无必要收得更窄。

*风险*：具名匹配引入 locale 耦合。缓解见 D4。

### D2：「已拒绝」自成一档终态，判据用文案不用样式

新增独立 reason（如 `comment_rejected`），语义 = **确定被拒、确定没上墙**。MUST NOT 打去重、MUST NOT 计成功。

*备选 1*：塌进 `verification_ambiguous`。**否**——那条语义是「可能已发出」且**会打去重**，把一个确定失败当成可能成功、还顺手烧掉目标帖，方向完全错。
*备选 2*：塌进 `pending_group_approval`。**否**——那是「待批准、可等、批准后可重试」；已拒绝是终局，重试无意义。
*备选 3*：用透明度/颜色判别。**否**——真机实测 `opacity` 同为 1、`color` 同为 `rgb(28,30,33)`，零差异，该路线结构上不成立。

### D3：删刷新腿，纯就地观察；预算内部重分配、总额不变

刷新腿真机当场制造假阴性；其判据（只要本人+文本）对被拒评论必定假绿；刷新还刷掉押审证据。删掉后把它约 9 秒的预算还给就地窗（约 10 秒 → 约 19 秒）。

**总预算不变是硬约束**：云端提交步超时 = `max(28s, 18s + 220ms×字数)`，这**一个**预算要覆盖「逐字输入 + 确认」全程。若总额变大（例如把窗口放到 30 秒），短评论会超预算 → 云端记 `timeout` → `reallySubmitted` 为假 → **不打去重** → 下轮同帖再发一条真评论（平台可见重复）。这正是 `facebook-comment-idempotency` 当初要堵的洞，绝不能重开。

*备选*：保留刷新腿只作诊断、不作判据。**否**——它唯一的价值主张（治慢渲染假阴性）已被「就地窗加长」覆盖，而它的代价（假阴性、假绿、毁证据）都是实的。YAGNI。

### D4：文案判据只做 veto / 分诊，不做唯一成功判据

「发布中」「已拒绝」「查看反馈」都是 locale 文案。**成功**仍以语言无关信号为准（服务器 base64 id），具名控件为辅。文案只用于：①否决（已拒绝 → 不判成功）；②分诊（发布中 → 在飞）。

这个不对称是既有设计已经确立的（待审徽章就是纯文案 veto）：**文案漏检 → 回落到诚实非成功**（安全）；**文案误命中 → 只会少报成功**（保守）。反过来若拿文案当成功判据，漏检即假绿——不可接受。

### D5：「发布中」= 在飞态，MUST NOT 判终态

识别到「发布中」→ 继续等，不落任何终态。窗口耗尽仍停在「发布中」→ 诚实回「提交了但没等到结果」（区别于「压根没提交」）。这是系统今天缺的分诊维度。

## Risks / Trade-offs

- **[「已拒绝」文案未覆盖越南语/英语实际措辞]** → 真机只坐实了简体中文「已拒绝 / 查看反馈」。缓解：正则用语义高置信超集 + 中英覆盖 + 越南语扩展缝；**漏检回落到既有诚实非成功路径**（不假绿），不引入新风险面。真机验收项专门收口逐字措辞。
- **[具名赞/回复控件匹配引入 locale 耦合，可能漏检 → 确认率下降]** → 服务器 base64 id 是语言无关的并行判据，两者几乎同时出现（真机 99ms 内），单条漏检不致命；漏检方向是「少报成功 → 落诚实非成功」，安全侧。
- **[删刷新腿后，若就地渲染真的坏死（SPA 卡住），失去唯一的「重新拿真相」手段]** → 真机两跑显示就地渲染在 3 秒内稳定收敛；且刷新腿实测**本身就在制造假阴性**，留着的净收益为负。窗口耗尽仍诚实回非成功（不假绿），与今天同侧。
- **[「已拒绝」渲染时机若晚于确认窗]** → 用户实证「发布后就出现」，落在窗内。若真机发现有延迟拒绝的变体，那属于「确认时确实成功、之后被拒」——超出提交期判定的能力边界，需另开事后对账（明确列为 Non-Goal）。
- **[本 change 推翻两条已归档 spec 要求，与历史 change 的验收记录冲突]** → 通过 delta spec 显式撤销并写明真机证据来源，归档时以本 change 为准；不静默留旧要求。
- **[桩测盲区]** → 三态判别全在页内 JS，FakeCdp 桩不了。单测只能覆盖正则/纯函数层；行为正确性依赖真机验收，必须进 backlog，不得以「单测全绿」冒充验收。

## Migration Plan

1. edge 侧改动 + 单测（正则/纯函数层）→ `npm run test:acceptance` → `npm test` → `npm run typecheck`。
2. cloud 侧加 outcome 映射 + 卡片文案 → 同上三件套 → 按默认序列部署 dev。
3. 探针补丁回写 `scripts/fb-comment-verify-probe.ts`（每帧存 `nodeText` + 时间戳 `<a>` 回落），否则下次仍测不到「发布中」。
4. 真机验收（见 backlog 簇）：①被拒评论不判成功、落独立档、不打去重；②正常评论仍约 3 秒确认成功（零回归）；③在飞态不被误判终态。
5. **回滚**：edge 侧行为改动集中在确认段，回滚 = revert 该提交并重建安装包；cloud 侧新 outcome 未知值会落既有 `default` 分支（`submit_failed`），不会崩——但**注意**这会重新变成「不打去重 → 可重试」，与被拒语义一致，回滚安全。

## Open Questions

- 「已拒绝」的具体 reason 字符串命名（`comment_rejected` / `rejected_by_platform`）与飞书卡文案措辞——实装时定，不阻塞。
- 越南语「已拒绝 / 查看反馈」的逐字措辞未知（真机只有简体中文样本）→ 真机验收项收口；在此之前正则留超集 + 漏检安全回落。
- 「发布中」窗口耗尽仍在飞时，是复用 `verification_ambiguous` 还是新增「提交未定」档——倾向复用既有档（它语义正是「提交了、没确认」）并在日志/分诊里带上在飞证据，避免枚举膨胀；实装时定。

## ADDED Requirements

### Requirement: 同意条按钮的采集作用域由同意语义自身界定

同意条接受按钮的采集范围 MUST 由同意语义自身界定：只有当某个候选容器**自身文本命中 cookie 政策语义文案**时，采集才可以收窄到该容器；否则 MUST 在整个文档上采集。系统 MUST NOT 把「页面上首个可见对话框」当作采集框——同意条在 Facebook 上常以**非对话框的底部横幅**呈现，而首页常年挂着与同意无关的良性对话框（聊天弹窗 / 加载浮层）；一旦采集框落到良性对话框上，接受按钮永远采不到，判定却仍成立「有同意条」，于是每一个受同意闸保护的动作（评论 / 点赞 / 发帖 / 加群 / 滚动 / 刷新）都会被判成被同意条阻断。

采集到多个符合当前策略的按钮时的处置口径，MUST 与本能力既有的「策略所需按钮缺失时绝不改点另一个按钮」红线保持一致：无论选取哪一个，被点的按钮 MUST 是当前策略所要求的那一类。

#### Scenario: 良性对话框在场时仍能采到底部同意横幅的按钮

- **WHEN** 页面同时存在一个不含 cookie 文案的可见对话框与一条非对话框的底部 cookie 同意横幅
- **THEN** 接受按钮在整个文档范围内被采到，策略所需的点位可用
- **AND** 该动作不因采集不到按钮而被判成被同意条阻断

#### Scenario: 同意条本身就是对话框时收窄到它

- **WHEN** 承载 cookie 政策文案的容器自身就是一个可见对话框
- **THEN** 采集收窄到该容器
- **AND** 采集结果只包含该同意条内的按钮

### Requirement: 无可点接受按钮即不成立同意条，受闸动作照常继续

「存在同意条」的判定 MUST 是一组**合取**条件，其中 MUST 包含「至少存在一个可点的接受按钮」这一项；仅凭 cookie 政策文案成立即判「存在同意条」是被禁止的。当页面存在 cookie 文案但按钮词表全不命中时，系统 MUST 判「不存在同意条」并让调用方照常继续，MUST NOT 把受同意闸保护的动作判成被同意条阻断。

该判定还被同一层的阻断分类复用（真登录墙的识别以「不存在同意条」为前置条件），因此一个假成立的「存在同意条」不仅会误阻动作，还会**掩盖真登录墙**：带 cookie 文案的登录墙会被报成同意条阻断而拿不到登录所需的处置。判定 MUST NOT 出现这种假成立。

#### Scenario: 文案在页但按钮词表未命中时放行

- **WHEN** 页面命中 cookie 政策文案，但可见控件里没有任何符合接受按钮词表的控件
- **THEN** 判定为「不存在同意条」，调用方继续原动作
- **AND** 不产生任何被同意条阻断的失败回执

#### Scenario: 带 cookie 文案的登录墙仍被识别为登录门

- **WHEN** 页面是真登录墙（含登录语义文案、无 cookie 接受按钮），且页面上同时存在 cookie 政策文案
- **THEN** 判定为「不存在同意条」，阻断分类给出登录门结论
- **AND** 该动作不被报成被同意条阻断

### Requirement: 同意探测失败降级为「无同意条」，绝不把命令变成引擎错误

同意条探测本身失败（求值失败、结果无法解码等）时，系统 MUST 既不假设存在同意条、也不假成功，MUST 当作「无同意条」让既有各闸继续处置，并记录该次探测失败。探测失败 MUST NOT 被上抛成使整条动作命令失败的引擎错误——探测是动作前的一道旁路检查，它自身的失败不构成动作失败的证据。

#### Scenario: 探测求值失败时动作照常继续

- **WHEN** 动作前的同意条探测抛出失败
- **THEN** 该次探测被记录为失败并按「无同意条」继续
- **AND** 动作命令不因该失败而终止为引擎错误

### Requirement: 同意闸的失败按可诊断的档位区分并在回执中可观测

同意闸的失败 MUST 至少区分两档：**认出同意条但策略所需按钮定位不到**（文案 / 布局漂移，可诊断、可修词表），与**点击到重试上限仍未清除横幅**（升级停手）。把两者折叠成同一个原因，会让「词表该更新了」与「平台真的挡住了」在运营侧不可分。系统 MUST NOT 为此引入在消费侧没有归宿的新原因码：可复用既有的诚实原因码，或把档位落在回执的诊断 / 观测字段里，但两档 MUST 可分。

同意闸的处理结果 MUST 可观测地表达「是否探到同意条」「是否已清除」「尝试了几次」，使「探到了但没清掉」与「压根没探到」在回执上不同。

#### Scenario: 按钮定位失败与横幅清不掉是两档

- **WHEN** 一次动作因策略所需接受按钮定位不到而失败，另一次动作因点击到上限仍检出横幅而失败
- **THEN** 两次失败在回执上可区分
- **AND** 两者都不谎报成功，且所用的表达方式在消费侧有归宿

#### Scenario: 回执区分「没探到」与「探到没清掉」

- **WHEN** 一次动作前未探到同意条，另一次探到同意条但未能清除
- **THEN** 两次的回执分别体现「未探到」与「探到且未清除 + 尝试次数」
- **AND** 不新增边云协议消息类型

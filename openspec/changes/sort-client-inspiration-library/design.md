## Context

客户灵感库当前以 `updated_at DESC` 在 Cloud 中分页，Edge 每页读取 12 条，并按环境保存“未创作 / 已创作 / 全部”、页码和滚动位置。客户已经能看到点赞、收藏与评论快照，但不能按这些信号找出更值得参考的内容。

排序跨越客户鉴权 HTTP、Cloud 存储查询、Electron 主进程 IPC 与渲染层。安全边界保持不变：渲染层不能提交账号 id、任意 URL、SQL 字段或鉴权头；Cloud 必须从 `envKey` 重新解析当前客户所拥有的账号。当前精选池共 432 行、9 个账号，单账号最大 173 行，并有每账号 1000 行保留上限。

并行变更 `normalize-source-published-time` 会触及同一 Store、DTO 与灵感卡片文件；开发使用独立 worktree，最终集成和部署必须串行并在最新默认分支上重验。

## Goals / Non-Goals

**Goals:**

- 在当前账号和当前筛选条件下提供综合热度、收藏、点赞和最近更新四种服务端排序。
- 综合热度固定为 `点赞 + 收藏 × 1.43`，并保持缺失计数与真实零值的区别。
- 排序发生在 `LIMIT/OFFSET` 前，当前页、分页总数和排序使用同一筛选范围。
- 提供清晰、克制、可访问、窄窗口可用的客户排序控件，并按环境恢复状态。
- 排序请求期间保留已有列表；失败时恢复已确认的排序和内容，不制造空池假象。

**Non-Goals:**

- 不增加 `weighted_score` 列、触发器、回填、表达式索引或缓存层。
- 不实时回小红书刷新热度，不把快照排序描述为实时排名。
- 不增加升序、任意字段排序、客户自定义权重或 Console 排序。
- 不改变精选准入、保留上限、筛选归类、详情或参考创作行为。
- 不构建或发布 Edge 安装包。

## Decisions

### 1. Cloud 查询时使用整数化表达式，不持久化派生列

综合热度使用 `like_count::bigint * 100 + collect_count::bigint * 143` 排序，等价于把点赞记 1 分、收藏记 1.43 分。`bigint` 避免大计数乘权后的 `int` 溢出，整数权重避免浮点比较误差。

派生列会要求每次热度刷新同步更新，并在权重调整时回填；生成列虽然能避免同步漂移，但仍把产品公式固化进 schema。当前单账号上限 1000 行，数据库内部计算和 top-N 排序成本可忽略，因此不增加列或索引。若未来解除上限并由真实查询指标证明排序变慢，优先增加与固定表达式一致的账号级表达式索引，而不是复制数据。

### 2. 固定排序白名单映射到静态 SQL 片段

客户 API、Electron 主进程和 Store 使用同一语义集合：`weighted | collects | likes | recent`。Cloud 只从固定映射选择 `ORDER BY`，绝不把请求字符串拼成 SQL 标识符。

- `weighted`: 完整综合分降序；点赞或收藏任一缺失则该分为 NULL 并排在完整证据之后。
- `collects`: 收藏降序、点赞作为次级热度信号。
- `likes`: 点赞降序、收藏作为次级热度信号。
- `recent`: 保持当前 `updated_at DESC` 行为。

所有排序最终使用 `counts_captured_at DESC NULLS LAST, updated_at DESC, id DESC`（`recent` 使用 `updated_at DESC, id DESC`）形成稳定顺序。NULL 不 `COALESCE` 为 0，避免把“没抓到”伪装成真实零值。

### 3. 排序在账号、创作状态筛选后和分页前完成

`CuratedContentStore.listForClient` 继续先构造账号与 creation-status 条件，再把固定 `ORDER BY` 放在 `LIMIT/OFFSET` 前。`COUNT(*) OVER()` 继续给出同一筛选范围的总数。数据库可能遍历当前账号候选行，但只向 Cloud/Edge 返回当前页；不会把整个精选池交给客户端。

### 4. Edge 只传枚举排序值并按环境保存

主进程 `curated:list` IPC 验证排序枚举并将其编码进固定 customer-auth 路径。渲染层环境状态增加 `sort`，默认 `weighted`；切换筛选时保留排序，切换排序时回到第一页并清零列表滚动位置，从详情返回恢复排序、筛选、页码和滚动位置。不同环境状态相互隔离，迟到回包继续由现有 envId + epoch 闸丢弃。

### 5. 排序控件属于列表工具栏，不属于全局标题栏或筛选标签

桌面宽度下，左侧保留三段筛选，右侧组成“总数 + 排序下拉”；最小窗口附近工具栏换行，筛选占一行，总数和排序占下一行。排序使用白色、浅灰蓝边框的 32px 次级工具按钮，不使用主操作实底色，也不做成第二组分段标签。

下拉菜单展示“综合热度 / 收藏最多 / 点赞最多 / 最近更新”，综合项辅以“点赞 + 收藏 × 1.43”，底部说明依据最近一次采集的赞藏数据。菜单使用 checked option、`aria-haspopup=listbox`、`aria-expanded`、方向键、Enter、Escape 和外部点击关闭。

### 6. 排序刷新保留已确认内容并可回滚

客户切换排序时立即更新控件待选态、禁用重复操作、保留原卡片并轻微淡化，同时显示细进度提示。成功回包后原子替换为第一页新顺序；普通网络或服务失败时恢复先前排序、页码、滚动位置和卡片，并显示“排序未更新，请重试”。会话失效、环境撤权、绑定未知/冲突/不可证实时不得继续显示缓存内容，必须清除列表并进入现有具名 fail-closed 状态。初次进入、筛选或分页仍可使用现有全列表加载态。

## Risks / Trade-offs

- [热度是采集快照而非实时值] → 菜单明确说明数据来源，缺失值继续显示“暂无数据”，不使用“实时热度”文案。
- [热度刷新可能使 OFFSET 分页期间顺序变化] → 使用稳定次级排序减少同分抖动；当前刷新频率和每账号上限下接受该一致性，暂不引入游标快照。
- [并行来源发布时间变更发生文件冲突] → 独立开发、串行集成，在最新默认分支上合并并重跑 Cloud/Edge 全部门禁。
- [自定义下拉增加交互复杂度] → 锁定键盘、外部关闭、焦点和 aria 回归测试；不引入第三方 UI 依赖。
- [公式文案与服务端漂移] → OpenSpec 固定 1.43，Cloud 查询测试与 Edge 文案测试同时锁定；未来改权重必须作为契约变更同步两仓。

## Migration Plan

1. 先合并并部署 Cloud：旧 Edge 不传 `sort` 时服务端默认 `weighted`；列表响应结构保持兼容。
2. 再合并 Edge 源码；不构建安装包，已安装客户端继续使用旧 UI。
3. Cloud 部署到 `dev` 后以客户鉴权接口验证四种排序、非法值拒绝和分页总数。
4. 回滚时先回滚 Edge 源码，再恢复 Cloud 上一备份；没有数据库列或数据回滚。

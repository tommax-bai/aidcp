## Context

边缘节点(aidcp-edge)在本机 macOS 运行,连云端 ECS。它经 CDP(DevTools)WebSocket 驱动一个本机 Chrome;该 WS **连的是某个具体 page target**(由域名过滤挑出),不是浏览器本身。已有的 `browse-loop-resilience` 规定:CDP 意外断开时有界自愈(重发现 target → 重连 → 续跑),耗尽则「诚实终止」。

现状落地有一处与红线相悖的缺口:不可恢复终态时,边缘只停掉后台监测、却**保持边-云连接开着**(`main.ts:316-319`),既不诚实下线也不退出。云端「在线」是纯连接存活判据(连接 OPEN 且最近活跃在 `staleAfterMs≈75s` 内,且任意入站帧/心跳刷新活跃时间,`ws-server.ts:186-190`),无浏览器能力维度;于是失去浏览器的节点最长一个窗口内仍被算在线、仍被账号→节点路由(`resolveEdgeIdForAccount`)选中派活(含真实账号发帖)。这是「MUST NOT 静默假成功」在连接/能力层的翻版。

且本机当前没有任何东西会重启退出的边缘:单机裸跑 `npm start` 无看护;多节点启动器 `scripts/launch-multinode.ts` 的子进程退出只打日志、不重起。要让「节点失去浏览器」可被安全恢复,必须同时补**诚实下线**与**有看护的回收重起**。

本设计经一道「业界方案 + 对抗评审」编排产出,三道评审(过度设计 / 约束违背 / 失败模式)一致认可方向,并揪出 3 个会让方案原地复现僵尸的硬伤,已全部折叠进下列决策。

## Goals / Non-Goals

**Goals:**
- 不可恢复终态 → **主动诚实下线**(关闭边-云连接使云端立即停止路由)+ **以可重起语义退出**,结构性消灭「在线但无能力」僵尸。
- **进程外、crash-only 回收**:看护进程按固定槽位有界重起,复用同一登录目录起全新浏览器;云端凭重连自动重置会话,**云端零业务码改动**。
- **崩溃循环有界 + 诚实放弃**:连续失败到顶不再无限重起,留节点死着 + 诚实日志,兄弟节点不受影响。
- **真账号发布零重复**:回收撞上在途发布 → 先诚实判失败再退,提交为最后不可逆步。
- **零新增云边协议消息**(免协议四处同步)。

**Non-Goals:**
- 不做 in-process Chrome 回收(保持边缘「一进程一浏览器」不变量,避免拆 teardown 的风险与僵尸/下线时序坑)。
- 不给云端在线判据加浏览器能力维度、不做云端主动能力探测。
- 不做「开新标签页」式重连快补(经 2026-06-24 两次真机复现:页面 target 归零基本不可恢复,整副重起更干净)。
- launchd 之类「重启/登出后存活」外层仅作文档,非主引擎。
- 不改复用模式 / 单机开发的现有工作流(它们连不上时只诚实退出、不回收外部浏览器)。

## Decisions

### D1. 恢复落点 = 进程外 crash-only,而非 in-process 回收
节点终态 → 诚实下线 + 进程退出(可重起退出码);看护进程重起。**为何非 in-process**:① in-process 回收若保持连接开着,正是静默假成功违背(云端无能力维度仍会派活);进程退出关闭连接、立即让云端掉线清理生效、移除路由目标,零协议改动。② 2026-06-24 真机两次复现「浏览器活着但 page target 归零」不可恢复,整副新进程+新浏览器最大限度抖掉脏状态。③ 边缘保持薄:边缘核心只做机械的「终态→下线+退出」,**全部重起/退避/放弃策略落看护层**(本就是「编排在边缘核心之外」的层)。④ 云端重连已幂等(掉线 teardown + 新握手 → 重置会话),Happy path 云端无需改。业界对应:crash-only software(Candea & Fox)+ 带重起节流的 supervisor(OTP one-for-one / k8s CrashLoopBackOff)。

### D2. 看护机制 = 启动器内重起循环;launchd 仅文档
在 `launch-multinode.ts` 的子进程退出处加「有界重起 + 退避 + 诚实放弃」。**为何非 launchd 为主引擎**:launchd 的 KeepAlive+ThrottleInterval 只能限速、会永远重起,**没有干净的「试了 N 次、诚实判定节点永久下线」终态**,而诚实失败红线要求这个终态。launchd 仅作为「看护进程自身在重启/登出后存活」的可选外层写进文档。单机裸跑 `npm start` 无看护 —— 终态就诚实退出一次,开发者手动重起,**行为与多节点一致,只是无人重起**。

### D3. 终态分类 + 快判,避免每轮烧满重连预算 〔评审 MAJOR⑦〕
断连(page-WS close)时**先探一次浏览器进程级端点**(GET /json/version):
- 探测失败(端口拒连)→ 浏览器进程已死 = 终态,**立即回收,跳过重连**。
- 探测通过但无可用 page target(重发现持续找不到)→ 浏览器活着但页面归零(窗口被关 / 标签崩,`chrome-launcher.ts:473-474`),按 06-24 经验**亦判终态、立即回收**,不在病浏览器上磨满重连。
- 仅当探测通过且 page target 复现 → 走既有有界重连(透明续跑)。
把快判放在**进入重连之前**(而非只在重连耗尽后),让主导失败case从约 90s/数十秒坍缩到近零,也缩短每个崩溃循环周期。

### D4. 诚实下线必须「等连接真关闭再退」〔评审 BLOCKER①〕
关闭边-云连接只是**发起**关闭握手;若紧接着同步退进程,关闭帧可能没刷上线,云端收不到干净关闭 → 最长 `staleAfterMs` 内仍当其在线、仍路由(含发帖)→ 僵尸复活。决策:退出路径改异步,**await 连接 'close' 事件(带 ~1-2s 上限)再退**;加回归测试断言云端侧观察到的是干净关闭、非超时/RST。

### D5. 回收前确认旧浏览器真死、端口/登录锁真空再退 〔评审 BLOCKER②〕
杀浏览器是异步 SIGTERM,进程却可能在浏览器真退前就退了 → 端口与单例登录锁未释放 → 新进程被 `clearStaleSingletonLock` **诚实拒启**(锁被活进程占,`chrome-launcher.ts:239-244`)→ 把重起预算烧光、自锁死。决策:**确认屏障放在仍活着的旧进程**:杀后轮询端口探测到空(SIGTERM 不生效则升级 SIGKILL),再退。屏障不能放在已退出的进程里,也不可只信 kill 返回。

### D6. 看护进程杀进程模型修复(前置必做)〔评审 BLOCKER③〕
启动器以 shell 起 `npm start`,杀信号只到外壳 `/bin/sh`,真正的执行体(node/tsx)及其自启 Chrome 被孤儿化、霸占端口+锁 → 边缘的关机路径(唯一调真 kill 的地方)永不运行 → 后续重起全堵。决策:**直接拉起执行体(去掉 npm/shell 外壳层,直跑 tsx)**,或进程组负 PID 信号,使停止/重起信号真达边缘关机 → 真杀 Chrome。加测试:启动器收到终止信号后**零孤儿边缘 / 零孤儿 Chrome**。**此项最先做**,否则建立在「杀不死的 kill」上的重起逻辑全无意义。

### D7. 崩溃循环预算 = 连续失败计数 + 健康存活清零,而非墙钟窗口 〔评审 MAJOR⑥〕
每轮失败可能耗时数分钟(重连上限 + 登录等待),用「窗口内重起次数」做预算时**滑动窗口永远凑不满 → 永不放弃、无限重起**。决策:① 改「**连续失败计数**」(达到 ACTIVE 并健康存活 ≥ min-uptime 才清零),k8s 式,慢失败击不穿;② **重起子进程的登录等待从 5min 收到 ~30-60s**(headless 无 TTY 无从扫码,登录态本应秒级命中,否则按 crash 快速计入预算)。

### D8. 回收 vs 真关机的退出码仲裁 〔评审 MAJOR⑤〕
关机(SIGINT/SIGTERM)退 0=不重起,回收退非零=请重起。两者都经同一个幂等关机入口,可能撞车致退出码被先到者覆盖 → 要么关机期间误重起、要么真终态被掩成 clean exit 不重起。决策:① 看护进程收到终止信号即置「正在关机」,子进程退出处**无条件抑制重起**(关机优先);② 边缘用「已请求回收」标记,确保真终态即便信号撞入也以回收码退出。两种时序都加测试。

### D9. 在途发布回收契约 = 诚实判失败(用户决策:选项 A)〔评审 MAJOR④〕
回收若发生在一次发帖执行中途 → **先把这次发布诚实判失败**(让飞书看到失败而非半成品)再退,符合诚实失败红线;并确认**提交是发布链最后一个不可逆动作**,保证回收发生在提交前不会留半张帖、不会跨重起在真账号上重复发帖。浏览侧在途互动接受丢失(返回 feed 重入),并复用既有「重连不重放断连前半截动作」约束,确保新握手后不自动重试旧命令。

### D10. env 快照冻结、按固定槽位重起 〔评审 MINOR〕
看护进程把每节点 env(端口=base+i / 登录目录=<base>-<accountId>-<节点号> / accountId / edgeId,且删除复用开关)在启动时**快照冻结**,重起时按**固定 index** 重用该快照,**不重新展开看护进程的活 env**(防复用开关漂移泄漏导致新进程去接管孤儿浏览器)。边缘侧再加一道「回收路径断言本进程独占浏览器、复用开关泄漏即拒回收」的背板。

## Risks / Trade-offs

- [硬杀(无干净关闭帧)时云端最长 `staleAfterMs≈75s` 仍可能短暂当其在线、并被路由] → D4 力求优雅关闭(发干净关闭帧);叠加同 edgeId 重连时云端 `closeEdge` 驱逐旧连接;接受硬杀边角的有界窗口,不为它给云端加能力探测(YAGNI)。
- [高频回收带来同 edgeId 快速重连churn,更频繁触发云端驱逐与会话重置] → 云端零码改动但**加回归测试**:断言快速重连只活一个会话运行时、路由解析到新连接、不广播会话结束(守 a38fb96 不变量);并由看护退避限制 churn 频率。
- [永久误配节点(如缺 accountId 致云端拒握手)会烧满重起预算才放弃] → 可接受(诚实放弃兜底);留「为配置类错误保留专用不重起退出码」的扩展缝,V1 不做。
- [放弃态仅日志 + 云端掉线,运维易漏看] → V1 接受;留「写本地状态标记供面板读取」的缝,后续按需。
- [复用模式节点若误走回收路径,杀是空操作会空转] → handler 按「是否复用」分支:复用模式只诚实退出、不回收;并加断言。

## Migration Plan

落地顺序(edge 为主,**D6 杀进程模型修复最先**):
1. edge:修启动器杀进程模型(D6)→ 抽按固定槽位可重起单元(D10)→ 退出码参数化(D8)→ 断连诚实退出 + 快判分类(D3)+ 确认旧浏览器死(D4/D5)→ 回收 vs 关机仲裁(D8)→ 看护重起预算/退避/诚实放弃(D7)→ 在途发布诚实判失败(D9)。
2. edge 验证:单测(快判分类 / 回收时序 / 重起预算 / 多节点隔离 / 单机终态只退不重起)+ `test:acceptance` + 全量 + `typecheck`。
3. cloud:零业务码;加回归测试守 a38fb96 不变量(高频回收快速重连)。
4. 本仓:`openspec validate --strict`,sub-repo 任务全绿后归档。

**回滚**:本变更主要是 edge 本地行为 + 看护脚本,无云端码、无协议、无数据库迁移;回滚即还原 edge 提交(终态退回「停后台监测、被动等云端看门狗」旧行为)。无部署级回滚耦合。

## Open Questions

- 崩溃循环放弃阈值默认值(连续失败 5 次 + min-uptime 60s)是否合适,后续按真机观感调。
- 全队节点都放弃时,看护进程是「留活记日志」还是「退非零让外层 launchd 复活看护进程自身」—— V1 默认留活记日志。
- 启动器杀进程修复采「直跑 tsx」还是「进程组负 PID 信号」—— 默认直跑 tsx(最简、去掉 npm/shell 间接层);如需保留 npm 脚本间接层再换进程组方案。

## Why

通知巡视现在「奔着收尾去」而非「奔着清零去」：分诊每类只看一眼、标记已处理、最多 3 轮、不回头。加上边缘是「边沿触发」——只在「无未读→有未读」翻转时上报一次。两者叠加产生一个隐性失聋：**一旦某趟巡视没把平台未读真清零，未读就永久为真 → 再不会有「无→有」翻转 → 边缘不再上报 → 机器人对后续所有通知装聋**（一个会话基本只巡视一次）。

真机探针（`aidcp-edge/scripts/notification-clear-probe.ts`）已证明「看一眼某分类能让平台服务端把该类未读清零」（赞收藏 1→0、新增关注 1→0，重载确认服务端真清、入口红点 4→0，生产 tab 选择器全部命中；评论/@ 人工确认同样可清）。既然清零可靠，正解就是让巡视**真把三类未读都扫到零**——清零本身成为天然且正确的再触发节律，那个「已处理过（epoch）」闸随之多余。

## What Changes

- 分诊循环语义：从「≤3 轮 + 标记已处理、不回头」改为「**循环直到首页三栏未读计数全部为 0**」；每处理完一类**重读**三栏计数，仍有未读就继续下一类/下一轮。
- 循环有界 + 诚实放弃：设最大尝试上限；某类到上限仍清不掉（选择器漂移 / 平台不认动作）→ 记日志并停止该类，**不空转、不假报已清**（红线：MUST NOT 静默假成功）。
- **BREAKING（巡视行为）**：去掉准入闸里的 epoch「已处理过」判定（`lastHandledEpoch` 比较），按「真有新消息」即处理；**保留**「正在处理中」闸（防并发第二趟）与硬暂停闸（验证码/人工接管）。新一波在巡视途中到达时，由正在跑的循环自然吸收，不再被丢弃。
- 三类都「清零」、但飞书通知仍只发评论/@：赞/关注「看一眼即清」（已验证），评论/@ 抽取内容并推飞书。原「忽略赞/藏/关注」表述更正为「这三类都要看以清未读，只是不为赞/关注发飞书」。
- 评论/@ 浏览改为「**滚到底 / 直到不再有新项或角标清零**」而非固定 3 屏滚动——避免未读条数多于一屏窗口时清不干净。
- 显式区分两种「去重」并**保留飞书通知去重水位**（`notifiedItemKeys`）：删的是「巡视触发去重（epoch）」，留的是「飞书通知去重（防重复打扰）」——扫得更勤更需要它，二者不可连带误删。
- 文档化：「看一眼可清零」是 loop-to-zero 的承载假设；保留「按计数增量触发」作为某类将来被证实不可清时的兜底（仅该类、次选，优先清零）。
- 校准项（低优先）：入口红点 count 与首页三栏求和口径不一致（探针实测入口 4 vs 三栏 2）；reconcile 两处扫描判据，使触发信号与「清零」终止信号一致。

### Modified Capabilities
- `notification-monitoring`: 巡视的「清零/再触发/去重」模型变更——分诊循环到三栏未读全 0（有界 + 诚实放弃）；去掉 epoch「已处理过」准入闸、保留「正在处理中」与硬暂停闸；三类均看以清未读、飞书仍只发评论/@；飞书通知去重水位明确保留。

## Impact

- **云端（aidcp-cloud）**：`agents/notification-triage.ts`（循环到零 + 重读计数）、`agents/notification-gatekeeper.ts`（去 epoch 闸）、`agents/session-context.ts`（清理 `lastHandledEpoch`、保留 `notifiedItemKeys`）、相关 per-category 浏览角色与 `agents/excursion-resumer.ts`（终止/收敛口径随循环语义调整）。
- **边缘（aidcp-edge）**：`browse/browse-session.ts` 评论/@ 浏览（滚到底 / 直到清零）；`browse/notification-monitor.ts` 触发与入口/per-tab 计数口径校准。赞/关注「看一眼」保持。
- **协议**：不新增 cloud↔edge 消息类型；沿用现有 `notification.*` 通道与 `browse_notification_*` 命令。
- **测试**：分诊「循环到零 + 有界放弃」单测、gatekeeper「去 epoch、保留 active/硬暂停」回归、飞书去重水位保留回归；真机校准评论/@ 清零（探针已就位，可复跑）。
- **依赖/顺序**：`notification-monitoring` 能力由仍在进行的 `notification-monitor` change（34/38）引入、尚未合并到 `openspec/specs/`；本 change 的 delta 逻辑上在其归档后叠加。安全红线沿用：诚实失败不静默假成功、风控/发布闸不漂移。

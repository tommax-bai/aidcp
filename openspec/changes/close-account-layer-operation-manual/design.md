## Context

### 现状（2026-08-06 实读快照）

集中式操作登记表已经是**真闸**，不是文档：

| 消费方 | 位置 | 用它干什么 |
| --- | --- | --- |
| 云端出口 | `aidcp-cloud/src/comm/ws-server.ts:333` | 未登记拒发，日志 `operation_unclassified` |
| 边缘入口 | `aidcp-edge/src/client/edge-client.ts:707` | 未登记拒收，**位于路由分支之前** |

描述符四维：类别 / 传输 / 身份 / 浏览器前置。Cloud→Edge 46 条，客户端 29 条。

### 问题：同一份知识有四份，登记表只是其中一份

| # | 副本 | 位置 | 由谁守 |
| --- | --- | --- | --- |
| 1 | 登记表 | 两仓 + 派生仓 | 跨仓对表闸（`scripts/operation-registry-parity`） |
| 2 | 路由分支 | `edge-client.ts:738–884` 一长串 `env.type === '…'` | `align-cloud-edge-operation-registries` 新加的反向结构断言 |
| 3 | 测试手抄清单 | `test/client/operation-registry.test.ts` 的 `routedActiveCommands`（46 条） | **无人守**（它自己就是断言的一侧） |
| 4 | 身份救援清单 | `identity-command-gate.ts` 的 `IDENTITY_RESCUE_OPERATIONS`（6 条） | **无人守** |

副本 2 是 CLAUDE.md §2 点名的「第 4 处协议同步点，typecheck 抓不到」，已经吃过一次亏。副本 3、4 至今没有任何机械手段。

### 判据里缺的那一维

刚归档的 `edge-addressing-layers` 有四条尺子，第③条是「判错了会不会**在平台上留痕**」。这条线同时决定了本仓最贵的那类错误的边界——**可重放 vs 不可重放**（CLAUDE.md §2：「重投一条可能已上墙的内容是本仓代价最高的错误」）。

它今天在代码里**没有任何机读形态**——但**事实本身已经散落在协议注释里**，只是人读的：`interaction.reply.reconcile` 注着「只核验既有 attempt，绝不发起新平台写」，`interaction.offboard.result` 注着「可重放的凭证清理结果」。有人已经逐条想清楚过，只是想清楚的结果落在了注释里，没有任何东西消费它、也没有任何东西守着它不漂。本 change 做的就是把这份既有判断收进登记表并架上闸。

## Goals / Non-Goals

**Goals:**

- 给登记表补上「平台留痕」这一维，让尺子第③条第一次有机读形态
- 用它机械约束身份救援清单的成员资格，堵住「误把留痕命令放进救援清单」这条路
- 删掉能安全删的那一份手抄（副本 3），四份降到三份
- 为后续两步（可重放动作 / 不可逆动作的检查拆分）铺好前置

**Non-Goals:**

- 不改任何命令的运行时放行 / 拒绝行为（新维只被测试断言消费）
- 不动两份 `protocol.ts`、动作↔消息映射、消息类型集合
- 不删身份救援清单本体（理由见决策二）
- 不把登记表展开到 `publish.command` 的 kind 粒度（理由见决策四）
- 不解决「路由分支本身是手抄的」（副本 2）——它由已落地的反向结构断言守着，物理消除属后续「划边界落到代码」的范围

## Decisions

### 决策一：补的是「平台留痕」，不是「所属层」

**先走过的弯路（记下来防止重走）**：第一直觉是给登记表补一个「所属层」字段（宿主 / 环境 / 翻译 / 账号），让刚落地的分层判据有机读落点。**推翻它的是逐条代入救援清单**：

| 救援清单成员 | 按层判 | 今天的行为 |
| --- | --- | --- |
| `identity.read_current` / `read_self_profile` | 翻译层 → 放行 | 放行 ✓ |
| `captcha.assist.capture` / `click` | 环境层 → 放行 | 放行 ✓ |
| `edge.task.release` | **账号层** → 拦 | **放行** ✗ |
| `session.end` | **账号层** → 拦 | **放行** ✗ |

层字段复现不了这张清单。读闸自己的注释可知真正的判据是**合取**：「不在平台留痕」**且**「拦掉它会让节点更难救」。后一条不是命令的固有属性，是该闸相对「身份未落定」这个特定终局的策略。

**所以：能进登记表的只有前一条**——它是命令的固有属性，且正是尺子第③条。层字段的处置见决策五。

### 决策二：救援清单保留，但成员资格由登记表机械约束

不把清单推导掉，因为推导不出来（决策一）。硬推导等于**把策略伪装成事实**——那正是本仓反复付代价的形态。

改为单向包含断言：

```
救援清单 ⊆ { 登记表里声明为「不留痕」的命令 }
```

- 误把一条会留痕的命令加进救援清单 ⇒ 测试当场红。**这是这张清单唯一的危险方向**（少放行一条只是更难救，多放行一条会在未知身份下真发内容、记错账）。
- 反方向**不断言**：「不留痕」不蕴含「该放行」。反例现成——`edge.task.acquire` 不留痕，但今天照拦（认领租约是执行代表账号动作的前置准入）。写成双向就是把两个不同的问题焊在一起。

### 决策三：删测试里那份 46 条手抄清单（副本 3），但必须先变异验证

删它的论据是**两个方向都已被覆盖**：

- 「登记表有、源码漏路由」→ `align-cloud-edge-operation-registries` 的反向结构断言（以登记表为事实源、逐条去源码找分派点，带 ≥25 条防空转下限）
- 「源码路由了一条未登记命令」→ **结构上不可能**：入口 fail-closed 闸在 `edge-client.ts:707`，路由分支从 `:738` 起，未登记的命令根本走不到路由

**但论据不等于事实。** 删除前 MUST 各跑一次变异：摘一条路由分支 → 反向断言必须红；构造一条未登记类型走到路由 → 必须被入口闸拦下。任一条验不出来，就**保留清单并写明它守的是哪个方向**——留一份有理由的手抄，好过删掉一份其实还在干活的。

### 决策四：留痕维按消息类型取「最坏一档」，MUST NOT 按 kind 展开

`publish.command` 一条消息类型下有多种原子（填标题、选图、点提交），只有最后一个真留痕。登记表按**消息类型**编址，表达不了这个差异。

**裁定：取该消息类型下最保守的一档**（`publish.command` ⇒ 会留痕）。理由：这一维的用途是划「能不能重放」，而重放判断错在保守侧只是多一次人工确认，错在激进侧就是重复对外写入。

**MUST NOT 在登记表里按 kind 展开。** 展开就是在按消息类型编址的表里塞进另一套编址——即第二张表。kind 级细分若将来真需要，落在发布链自己那层。

**同理两条边界裁定**：

- **只算直接后果，不算间接触发。** `automation.start` / `edge.task.acquire` 会让后续留痕动作成为可能，但它们自己不产生任何对象。算进间接，则一切操作最终都留痕，这一维退化成恒真、失去全部区分力。拦这类操作的理由是**准入**，不是留痕（决策二那条反例正是它）。
- **本地 IPC 那份 29 条不加这一维。** 它不经过身份闸、不参与重放决策——两个消费方一个都不沾。给它加，就是决策五自己反对的那件事：一个没有闸消费的标注，必然漂移，且看起来像事实源。

### 决策五：所属层不进登记表（这一轮）

层字段今天**没有消费方**。本仓的教训是：没有闸消费的标注必然漂移，而漂移的标注比没有标注更坏——它看起来像事实源。

分层落到代码的粒度（标注 + 门禁 vs 物理拆分）是 `edge-addressing-layers` 明文登记的待决问题，本 change 不代它决定。等真有消费方（如跨层直调门禁）再补。

### 决策六：留痕维必须同时进云端那份

不是为了对称。后续「可重放动作的检查拆分」里，**做重放决策的是云端**——重试上限、升级、绝不重放，全在云端侧。这一维在云端的用途比在边缘更直接。

同时也意味着三份副本（边缘 / 云端 / 派生仓 `aidcp-automation`）必须同批更新，派生仓一律走 `scripts/sync-split-repos`，MUST NOT 手工搬（CLAUDE.md §8.1）。

## Risks / Trade-offs

- **[逐条判定 46 条留痕值时判错]** → 判错的方向不对称：判成「留痕」最坏是将来少一次自动重试；判成「不留痕」可能让一条真会写入的命令进救援清单。因此**默认值与未声明一律落在「会留痕」一侧**，且逐条判定 MUST 在 tasks 里留下每条的理由，不批量套用。
- **[归档顺序把措辞改回去]** → `align-cloud-edge-operation-registries` 的未归档 delta 写着「四个字段 MUST 逐字相同」。两条 change 无论谁先归档，后归档的那份都会把主 spec 里的措辞覆盖成自己的。**处置**：本 change 的 delta 一律写「全部描述符字段」不写死数量，并列为归档前置逐条核对。这是本仓有前科的失败形态（归档顺序静默还原定义号）。
- **[删掉副本 3 后其实丢了覆盖]** → 决策三的变异验证就是为此设的；验不出来就不删。
- **[新维被误当成放行依据]** → 类型上无法阻止。**处置**：字段注释与 spec 各写一次「本维 MUST NOT 单独决定放行」，并保留决策二里那条反例（`edge.task.acquire` 不留痕却照拦）作为常驻反面示范。
- **[零运行时变更 ⇒ 看不出做没做]** → 这正是它零真机、零出包、零生产风险的原因，也是它的验收只能靠变异验证的原因。tasks 里每一道新闸都 MUST 配一次变异，摘掉它必须有东西变红。

## Open Questions

- **视频号 API 写入路径不经过页面身份闸**：`interaction.reply.send`（真发私信）登记为 `platform_api_automation` / `bound_account`，而身份闸只拦 `page_account`。也就是说身份未落定时，页面动作被拦、API 私信照发。这可能是真缺口，也可能是有意为之（API 路径的身份由令牌而非页面保证）。**本 change 只登记，不修**——它属于身份闸的判据范围，动它就变成行为变更，与本 change「零运行时变更」的边界冲突。

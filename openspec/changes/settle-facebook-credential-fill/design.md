## Context

Facebook 首登由两层协作：**页面观测层**（Rust 引擎里的 Facebook auth 路由 `06-auth.js`，无跨调用状态、每次探测都是一次全新的页面求值）和**协调层**（`src/native-page-engine/facebook-auth.ts` 的有界协调器，持有节拍、预算与时间窗）。

现状是观测层同时承担了两件不同性质的判断：

1. **结构判断**——页面上有没有唯一的登录表单、两个输入框在不在、提交按钮唯一不唯一、是不是最顶层。这是它该做的。
2. **时间判断**——「填了 25 秒还是空的，就算凭据不可用」。这是它做不好的：它没有跨调用状态，只能拿 `performance.now()`（文档年龄）当时钟，而文档年龄的零点是**页面开始加载**，与「表单出现」「开始敲字」都差着 10–15 秒。

而指纹浏览器的凭据是**逐字符模拟人手敲**的（实测：表单第 ~10.7s 出现 → 邮箱 26–27 字符敲约 4s → 密码第 ~15.2s 开始、约 5 字符/秒 → 第 ~18s 敲完）。观测层的就绪判据只有「两个框都非空」这一条，协调器 500ms 一拍，于是密码第一个字符落下后半秒内就被判成就绪并点击提交。

现有的两道保护都对这个失效模式无感：

- **点击前的 fresh-revalidate**（`facebook/auth.rs:667` `fresh_action_observation`）比对的是**完整 signal id**，而 signal id 的证据里只有按钮的 DOM 路径 / 角色 / 名称 / 类型 / aria-label / 几何、文档代次和信号种类（`06-auth.js:26-48,66-73`）——**不含输入框内容**。密码从 2 位涨到 4 位，id 不变，照点。
- **后置校验**（7s 窗口）只看信号有没有消失、文档有没有换代。提交半截密码后 Facebook 是在**同一文档内**渲染错误文案，所以后置校验拿到的是「没变化」，最终只能给出一个含混的失败原因。

同时协调层这一侧有一处必须一并处理的风险：`dispatchAction`（`facebook-auth.ts:598-613`）把**任何**非 ok 的动作回执都判成 `failed` 终局，而 `fresh_action_observation` 的拒绝路径回的是 `stale_auth_signal` + `EffectPhase::NotStarted`——**明确没有任何输入被发出**。一旦把指纹改成「内容变了 id 就变」，这条拒绝路径会从「几乎不发生」变成「正常竞态下会发生」，若仍按终局处理，等于把「它还在打字」记成「这个环境登不上」，浏览器随即被杀（`main.ts:433` `terminateAfterFacebookAuthFailure`）。这与 `docs/stop-or-continue.md` 的判据直接冲突：同一步在原页面上重来完全可能得到不同结果，它就不是结构性失败。

## Goals / Non-Goals

**Goals:**

- 提交登录**只在凭据不再变化之后**发生；仍在逐字符输入的过程中一律继续等待。
- 「我准备点的这段时间里凭据又变了」必须能被点击前那道复核抓住，且抓住之后**不落终态**、在预算内重来。
- 凭据填充的等待预算从一个与实际输入起点错位的零点，改到与之对齐的零点，并给足代理慢的余量。
- 三条改动共用**一份**具名常量与判据，可在不起浏览器的前提下被用例喂违规输入验证。

**Non-Goals:**

- 不让边缘读取、持有或输入密码。凭据永远只由指纹浏览器填入，这条不变。
- 不去「催」或「重放」指纹浏览器的填充。页面被重绘导致半截内容被清空时，仍走既有的人工登录等待，不新增任何自动补填。
- 不改 `credential_fill_pending` / `credential_fill_unavailable` 这两个原因值，也不改客户端文案与失败归因。
- 不改动 2FA、警告弹窗、推送拦截、Remember Password、广告数据审查、申诉页这些既有信号的判据与窗口。
- 不处理「已经提交过错密码的存量账号」的恢复（checkpoint / 锁定的解除是另一条线）。

## Decisions

### 决策一：安定判据用「同一个 signal id 连续观测到跨越具名时长」，而不是在页面里记状态

**选择**：观测层把两个凭据框内容的**长度**并入 signal id 的证据串；协调层记住上一次看到的 `login_submit_ready` signal id 与首次看到它的时刻，只有当**同一个 id** 被连续观测到、跨度达到安定窗口（`CREDENTIAL_SETTLE_MS = 1500ms`，即 3 拍以上）时才允许下发提交。id 一变就重置计时。

**为什么**：观测层无跨调用状态，要判「变没变」只有三条路——

- *在页面上挂全局变量记住上一次的值*：给页面留下一个可被检测的自有全局，且页面重绘 / 导航后语义含糊，与本仓反检测取向相悖。
- *把上一次的观测值经参数传回去让页面比对*：可行，但等于把时钟和记忆都放在协调层、只把比较放在页面，判据被劈成两半，两边都测不全。
- *把内容长度并入 id，由协调层比 id*：**选它**。协调层本来就持有节拍与时钟，"同一个 id 连续出现" 天然等价于 "结构与内容都没变"；而且这条改动**顺带**就把决策二要的东西做出来了，两个目标一份实现，不会出现"第二份实现悄悄漂移"。

存在先例：`06-auth.js:72` 对 `totp_refresh_required` 已经把输入框的值本身推进过证据串。本次只推**长度**，比既有做法更保守。

**副作用是良性的**：错误文案出现、布局位移都会改变按钮几何 → id 变 → 安定计时重置。方向是"更谨慎地多等一会儿"，不是"更容易点下去"。

**为什么是 1500ms**：实测相邻按键间隔约 100–250ms，邮箱敲完到密码第一个字符的间隔约 220ms。1500ms 给到 6 倍余量，同时只占 45s 填充预算的 3%。

### 决策二：signal id 只并入长度，绝不并入内容

**选择**：证据串里推的是 `${邮箱长度}:${密码长度}`。

**为什么**：signal id 是 SHA-256 摘要、且要跨进程传递并落进日志上下文。长度足以让"又敲进去一个字符"改变 id，而**长度本身不构成凭据**。把明文推进摘要虽然理论上不可逆，但没有任何额外收益，只会让一个本可以完全无关的字段变成需要论证的字段。回执与日志侧维持既有约束：不打印长度、不打印内容。

### 决策三：填充宽限期的锚点改成「两个凭据框首次同时被观测到」，并把这个时间判断整体收进协调层

**选择**：观测层在两个框存在但未填好时**恒回** `none` + `credential_fill_pending`，不再自行宣告 `credential_fill_unavailable`；协调层记住第一次拿到 `credential_fill_pending` 的时刻作为锚点，超过 `CREDENTIAL_FILL_GRACE_MS = 45000ms` 未安定，才进入 `manual_login_required` + `credential_fill_unavailable`。

**为什么改锚点**：现值 25s 从**文档开始加载**起算，而表单第 ~10.7s 才出现、密码第 ~15.2s 才开始敲——真正留给"敲完"的只有约 10s。代理慢一点（这批环境走的是越南住宅代理）就会在敲完之前先判"凭据不可用"。锚在"两个框都出现了"上，量的是正确的那一段。

**为什么整体收进协调层**：观测层只有文档年龄这一个时钟，锚点一旦不是文档零点，它就量不了。协调层本来就持有 `now()` 与整个预算，`enteredTotpWindowStartUnixMs` 已是同款先例（协调层记住状态、观测层只做结构比对）。收进来之后这条判据可以在不起浏览器的前提下被用例直接喂违规输入。

**对外行为不变**：仍然是 `manual_login_required` + `credential_fill_unavailable`，仍然保活当前核心 / 浏览器 / CDP 代次，客户端读到的原因值一个字都没变。spec delta 里把主语从 "Native returns" 改成 "edge enters"。

**为什么是 45s**：实测从"两个框出现"到"敲完"约 7.5s。45s 给到 6 倍余量，且远小于 300s 的外层登录等待门；到点后进入的人工登录态本身是安全态（不设超时、保活会话），所以这个值宁大勿小。

**锚点只认「两个框都在」**：`login_form_hydrating`（还没有带字段的表单）与 `login_fields_hydrating`（两个框没同时出现）都**不**启动计时——那两段是页面自己还没渲染完，不该消耗给填充的预算。

### 决策四：`stale_auth_signal` 且 `not_started` 的登录提交拒绝，是可恢复的，不落终态

**选择**：协调层对 `facebook_auth_submit_login` 增加一条具名分支——回执 `ok=false` 且 `reason=stale_auth_signal` 且 `effectPhase=not_started` 时，**不**判 `failed`，而是丢弃该观测、重新探测、在预算内继续，并计入一个具名的有界重试计数（`MAX_STALE_LOGIN_SIGNAL_RETRIES = 5`）。超出计数才如实失败。

**为什么必须有这条**：决策一二把"内容变了"从"看不见"变成"看得见"，看得见的代价就是这条拒绝路径会在正常竞态下被走到。若不处理，本次改动会把一个静默的错误提交换成一个响亮的假失败——按 `docs/stop-or-continue.md`，"重新探测一次就会拿到新 id 并成功"显然不是结构性失败，MUST NOT 落终态。

**为什么安全**：`fresh_action_observation` 的拒绝发生在 `reserve_signal` 与 `dispatch_pointer_click` **之前**，`EffectPhase::NotStarted` 是"确定没发出任何输入"的权威证据，不是"不知道发没发"。因此这条重来不触碰"提交点是最外层前置"那条红线。含混（`Ambiguous`）与已发出的回执**不**走这条路径，维持既有终局语义。

**为什么有界**：5 次乘以 1.5s 安定窗口远在 45s 填充预算之内；引擎侧 `MAX_CONSUMED_AUTH_SIGNALS = 64` 也不会被这条路径吃掉（被拒的观测不消耗预留）。

### 决策五：不改后置校验窗口

7s（200ms × 35）的后置校验窗口与本次失效模式无关——半截密码被拒是在同一文档内渲染错误文案，加长窗口只会更慢地拿到同一个含混结论。真正的修复是不要提交半截密码。窗口维持原值，且既有的 `auth_postcondition_receipt_window_is_seven_seconds` 断言用例不动。

## Risks / Trade-offs

- **安定窗口选小了，仍会提交半截密码** → 决策四的 `stale_auth_signal` 分支是第二道网：即便安定判断被一次异常的长停顿骗过，点击前的复核仍会因长度变化拒绝下发，且不落终态。两道网必须同时存在，只做其一都不够。
- **安定窗口选大了，登录变慢** → 1.5s 相对于整段填充（约 7.5s）与外层预算（300s）可以忽略；且它只在"两个框都非空"之后才开始计，不影响已登录环境（那类环境根本不出现登录表单）。
- **45s 宽限期让「确实没有凭据」的环境更晚进入人工登录** → 晚 20 秒进入一个不设超时的安全等待态，代价可忽略；反向的错误（敲完之前先判不可用）代价是一次假失败加一次无谓的人工介入。
- **按钮几何抖动导致 id 频繁变化、安定窗口迟迟不满足** → 最坏结果是走到 45s 宽限期到点、进入人工登录等待，属于安全态；不会退化成提交或终局失败。若实测发现该抖动常态化，再单独收窄几何在证据串里的粒度，不在本次范围。
- **把时间判断从观测层搬到协调层，是一次边界移动** → 对外原因值与保活语义完全不变，spec delta 显式改写主语；风险集中在"两边都以为对方在判"，用例侧以"观测层在任何文档年龄下都不再产出 `credential_fill_unavailable`"作为反向断言锁住。
- **实测样本只有三个环境、且都在同一台机器同一批代理上** → 时序常数（10.7s / 15.2s / 5 字符每秒）是这批环境的观测值，不是平台契约。因此三个常数全部按"宁大勿小"取值，并且判据本身不依赖任何具体时序——依赖的是"变没变"，这一条与快慢无关。

## 偏离说明

**A. 回滚旋钮设 0 时走「配置类」终局而非「预算耗尽」终局。** design 只说设 0「逐字退回今天的行为」。实装时发现：若 max=0 仍走预算耗尽出口，回滚后运营会读到一句本不存在的新文案「代理重试预算耗尽（已探测 1 次）」。一个本该「什么都没变」的回滚不该改变回执措辞，故 max=0 直接走配置类出口，与旧行为逐字一致。已加用例锁住。

**B. 决策逻辑抽成纯函数，宿主只做薄接线。** design 未指定分层。实装时发现宿主那段活在 Electron 主进程大闭包里，既有测试手法只能扫源码文本，而文本断言扫不出「这道闸真的会拦」——把重排改成无条件、把预算判反、把不可恢复也放进重排，这些削弱形态在文本断言下全部存活。故把三条出口的判据抽成 `decideProxyPreflightFailure` 纯函数真单测，接线另用契约测试锁。两个变异验证确认：分类器改恒真、删掉重排前的作废，各自被**对应**的那条用例抓红。

**C. 两条用例的断言形式与 tasks 原文不同（能力等价，手段不同）。**
- 5.3 原文要求断言「排在既有等待者之后」。重排落点是「延迟重入既有启动入口」，队尾与受闸是那个入口的结构性后果，不是本次新写的逻辑；真去构造多环境排队需要拉起整个 Electron 主进程闭包。改为断言「必须经既有入口、且不得出现 launchQueue/startEdge 旁路」——旁路正是唯一能绕过队尾与闸的实现方式。
- 5.4 原文要求用探测调用次数断言。重排的执行体同样在主进程闭包里，无法在单测中真调探测。改为断言 `invalidate` 必须先于入队 / 唤醒（顺序断言），变异验证已确认删掉 invalidate 会当场红。**登记为已知的覆盖缺口**：这两条的最终确认落在 6.2 的真机验收项上。

**D. 全量 `npm test` 存在与本改动无关的既有 flaky。** 两次运行失败集不同：一次是 native 引擎会话恢复（EPIPE），一次是互动工作区三项（17–24 秒超时类）。已验证：互动工作区那个文件单独跑 48/48 全过；两个 flaky 文件都不 require 本次改动的任一模块（一个走 jsdom 读 renderer，一个走 native 引擎 client），物理上不可能被影响。本 change 自己的 21 个用例、acceptance 40/40、typecheck 均稳定通过。

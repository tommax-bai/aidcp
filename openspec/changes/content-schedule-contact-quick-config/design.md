## Context

`ContentSchedulePage` 的目录行只携带 `hasContactInfo`，用于决定自动联系评论模式和日上限是否可操作；真正的 `contactInfo` 主数据由账号接口持有。当前账号页已经通过 `PUT /api/accounts/:accountId/contact-info` 写入该字段，并约定非空内容原样保存、全空白输入等价于清空。排期页只显示不可点击的“未配联系方式”，导致运营必须跨页面完成同一前置配置。

## Goals / Non-Goals

**Goals:**

- 在排期页点击缺失提示即可添加当前账号的联系方式。
- 复用账号联系方式的唯一写入端点与原样保存语义。
- 让保存中、保存成功、保存失败三种状态对运营清晰可见，并让自动联系评论门禁始终服从服务端确认状态。
- 用页面级回归测试覆盖直接添加、原样传值、确认后解锁和失败保留草稿。

**Non-Goals:**

- 不新增联系方式字段、Cloud 端点或数据库迁移。
- 不在排期表展示联系方式正文，也不把排期目录扩展成联系方式主数据接口。
- 不改变自动联系评论的调度、配额、审批或一码一号规则。
- 已配置联系方式的编辑仍由账号页承担；本变更只修复“未配”状态下的就地补齐入口。

## Decisions

1. **使用受控 Popover 承载多行输入与显式保存/取消。** 表格中的“未配联系方式”标签本身成为可点击入口，点击后在原位置附近编辑，不发生页面跳转。相比直接用失焦提交，显式按钮能避免运营在表格横向操作时误提交，也能在失败后稳定保留输入内容。
2. **直接调用账号页现有写入端点。** 排期页不创建新 API；非空草稿按原字符串发送，只有 `trim()` 后为空时阻止提交并提示输入。这样保留 emoji、换行和首尾空白，同时避免把“添加”操作变成一次无意义的清空写入。
3. **服务端确认后才解除门禁。** 保存按钮在请求发起时立即显示进行中，排期行在回执前仍保持 `hasContactInfo=false`，自动联系评论控件继续禁用。成功后定点更新 `['config', 'content-schedule']` 缓存中的布尔派生列，再重取排期目录并使账号目录失效；失败时不改缓存、不关闭编辑器，并展示统一映射后的真实错误。
4. **紧凑页面不展示敏感正文。** 保存成功后仅移除缺失提示并解除既有控件门禁，联系方式正文仍只在账号配置入口按需编辑，避免在排期总表横向扩张或泄露长文本。

## Risks / Trade-offs

- **[Risk] 联系方式在请求成功后又被其他会话立即清除，短暂缓存会显示已配置。** → 成功后立即对排期目录做精确失效与服务端重取，最终以 JOIN 派生真态收敛。
- **[Risk] 每行 Popover 增加少量局部组件状态。** → 状态封装在独立的小组件中，只在打开的行持有草稿，不扩展全表数据契约。
- **[Trade-off] 已配置内容不能从排期页修改。** → 这是有意的窄范围：用户当前痛点是“未配”阻断；完整编辑仍保留账号页的既有能力，避免排期页承担联系方式主数据管理。

## MODIFIED Requirements

### Requirement: 巡视分诊循环到未读清零，有界且诚实放弃

通知巡视 SHALL 以「把平台未读扫到零」为目标：分诊每处理完一类后 MUST 重新读取通知首页三栏（评论/@、赞收藏、新增关注）的未读计数，只要任一栏 > 0 就 MUST 继续处理对应分类，直到三栏全部为 0 或达到最大尝试上限。循环 MUST 有界（每趟巡视设最大尝试/轮次上限，作总兜底）。若达到上限仍有某栏未清零（选择器漂移、平台不认动作等），系统 MUST 记录该栏未清原因并停止该趟，MUST NOT 空转、MUST NOT 假报「已清除」（红线：不静默假成功）。

此 SHALL 取代旧的「每类标记已处理、最多 N 轮、不回头」收敛方式——旧方式为「奔着收尾去」，会在某栏一眼没清干净时遗留未读；新方式「奔着清零去」，未清零即重试（有界）。

上句「重新读取通知首页三栏」是一条**跨层可验证的观测终局**，不只是决策端的内部义务：驱动这次重读的那条命令，其终局观测 MUST 是通知首页的三栏未读读数，MUST NOT 是信息流列表读数或任何其他页面的读数。执行端 MUST NOT 把这条命令理解成「回信息流首页」——回信息流是**巡视收尾之后的另一步**，由恢复通道用返回命令单独完成；两步合并会让决策端永远等不到重读结果，使循环在第一类处理完后静默停摆，而每一层的回执都仍然是成功的。该命令的失败 MUST 诚实分型（找不到通知入口 / 点击未生效 / 导航未确认 / 分类栏读不到），读不到分类栏时 MUST 回「未确认」，MUST NOT 回一份全 0 的三栏读数——全 0 会被分诊当作三类均已清零而直接收尾，把一次读取失败静默变成「已清完」。

#### Scenario: 循环直到三栏清零
- **WHEN** 一趟巡视开始且首页存在多类未读（如赞收藏与新增关注各有未读）
- **THEN** 分诊逐类处理并在每类处理后重读三栏计数，直到三栏均为 0 才结束本趟巡视

#### Scenario: 某栏看一眼未清则在上限内重试
- **WHEN** 处理某栏后重读该栏计数仍 > 0
- **THEN** 在最大尝试上限内对该栏再次处理（而非旧方式的「标记已处理不回头」）

#### Scenario: 到上限仍清不掉则诚实放弃
- **WHEN** 达到最大尝试上限后某栏未读仍 > 0
- **THEN** 记录该栏未清原因并结束本趟，不空转、不上报「已清除」，并仍正常恢复浏览

#### Scenario: 一类处理完后回到的是通知首页而非信息流
- **WHEN** 某一分类刚处理完，决策端下发「回通知首页」以挑下一类
- **THEN** 执行端回到（或留在）通知页并以通知首页三栏未读读数作为该命令的终局观测
- **AND** 该命令 MUST NOT 导航到信息流列表、MUST NOT 以信息流列表读数作为终局

#### Scenario: 分类栏读不到时不得回全 0 读数
- **WHEN** 「回通知首页」已落在通知页上，但分类栏在有界等待后仍读不到
- **THEN** 该命令回「未确认」并交由恢复通道收敛
- **AND** MUST NOT 回一份 `评论/@ = 0、赞收藏 = 0、新增关注 = 0` 的读数把读取失败伪装成已清零

## Why

小红书通知巡视的「一类看完、回通知首页挑下一类」这一步，边缘与云端对「首页」的理解不一致：云端指的是**通知页的分类栏那一层**（回去重读三栏未读、好挑下一类），边缘 Native 引擎实现成了**信息流首页**（点发现页链接走人，并回报一屏信息流卡片）。

后果不是报错，而是**回执成功、循环断掉**：

- 云端等的第二次「通知首页三栏未读」永远等不到 → 分诊不再触发 → 既没有正常收尾、也没有失败信号 → 巡视永久挂着 → 该账号的浏览被巡视的暂停开关**无限期按住**。
- 已上线要求「分诊每处理完一类后 MUST 重新读取通知首页三栏的未读计数，只要任一栏 > 0 就 MUST 继续处理对应分类」因此**从未真正生效**：每趟巡视实际只处理优先级最高的那一类。

OL 实测（2026-08-05 14:17，账号 63e2ff05…49ce）：侧栏未读 50 条 → 打开通知页 → 「评论和@」2 条正常抽取并推飞书 → 下发「回通知首页」→ 边缘回到信息流并回报卡片 → 此后 9 分钟内该账号零浏览命令，边缘任务租约 200 秒后过期（租约过期只释放任务、不解巡视）。剩余约 48 条未读所在的「赞和收藏 / 新增关注」两栏**一次都没进去过**。

这是 Native 化切换时改错的语义（`317cd47` 首版即错，`0e8e4b9` 加固时把「回发现页」写得更死了）；退役的 TS 实现是对的——点通知入口 + 重报三栏。两份测试也把这个错误终点当契约锁住了，所以本地全绿。

## What Changes

- 边缘「回通知首页」命令改为**回到 / 留在通知页并重报三栏未读**，与「打开通知页」命令同一套页面判据与三态口径（读不到分类栏时诚实回未确认，MUST NOT 回一份全 0 读数）。
- 明确**回信息流是另一步**：巡视收尾由云端的恢复角色发「返回」命令完成，不由「回通知首页」顺手代劳。
- 修正把错误终点锁成契约的两处测试（行为契约测试的断言、回执声明对账表的条目），并补一条守「回的是通知页、不是信息流」的用例。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `notification-monitoring`：把「每处理完一类后重读三栏」这条要求从云端单侧口径，收紧为**跨层可验证的观测终局**——该步的终局观测必须是通知首页读数，且不得是信息流读数。

## Impact

- `aidcp-edge/native/page-engine/src/xhs-command-router.js` 的「回通知首页」分支（规则脚本在构建期编进 Native 二进制，**改完必须重编引擎才生效**）。
- `aidcp-edge/test/native-page-engine/xhs-navigation-command-contracts.test.ts`、`runtime-contracts-command-receipts.test.ts` 的对应契约。
- 不改协议消息集、不改云端代码、不改风控与配额、不动 Facebook / 微信侧任何路由。
- 云端侧的「巡视停滞总超时兜底」缺口由并行 change 处理，不在本 change 范围内。

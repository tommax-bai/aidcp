# 设计：把「回通知首页」的终局钉在观测上

## 1. 现状（坐实）

- 云端下发这条命令的唯一意图写在 `aidcp-cloud/src/agents/notification-return-home.ts:4`：「一类处理完，返回通知首页……边缘重报各类未读 → 分诊下一轮」。
- 分诊只在收到通知首页读数时才跑：`aidcp-cloud/src/agents/notification-triage.ts:48` 订阅的是通知首页到达事件，`:82` 只有在三栏全清或全部放弃时才发收尾信号。
- 收尾之后**才**回信息流：`aidcp-cloud/src/agents/excursion-resumer.ts:59-62` 先关暂停、再发「回信息流」意图，调度器把它翻成 `back` 命令（`role-dispatcher.ts:4104-4119`）。所以回信息流这一步**已经有专门的命令**，不需要「回通知首页」代劳。
- 边缘现实现走的是发现页：`aidcp-edge/native/page-engine/src/xhs-command-router.js:802-819`，判据是 `/^\/explore\/?$/`，终局是一屏信息流卡片。
- 退役的 TS 实现是对的：`aidcp-edge/src/browse/browse-session.ts:3075` 点通知入口 + 重报三栏。

## 2. 为什么本地测试全绿

两份测试把错误终点当成了契约：

- `test/native-page-engine/xhs-navigation-command-contracts.test.ts` 专为这条命令立项，理由写得很清楚——「出口的假成功不体现在自己身上，体现在它之后的每一条命令上」。它把「有没有真到达」守得很严，**但守的是错的那个目的地**。
- `test/native-page-engine/runtime-contracts-command-receipts.test.ts:342` 的声明对账表直接把「信息流卡片」登记成这条命令的合法回执。

这正是「第二份实现按行为测不出来」的典型：两侧各自自洽，只有跨层对账才看得见。所以本 change 的测试补法不能只加行为断言，**必须让契约表也指向通知首页读数**。

## 3. 方案

「回通知首页」与「打开通知页」共用同一套页面身份判据与三态口径，唯一区别是前者允许「已经在通知页上」直接成立（分类浏览只切栏、不离页，绝大多数情况下本就还在通知页）：

1. 不在通知页 → 找通知入口点进去，等页面身份成立；找不到入口 / 点不动 / 等不到 → 按各自原因诚实失败或回未确认。
2. 分类栏读不到 → 有界等待一次；仍读不到 → 回**未确认**，MUST NOT 回一份全 0 的三栏读数（全 0 会被云端当作「三类都已清零」直接收尾，把一次读取失败静默变成「已清完」）。
3. 分类栏就绪 → 终局观测 = 通知首页三栏读数。

动作名保持 `notification_back_home` 不变：云端把它列在巡视命令集合里，失败回执是恢复角色的三个入口之一（`excursion-resumer.ts:20-26`）。改名会让失败恢复这条腿一起断掉。

## 4. 加闸准入自检

本 change **不新增任何闸**，只是把一条走错的导航改回去，并把它的终局观测钉死。唯一新增的拒绝路径是「分类栏读不到 → 回未确认」——它替代的是「回一份全 0 读数」，即用一次诚实的未确认换掉一次静默假成功，方向与红线一致。

失败终局仍是**结构性可恢复**的：同一步在重新加载后的页面上重来完全可能成功（页面没渲染完、入口还没挂上）。所以这里回的是未确认 / 诚实失败，交由云端的恢复通道收敛，**本层不落终态、不自行终结这一趟**。

## 5. 不在本 change 范围

- 云端巡视的**总超时兜底**（已上线要求但从未实装）——由并行 change 处理。本条修好后，本 case 不再复现；但「回执成功但走岔了」是一整类失效，仍需要云端那条腿。
- 「赞和收藏 / 新增关注」两栏看一眼是否真能清零——依赖真机验证，登记进真机验收 backlog。

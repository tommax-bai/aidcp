## Why

风控计数对账器（`risk_counter_drift`，P1、零容忍阈值）当前对**本进程内存里存在的每一个账号**做对账，不看归属。而计数账本 `risk_counters` 是 dev / ol **共用且不带 `execution_target`** 的既成事实账本（design D4「分裂的是写权限，不分裂的是事实」），内存计数却只在**本进程自己记账**时才递增。

于是对「归属在另一个 target 的账号」，两者结构上不可能相等：对面在真干活往共用账本里写行，本进程那份内存快照一动不动。而本进程为什么会持有这些账号的内存计数——面板 / 客户端每查一次某账号的当日用量、配额或自动化目录，就会顺手在本进程物化一份（`server.ts` 的日用量与目录读路径）。结果是**每 5 分钟、每账号、每动作各刷一条 P1**。

2026-08-05 生产实测已坐实这就是误报，而非记账缺陷：

- dev（automation 进程）报的 4 个账号（`61591782937395` / `61591641343830` / `61591715201364` / `61591824155856`）归属**全是 ol**；
- ol（单体进程）报的 5 个账号（`61591753702668` / `61591723990513` / `61579303864396` / `61579315453135` / `61579069246637`）归属**全是 dev**；
- 两边零交集、与归属完全反相关；
- 日志数值签名同样吻合：本轮「内存」恰等于上轮「库」（对账后按库重建过，此后 5 分钟本进程一次都没加过）。例 `61591753702668` 的 view：`内存=1 库=12` → `内存=12 库=22` → `内存=22 库=33`。

代价不是判定出错（不驱动该账号的进程本就不给它下发动作，且每轮都会按库重建），而是**把一条刻意做成零容忍的信号淹进常态噪音**——它原本要抓的恰恰是「有人在偷偷写我管的账号」。附带的可观测缺口：`alerts` 表没有来源 target 字段，dev 与 ol 的告警混在同一个列表里，看卡片分不出是谁报的。

## What Changes

- 对账范围收敛为「归属为本 target 的账号」：归属在另一个 target 的账号跳过，不再计为偏差、不再告警。
- 归属读不到（无行 / 读失败）一律跳过并计数，MUST NOT 默认当成本 target 的账号去对账。
- 加一道**反向可观测闸**：一轮下来「实际对账账号数」为 0 而已物化账号数不为 0 时响亮记录——防止这道过滤器把对账器变成永远沉默的死代码（沉默与健康在现有信号里长得一模一样）。
- 风控类告警统一带上来源 target 标注，使 dev / ol 的告警在同一个列表里可分辨。
- 补单测：他 target 账号不告警、本 target 账号照旧检出偏差、归属未知跳过并计数、全跳过时响亮记录。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `interaction-risk-gating`: 修改「配额判定依据的计数必须与库内事实一致」这条要求的**对账范围**——从「本进程已物化的全部账号」收敛为「归属为本 target 的账号」，并要求跳过可数、全跳过可见、告警标注来源 target。原有的零容忍判据、告警内容、以库为准重建，全部不变。

## Impact

- `aidcp-cloud/src/risk/risk-counter-reconciler.ts`：新增归属过滤依赖与跳过计数。
- `aidcp-cloud/src/server.ts`：对账器装配处注入归属读口（复用风控条件写已在用的那一个）+ 风控告警统一带 target 标注。
- `aidcp-cloud/test/risk-counter-outbox.test.ts`：对账器用例扩充。
- 不改协议 v2、不改数据库 schema、不改风控状态机、不改配额判定路径。
- 部署：默认 `dev`。**ol 仍跑单体旧码**，在 ol 更新之前，它对 dev 归属账号的误报会继续——需用户明确要求才走发布分支上 ol。

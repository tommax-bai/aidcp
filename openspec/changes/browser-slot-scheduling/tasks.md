## 1. aidcp-edge — 核心：待机即释放、唤醒即重建、一道闸

- [ ] 1.1 **收拢浏览器层持有者**：审计 `src/main.ts` 及其下游，确认浏览器控制连接只有单一持有点；把私藏连接副本的长期组件（浏览会话、监测体、身份读取、任务协调器）改为持**入口**而非持连接。这是「释放不留悬挂句柄」的唯一可审计点。
- [ ] 1.2 **实现「释放浏览器层」**：断开控制连接 → 退订依赖浏览器的监测体 → 清页面/目标引用 → 关浏览器；保留核心进程与云端连接。释放前复用已 landed 的排空契约（`persona-bound-tristate-and-standby-drain` 的 `closeAndWait`）把浏览循环有界排空。
- [ ] 1.3 **实现「原地重建浏览器层」**：拉起浏览器 → 重连控制 → **重新确认登录态与账号身份**（当作新的一代浏览器，不复用释放前的缓存状态）→ 重挂监测体。必须**幂等**（重复触发不产生第二个浏览器 / 第二组监测体）。重建失败诚实报错并保持待机（可再唤醒）。
- [ ] 1.4 **`core-lifecycle.ts` 新增原地重建意图**：今天 `resume` 走 `finalize({preserveBrowser:true})` = 进程退出，没有「保住引擎、只重开浏览器」这条意图。新增之，且它 MUST NOT 触发进程退出。
- [ ] 1.5 **统一浏览器闸**：把「浏览器不在 → 请求唤醒 → 有界等待（默认 180s，可配）→ 就绪则继续 / 否则诚实失败」抽成一处，让**全部**碰浏览器的入站动作走它。
- [ ] 1.6 **接上任务受理与发布这两个漏网入口**：`src/main.ts:475` `onEdgeTaskCommand` 与 `:483` `onPublishCommand` 今天没有冷待机守卫，改为走 1.5 的闸。
- [ ] 1.7 **`cdp_unhealthy` 与「停泊缺席」分离**：`EdgeTaskCoordinator` 的 `canAcquire`（`src/main.ts:414` = `session.cdp.isControlReady()`）在浏览器已被自己收起时返回假，导致回一条**假的** `cdp_unhealthy`。改为区分两态：浏览器在但不健康 → 保持 `cdp_unhealthy`；浏览器缺席可唤醒 → 走唤醒路径，失败回**独立的唤醒失败原因**。
- [ ] 1.8 **释放 ⊥ 在跑租约**：有租约在跑时拒绝释放（推迟到租约结束后重判待机）；浏览器缺席且唤醒未成功时拒绝授予租约。竞态以「不释放」为安全侧。
- [ ] 1.9 **动作完成后重判待机**：被唤醒的环境跑完任务后按待机规则重新判定（仍在长等待 → 再次停泊还槽位；该继续浏览 → 保持打开）。既不「唤醒即关」，也不「无条件常开」。
- [ ] 1.10 **上报「在线但浏览器缺席」**：把「引擎在线」与「浏览器就绪」表达为两个独立事实，供云端与运维界面区分停泊与空闲就绪。
- [ ] 1.11 单测：释放后所有旧句柄不可用（响亮失败而非静默错误行为）；重建幂等；重建后身份重新确认；释放与租约互斥；闸在缺席时唤醒、在唤醒失败时回诚实原因。

## 2. aidcp-edge — 外壳：槽位池 + 串行启动队列

- [ ] 2.1 **唤醒不再 stopAndRestart**：`main.cjs` 的 `wakeColdStandby` → `resumeEdge`（`:2583`）在浏览器已关时落到 `stopAndRestart` = SIGTERM 核心 + 整进程冷启。改为下发 1.4 的原地重建意图；进程与云端连接不动。
- [ ] 2.2 **槽位池**：上限 = ⌊可用内存 ÷ 单环境估值（0.1 的实测值）⌋，可配。同时打开的浏览器数不得超过它。槽位**只由冷待机自然释放**，不抢占、不踢人。
- [ ] 2.3 **串行启动队列**：所有开浏览器的动作（自动续场、冷待机唤醒、崩溃重起、手动任务、排期任务唤醒）走同一条队列；**一次只放行一个，等它真正就绪（浏览器起来 + 云端连上）或诚实失败，再放行下一个**。保留既有 ≥1.1s 的 AdsPower 限频错峰作为下限。
- [ ] 2.4 **内存准入闸搬进队列，全路径覆盖**：今天 `ramAdmission`（`fleet.cjs:173`）只在 `main.cjs:2730` 的「全部启动」里调，单启 / 唤醒 / 重起全部绕过。改为队列内部统一过闸，**没有任何路径能绕过**。
- [ ] 2.5 **队列优先级**：手动任务 > 带任务的唤醒 > 普通续场恢复；同级 FIFO。
- [ ] 2.6 **排队等待计入 180s 死线**：队列在放行前若已能判定该项无法在死线内就绪（队列过长 / 准入不通过），**立刻让调用方诚实失败**，不吊到超时。
- [ ] 2.7 **拆掉零抖动唤醒羊群**：`scheduleColdStandbyWake`（`main.cjs:1641`）的定时器零抖动——撞日额的账号会在上海零点**同一秒**齐冷启。改为定时器到点后**投进串行队列**（用户已否决抖动方案）。
- [ ] 2.8 **手动任务策略**：插队首 → 启动浏览器 → 执行 → 完成后关闭归还槽位；**绝不驱逐**正在运行的环境；内存 / 槽位不足则**诚实报失败**（不静默排队、不假装已执行）。
- [ ] 2.9 **1:2 上限**：可设账号数上限 = 2 × 槽位上限；超出时诚实告警「存在永远排不上的风险」。
- [ ] 2.10 单测：队列串行性（并发请求下同时只有一个在启动）；准入闸不可绕过（逐条路径断言）；优先级与 FIFO；零点羊群被拆成逐个；手动任务不驱逐他人；槽位满诚实拒绝。

## 3. aidcp-cloud — 不再往关着的浏览器上盲发

- [ ] 3.1 **区分「引擎在线」与「浏览器就绪」**：`connection-runtime.ts:317` 的 `onlineAccountIds()` 只认「有 edgeId 就是在线」，会把停泊账号当成随时可干活。接上 1.10 上报的缺席态。
- [ ] 3.2 **两段式派发**：对停泊账号先发唤醒 → 等其报到就绪 → 再下发业务命令；不再直接下发靠失败回执兜底。
- [ ] 3.3 **受理超时容得下冷启**：`edge-task-lease-client.ts` 默认 45s 短于 30–90s 冷启；带唤醒的请求用更长的按请求超时（覆盖口子已存在于 `:94`）。
- [ ] 3.4 **排期任务失败不烧名额**：`content-scheduler.ts` 的 `lastFired.set()` 现写在触发**之前**（`:243/:265/:279/:296`）。改为**触发真正开始之后**才记；未开始的失败保留小时格，该小时格剩余分钟内可重试。
- [ ] 3.5 **「浏览器停泊 / 唤醒失败」作为独立的接管失败原因**：与 `edge_offline` 区分（前者可恢复，后者不是），结果卡如实呈现，别把停泊读成离线误导运维查连接。
- [ ] 3.6 单测：停泊账号不被计为完全就绪；失败不消耗小时格且可在小时内重试；唤醒中的账号下一分钟可再试；唤醒失败的结果卡措辞与 `edge_offline` 可区分。

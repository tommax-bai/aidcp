# 设计：同机浏览器槽位调度

## 一、约束（全部来自现状坐实，非假设）

| 约束 | 来源 |
| --- | --- |
| 单个有界面指纹浏览器 ≈ 700MB；一机约 10 个封顶 | 用户实测口径（代码里 `PER_ENV_BYTES_DEFAULT = 1GB` 是没量过的设计默认值，`fleet.cjs:167`） |
| AdsPower **不限**并发席位 | 用户确认 |
| AdsPower 本地 API ~1 req/s | 既有错峰队列 `DEFAULT_STAGGER_MS = 1100`（`fleet.cjs`） |
| Cloud 单一冷待机门槛 5 分钟、预热 90 秒 | `browser-standby.ts:4-5` |
| 冷待机**只认浏览配额等待** | `buildBrowserStandbyHint` 只看 `explain('view')`，reason 必须 `quota:` 开头（`browser-standby.ts:57-59`） |
| 云端空转看门狗 240 秒 | `DEFAULT_IDLE_NUDGE_MS = 240_000` |
| 冷启预算 30–90 秒 | AdsPower start ≤30s + CDP ready ≤15s + 身份 + 云端握手 |

## 二、算账：槽位够不够，1:2 安不安全

正常档配额（`quotas.ts`，`deriveWindowQuotasFromDaily`）：日浏览 150；小时 `min(60, ⌈150/4⌉) = 38`；分钟 `min(8, ⌈150/20⌉) = 8`。撞配额则睡到滑动窗最早那条事件滑出（`sliding-window-counter.ts:37-54`）：撞分钟窗 ≤60s；**撞小时窗睡几十分钟**（达到 Cloud 单一 5 分钟门槛 → 冷待机关浏览器）；撞日窗睡到次日上海零点。

- 跑满一小时 38 次浏览约需 ~20 分钟真实操作 → 随后约 40 分钟停泊。
- 日额 150 次约需 **4 小时**跑完 → 之后约 20 小时全程停泊。
- **每账号每天需要浏览器打开约 3–4 小时，占用率 ≈ 15%。**

10 槽位 × 24h = 240 浏览器·小时/天；20 账号 × 4h = 80 浏览器·小时/天 → **利用率约 33%，宽裕**。饿死的临界点在 ~60 账号量级，**1:2（10 槽 / 20 账号）有 3 倍余量**。

**这笔账依赖一个未验证的假设**：单次浏览墙钟 < 95 秒（= 3600/38）。若单次浏览慢于 95 秒，小时配额**永远触不到顶**，冷待机就再也不会因小时窗触发，槽位只在日额耗尽（约 4 小时后）才释放一次——那时 10 槽只能服务 10 个账号，1:2 立刻失效。**所以「量单次浏览耗时」是任务，不是可选项。**

## 三、为什么是「待机即释放、唤醒即重建」

唤醒有两条路：

- **路 A（选中）——原地重建**：待机时释放浏览器层、保住进程与云端连接；唤醒时重建浏览器层。
- **路 B（否决）——保持现状的进程重启**：`resumeEdge` 在浏览器已关时落到 `stopAndRestart`，SIGTERM 核心、整进程冷启，云端连接断一次重连一次。

路 B 的问题不是慢，是**它把每次唤醒都变成一次完整的启动重放**——云端看到断连重连、身份重读、启动时间线重播，这正是刚归档的 `cold-standby-reconnect-stability` 在修的那类症状。既然要把唤醒变成**高频**动作（每小时都可能发生），就不能让它每次都掀一次桌子。

路 A 的风险是**悬挂句柄**：浏览器关了，但某个长期活着的组件还攥着旧连接，之后拿它去摸页面，得到的不是「设备没了」的响亮报错，而是静默的错误行为。**解法恰恰是「全部释放」本身**——把「可能过期的句柄」变成「根本不存在的句柄」，把静默失败变成响亮失败。这是用户提的，比我原本的保守方案更好。

四条不变量：

1. **单一持有者**：浏览器层只有一个持有点；其他组件持入口，不私藏连接。
2. **一道闸**：所有碰浏览器的动作走同一道「不在 → 唤醒 → 有界等 → 干活或诚实失败」。
3. **释放 ⊥ 在跑租约**：两者互斥。有任务持着执行权就不能释放；浏览器不在且唤不醒就不能拿到租约。
4. **重建 = 新的一代浏览器**：不假设还登着；重新确认登录态与身份；可反复执行。

## 四、为什么是串行启动，不是抖动

零抖动的定时唤醒（`main.cjs:1641` 的 `setTimeout`）会让所有撞日额的账号**在上海零点同一秒**一起冷启浏览器——今天没有任何东西拦得住。

抖动能打散羊群，但用户明确否决：「太不可理解且随机」。**串行启动**同样能打散，而且是确定性的：一次只起一个，起完再起下一个；10 个环境约 10–15 分钟起完，用户接受。

浏览器并发的自动值只在 **Edge 外壳启动时**按内存快照计算一次。串行队列后续只比较当前执行数与这个固定值；不得在每次启动任务时重读剩余内存，否则已启动任务本身消耗的内存会反过来持续压低推算结果。第二个可配置值是**启动排队上限**（默认并发 × 2），不是账号挂载或环境创建上限。

## 五、超时纪律

- 唤醒死线 **180 秒**：冷启 30–90s + 排队 + 余量；必须**小于云端 240s 空转看门狗**，否则唤醒中的账号会被当成卡死杀掉整个会话。
- **排队等待算进死线**。带任务的唤醒插队（手动 > 排期 > 普通续场）。
- **算得出排不进死线的，立刻诚实失败**——不吊着等 180 秒再超时。这条是红线的直接推论：静默拖延也是一种假成功。
- 云端任务受理超时（默认 45s）对带唤醒的请求要放长到容得下一次冷启；按请求覆盖的口子已存在（`edge-task-lease-client.ts:94`）。

## 六、明确不做

- **不做抖动错峰**（改串行启动）。
- **不做抢占 / 踢人**。手动任务新开一个，跑完关掉；内存不够就诚实失败。
- **槽位满时不排队等**（沿用既有 `publish-concurrency` 的「帽满 MUST NOT 排队」口径）——排期任务的「小时内重试」是重试，不是排队。
- **不碰养号节奏 / 风控配置默认值的漂移**（单场时长、休息比例、活跃时段与风控文档差得远）——用户明示先放着，另开 change。

## 七、短时浏览器通道与视频号生命周期

浏览器资源拆成两类，二者不可互相冒充：

1. **公共执行槽位**：容量为现有 `browserSlots`，供需要持续页面控制的浏览自动化使用；占用从浏览器启动持续到冷待机/关闭。
2. **临时浏览器通道**：机器级容量固定为 1，严格 FIFO，供短时鉴权、一次性人工验证等明确声明 `transient` 能力的工作流使用；普通浏览自动化不具备该能力，不能借此绕过公共上限。

两池可以同时占用，因此公共槽位 2/2 时，临时通道仍可短时打开第 3 个浏览器。资源分池不放宽既有 AdsPower 调用限频约束；临时 sidecar 继续使用提供方内部 1 req/s 节流。本 change 不借资源分池扩大本机 API 并发，也不把既有跨进程提供方限频重构混入本次范围。

视频号每次环境启动都先进入临时通道，保证多个视频号按确定性 FIFO 顺序完成初始化：

- 先在浏览器关闭状态校验加密会话与绑定身份；有效则确认 connector 已启动并立即释放通道。Cloud capability 与新鲜往返继续决定是否可显示「运行中」，但不反向占住已不需要浏览器的临时通道。
- 会话缺失、过期或遇到 challenge 时，才在持有通道租约期间打开 sidecar；登录确认后保存会话，关闭并确认浏览器已退出，再启动/恢复 connector 并释放租约。
- 失败、超时、环境关闭、子进程退出和代际切换都必须释放租约；旧代的迟到消息不得释放新代租约。手动重登/打开鉴权浏览器也走同一通道。

视频号的「运行中」是**互动数据面状态**，不是浏览器状态。只有当前身份匹配、授权 active、connector 已启动且 Cloud 协议已协商、环境未暂停/解绑，并存在当前进程生命周期内的新鲜 API/Cloud 成功往返证据时，才投影为运行中。浏览器可同时如实为 `closed`，且公共槽位/临时通道均为未占用。

人设能力按平台显式声明。视频号 `personaApplicable=false`：主进程不接受 Cloud `personaBound` 覆盖，不创建行内入口，不跑 gate/自动弹窗；切换到视频号时清掉先前环境遗留的人设浮层。IPC 收到过期调用时返回 `not_applicable`，而不是继续执行或弹窗。

## 八、控制面在线不等于浏览会话已启动

排队环境会先启动 Edge 核心并完成 Cloud `hello/welcome`，但此时浏览器从未创建。Cloud 若仍把握手当成浏览会话开场，`SessionMonitorRole` 会从握手时刻启动 240 秒空转计时；到点后把 `session.idle_nudge` 翻译成 `page.scroll`。Edge 只能回 `browser_absent_wake_requested`，于是页面没有可滚动对象，活动流却每四分钟出现一次“已交给执行器”。

这不是浏览器唤醒机制，而是会话生命周期接错：没有浏览器时不存在可恢复的页面停滞，也不存在可被页面看门狗唤醒的对象。资源队列负责在槽位释放后放行队头；页面看门狗只负责一个已经就绪、已经开始浏览的页面会话。

采用显式的两段状态：

1. `hello.browserState` 上报握手当刻的 `absent | ready` 快照；字段缺失按旧 Edge 兼容，沿用既有开场行为。
2. 同一 WebSocket 生命周期内，Edge 以 `browser.status` 上报后续 `absent ↔ ready` 变化。状态只陈述事实，不请求 Cloud 下发页面动作。
3. Cloud 在 `absent` 时保留传输连接、账号路由与任务派发能力，但不激活浏览角色、不开 `SessionMonitorRole`、不产生 `session.idle_nudge/page.scroll`；收到 `ready` 后才启动浏览会话。
4. 已激活会话随后变为 `absent` 时，Cloud 拆除浏览角色与页面看门狗；再次 `ready` 时新开一场。重复状态必须幂等，不得重复订阅或重复开场。

任务派发与浏览会话是两条不同的链：排期任务仍可向在线但浏览器缺席的 Edge 请求租约，由 Edge 的统一浏览器闸触发有界唤醒；本节只禁止“为了探测页面是否卡住而盲发滚动”，不把停泊账号误判为离线，也不削弱按需任务唤醒。

## Context

**现状（2026-08-03 实测，不是转抄）**：

- `/opt/aidcp/` 下只有 `cloud`（单体，现役，8787）+ `console` + `downloads`。**三个业务仓从未部署过任何机器**。
- dev 上有四个 `disabled` 的 unit：`aidcp-cloud-{api,automation,content,core}.service`。四个的
  `WorkingDirectory` 都是 `/opt/aidcp/cloud`、`ExecStart` 都是 `npx tsx src/server.ts`，靠 `AIDCP_SERVICE` 切段。
  **它们跑的是单体**。其中三个在 2026-07-26 10:54–10:55 真跑过约一分钟：三个都起了监听、之后被干净停掉
  （`Succeeded`）。⇒ **"三进程一次都没真跑过"这条记载对那条路径已经过期**；对派生仓则仍然成立。
- 三仓的启动外壳只有 automation 有（`automation-service-entry.ts`：读配置 → 建根 → 先监听 → 就绪闸 →
  放行业务 → 优雅关停）。**api 与 content 没有**：两者的 `server.ts` 靠文件末尾
  `if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href)` 自举，
  `src/index.ts` 是纯出口桶（content 那份还专门注释了"组装根不在这里出口"的理由）。
- 配置契约已经是必填形态：automation 要 `AIDCP_API_URL` / `AIDCP_CONTENT_URL` + 三把令牌 +
  `AIDCP_DEPLOY_ENV`；api 要 `AIDCP_AUTOMATION_URL` / `AIDCP_CONTENT_URL` + 三把令牌。
  **缺一即启动抛错**，没有回落——这一点已经对了，不用改。
- 三个属主库已物理分开（`AIDCP_PG_{API,AUTOMATION,CONTENT}_URL`），各自迁移账本；
  dev 上实测 api=69 条 / automation=57 条 / content=20 条，各自 0 待应用。

**归属冲突（本 change 的第一件事）**：单体的 `segmentsForMode` 里 `api = segA+segD`（不含 segC），
而内容排期调度器在 `segCAutomation` 内构造（`aidcp-cloud/src/server.ts:8299`）⇒ **单体切分下它跑在 automation**。
已上线 spec `api-process-content-scheduling` 却写"只由接口服务承载、自动化装配 MUST NOT 构造它"，
派生仓那套照此接线。两条相反的活路径。

## Goals / Non-Goals

**Goals:**

- 三个业务服务在 dev 上以**独立进程**真跑起来（各自目录 / 依赖 / 配置 / unit / 手写 `main()`）。
- api 与 content 补齐启动外壳，三者就绪与退出语义同形。
- 三个属主库各自过契约门，部署顺序按"先迁移后重启"。
- 裁定排期器归属，消掉两份互斥权威。
- soak 并**逐条**走簇 60 的验收项，如实分开记"验到了什么、没验到什么"。

**Non-Goals:**

- **不上 ol**（须用户明确要求，且从发布分支走）。
- **不退役单体**：单体仍是 dev/ol 的现役形态，本批只是让派生服务在旁边同时跑得起来。
- **不改任何业务行为**。本批一行业务逻辑都不动；碰到"顺手修一下"的冲动一律记 backlog。
- **不做面板 / 客户端 API 的对外切流**：派生 api 进程即使起来了，Nginx 也不改指向。

## Decisions

### 一、派生服务与单体**并存**，端口物理隔离，Nginx 不动

单体继续独占 8787 与既有面板端口。派生服务各自另占端口，只监听回环。

**替代方案（否决）**：停掉单体、让派生服务顶上。否决理由——那把"跑不跑得起来"和"跑起来对不对"
两件事绑在一起，一旦出问题 dev 直接不可用，而 dev 是车队每天在用的环境。
并存的代价是同一批数据会被两处读到，这正是下面第二条要处理的。

### 二、并存期间，**周期性任务只允许一处推进**——派生服务先只跑"被动面"

并存的真实风险不是端口撞车，是**同一件事被做两遍**。数据库那道小时格幂等闸能拦住重复发帖，
但它是最后一道防线：靠它兜住意味着两处都在尝试，而尝试本身已有副作用（唤醒边端、占配额、烧时段名额）。

**决定**：派生服务第一阶段以**不推进任何周期任务**的形态起（排期心跳、委托泵、恢复扫描等一律关），
只验"起得来 + 被调面答得上"。确认无误后，再按裁定结果把周期任务从单体切到派生服务，
**切换是原子的**：单体那一侧同时关掉。

**替代方案（否决）**：两边都跑、靠幂等闸。否决理由见上——它把"最后一道防线"当成设计。

### 三、排期器归属：派生仓形态按已上线 spec（归 api）；单体切分那条路径**显式退役**

**决定（用户 2026-08-03 裁定）**：单体的按角色切段形态（`AIDCP_SERVICE=api|automation|content|core`
四个 unit）**判定退役**；退役**动作**推迟到派生服务切换完成、主要测试跑过之后执行。

退役的理由：
1. 它执行的是单体的装配代码，**与派生仓的手写 `main()` 一行都不重合**，跑通它证明不了派生仓的任何事；
2. 它对排期器的归属与已上线 spec 相反，留着就是两份互斥权威；
3. 它是拆仓过程中的脚手架，拆仓的终点是派生仓——脚手架留着不拆，下一个人会以为它是可选形态之一。

处置因此分两拍，且**两拍都不许沉默**：

- **第一拍（本批立即做）**：在规格与文档里写死"这四个 unit 已判退役、只作为切换期的回滚路存在"。
  它们**保持 `disabled`、本批不启用、不用它们做任何验证**——用它们跑一遍证明不了派生仓的任何事
  （它们执行的是单体的装配代码，与派生仓的手写入口一行都不重合）。
- **第二拍（切换完成 + 主要测试通过后）**：删除或改名归档这四个 unit 文件，
  `segmentsForMode` 里那几个角色分支的处置同批写清。

**为什么留这一段窗口是对的**：并存期间派生服务一旦出问题，回滚的第一选择是"停掉派生服务、
单体照常"（单体全程没停）；这四个 unit 是**第二条**回滚路，用于"单体也需要按角色拆开跑"的极端情况。
留窗口的代价只有一个——期间存在两条对排期器归属答案相反的路径，故第一拍必须先把
"哪一条是活的"写死，否则窗口本身就变成两份互斥权威。

**MUST NOT 因为"反正要退役"就跳过第一拍**：只活在会话里的退役决定，等到第二拍时没有任何机制会提醒人。

### 四、api 与 content 的启动外壳**照抄 automation 那一份的形态**，不发明第二种

`automation-service-entry.ts` 已经把顺序定死：读配置 → 建根 → **先监听** → 就绪闸 → 放行业务 →
优雅关停 → 信号。三者同形是有具体理由的：不同形的直接后果是"某个服务在就绪之前就开始干活"，
而那件事在这套系统里意味着一个还没放行的进程去认领带租约的任务。

**先监听后就绪**这个顺序也不能倒：倒过来的话，健康检查在就绪之前拿不到任何应答，
"还在初始化"与"进程死了"从外面同形。

### 五、依赖安装：三仓各自 `npm ci`，共享包走 git pin

内网 registry 对 `@types` 域的劫持已知，本机绕法 `--userconfig /dev/null` 实测可用，**ECS 上须复验**
（这是本批的第一个可能卡住的点，故排在最前面做）。

三个共享包的 pin 顺序是硬的：`aidcp-kernel` → `aidcp-transport`（它自己也 pin kernel）→ 三个业务仓。
只 bump 业务仓的表现不是"装到旧 sha"，而是 `npm install` 直接失败在 transport 的构建步骤，
报错栈全是 transport 的文件、看不出根因在顺序。

### 六、验收记录的形状：**逐条声明，不概括**

每一条验收项记三态之一：**已验（附证据）/ 未验（附为什么没覆盖到）/ 不适用（附理由）**。

禁止出现"三进程已验证"这类表述。理由不是文风：本项目上一个 change 的记载
"runAutomationMain 至今一次都没真跑过"在本次勘察中被证明对单体切分那条路径已经过期，
而那条过期记载差点让本 change 从错误的前提开工。**概括性的验收结论会以最快速度过期。**

## Risks / Trade-offs

- **ECS 上装不上依赖**（内网 registry 劫持 / git+ssh 拉不到私有共享包）→ 这是本批最可能卡住的点。
  **Mitigation**：排在第一步做，且**先只装一个仓**验通路；不通就停手上报，不要三个仓一起试错。
- **并存期间同一件事被做两遍** → **Mitigation**：决策二（派生服务先只跑被动面）；切换时原子对切。
  **判据是"说得出是哪一处在推进"**，不是"有幂等闸"。
- **迁移顺序倒置** → schema 门在 enforce 下抛出、进程反复重启且零告警。
  **Mitigation**：三个属主库各自"先 status 看清、再 up、再重启"；status 与预期不符即停。
- **派生仓入口注册的路由少于单体** → 编译过、各仓测试全绿，只有真跑才 404。
  **Mitigation**：这正是本批要暴露的东西，不是要绕开的。第一次两进程互调 SHALL 逐条点名核对
  （automation 侧已有只许下降的路由清单闸，但它只管本仓装配、管不了对面起没起）。
- **soak 时长不够覆盖周期任务** → 会得到一个"进程一直活着"的假通过。
  **Mitigation**：按小时开火的任务至少覆盖一个完整小时；覆盖不到就如实记未验。
- **本批动的是部署面，回滚不像代码那样干净** → **Mitigation**：单体全程不停、Nginx 不动，
  所以回滚 = 停掉三个派生 unit，dev 立刻回到今天的状态；数据面无残留（本批不改任何业务写路径）。

## Migration Plan

1. **通路验证**：ECS 上先只为一个仓建部署位并装依赖，确认 registry 与 git+ssh 两条通路都行。不行则停手上报。
2. **补启动外壳**：api / content 各补一份，照 automation 的形态；本地先跑起来。
3. **归属第一拍**：把"这四个 unit 已判退役、切换期内只作回滚路、本批不启用"写进规格与文档。
   （**退役动作本身在第 9 步之后**，见决策三。）
4. **三个部署位就位**：目录 / 依赖 / `.env` / unit；周期任务**全关**。
5. **各属主库迁移**：逐个 status → up → 记录。
6. **起三个服务**，只验"起得来 + 被调面答得上"；逐条核对跨进程路由。
7. **切周期任务**：按裁定把排期心跳等从单体原子切到派生服务。
8. **soak + 逐条验收**，如实分开记。
9. **回滚**：停三个派生 unit（单体全程未停，dev 立刻回到今天状态）。
10. **归属第二拍（主要测试通过后）**：删除或改名归档单体那四个按角色切段的 unit，
    `segmentsForMode` 的处置同批在代码里写清。**这一步不做完，本 change 不算收口。**

## Open Questions

1. ~~单体按角色切段那四个 unit：退役还是保留为过渡形态？~~ **已裁定（2026-08-03，用户）：退役，
   但退役时点推迟到派生服务切换完成、主要测试跑过之后。** 处置分两拍，见决策三。
2. **派生服务的端口分配与是否需要 Nginx**：本批默认只监听回环、不动 Nginx。
   若要让派生 api 进程承载面板/客户端 API 的对外流量，那是另一件事、另一批。
3. **soak 时长**（待用户确认，已给建议）。**为什么有下限而不是随便跑跑**：按小时开火的任务，
   每个账号每小时只有固定的一分钟开火窗口；跑不满一小时，那个窗口大概率根本没到 ⇒
   什么都没验到，而进程全程健康、日志干净、**看着像通过了**。这正是本 change 明令禁止的假通过。
   **建议分两段**：先 1 小时（覆盖一次真实到点判定，快速拿到"闹钟真会响"这个答案），
   看结果无误再挂 8–12 小时（覆盖多轮 + 暴露内存 / 连接池 / 日志量这类渐进型问题）。
   两段之间停下来看结果再决定是否继续。
4. **飞书长连接**：单体已建一条。派生 api 进程若也建一条，同一个应用两条长连接的行为需要先确认
   （可能重复消费事件）。本批默认**派生 api 进程不建飞书连接**，待确认。

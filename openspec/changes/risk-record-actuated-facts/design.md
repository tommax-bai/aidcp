## Context

`RiskController.record(action)` 是 `risk_counters` 的**唯一写入者**（`appendCounter` 全仓仅此一处调用）。它在写之前重判一次 `canDo`，拒则静默返 `false`、什么都不写。

而它的主调用点（`server.ts:1391`）订的是 `interaction.occurred`——**边缘回执「已在真实页面上做完」之后**才发的事件。所以这道闸只可能在**既成事实**上开火。

### 这道闸能被拒的全部理由（`explain()` 的返回集）

`state:frozen` / `state:restricted` / `state:warned_publish_paused` / `quota:{minute,hour,day}` / `ratio:like_view`。

**每一条都是「你本来不该做」，没有一条是「这件事没发生」。**

### 预闸已经无处不在 ⇒ 这道重判只在缝里开火

自动下发路径全部已在动手前过 `canDo` / `explain`：角色调度（`server.ts:2661` `canInteract`）、发布排期（`publish-scheduler:297/351/398`）、`gated-auto-comment`、`send-orchestrator:116/178`、加群（`canJoin:3264`）。

所以 `record()` 的重判**只可能在预闸与回执之间的缝里**命中：

1. **运营手动绕闸**（产品明文裁决：手动 `/comment --join` 跳过配额闸，`facebook-group-join-scheduler.ts:161`）
2. **动作飞行途中状态翻转**（一次加群 60–90s，其间 FB 限流浮层触发 `applySignal` → `restricted`）
3. **突发窗在预闸与回执之间被别的动作填满**
4. **并发**

**这四种恰恰是真相最要紧的时候。** 这道重判买不到任何预闸没给的保护，它只在预闸失效处**销毁证据**。

### 类内已有「无条件写入」的先例

`RiskController.create()`（`:130`）的 PG 水合路径把持久化事件**直接回放进计数器**（`controller.counter.record(...)`），**不过 `canDo`**。**这个类自己已经同意「记录一件过去的事不是策略决定」**——每次重启它都这么干。

## Goals / Non-Goals

**Goals:**
- 计数器**如实反映真实发生过的动作**，不再因「本不该发生」而丢弃。
- **红线逐字保住**：拒时仍返 `false`，绝不 `applySignal`、绝不自升状态。
- 顺手修同病的第二处（微信入站已确认回复被丢）。
- 零协议 / 零 DB / 零边缘 / 零 console；纯云端单边。

**Non-Goals:**
- 不碰 `canDo` / `explain` / 状态机 / 配额数值 / `quota_config`。
- 不改返回值语义。
- 不做 join「统一分子」（本 change 只**解除其前置条件**，不等于该做）。
- 不修 `publish` 无回执 / `view` 手动路径无预闸（登记）。

## Decisions

### D1：写入无条件，返回值不动

```
async record(action: RiskAction): Promise<boolean> {
  const now = this.clock();
  this.counter.record(action, now);                        // ← 无条件：既成事实
  await this.store?.appendCounter(this.accountId, action, now);
  return this.canDo(action);   // ← 语义与红线逐字不变（注意：须在写入**之前**取值，见下）
}
```

**⚠️ 求值顺序是本 change 最容易写错的一行**：`canDo` 依赖计数器。若先写后判，刚写的这一笔会把自己算进去，撞顶那一次的返回值会从 `true` 翻成 `false` ⇒ **节奏告警提前一格开火 + 幂等占位路径行为变化**。必须**先取判定、再写入**：

```
const allowed = this.canDo(action);   // 先问
this.counter.record(action, now);     // 再记
await this.store?.appendCounter(...);
return allowed;
```

**返回值从此只回答一个问题：「这个动作在策略内吗」。它不再回答「我写下来了吗」。** 后者的答案现在恒为「是（除非抛错）」。

### D2：为什么这不是「求红线的例外」

**已用执行证明，不是论证**（2026-07-17 实跑，一次性副本、未碰任何 canonical checkout）：把 D1 的补丁打上后，

| 跑什么 | 结果 |
| --- | --- |
| 四条 `AC-RISK-*` 断言，**原样、零改** | **4/4 全过** |
| **全量套件** | **2432 pass / 0 fail，零改测试** |

**桩层爆炸半径 = 零。** 这是**双刃**，必须两面都说：

- **好消息**：没有任何既有行为被这道闸钉住 ⇒ 它确实是空壳，不是承重墙。
- **⚠️ 警告（更重要）**：**整个测试套件根本看不见这个改动。** 2440 条测试里没有一条能区分「写了」和「没写」。所以 tasks §5 的新测试是**唯一的机械保障**，而真机（§6.4 / §6.5）是**唯一的真实验证**。**「全绿」在这个 change 上不构成任何证据**——上一个 change 的 §3 就是全绿着走到提交前才被对抗性复核打穿的。

- 它们管的是**返回值**与**威胁状态机**；`RiskState`（`types.ts:59-67`）**没有计数器字段** ⇒ 它们**结构上看不见**这个写入。
- `spec:127` 给了 `绝不自残` 的定义：「**撞自己配额还自升状态**」。`spec:123` 的 MUST NOT 清单五条全是状态机。
- **方向性**：计数器只增，闸是 `count >= quota → deny` ⇒ 诚实记账**只可能更早拒绝**。自残 = 凭空信号把自己越限越死；记下真实点击**造不出幻象，只消掉一个幻象**（「我还有额度」）。

**但 `spec:123` 的「MUST 只返回 `false`」是真实的文本风险**：敌意解读 = 「且什么都别干」。**必须显式改写这句，绝不靠解释含混过关**——否则本 change 拿本仓自己的红线文本去赌一个歧义，下一个人会重新翻案。改法照该要求**自己立的先例**（`spec:127` 那句「此要求**强化**既有红线：返 false 不变，只去掉自残副作用」）：**同一招再进一格**。

### D3：节奏告警改读 `explain()`，行为不变

`server.ts:1394` 今天用 `!recorded` 当**便宜代理**，随即**当场又调 `c.explain(evt.action).reason` 重算真信号**（`:1395`）。且 spec 那条要求（`spec:146`）**本来就是按 `explain()` 的 reason 措辞的，不是按 record 的返回值**。

⇒ 告警挂到「写入前的一次 `explain()`」上，**行为逐位相同**，成本一行。

**顺带说清它今天有多脆**（避免把「保住它」抬成设计约束）：

- `:1395` 的 `explain()` 是**第二次独立求值**、时间戳更晚、窗口在滑 ⇒ 分钟窗若在两次之间滑走，`reason` 回 `undefined`、**告警本来就静默不发**。
- P2、按「账号+动作」20min 冷却去重、自陈「是提示、不是阻断」。
- **手动 `/comment` 早就完全不发它**（`skipRiskRecord` 跳过整块）⇒ **「运营绕闸把这个告警弄瞎」是已被接受的既有行为**。
- join 的小时配额 = 1 ⇒ 运营存心连加三个群时，第二个就报「节奏过载」——**那是噪声，不是信号**。

### D4：微信入站——同病第二处，且**必须与 D1 同批**

`interaction-inbox-service.ts:94-108`：在 `payload.status === 'confirmed'`（**平台已确认发出**）时 `claimRiskRecord` → `record` → **若被拒则 `releaseRiskRecordClaim` + 记 `denied` 指标**。

D1 落地后若不同批改这里，会出**真实的重复计数**：写入已经发生了，占位却被释放 ⇒ 重放会**再写一次**。

**改法**：占位**只在真抛错时释放**。判据从「返回值是不是 false」改成「有没有抛」。

**顺带修好的**：`denied` 那条路今天把「策略拒绝」与「PG 抛错」**收敛成同一种处理**，下游分不出来。改后 `denied` 这个分支消失，`failed` 只剩真故障 ⇒ **语义反而更干净**。

**注意**：`interaction_risk_record_total{status:'denied'}` 是**既有的可观测通道**——证明这个仓早就想看见「记账被拒」这件事。D1 之后它不再代表「没记下」，而应代表「记下了、但超策略」。**指标含义变了，须显式登记**（见 tasks）。

### D5：范围 = **全部动作**，不是只 join_group

**这一条与直觉相反，故据实论证。** 「窄=安全」在这里**不成立**：

- **方向性（D2）**：计数器只增、闸是 `>=` ⇒ 诚实记账**只会让系统做得更少**。**不存在**任何路径让它放行今天会挡住的动作。「宽」在这里 = 「系统更保守」，正是风控系统该失败的方向。
- **只做 join_group 反而更糟**：会让 `handler.ts:565` 那条**全局措辞**的注释（「record 内部还会再过一次 canDo，故账号被限/配额已耗尽时仍不落数」）变成**半真半假**——比现在「完整地错」更坏的认知状态。
- **`view` 那一处是反向的**（唯一需要单独想清的）：`likeRatioAllowsNextLike()` 有一条 `if (views < minViewsForLikeRatio) return true;` ⇒ **view 被少记 → 跌破阈值 → 整条点赞比例规则被跳过 → 更宽松**。诚实记 view **反而让这条规则真正生效** ⇒ 仍是收紧方向。

**⚠️ 但收紧是真的会被运营看见的**：view 在保守档的分钟配额是 4。若手动路径的 view 此前一直在被丢，诚实记账后**浏览可能更早撞窗**。这是**本 change 影响面最大的一项**，必须真机核（见 tasks）。

## Risks / Trade-offs

- **[全局收紧 —— 这是目的，但会被当回归报回来]** 所有动作的计数器都会**变大**（变准），⇒ 各闸更早拒绝。→ **缓解**：部署前向运营打招呼；真机优先核 view / 浏览节奏。**若真的过紧，正确动作是评估配额数值，不是把丢数改回去。**
- **[`dm_reply` 三档配额都是 0]** ⇒ `canDo('dm_reply')` **恒 false**（`0 >= 0`）⇒ 今天每一条已确认的微信回复都被丢、占位被释放、记 `denied`。D1+D4 之后：计数器**首次**开始从 0 累加、占位保留。**`0` 是占位而非真上限**（`quota_config` 覆盖是它唯一的启用路径）⇒ `canDo` 仍恒 false、门不变。→ **缓解**：微信入站路径必须单独跑测试；**且必须先回答 Open Question 2**。
- **[求值顺序写反]** 见 D1 的警告：先写后判会让撞顶那一次的返回值翻转。→ **缓解**：tasks 列为独立勾选项 + 专门的测试（撞顶那一次仍返 `false` 且计数已写）。
- **[重复计数]** D4 若漏做。→ **缓解**：D4 与 D1 同批，tasks 强制。
- **[`AC-RISK-*` 是主防线]** 本 change 动的正是它们环绕的那个函数。→ **缓解**：必须全过且**零改测试**——**任何一条需要改测试才能过，都说明设计走错了，停手。**

## Migration Plan

1. `risk-controller.ts`：`record()` 先取 `canDo` 判定、再无条件写入 + 持久化、返回判定（D1）。
2. `interaction-inbox-service.ts`：占位只在抛错时释放（D4）。
3. `server.ts:1394` 一带：告警改读写入前的 `explain()`（D3）。
4. 单测：撞顶仍返 false 且计数已写 / 被限时计数照写 / 手动绕闸的 join 被记 / 微信已确认回复被记且占位不释放 / view 记账不再跌破比例阈值。
5. `test:acceptance` → `test` → `typecheck`（顺序照 §4；`typecheck | tail` 退出码是 tail 的，会假绿——直接跑看退出码）。**`AC-RISK-*` 必须零改测试全过。**
6. 向运营打招呼（全局收紧）。
7. 部署 dev。无迁移、无需出安装包。
8. **回滚**：还原上一版本 tar。多记的计数残留，滑动窗一天内自然收敛，无需数据修复。

## Open Questions

1. **【最重要，实装前必须要到裁决】手动加群到底该不该吃自动预算？**
   本仓对「操作员全权」有**两套互相矛盾的实现**：
   - **手动 `/comment`**：`server.ts:1385` 的 `skipRiskRecord` **根本不调 record** ⇒ 运营的活**不吃预算**（刻意、且 spec 有据）。
   - **手动 `/comment --join`**：绕过预闸，却照样把回执送进 record ⇒ 代码的意思是**吃预算**。
   `skipRiskRecord` 硬绑 `evt.action === 'comment'`，join **永远够不着它**。**同一条裁决、两种机制、其中一种在丢事实。**
   ⇒ 若裁决是「手动加群**不该**吃预算」，**正确修法是给 join 补一条 `skipRiskRecord` 豁免——那是本 change 的反面**（连 record 都不调，自然无所谓丢不丢）。**本 change 仍然需要**（缝 2/3/4 依旧丢真实数），但**动机与真机预期会小一圈**。
   > **注**：这两条并不真正互斥——可以「手动 join 豁免记账（照 comment 的先例）」**且**「凡是进了 record 的就如实写」。但必须先要到裁决，否则真机数字对不上账。
2. **`dm_reply` 的 `quota=0` 是「不限量」还是「禁止」？** 今天这两者**不可区分**，正是这道闸把问题藏住了。D1+D4 之后 `dm_reply` 计数器首次开始累加（`canDo` 仍恒 false、门不变）。实装前坐实：`0` 是占位（`quota_config` 覆盖是唯一启用路径），故**预期无行为变化**——但微信入站是活路径，**必须单独测**。
3. **`view` 诚实记账后浏览会不会更早撞窗？** 见 D5。**不在本 change 调数值**，但真机必须核，且**这是最可能被当回归报回来的一项**。

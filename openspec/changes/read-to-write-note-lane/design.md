# Design: 阅读后写笔记旁路

## 1. 现状依据

- 浏览主链路已经由事件驱动闭环承载：`docs/architecture.md:134-151` 描述 `page.cards -> note.detail -> reading/interact -> action.completed -> feed.entered` 的往复。
- 角色职责已把“读”和“互动/返回”拆开：`docs/architecture.md:90-97` 列出阅读、互动、返回和发布链分别由不同组件承担。
- 参照创作能力已经存在：`openspec/specs/curated-note-actions/spec.md:25-48` 约定单条精选笔记可作为参照进入完整发布链，并在发布占用时诚实拒绝。
- 发布生成本身是全局串行且已有 busy 语义：`../aidcp-cloud/src/publish-agent/publish-orchestrator.ts:40-58` 在运行中会跳过新触发；`../aidcp-cloud/src/publish-agent/publish-orchestrator.ts:95` 说明生成候审段不触碰浏览会话。
- 面板动作已有“触发态”和“终态”分离：`openspec/specs/curated-note-actions/spec.md:116-129` 明确 triggered 只表示已受理，不代表最终成功。

## 2. 切换模型

把三者定义成互斥场景，而不是并排模块：

```text
Feed
  -> 打开笔记
阅读详情
  -> 互动/跳过
Feed

Feed / 阅读详情
  -> 写笔记
创作旁路
  -> 草稿受理/拒绝/占用
回到原场景并继续主循环
```

系统层面的“写笔记”不是直接让边缘端立即进发布页，而是触发现有发布生成链：当前笔记作为参照输入生成待审草稿，后续仍由飞书/控制台人审决定是否真的发布。

## 3. 决策点

写笔记判定应发生在阅读已经拿到足够上下文之后，且早于返回续刷完成态。推荐接在阅读完成后的互动评估附近，输入包括当前笔记标题、正文、作者、赞藏、话题、账号人设和本场发布占用状态。

判定结果分三类：

- `trigger`: 参照足够强，发布链空闲，触发生成候审草稿。
- `skip`: 普通内容、参照价值不足、账号不适合、当天/本场写作额度用完。
- `blocked`: 发布链占用、缺人设、正文缺失、依赖不可用；必须诚实记录原因，不染成成功。

触发成功后，浏览主链路仍继续返回 feed。生成草稿和人审是后台/异步结果，不阻塞刷 feed。

## 4. UI 口径

控制台不应同时常驻展示 Feed、详情、编辑器三块主内容。推荐：

- 列表/Feed：保留筛选和低干扰入口；行点击进入详情阅读。
- 详情浮层/阅读页：底部提供写笔记、评论、打开来源等上下文动作。
- 写笔记：在本阶段是“触发生成草稿并走人审”的动作，不是内嵌编辑器；成功提示只说已触发、去人审，不说已完成。

## 5. 失败边界

- 发布链 busy：返回未触发与稳定原因码，浏览继续。
- 当前笔记无正文/无标题/缺账号人设：拒绝触发，不进入发布链。
- 触发后生成失败：终态走既有发布/人审渠道，不能把触发回执追溯成成功。
- 人审未通过或未授权：绝不发布。
- 浏览返回失败：仍由既有返回 feed 自愈契约兜底，不因为写笔记旁路削弱。

## 6. 对抗性评审

- 风险：过度自动写笔记导致账号像内容农场。约束：判定要偏保守，并增加本场/日级触发上限或冷却。
- 风险：写笔记阻塞刷 feed。约束：生成候审段异步，不等待发布终态再返回。
- 风险：把“触发成功”说成“发布成功”。约束：沿用 triggered 与终态分离。
- 风险：参照创作变成照搬。约束：复用既有 referenceNote 独立参照块和非照抄红线。
- 风险：多个 UI 入口让用户困惑。约束：详情是阅读主场景，写笔记是上下文动作；列表只保留必要入口或迁移到详情动作区。

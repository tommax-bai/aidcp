# Proposal: 阅读后写笔记旁路

## Why

现有浏览主循环已经是「刷 feed -> 选笔记 -> 阅读 -> 互动/跳过 -> 返回续刷」。发布链路也已经存在，并且精选内容页能对单条素材触发「参照创作」。缺口在于：当系统在阅读现场发现一篇足够有启发的笔记时，不能只能点赞/收藏/评论后离开，也不能把“写笔记”塞成每篇必走的主链路。

需要把“写笔记”定义为一个可被阅读触发的创作旁路：它从阅读现场临时唤起，进入已有发布生成与人审链路；无论触发、拒绝还是占用，都不应打断浏览闭环继续返回 feed。

## What Changes

- 将 Feed、阅读详情、写笔记定义为互斥场景：同一时刻只有一个主场景；写笔记是从 Feed 或阅读详情唤起的创作旁路。
- 在阅读完成后增加“创作机会”判定：只有当笔记对当前账号人设有明确选题/结构/观点启发时，才触发写笔记；普通笔记继续走互动/返回。
- 写笔记复用既有发布链：以当前笔记作为 `referenceNote` 进入生成草稿、配图、人审、下发流程，保留 AC-PUB 人审闸。
- 浏览恢复优先：创作触发成功只表示“草稿生成已受理/将走人审”，不得阻塞当前阅读页返回 feed，也不得谎称已经发布。
- 控制台呈现与触发口径统一：列表是主场景，详情浮层是阅读场景，写笔记入口放在详情或明确的创作按钮，不把 Feed、阅读、编辑器三个大块同时常驻展示。

## Non-goals

- 不实现站内富文本编辑器或小红书原生编辑器常驻 UI。
- 不绕过已有发布审批、人审卡、失败回执和发布记录。
- 不把每次收藏/点赞都自动升级为写笔记。
- 不新增边缘端发布协议；本阶段优先复用既有发布生成与下发链路。

## Impact

- **aidcp-cloud**：在浏览阅读后的决策层增加创作旁路判定与触发；复用发布调度器的参照创作输入；补充触发、拒绝、占用和恢复测试。
- **aidcp-console**：将精选/阅读场景中的写笔记入口与详情阅读场景对齐，避免 Feed 列表同时暴露过多主动作；补充页面行为测试。
- **aidcp-edge**：预计不新增协议或动作；继续执行阅读、互动、返回和既有发布指令。
- **OpenSpec/docs**：新增 `read-to-write-note-lane` 能力，明确状态切换和失败边界。

## Validation

- `openspec validate read-to-write-note-lane --strict`
- 后续实现阶段：
  - cloud：相关角色/调度测试、浏览闭环集成测试、发布参照链测试、typecheck
  - console：精选/详情页交互测试、build/typecheck
  - 若触及协议或边缘端，再按协议/edge 回归纪律执行

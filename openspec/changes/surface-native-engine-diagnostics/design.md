## Context

Native 引擎是宿主（边缘核心进程）用 `spawn` 起的子进程，stdout 是 IPC 协议通道、stderr 是它唯一的自由输出口。引擎在 stderr 上已经写了 11 类具名诊断（15 处 `eprintln!`），其中相当一部分**写在成功路径上** —— 命令正常返回、进程正常退出。

宿主端 `NativeProcessTransport` 对 stderr 只做一件事：拼进 2048 字符的滚动尾缓冲（`client.ts:626-628`），并在构造进程级失败对象时把它挂进 `detail`。于是：

| 引擎写诊断的时机 | 今天能不能被人读到 |
| --- | --- |
| 命令成功返回（如逐字输入降级） | **不能**（进程不死，尾缓冲永不挂出） |
| 命令失败但进程存活（`session_open_failed` / `request_rejected`） | **不能**（同上） |
| 进程崩溃 / 超时 / 协议非法 | 部分能（仅最后 2048 字符，且被后续输出挤掉的先丢） |

**末端不缺，缺的是中间一跳。** Electron 外壳对核心子进程的 stdout/stderr 做逐行处理（`main.cjs:4772-4773` → `handleEdgeOutput`），按行 trim、去空行，未命中任何已知前缀的行**原样进 `edge.log` 与 UI 活动流**（`main.cjs:5836-5841`，单文件 ~5MB 轮转 + 1 份备份）。也就是说：**核心进程只要把引擎那一行打到自己的 stderr 上，它就到得了人眼前，Electron 侧零改动。**

约束三条：

1. `src/native-page-engine/client.ts` 是刻意保持的**纯协议客户端**（只 import Node 内置，`:1-6`），不能在里面直接写文件或 `console`。
2. `NativePageRuntime.serial()`（`runtime.ts:214-220`）保证同一运行时同一时刻只有一条命令在飞 —— 归因有依据。但 `NativeProcessTransport.pending` 里除命令外还可能并存控制记录（`commit_window_ack` 是 `void this.request(...)` 并发发出的，`client.ts:806-816`），所以**「pending 只有一条」不等于「命令只有一条」**，归因不能在传输层按 pending 数推断。
3. 核心 stdout 已被两条前缀桥占用（`[persona-reply]` / `[publish-approval-reply]`，`main.cjs:137/142`）。

## Goals / Non-Goals

**Goals:**

- 引擎子进程的每一行错误输出，在**不依赖进程死亡**的前提下，到达运营可读的位置（`edge.log` + UI 活动流）。
- 转发按行成帧、带在飞命令归因、有量上限且**上限是响亮的**。
- 现有的滚动尾缓冲行为**一字不改**（进程级失败仍靠它归因）。这是 tee，不是搬迁。
- 通路建成后，补上指针拟人轨迹的降级留痕（E12），并让「预算不够」与「目标已在脚下」在返回形状上两态可分。

**Non-Goals:**

- **不动 Native IPC 协议版本**（`NATIVE_PAGE_ENGINE_PROTOCOL_VERSION = 2`）。不新增诊断记录类型。
- **不动 Edge-Cloud WebSocket 协议**，诊断不回传云端（沿用 `src/client/command-diagnostics.ts:5` 已声明的边界）。
- **不扩 `[command-diagnostic]` 那条结构化通路**（见 Decision 2）。
- **不改任何命令的成败判定**。降级下的点击业务结果是真的，回执仍如实为成功；本 change 只让降级**被看见**，不让它改变结论。
- 不做诊断的聚合、告警、上报或 UI 专属视图。

## Decisions

### D1. 走「宿主转发子进程错误输出」，不走「协议加一条诊断记录」

**选它**：改动集中在宿主一侧（切行 + 回调注入），Electron 侧零改动，引擎侧一行不改就能立刻让 11 类既有诊断可见。

**否掉协议方案的理由不是「麻烦」，是它会碰就绪握手**：未就绪时任何非就绪记录都会被判协议非法并终止引擎（`client.ts:657-662`）。要让诊断在就绪前也能发，就得改握手状态机 —— 而「引擎起不来」恰恰是最需要诊断的时刻。协议方案还要跨语言四处同步（Rust 编码 / TS 解码 / 版本号 / 文档），本仓已多次为这类双写付出代价。

**代价（如实记）**：转发的是自由文本，不是结构化记录。所以本方案给的是「可读、可 grep」，不是「可被程序按字段消费」。行格式留了固定字段前缀，将来若真需要结构化消费者，可在不改引擎的前提下再加解析层。

### D2. 落到「未命中前缀的普通日志行」，不扩 `[command-diagnostic]` 结构化环

`[command-diagnostic]` 的形状是**云端命令生命周期**：`stage` 是 5 值枚举（received/rejected/dispatched/completed/failed）、`reason` 是 6 值枚举、`summary` ≤160 字符、只留 50 条 / 30 分钟。引擎降级既不是那 5 个阶段之一，也不该 30 分钟后蒸发。

**更硬的理由是同步成本**：那套校验有**两份实现**（`src/client/command-diagnostics.ts` 与 `src/electron/command-diagnostics.cjs`，一份 TS 一份 CJS，枚举各写一遍），扩枚举必须两处同改、且没有任何机械手段会在漏改时报警 —— 本仓已在同类双写上摔过（枚举漂移致整页白屏、客户 API 契约双写两次断线）。

**代价**：诊断行不进渲染层那个 50 条环，运营要看得去 UI 活动流或 `edge.log`。接受 —— 这批诊断的读者是排障，不是实时看板。

**顺带保住的一条**：`[command-diagnostic]` 分支**故意不把原始 JSON 写进 `edge.log`**（`main.cjs:5857-5859`，只留固定安全痕迹）。走普通行路径正好绕开这个矛盾：引擎诊断按契约是有界无内容的，**应当**原样落盘。

### D3. 出口用核心进程的 **stderr**，不用 stdout

核心 stdout 已被两条前缀桥占用。stderr 同样被 Electron 逐行 tee（`main.cjs:4773`），且天然不与任何 stdout 协议桥交织。

### D4. 归因在 `runtime.ts` 层做，不在传输层做

传输层不知道哪条 pending 是命令、哪条是控制记录（约束 2）。`NativePageRuntime` 知道自己此刻在执行什么。

**做法**：传输层只把「一行 + 单调序号」交给注入的回调；`runtime.ts` 注入的那个回调闭包读运行时当前命令并盖章。命令之间到达的行（建会话、重连、关闭期）如实标 `cmd=none`，**MUST NOT 顺手挂到上一条或下一条命令上** —— 那是把「不知道」写成「知道」。

**备选（否）**：让引擎在每行里自带命令 id。要改 15 处打点，且每个新打点都是一次可以忘记的地方；而宿主侧盖章只有一处。

### D5. 按行成帧，半行必须被识别为半行

今天的尾缓冲允许一行被 chunk 边界截成两半、也允许前半行被后续输出挤掉。转发必须自己维护行缓冲：

- 遇 `\n` 才成行；
- 单行超长（上限 2048 字符）→ 截断后**追加显式截断标记**，不静默截断；
- 进程退出时缓冲里还剩半行 → **冲出去并标记为不完整**，不丢弃（引擎崩溃时那半行往往最有价值）。

### D6. 量的上限必须响亮

**按命令计数**：单条命令内最多转发 N 行（取 50），超出部分计数而不逐行转发；该命令结束时补一行 `suppressed=<n>`。**保留最早的 N 行而非最新的** —— 排障要的是第一次出问题的现场。

**为什么不能静默截断**：一个只转发前 50 行、之后闭嘴的通路，读起来和「引擎从第 51 行起没再说话」完全一样。这是本仓反复点名的「静默假成功」在可观测性上的同形。

**不加环境变量开关**（YAGNI）：上限本身已经封住了日志量失控的风险；再加一个默认开启的旋钮只是多一处会漂的状态。

### D7. 转发**全部**行，但分类

只转发 `native_page_engine_*` 形状的行会更"安全"，但会把 Rust panic 与 backtrace 丢掉 —— 而那正是最该被看到的一类，且丢掉它是**静默的**。

**做法**：全部转发，每行标 `class=known`（命中引擎具名诊断族）或 `class=other`。分类不是装饰：它让「我们转发了一条不认识的东西」这件事可见，而不是与已知诊断混为一谈。

**内容安全边界随之前移并显式化**：`native-page-engine` 现有要求已规定解码诊断是有界、无页面内容的（其场景明写 bounded stderr 只含字段路径与 JSON 类别）。通路打开后这条从「反正没人看」变成真正承重，因此在新能力里把它升成对**整个引擎错误输出**的义务，而不只是解码诊断那一支。宿主侧同时做长度兜底（D5），但**宿主无法校验内容无关性** —— 这条义务只能由引擎侧承担，必须在规格里写明是谁的义务。

### D8. E12：把「两态压成一态」拆开，在 `input.rs` 单点打点

`generate_pointer_path`（`input.rs:1215-1233`）今天用一个 `if` 把两件完全不同的事返回成同一个形状：

```
if distance <= POINTER_DEGENERATE_DISTANCE_PX || budget == 1 { 单帧 }
```

- `distance <= 2.0`：目标就在指针脚下，单帧是**正确**行为，不是降级；
- `budget == 1`：帧预算只剩一帧（剩余预算 ≲63ms），单帧是**降级**；
- 另有一条今天完全无声的中间态：`count.min(budget)`（`:1240`）在 budget ∈ [2,14] 时把帧数压到拟人下限 `POINTER_FRAME_COUNT_MIN = 15` 以下（剩余预算 ≲480ms）。

**做法**：`PointerPath` 增一个降级字段（三态：无 / 低于拟人下限 / 塌成单帧），`input.rs` 增一个纯函数把它转成 note（形态对齐已有的 `typing_degradation_note`，`:499-506`），由 `dispatch_pointer_click` 这**一个**分发入口打点。

**为什么不按现有「input 建 note、engine 打点」的分工**：`dispatch_pointer_click` 有 **12 个调用点**（`engine.rs` 6 处、`facebook/auth.rs` 4 处、`facebook/shared.rs` 1 处、定义 1 处），且几乎全是 `if let Err(failure) = ...` 形式、把 `Ok` 值直接丢弃。把降级信息穿回 12 个调用点去打印，等于开 12 个可以忘记的口子，还要动一个串行热点文件的 12 个位置。分发入口只有一个，忘不掉。

**打点不带业务标签**：单靠引擎自己说不清「这次点击是哪条命令的哪一步」。**这正好由 D4 的宿主盖章补上** —— 两个决定合起来才完整，任何一个单独做都只得到半条信息。

**可达面如实**：传真实死线的路径才可达（小红书评论提交 `engine.rs:1510`、详情浮层关闭 `:2112` 等）；Facebook 那条传 `u64::MAX`（`facebook/shared.rs:1043`），永远不降级。

### D9. 降级不进回执

回执是业务结果，降级不是业务失败 —— 点击真落在目标上、真按下抬起，`ok=true` 属实。把降级塞进回执会（a）动协议、（b）诱使上游把它当失败处理。**本 change 明确不做**，并把这条边界写进规格，免得下一个人以为是漏了。

## Risks / Trade-offs

- **[日志被冲淡]** 引擎变啰嗦时，`edge.log` 的 5MB 窗口会更快滚掉历史 → 单命令 50 行上限（D6）封顶；且超限有响亮计数，量真的失控时看得见，而不是靠猜。
- **[内容安全义务转移到引擎侧]** 通路打开后，引擎侧任何一处把页面文本写进 stderr 都会落盘 → 在规格里把「引擎错误输出 MUST 无页面派生内容」写成显式义务（D7），并在宿主侧做长度兜底；**如实承认宿主无法校验内容**，不假装有兜底。
- **[归因可能落到 `none`]** 建会话 / 重连 / 关闭期的诊断没有在飞命令 → 如实标 `cmd=none`。这是设计而不是缺陷：宁可承认不知道，也不挂错。
- **[E12 改的是串行热点文件]** `input.rs` 是并行开发点名的单写区 → 本 change 独占该文件期间不与他人并行；改动集中在路径规划与分发入口两处，不碰按下/抬起配对与不可打断窗口。
- **[「加了但没接上」]** 最像成功的失败形态是：回调选项加好了、`runtime.ts` 没传 → 通路仍然不存在，而所有单测都绿。→ 必须有一条**按引用**断言注入确实发生的用例，不能只测回调本身可用。
- **[转发行本身把 UI 刷屏]** 诊断行会进 UI 活动流 → 上限已封顶；且这批诊断本就是低频（降级、拒绝、控件缺失），高频出现本身就是该被看见的信号。

## Migration Plan

无数据迁移、无协议版本变更、无部署顺序依赖。宿主转发缺省开启；未注入回调时行为与今天逐字相同（回调可选，缺席即今天）。回滚＝还原 `client.ts` / `runtime.ts` 两处提交，引擎侧改动（E12 的两态可分）可独立保留。

Native 引擎二进制随桌面客户端出包分发，**本 change 的效果要等下一次出包才到运营机**（与 handoff §2.2 的口径一致：不为此专门打包）。

## Open Questions

- 将来是否需要把降级做成**跨命令的聚合信号**（例如「本会话内 N 次点击降级」）以驱动节奏调整？本 change 不做，也不预埋抽象；等真有消费者再谈。
- `class=other` 的行（panic / backtrace）在真机上到底长什么样、量有多大，只有出包后才知道；上限与格式可能需要按实测调一次。

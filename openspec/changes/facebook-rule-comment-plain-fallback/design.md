## Context

联系方式注入今天只发生在命令式评论任务机器里，六个入口共用同一台机器：飞书手动命令、内容排期联系评论、精选定向联系评论、引流热帖联系评论、委托任务联系评论，以及 Facebook 规则模式的加群联系评论。机器入口处有一道联系方式闸——当本次任务标记为「需注入」而账号无联系方式时，直接回一张告警回执并本次不发。

这道闸的位置很关键：**它在加群之前**。因此规则模式下缺联系方式的账号今天连加群命令都没下发过，规则轮次以「加群未启动 / 评论未启动」终结。运营看到的是这类账号长期零产出。

同时，规则模式的开关写入侧只校验账号平台，不像内容排期那样在开启时校验联系方式，所以「开着但没配」是一个可以长期存在的稳定状态。

还有三处与本设计强相关的现状：

1. **对外表述按请求意图渲染**。合并结果卡与触发回执用的是「本次请求是否要求注入」，不是「本次实际是否注入」；而人审卡用的是实际值。一旦允许降级，同一次动作的两张卡会互相矛盾。
2. **审批模式来源分叉**。联系评论取联系评论的审批配置，普通评论取普通评论的审批配置，两者可各自独立设为免审或关闭；此外还有一层账号级全局免审会把有效审批模式强制拉成免审，且这一层与「联系评论 vs 普通评论」的区分完全无关。
3. **正文来源与联系方式无关**。正文是「账号模板优先、账号模板为空回落群组区域模板」，两级都取不到就诚实停止。降级不改变这条链。

## Goals / Non-Goals

**Goals:**

- 让规则模式下缺联系方式的账号不再零产出：入群继续发生，评论以不带联系方式的普通评论发出。
- 把这次红线放弃限制在**一条链路**上，其余五个入口保持原保证不变。
- 保证降级后没有任何一处对外表述宣称「带了联系方式」，也没有任何一处授权外溢。
- 保证降级引入的新平台写动作（真实加群）是被显式声明的，而不是副作用。

**Non-Goals:**

- 不解决「账号也没有模板」。降级后仍可能诚实停在缺模板，本变更不为提高成功率引入任何默认文案或生成式回退。
- 不改正文来源解析链、不改评论校验器、不改联系评论额度台账。
- 不改其余五个入口，尤其**不**改飞书手动 `--contact`：运营显式要求带联系方式却发出不带的，正是既有保证的判例本身。
- 不改规则模式节奏（另一变更承接）。

## Decisions

### D1：降级意图由调用方显式传入，共用闸默认仍是 fail-closed

**选择**：命令式评论任务机器的联系方式闸新增一个显式的降级意图参数，默认值为 fail-closed。只有规则模式的触发处传入「允许降级」。

**理由**：六个入口共用同一道闸。如果在闸上一刀切降级，飞书手动 `--contact` 也会被降级——那是操作员的显式指令，降级即违背指令。默认值必须是安全的那一侧，让每个想要降级的调用方自己承担声明责任。

**备选（否决）**：在规则模式触发处直接把「需注入」置为 false 再往下走。否决理由：这样机器内部就完全不知道「本来是要带联系方式的」，审批车道、回执话术与结果投影都失去了区分依据，等于把降级伪装成「本来就是普通评论」——这正是需要避免的静默。

### D2：「本次实际是否注入」升为独立事实，向下贯穿

**选择**：把「请求意图是否需要注入」与「本次实际是否注入」拆成两个事实，一路带到审批、回执、通知与结果映射。

**理由**：今天这两件事共用一个值，所以只要允许它们不一致，任何按意图渲染的地方都会说谎。合并结果卡会宣称「已在群内发出一条带联系方式的评论（服务器已确认）」，而人审卡上运营刚刚看过的是不带联系方式的正文——**两张卡自相矛盾比单张卡说谎更难排查**。三处对外表述统一到实际值，并为降级新增可辨识话术。

### D3：降级产出走普通评论的审批车道

**选择**：降级后的审批模式取普通评论的配置，不取联系评论的配置。账号级全局免审对该次动作的作用同样按普通评论车道判定。

**理由**：既有规格把两者定为两条车道——联系评论走人审车道、普通评论走无人值守校验车道；代码里唯一的区分就是审批模式的来源字段。运营给「联系评论免审」时授权的是「带联系方式的模板评论」，把这份授权自动扩展到一条他从未为该车道授权的普通评论正文，是授权外溢。

**代价**：如果运营给联系评论开了免审、普通评论没开，降级后的评论会需要人审。这是正确的默认——它把「我从没为这条车道授权过」如实呈现给运营，而不是替他决定。

### D4：降级会真实加群，这是行为扩张而非副作用

今天缺联系方式时加群从未下发。降级后加群会真正执行，因此加群的实时风控闸与会话预算**第一次真正生效**，加群日配额成为新的收敛点；且加群的风控记账判据是「点到了」而非「整体成功」，所以即使评论最终失败，这次加群尝试也会占掉当日额度。

**选择**：把这件事写进规格与运营说明，而不是让它在上线后被发现。

### D5：规则轮次的评论段结果必须可区分

**选择**：规则轮次的评论段结果需要能表达「降级普通评论已确认」，与「联系评论已确认」区分开。

**理由**：规则轮次的动作状态是一个有限枚举，且阻断原因是三阶段共用一列、后写覆盖先写。若不做区分，后台与客户端会把一条降级普通评论显示为联系评论已完成——运营会以为联系方式发出去了。这属于「静默假成功」红线。

### D6：开关侧给提示，不给硬拒

内容排期在开启联系评论时对无联系方式账号是硬拒的。规则模式**不**照搬硬拒——因为本变更的前提就是这类账号也要能跑。**选择**：开关写入成功，但回读中带出具名说明「该账号无联系方式，联系评论将降级为普通评论」，让运营在配置当刻就知道会发生什么。

## Risks / Trade-offs

- **[降级后仍评不出来]** 正文来源是模板；区域模板目录在 DEV 上真态为空，未配模板的账号降级后会诚实停在缺模板。→ 缓解：规格明写降级不承诺产出；运营说明里同时给出「要真正见效需先配模板」的前置条件；MUST NOT 通过默认文案或生成式回退来「提高成功率」。
- **[红线放弃的范围蔓延]** 共用闸上的降级参数一旦存在，后续调用方很容易顺手打开。→ 缓解：默认值 fail-closed；为其余五个入口各留一条断言，锁死它们的 fail-closed 行为，任何人打开都会打红。
- **[授权外溢]** 见 D3。→ 缓解：审批模式来源按车道判定，并为「联系评论免审 + 普通评论未免审」这一组合补断言。
- **[两张卡口径不一致]** 见 D2。→ 缓解：三处对外表述统一到实际注入值，补断言覆盖「降级后结果卡不得宣称带联系方式」。
- **[新增真实入群]** 见 D4。→ 缓解：显式声明；DEV 验收时观察加群日配额消耗是否符合预期。
- **[原生页面引擎路径不等价]** 边缘有两条评论执行路径，正文与联系方式的拼接方式不同，且原生路径正在切换中。→ 缓解：实装期两条路径分别核验，不以一条通过代表另一条。
- **[规格叠层与并行]** `facebook-rule-mode` 未并入主 spec；`facebook-rule-mode-without-persona` 同改规则轮次评论段。→ 缓解：归档顺序与串行纪律列入前置闸。

## Migration Plan

1. 前置：确认 `facebook-rule-mode-cadence` 已归档；与 `facebook-rule-mode-without-persona` 对齐落地顺序。
2. 拆分「请求意图」与「实际注入」两个事实，闸改为按显式意图分流，默认 fail-closed。
3. 规则模式触发处传入降级意图，并按普通评论车道解析审批模式。
4. 三处对外表述改按实际值渲染，新增降级话术。
5. 规则轮次结果映射新增可辨识终态；后台同步。
6. 开关写入侧增加降级提示。
7. 为其余五个入口补 fail-closed 锁定断言。
8. 部署 DEV，验收：无联系方式账号能入群并发出普通评论（或诚实停在缺模板）；结果卡不宣称带联系方式；飞书手动 `--contact` 仍 fail-closed。
9. 回滚：降级意图是显式参数，回滚只需在规则模式触发处停止传入，无数据迁移。

## Open Questions

- 降级产出的普通评论是否需要计入某条额度轴？规则模式的联系评论今天**不**进联系评论额度台账，因此降级后也不会占该轴；是否需要为规则模式单独立一条评论额度上限，还是继续只靠风控的评论配额收敛。
- 运营说明的落点：降级提示只在开关回读里给，还是同时在后台账号页给出常驻提示。

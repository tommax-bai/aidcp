## Why

云端的「会话启动闸」目前是**一次性判决**：边缘握手那一刻判一次，判到「未绑人设」就短路并且**永不复判**，该连接整个生命周期停手。

而「自动补人设」与「握手开工」是**同一个事件（环境绑定账号）**触发的两条并行分支——一条往接口域库写人设，一条读自动化进程的只读副本。读永远快于写落到副本，于是**每一个新账号的第一次运行必然踩中**，不是偶发竞态。

2026-08-05 在 dev 上实测坐实：4 个新账号（`k1fd399h` / `k1fd39cj` / `k1fd39dv` / `k1fd39f4`）的人设自动补齐台账全部 `succeeded`，写入时刻与被判「未绑人设」的时刻相差 0.1~0.8 秒，四个账号**全部**被判死、整机零动作。运营手动补设人设也无效——单体时代那条「绑定成功即就地开跑」的自愈通道，在云端三等分后落在接口进程，而接口进程给不出自动化段的句柄（该处已有具名残留注释），通道断了。

这违反本仓红线「终结与否只看结构性」：「此刻副本里还没有这个账号的人设」显然是**重来会得到不同结果**的非结构性失败，却被落成终态、且没有留任何自愈通道。

## What Changes

- 会话启动闸的拒绝结论**按结构性分三类**，不再一律终态：
  - **结构性拒绝**（该平台根本不具备浏览能力）→ 维持既有终态行为，MUST NOT 复判。
  - **可恢复拒绝**（未绑人设 / 人设副本陈旧 / 配置镜像陈旧）→ MUST NOT 落终态，MUST 武装一条复判通道。这三条的共同点是「云端此刻读到的事实还会自己变好」。
  - **运营意志类拒绝**（全局调度开关关闭）→ 本 change **不纳入复判**：它不是「读早了」，是运营的显式停机，且已有专门的恢复入口。把它纳入等于让全局停机在任一连接上 60 秒后被自动解除，那是另一件事。
- 复判用**纯判据**（无副作用的那一支），一旦结论变为可启动即走既有的「绑定人设后就地开跑」路径（该方法已实现「起会话 + 补一条重驱唤醒干等的边端」）。
- 复判节奏按退避拉开，生命周期绑定在**连接**上：连接拆除或会话真起来即解除武装。每跳只是一次纯内存读，不产生任何 I/O、不落库、不发命令。
- 日志只在**两个跃迁点**出现（首次被拒、复判后放行），中间每跳静默——既有代码明确记过「一个只读方法不该有每分钟一次的告警脉冲」，复判 MUST NOT 制造这种脉冲。
- 放行回执 MUST 说清是「被某闸挡住、复判后放行」，MUST NOT 表现成一次普通握手启动（否则档案里看不出竞态发生过）。

不改变的：任何「未绑人设就以默认人设开跑」的口子一个都不开；三态语义（`bound` / `unbound` / `unknown`）与各自的用户可见态、告警口径、Facebook 规则模式豁免全部照旧。本 change 只改「被拒之后还认不认这个结论」。

## Capabilities

### New Capabilities

（无——本 change 只收紧既有闸的终态语义，不引入新能力。）

### Modified Capabilities

- `persona-gated-session-start`: 新增要求——启动闸的拒绝结论 MUST 按结构性分类；可恢复类拒绝 MUST NOT 落终态、MUST 在同一连接内复判并在结论转好时就地开跑；复判 MUST NOT 重复触发告警与「会话被拒」回调。

## Impact

- **代码**：`aidcp-cloud/src/orchestrator/role-dispatcher.ts`（自动化段属主，会话启动闸与复判通道）。派生仓 `aidcp-automation` 经 `scripts/sync-split-repos` 同步，MUST NOT 手工搬文件。
- **行为**：新账号首次接入不再因竞态停摆；运营在客户端补设人设后，同一连接内自动开跑，无需重连环境。
- **不涉及**：协议无变化（不新增消息类型）、数据库无变化（不新增表/列）、边缘无变化、接口进程无变化。
- **明确不在本 change 范围**：接口进程写完人设后**跨进程叫醒**自动化进程（补回断掉的那条通道），需要新的传输通道，另立 change。本 change 落地后，那条通道的收益只是把「≤60 秒自愈」优化成「立刻」。

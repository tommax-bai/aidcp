## Context

FB 限流识别链路早已建成，现状（全部经代码复核）：

**通的部分**——边缘的 Facebook 遮罩监测体以 1s 轮询扫全页文字，评论执行器与它共用同一实例，因此评论提交后（含回车之后）弹窗弹出的那一刻，监测体是在场并且看得见的。命中后经既有的遮罩上报消息报给云端，云端把「已确认限流」升为 confirmed 信号，一步迁到 `restricted`（跳过 warned）、互动配额清零只留浏览、并暂停该边缘。终态仍由云端风控控制器单写，迁移表不动。

**断的部分**——两处，且**必须一起修**：

1. **判据不认这类措辞**。两仓限流词库的中文条目全是「封锁 / 不可用」框架，用户遇到的是「频率」框架，零命中 → 分类为无事 → 上报都不发。
2. **证据文本与判据文本不是同一份**。分类读的是「整页文字（截 4000 字）」，上报带的却是「遮罩快照里某个 DOM 元素的文字（截 500 字）」。而快照的候选筛选对「未知阻断」这一类要求：带 iframe，**或**（宽 ≥60% 视口 **且** 高 ≥40% 视口 **且** 无关闭控件）。FB 标准限流弹窗是 `role=dialog`、无 iframe、约占视口 35%、右上角有关闭 ×——三个分支全不满足 → 候选为空 → 上报证据文本为 `undefined` → 云端按「无文案不臆断限流」返回 false → 信号只到 light → 降速 30%（`warned`），而非刹车（`restricted`）。

**第三处是可见性问题**：命中限流这个布尔事实在协调器内是块级局部变量，从未传进告警构造函数，告警只按遮罩种类分支 → 一次确凿的平台限流被发成 P1「未知阻断弹窗」，与随便什么弹层同款。附带地，告警冷却是「按边缘、不分类型、10 分钟」，且落 `alerts` 记录的动作在同一道闸之后 → 窗口内先到一张验证码告警，限流告警连记录都不落。

**约束**：
- 协议零改动（遮罩上报消息与其证据文本字段本就是为此设计的）；风控状态机迁移表与终态云端单写不动；无 DB 迁移（告警类型字段是裸文本无约束，仅优先级被约束在 P0–P3）。
- **代价严重不对称**：命中一次 → `restricted` → 钉 3 天且不自动回滚，只能人工恢复。一次误报 = 一个号停摆 3 天。
- 两仓词库手工各维护一份、无共享模块，**且已实证漂移**（云端多两条英文条目边缘没有 → 那两条今天是死代码：边缘不分类就永不上报，云端永远收不到能命中它们的文本）。

## Goals / Non-Goals

**Goals:**
- 这句中文「频率」框架弹窗被识别，并驱动既有的限流→刹车链路真正生效（到 `restricted`，不是只降速）。
- 判为阻断态的上报**必然携带非空证据文案**，不再因快照候选筛选落空而报出无文案的空壳阻断。
- 确认的平台限流告警对运营**可辨**（独立类型 + P0），对面板**可过滤**，且不被其他阻断类型的冷却吞没。
- 误报面受控：判据只用长专属句片段，且真机逐字坐实后才定稿。

**Non-Goals:**
- 模型兜底分类未命中的弹窗（属 `fb-cross-language-recognition` L2/L4，另一 change 量级）。本 change 只把这一句已知文案接上；跨语言脆性只是被推后一格，不假装解决。
- 两仓词库共享模块（无跨仓共享基建，成本 > 收益；两侧单测锁对齐即可）。
- 评论侧新增限流归因回执（触碰失败原因枚举 + 云端映射，且必须插在页面重载之前，另属独立链路）。
- `restricted` 三天自动回滚策略、小红书侧限流词库（均正交）。
- 放宽遮罩快照的 DOM 可信阈（见 Decisions 第 2 条，明确否决）。
- 搬运 `account-nurture-discipline-spine` 孤儿分支的 spec（见 Decisions 第 5 条）。

## Decisions

### 1. 判据用「长专属句片段」，不用裸词，也不用结构信号单独定性

**决定**：词条取整句中最不可能随版本变动的中段（如「限制了你发帖、评论或执行其他操作的频率」「我们限制了你发帖」「限制了你执行此操作的频率」）。**绝不加裸词「限制」/「频率」**。

**为什么**：误报代价 = 一个号停 3 天且需人工恢复；漏报代价 = 维持现状（本来就漏）。**代价不对称，所以宁可漏不可错**。裸词在 FB 群规则页、隐私设置页遍地都是，必然误伤。

**备选方案 — 纯结构信号（提交动作后冒出 `role=dialog` 即判限流）**：否决。结构信号跨语言是它的优点，但它**区分不了限流弹窗、参与审批弹窗、权限弹窗**——而这几者代价天差地别（一个停 3 天、一个只是等管理员点头）。可行的分层是「结构定位（哪个 dialog、什么时机）+ 文本定性（是不是限流）」，本 change 只做后者的补全，前者留给后续。

### 2. 补齐证据文本走「回填分类时已取的整页文字」，**不放宽快照的 DOM 可信阈**

**决定**：在边缘的遮罩上报分支，当遮罩已被判为阻断态、而快照候选为空导致证据文案为空时，用分类那一次已经取到的整页文字回填（截断到有界长度，500–1000 字量级）。

**为什么**：这只影响「**已经判定为限流的那一刻带什么证据**」，**不改变判定本身**——判定仍由词库在整页文字上完成，回填不会让任何原本不命中的页面变成命中。

**备选方案 — 放宽候选筛选的 DOM 启发式（降低尺寸阈值 / 允许有关闭控件）**：**明确否决**。放宽 DOM 门槛会把大量良性弹层拖进快照，误报面成倍上涨，而误报代价是账号停 3 天。这条路是用「所有弹层的可信度」换「一类弹层的证据」，性价比是负的。

### 3. 匹配面放大到整页文字是本设计的已知代价，用词条纪律对冲

云端原本匹配的是「单个弹窗元素约 500 字」，回填后变成「整页约 4000 字」。页面别处随便出现「限制」字样就可能命中——**这正是 Decision 1 的词条必须是长专属句片段的原因，不是可选的谨慎，而是本决策的前置条件**。两条决策是绑定的，不可单独采纳其一。

### 4. 告警标注复用现有告警构造，只把已有的事实透传出去

「已确认限流」这个布尔在协调器里本就算出来了，只是作用域没逃出块级——把它提升到与状态同层并透传给告警构造即可，无需新数据流。类型字段是裸文本无 CHECK 约束，新增类型值**不需要迁移**。冷却键加类型维度，避免验证码告警吞掉限流告警。

**备选方案 — 新增独立告警通道**：否决，现有构造 + 路由（来源会话 → 团队群 → 默认群，统一口径）已足够，新造通道纯属重复建设。

### 5. 与孤儿 spec 划职责，不接管、不搬运

既有的「Facebook 限流信号 → 激进退避到 `restricted`」需求**不在主干 spec 上**：它属 change `account-nurture-discipline-spine`，spec delta 只存在于分支 `feature/fb-full-integration`，代码已进 edge/cloud master、文档从未合回 `main`（与已知的「隔离分支未合回 main → 清账必漏」同源）。

**决定**：本 change 的新增需求**刻意与那条不重叠**——只覆盖「文案覆盖面 + 证据非空 + 告警可辨」，不重述「→ restricted」的迁移行为。

**为什么**：两个 change 向同一 capability 添加语义重叠的需求，是已知会在归档时打架的失败模式（需要事后「划职责」补救）。提前划清比事后解冲突便宜。孤儿分支的清账另行登记，不塞进本 change。

### 6. 诚实红线两个方向都守

- **不能**因为发了告警就把评论算成功。
- **也不能**因为看到限流弹窗就把已被服务器确认的评论改判失败——评论执行器现有立场（提交后的误导性报错浮层不当作失败、确认信号权威）是**对的，不推翻**。

限流场景下评论的正确回执仍是「确认不了」，永远不是「成功」。归因回执（让运营看到「是被限流了」而不是「确认不了」）是 Non-Goal，留待后续。

## Risks / Trade-offs

- **[误报 → 账号停摆 3 天且需人工恢复]** → 词条只用长专属句片段（Decision 1）；且必须真机 CDP 抓取弹窗原文逐字比对后才定稿（用户提供文案来自截图转录，不保证与页面逐字一致：标点全/半角、「社群 vs 社区」地区差异）。真机未坐实前不合入词条。
- **[回填把匹配面从 500 字放大到 4000 字]** → 由 Decision 1 的词条纪律对冲；两条决策绑定采纳。
- **[快照候选为空这个前提是推理得出，尚未真机证实]** → 登记真机验收项专门确认；若真机发现候选**并非**为空（弹窗恰好命中某分支），则回填逻辑成为无害的兜底，判定不受影响，本 change 仍成立。
- **[现有告警测试是假绿盲区]**（消息通道被打成 undefined、告警函数第一行即返回）→ 告警标注改动会零覆盖上线；必须补一条带真实消息通道的用例，否则这一段等于没测。
- **[两仓词库手工同步、已实证漂移]** → 本 change 顺带消除现存漂移；两侧各加单测锁住词条集合，把漂移从「无人发现」降级为「测试失败」。不建共享模块（Non-Goal）。
- **[跨语言仍脆]** → 补这句只把问题推后一格，换个语种照样瞎。**这是本 change 承认并接受的局限**，彻底解法在 `fb-cross-language-recognition` L2/L4。
- **[告警冷却互压]** → 冷却键加类型维度缓解；注意落 `alerts` 记录的动作在冷却闸之后，故冷却不仅压卡片、也压记录——加类型维度同时修好这两者。

## Migration Plan

无 DB 迁移、无协议改动，纯代码 + 词库。

1. **两仓并行改**（edge 词库 + 证据回填；cloud 词库 + 告警标注 + 冷却键）。词库两侧词条集合必须一致，各自单测锁住。
2. **验证序**：先 `test:acceptance` 再全量 `test` 再 `typecheck`（协议/风控相关改动的既定纪律）。注意本 change 不碰协议，但触碰风控输入面，acceptance 的风控红线（绝不自残、被禁 record 返 false）必须全过。
3. **部署**：cloud 侧按标准安全序列部署 dev（先备份 → rsync → 重启 → healthcheck → 失败回滚）；edge 侧为本地运行，改动随默认收尾提交推送，不出安装包。
4. **真机验收**（登记 backlog，靠现有 FB 簇）：CDP 抓真弹窗整页文字逐字比对词条 → 确认候选为空这一假设 → 确认告警为 P0 且账号确实进到 `restricted`。
5. **回滚**：词条为纯数据、告警标注为纯分支，回滚即还原代码；无状态残留。**但注意**：若误报已把账号迁到 `restricted`，回滚代码**不会**自动恢复账号状态（风控态不自动回滚是既有设计），需人工恢复——这是先真机坐实词条再合入的另一个理由。

## Open Questions

- **词条最终字面待真机坐实**：用户提供的是截图转录文本，页面实际 `innerText` 的标点形态（全/半角）与用词（「社群」vs「社区」）需 CDP 抓取确认后才能定稿。**这是唯一阻塞词条合入的未决项**，其余实现（证据回填、告警标注、冷却键）不依赖它、可先行。
- **是否一并覆盖同框架的其他 FB 频率文案变体**（如仅「限制了你执行此操作的频率」的短变体）→ 倾向于真机抓到几条就收几条，不凭空扩充；未见过的变体不进词库。
- **评论侧限流归因回执**（让运营看到「被限流」而不是「确认不了」）→ 已列 Non-Goal，但可作为下一 change 的直接候选；其硬约束已探明：必须插在页面重载之前（重载会把弹窗刷掉、证据即失），且非侵入式探测不触发风控迁移——与 1s 轮询那条链是两条独立链，设计时不可当成一条。

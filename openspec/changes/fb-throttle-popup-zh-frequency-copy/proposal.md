## Why

Facebook 发布评论后偶发中文弹窗「为让社群免受垃圾信息打扰，我们限制了你发帖、评论或执行其他操作的频率。你可以稍后再试。」——**这条弹窗对系统当前是全静默的**：账号已被平台限流，云端风控态仍停在 `normal`，继续按原节奏发帖评论，零告警、零 `alerts` 记录。

识别机制本身早已建成且通路完好（边缘遮罩监测体全程 1s 轮询扫全页文字，评论执行器与它共用同一实例），断点只有两处，且**必须一起修才有效**：

1. **词库只认「封锁」框架，不认「频率」框架**。两仓限流词库的中文条目全是「暂时被限制 / 操作被封锁 / 功能暂时不可用」这类封锁措辞；用户遇到的是「限制了你……的频率」这类频率措辞，零命中 → 判为无事 → 连上报都不发。
2. **上报的证据文本是空的**（结构性洞，补词库也解决不了）。分类读的是整页文字，上报带的却是「某个 overlay DOM 元素」的文字，而该元素的入选条件要求弹窗带 iframe、或极大且无关闭控件；FB 标准限流弹窗（`role=dialog`、无 iframe、约占视口 35%、右上角有关闭 ×）三个条件全不满足 → 候选为空 → 证据文本 `undefined` → 云端按「无文案不臆断」返回 false → 只降速 30%，而不是刹车。

另有一处让运营看不见：命中限流这个事实在告警发出前被丢弃，一次确凿的平台限流被发成 P1「未知阻断弹窗」，与随便什么弹层同款，运营无从区分、面板无法按类型过滤。

**为什么是现在**：限流是账号已经受损的信号，越晚发现继续操作越久、损伤越深；而修复面极小（无协议改动、无 DB 迁移），没有理由继续让它静默。

## What Changes

- **边缘限流词库补入中文「频率」框架句片段**，使这类弹窗被判为阻断态并经既有上报通道报给云端。词条取整句最不可能随版本变动的中段（如「限制了你发帖、评论或执行其他操作的频率」），**绝不加裸词「限制」/「频率」**。
- **边缘补齐上报证据文本**：当遮罩被判为阻断态、但快照候选为空时，用分类时已取到的整页文字回填上报文案（截断到有界长度）。这是本 change 的真正价值点——不修它，词库补了也只到降速档。
- **云端限流词库同步同一批中文词条**，并补齐两仓已实证的漂移（云端多两条英文条目边缘没有，今天是死代码）。
- **云端告警标注限流分类**：命中限流的告警升为 P0、标题明确为「Facebook 限流阻断」、类型独立于泛化的阻断告警，使运营可辨、面板可过滤。
- **告警冷却按类型分维**：避免 10 分钟窗口内先到的验证码告警把限流告警连同 `alerts` 记录一起吃掉。
- **补测试**：现有告警测试是假绿盲区（消息通道被打成 undefined，告警函数第一行即返回），告警标注改动会零覆盖上线，必须补一条带真实消息通道的用例；并新增本 change 的钉子断言——判为阻断且快照候选为空时，上报证据文本必须非空。

**不改协议**：复用既有的遮罩上报消息与其证据文本字段（该字段本就是为此设计）。**不改风控状态机**：迁移表、终态云端单写均不动。**无 DB 迁移**。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `captcha-incident-handling`: 新增三条需求——① 平台限流文案的识别必须覆盖「频率」框架的中文变体，且判据必须是长专属句片段（误报代价不对称）；② 判为阻断态的上报必须携带非空证据文案，不得因快照候选筛选落空而报出无文案的阻断；③ 确认的平台限流告警必须以独立类型与更高优先级发出，且冷却不得与其他阻断类型互相吞没。

> **划职责说明**：既有的「Facebook 限流信号 → 激进退避到 `restricted`」需求**当前不在主干 spec 上**——它属 change `account-nurture-discipline-spine`，其 spec delta 只存在于分支 `feature/fb-full-integration`（代码已进 edge/cloud master，文档从未合回 `main`）。本 change **不接管、不搬运**那条需求，新增需求刻意与其不重叠，以免两个 change 抢同一 capability。该孤儿分支的清账另行登记，不在本 change 范围内。

## Impact

**aidcp-edge**（2 文件 + 2 测试）
- Facebook 遮罩分类模块：限流判据正则加中文频率框架句片段
- 主进程遮罩上报分支：证据文案为空时回填分类时已取的整页文字
- 对应单测：词条命中、候选为空时上报文案非空

**aidcp-cloud**（2 文件 + 2 测试）
- Facebook 限流词库：同步中文词条 + 消除两仓漂移
- 验证码/阻断协调器：把「已确认限流」这一事实透传到告警构造，标 P0 + 独立类型；冷却键加类型维度
- 对应单测：词库对齐、带真实消息通道的告警断言

**不受影响 / 明确不碰**
- 边-云协议（零改动）、风控状态机迁移表、终态云端单写
- 遮罩快照的 DOM 可信阈（放宽会成倍放大误报面，误报代价是账号停 3 天）
- 评论回执语义（提交后误导性报错浮层不当作失败、确认信号权威的现有立场是对的）
- 小红书侧（词库为 FB 专属措辞，换 XHS 零命中）

**告警路由**：沿用统一口径「来源会话 → 团队群 → 默认群」，本 change 不引入任何路由特例。

**风险面**：证据回填把匹配文本从「单个弹窗元素约 500 字」放大到「整页约 4000 字」，误报面随之扩大——这正是词条必须是长专属句片段、且必须真机逐字坐实后再定稿的原因（用户提供的文案来自截图转录，不保证与页面文字逐字一致：标点全/半角、「社群 vs 社区」地区差异）。

## Non-Goals

- **模型兜底分类未命中的弹窗** → 属 `fb-cross-language-recognition` 的 L2/L4，另一 change 量级。本 change 只把这一句已知文案接上，跨语言脆性只是被推后一格，不假装解决。
- **两仓词库共享模块** → 无跨仓共享基建，成本 > 收益；用两侧单测锁对齐即可。
- **评论侧新增限流归因回执** → 会触碰评论失败原因枚举与云端映射，且必须插在页面重载之前（重载会把弹窗刷掉、证据即失），另属一条独立链路。留作下一 change 或单独 task。
- **`restricted` 三天自动回滚策略** → 正交。
- **小红书侧限流词库** → 正交。
- **放宽遮罩快照的 DOM 可信阈** → 误报代价 3 天，不碰。
- **搬运 `account-nurture-discipline-spine` 孤儿分支的 spec** → 见上「划职责说明」，另行清账。

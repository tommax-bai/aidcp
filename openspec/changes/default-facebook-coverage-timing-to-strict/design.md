## Context

选群口的「放开时限兜底」在账号所有群都不合规时，丢掉预热、冷却与单群冷却三道闸照常评论。它今天由环境变量控制、**默认开启**。

2026-07-29 已在 dev 上显式关闭。但那个设置只活在服务器上的运行时配置文件里，而该文件被版本库忽略、部署时被显式排除、仓库里连模板都没有。所以代码库里**没有任何地方**记录着这个兜底应该是关的，生产环境至今仍是开启状态。

## Goals / Non-Goals

**Goals:**

- 让「严格」成为不需要任何配置就成立的默认姿态。
- 让这条安全姿态跟着版本走，而不是跟着某一台机器上的一个文件走。
- 保留「临时放开」的能力，但改成显式动作。

**Non-Goals:**

- 不改预热期与冷却期的取值。
- 不改选群口在**有合规群**时的任何行为。
- 不删除该环境变量。
- 不动 dev 上已有的那一行配置（改后它成为冗余，留着无害）。

## Decisions

**D1. 判据从「不等于关就是开」改为「等于开才是开」。**

这不只是取反。原写法把「配置缺失」「配置为空」「取值拼错」全部归入开启一侧——一个手滑写错的值会静默把保护关掉。新写法把这些情形全部归入严格一侧：**只有明确写对了才放开**。失败方向由此从宽松变为收紧。

仓内已有同款写法的先例（若干需要显式开启的能力都用「等于开才算开」判定），本次与之对齐，不引入新形态。

**D2. 保留环境变量，不改成后台配置项。**

放开兜底是一次具名的临时放宽，不是运营日常旋钮。做成后台可编辑会让它变成一个常备档位，与「它在最需要闸的时刻丢掉闸」这一性质相悖。保留为环境变量、且需要显式开启，正好匹配它应有的使用频率。

**D3. 把默认极性写进规格，并写明为什么必须由代码承载。**

本 change 的实质问题不是「值不对」，而是「值没有落脚点」。只改代码不写规格，下一次有人为别的目的调整这段逻辑时，仍然没有任何东西说明这个默认值是刻意的。规格里同时记下失效模式——不进版本库、部署被排除、静默失效——使它成为一条可被检查的约束而不是一次巧合。

## Risks / Trade-offs

- **群池薄的账号会从「看起来在跑」变成「明显不跑」** → 这是暴露而非制造问题。**缓解**：诚实空转有可诊断结果；正确处置是开自动加群补充群源，那条路径现在已独立可控。

- **dev 上那一行配置变成冗余，可能让人误以为它还在起作用** → **缓解**：改后无论有没有那一行，结果都是严格；tasks 里说明可留可删。

- **生产会在下次部署时行为改变** → 这正是目的：不需要有人记得单独去关。**缓解**：写进交接说明，使它是一个被预告的变化。

## Migration Plan

无数据库改动。部署即生效。

**回滚**：把判据改回原写法即可；或在运行时配置里显式开启。

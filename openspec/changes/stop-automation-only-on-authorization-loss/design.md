# 设计说明

## 1. 判据：哪些事实配当「停止理由」

| 云端投影 | 含义 | 今天 | 本 change |
| --- | --- | --- | --- |
| 不在权威可见集 | 管理员撤权 / 环境已删 / 归属被改 | 停 | **停**（授权事实，不变） |
| `binding_conflict` | 同一账号跨客户绑在别人环境上 | 停 | **停**（安全事件，不变） |
| `binding_unknown` | 从未成功握手过 / 绑定悬空 | 停 | **不停** |
| `binding_unavailable` | 绑定解析所需存储不可用 | 停 | **不停** |
| 权威可见集这次没读成功 | 网络 / 服务抖动 | 保留上次已知集，但仍会据其收敛 | **不据其收敛** |

判据的分界不是「云端答没答上来」，而是「这条观测换个结果会不会改变**谁有权用这个环境**」。归属与跨客户冲突会；「它是谁」不会——已上线规格对绑定的定性就是「只回答是谁，绝不回答归谁」，并且明写绑定不追溯、未绑定环境靠下一次握手自愈。拿「还没握过手」当停止理由，等于把自愈唯一的入口关掉；今天没有形成死锁，仅仅是因为这处收敛忘了撤在途启动（见 §2），也就是说**是一个 bug 在替另一个 bug 兜底**。

`binding_unavailable` 与「可见集没读成功」归入同一条纪律：不确定 MUST NOT 被消费成否定答案；跨进程 / 兄弟服务暂时读不到恒非结构性失败。

## 2. 停法：为什么必须复用显式关闭那条路

今天这处收敛只做了两件事——改自动化意图、SIGTERM 子进程。它没有推进操作代，因此：

- 串行启动队列里那条待执行项还在，轮到时照常执行；
- 启动排队名额没归还，等槽位资历没清；
- 队列执行时的取消复核只看「已被要求停止 / 已移出 / 正在退出」，看不见「意图被改成了停止」。

结果就是自动化被判停之后几分钟，浏览器自己浮出来，并占住一个并发名额。而客户端显式关闭那条路径本来就会推进操作代（推进即取消队列待执行项、归还名额）并清等槽位资历——所以修法不是新写一套撤销逻辑，而是**让内部判定走同一条收敛**，只把原因换成具名的授权原因。

「同一条收敛」也是这条不变量能长期成立的原因：以后再加任何内部停止判定，只要复用它，就不会再造出「已停止 + 仍会开浏览器」这种自相矛盾态。

## 3. 为什么不做自动恢复

授权恢复（管理员重新分配、冲突消解）后不自动拉起引擎。已上线规格明写「登录和 roster 刷新 MUST NOT 自动启动普通引擎」；自动恢复会把一次后台复核变成一次开浏览器动作，与该不变量直接冲突。恢复仍由用户显式启动——判据收窄之后，这种情况本来就只剩「真的被撤权 / 真的有冲突」两类，需要人介入是合理的。

## 4. 为什么把判据析出成纯函数

这道闸的失效形态是「恒真」——判据一旦被写宽，界面上不会有任何异常，只是再也拦不住撤权环境，而现有的形状断言测试（断言主进程源码里出现某个字符串）既证明不了它还拦得住，也拦不住把条件写反。析出为无副作用函数后，用「在可见集内 / 不在可见集内 × 每一种绑定态」的输入直接钉住判定结果，违规输入能被用例抓住。

主进程侧保留的形状断言只负责一件事：这处复核**不得**调用任何启动 / 唤醒 / 开浏览器入口（既有不变量，不能被本次改动顺手放宽）。

## 5. 与相邻 change 的边界

- `cancel-in-flight-environment-launch`：治的是「启动提交点原子性 + 所有权登记准入闸」，即取消意图落进 spawn 前那段等待里失效的问题。本 change 不碰那段；两者在「停止意图必须能覆盖在途启动」上同向，本 change 只把这处收敛接到既有收敛路径上。
- `browser-slot-scheduling`：槽位池与串行启动队列本体。本 change 不改队列语义与名额口径，只归还本就该归还的名额。

两者都动 `src/electron/main.cjs`，集成前必须 rebase 到最新默认分支再跑验收。

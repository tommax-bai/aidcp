## ADDED Requirements

### Requirement: 操作注册表的多份副本 MUST 一致且漂移可机械检出

当「每项操作 MUST 由集中式注册表显式分类」所要求的那张注册表以**多份副本**存在于不同仓时（现状：边缘一份、云端一份、云端派生仓各自一份），这些副本 SHALL 就 Cloud→Edge 命令集合保持一致，且副本间的不一致 MUST 由机械手段检出，MUST NOT 只依赖人工比对或代码评审。

具体要求：

- 各副本的 Cloud→Edge 命令**键集合 MUST 相同**；同名键的分类描述符（类别 / 传输 / 身份 / 浏览器前置）四个字段 MUST 逐字相同。
- 该检查 MUST 落在能同时读到全部副本的位置。**单仓自查 MUST NOT 被当作已覆盖**：一仓只看得见自己那份，缺条目在本仓视角下与「本仓不需要这条」完全同形。
- 参与比对的副本少于两份时 MUST 判失败并说明，MUST NOT 把「没得比」报成「比过了，一致」。
- 检查失败 MUST 打印差集（哪一份多 / 少哪些键）与差异字段，MUST NOT 只报「不一致」。

**为什么这条必须是机械的**：漏登记一条命令的后果不是报错，而是该命令在出口闸被判 `operation_unclassified` 静默拒发、投递数返回 0——发送方拿到的是一次「已处理」的返回，接收方什么都没收到。两份表都以「部分匹配」方式声明（缺 key 不构成类型错误），因此**编译期、两仓各自的验收用例、协议逐字对账三道现役闸门对这类漏登记全部无感**。

#### Scenario: 一份副本漏登记某条 Cloud→Edge 命令

- **WHEN** 某条 Cloud→Edge 命令在一份副本中已登记、在另一份副本中缺失
- **THEN** 跨副本对表检查 MUST 失败，并指出是哪一份缺哪一条
- **AND** MUST NOT 因为每一份副本各自都能通过本仓 typecheck 与验收用例而被判为通过

#### Scenario: 同名命令在两份副本中分类不同

- **WHEN** 同一条命令在两份副本中都已登记，但其类别、传输、身份或浏览器前置任一字段不同
- **THEN** 跨副本对表检查 MUST 失败并打印该键的差异字段
- **AND** MUST NOT 因为「两边都登记了」就判为一致

#### Scenario: 副本不足两份时不得判为通过

- **WHEN** 本机只找到一份副本（其余仓未 clone 或该仓本就没有副本）
- **THEN** 检查 MUST 判失败并说明参与方不足
- **AND** MUST NOT 输出「一致」这一结论

### Requirement: 身份读取命令 MUST 可从云端下发

`identity.read_current` 与 `identity.read_self_profile` SHALL 登记为可由云端下发的 `page_automation` 操作，云端 MUST NOT 因自身注册表缺条目而拒绝下发这两条命令。

这两条命令是**边缘身份救援放行清单**的成员：当边缘运行期身份落到「不知道浏览器里登着谁」的终局时，节点拒绝一切代表该账号的动作，仅放行少数读 / 收尾 / 救援命令，而这两条正是唯一能问出当前登录身份、从而解开该终局的事实来源。云端侧若发不出去，该自救通道结构上不成立。

#### Scenario: 节点身份未落定时云端仍能问出当前身份

- **WHEN** 某边缘节点的运行期身份处于未落定终局，云端下发 `identity.read_current`
- **THEN** 该命令 MUST 通过云端出口闸下发到该节点，MUST NOT 被判为 `operation_unclassified`
- **AND** 投递数 MUST 反映真实投递结果，MUST NOT 在未投递的情况下返回成功

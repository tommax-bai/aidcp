## Why

`aidcp-cloud` 今天没有迁移执行器，也没有迁移账本。唯一的工具 `aidcp-cloud/scripts/run-migration.ts:20-52` 接一个文件路径、建一次性连接、把整个文件丢给 `client.query()`、打印 `ok` 后退出：不记已应用版本、不排序、不校验内容、不识别执行目标；`aidcp-cloud/package.json` 里没有任何 `migrate` 脚本。59 个迁移文件里编号已出现四组碰撞（`0002` / `0030` / `0037` / `0038` 各两份）且缺 `0012`，两份同号文件的先后顺序今天由人手决定、无法复现。

更根本的问题是：迁移文件不是真实 schema 的事实源。34 个存储文件里 `CREATE TABLE IF NOT EXISTS` **文本命中 76 处、去注释后生效约 58–60 条、分布在 34 个源文件**（三个数 MUST 同时给出，MUST NOT 只写 76——按 76 立收口范围会多出十几条注释内的假目标；口径与定稿 §5.4.1 一致，扫描 MUST 先剥 `--` 与 `/* */` 注释，与 change `cloud-service-boundary-gates` 任务 4.2 同规则），由组合根 `aidcp-cloud/src/server.ts` 的 39 处 `.init()` 在启动时执行。按表名对账：迁移目录建 59 张表、存储自建 58 张，并集 83 张（**此计数 MUST 与 `cloud-service-boundary-gates` 任务 4.1 统一**——该 change 记「84 张 / 59 张由 `src/` 建」，两者只要差一张，它的「未登记的表出现即失败」当天就会红；MUST 由两个 change 中先动工的一个跑一次统一口径脚本、结果同时回写两处、脚本命令写进 tasks），其中 **24 张只由存储自建、任何迁移文件都不存在**（含被 26 处外键引用的 `accounts`，以及 `client_users`、`client_environments`、`anchors`、`curated_content`），25 张只由迁移建（微信收件箱 20 张等），34 张两处都有、可各自漂移。这 17 个存储的启动初始化还整体包在 `aidcp-cloud/src/server.ts:639-660` 的一个 `try/catch` 里，DDL 失败只打 `console.warn` 然后继续跑。

全仓零 `CREATE SCHEMA`、零 `CREATE ROLE`；唯一一条授权语句 `aidcp-cloud/migrations/0050_wechat_group_reply_config_privileges.sql:1-28` 是管理员角色误跑 `0048` 后运行时角色失去 DML 权限的事故补丁。dev 与 ol 不只是共用实例，是**共用同一个数据库**。

在这个地基上，云端拆分方案 §5.1「独立 Schema + 独立数据库账号 + 独立迁移目录」等于把 1 条无序线变成 3 条无序线：三个仓各自的 `CREATE TABLE IF NOT EXISTS` 会在启动时把对方域的表建回来，谁也说不清库里的对象归谁。

**最危险的一条**：因为存储自建表，「回滚到旧版本代码」在表已经迁走或列已经改名时，会由旧代码在启动期**静默重建一张空表并开始向它写入**。回滚动作本身变成一次静默假成功，直接违反本项目第一红线（找不到目标必须诚实报错，绝不伪装成功）。这个洞不修，拆分期的任何一次回滚都可能造成数据分叉且当场无告警。

**这一条不依赖拆分、可以立即做，并且是拆分的硬前提**：先有单一 DDL 所有者与可核对的迁移账本，才谈得上「为 Schema 建立唯一所有者」。

## What Changes

- 新增有序迁移执行器与迁移账本表：记录版本 id、文件校验和、应用时间、施加动作的执行目标、耗时；重复应用幂等；顺序不可跳；校验和不符即整批拒绝。
- 首次引入账本必须先做**实测对账再基线登记**：把每个迁移声明的表、列、索引与 `information_schema` / `pg_indexes` 实测比对，差异为空才允许写入基线，绝不允许「假设已跑过」。
- 冻结历史编号碰撞而不是重排文件名：版本 id 用「文件名去后缀」，排序按（数字前缀，文件名）复合序，四组碰撞的相对顺序被固定并写进测试；缺号 `0012` 显式登记为永不分配的空洞；新增迁移不得复用已有数字前缀。
- 补齐 24 张只由存储自建的表的迁移文件，使迁移目录成为完整事实源；此步不删任何存储代码，零运行时风险。
- 分批取消存储自建表：把 34 个存储的 76 条 DDL 收口到迁移执行器，按域分 6 批推进；过渡期用「迁移先补齐 + 白名单只减不增测试 + 单一回滚旋钮 + 每批切换后执行器实测校验」四重保险。
- 新增启动期 schema 契约门：读账本最高版本与构建内声明的所需/已知版本比对，落后或超前一律拒绝启动并报明确原因，绝不自建表继续跑；该门跑在所有存储初始化之前，且不得被 `try/catch` 吞掉。
- 写死「只扩张不收缩」纪律：迁移文件必须声明 `expand` / `contract` 类别，共库期执行器默认拒绝应用 `contract`；重命名一律改写为新增列 + 双写 + 影子读 + 切读 + 独立收缩变更。
- 给出一次表所有权迁移的六步模板（准备 → 双写 → 影子读对账 → 切读 → 停旧写 → 收缩），每步写明验收信号与回退动作，并诚实标注最后一步的回退只能靠备份。
- 盘点库级作用域机制：7 处 `pg_advisory_xact_lock`（`interaction-env:<envKey>` 命名空间被 client-auth 与 interactions 两域共用）、26 处指向 `accounts(account_id)` 的外键、跨 11 张表的单事务离场清理、8 处硬编码 `'public.'` 的形状探测。逐条标注拆 schema 后是否成立、拆库后是否成立，并用源码扫描测试锁死清单，新增未登记即测试失败。

## Capabilities

### New Capabilities

- `cloud-schema-migration`: 云端数据库 schema 的单一所有者——有序迁移执行器、迁移账本、启动期版本闸、只扩张纪律与表所有权迁移模板。

### Modified Capabilities

- `deployment-environments`: 部署序列增加「施加迁移 + 核对账本」步骤；dev/ol 共库期的只扩张约束与迁移账本的库级单一序列写进环境隔离契约。

## Impact

- Cloud：新增迁移执行器与账本表、24 张缺失表的补写迁移、启动期 schema 契约门、分批移除 34 个存储的 76 条 DDL、DDL 白名单与库级作用域清单的源码扫描测试。不涉及 protocol v2 五处同步、角色注册与风控状态机。
- Edge：无。本变更不改协议消息、不改边缘动作、不改边缘启动流程。
- Console：无。面板 API 契约与前端不变；只在 schema 契约门拒绝启动时表现为服务未就绪，而非返回错误数据。
- Control：新增 `docs/database-scope-inventory.md`；`docs/deployment-environments.md` 的 dev/ol 部署流程增加迁移步骤；本变更是云端拆分方案 §5.1 与 §12 阶段 2 的前置条件，方案文档引用本 change 作为该前置的落点。

## ADDED Requirements

### Requirement: 迁移执行器必须带账本、有序、幂等且可校验

Cloud SHALL 提供唯一的数据库迁移执行器，并在数据库内维护一张迁移账本，逐条记录版本 id、迁移文件名、文件内容校验和、迁移类别、应用时间、应用者、施加动作的执行目标与耗时。

版本序 SHALL 由「数字前缀数值升序，前缀相同时按完整文件名字典序升序」的复合键唯一确定，MUST NOT 依赖人工决定的执行顺序。

执行器 MUST 按下列语义处理每一条迁移：已在账本且校验和一致的 MUST 跳过且 MUST NOT 重复执行；已在账本但校验和不一致的 MUST 使整批拒绝并报出 `migration_checksum_mismatch`，MUST NOT 重跑该迁移，MUST NOT 用新校验和覆盖账本；版本序低于账本最大已应用版本却不在账本中的 MUST 使整批拒绝并报出 `migration_out_of_order`，MUST NOT 补跑。

整批执行 MUST 由一个固定 key 的数据库 advisory lock 互斥；未取得锁时 MUST 立即退出并报告存在并发执行器，MUST NOT 等待超时后继续执行。每条迁移 MUST 在各自的事务内执行并在同一事务写入账本，MUST NOT 把整批放进单一事务。任一条失败 MUST 停止整批并以非 0 退出码报出失败版本与原始数据库错误，已成功条目 MUST 保留在账本中。

`applied_from_target` 列 SHALL 仅作审计。dev 与 ol 共用同一个数据库时，账本 MUST 是库级的单一序列；该列 MUST NOT 进入主键或唯一约束，MUST NOT 参与任何查询过滤，MUST NOT 被用来为不同执行目标维护各自的版本序列。

#### Scenario: 重复执行不重跑已应用迁移

- **WHEN** 执行器在同一个数据库上连续执行两次
- **THEN** 第二次对全部已应用且校验和一致的迁移只做跳过，不执行任何 SQL，账本行不变

#### Scenario: 历史迁移被改动后整批拒绝

- **WHEN** 某个已记入账本的迁移文件内容被修改，校验和与账本不一致
- **THEN** 执行器拒绝整批、不执行任何 SQL，报出 `migration_checksum_mismatch` 与对应版本 id，并且不更新账本中的校验和

#### Scenario: 插入低版本迁移被拒绝而非补跑

- **WHEN** 目录中出现一个版本序低于账本最大已应用版本、且不在账本中的迁移文件
- **THEN** 执行器拒绝整批并报出 `migration_out_of_order` 与该版本 id，不补跑该文件

#### Scenario: 同号迁移的顺序可复现

- **WHEN** 目录中存在两个数字前缀相同的迁移文件
- **THEN** 执行器按完整文件名字典序确定二者先后，且任意次执行得到同一顺序

#### Scenario: 并发执行器不重叠

- **WHEN** 第二个执行器进程在第一个持有整批锁期间启动
- **THEN** 第二个进程立即退出并报告存在并发执行器，不执行任何迁移

#### Scenario: 共库下两个目标共用一条版本序列

- **WHEN** dev 与 ol 连接同一个数据库，且一次迁移由 dev 侧运维动作施加
- **THEN** 账本只有一条记录，`applied_from_target` 记为 `dev`，ol 侧执行器读到该迁移为已应用并跳过，不会因执行目标不同而再次应用

### Requirement: 引入账本必须先实测对账，再基线登记

首次在一个已有数据的数据库上启用迁移账本时，执行器 SHALL 提供实测对账能力：把每个迁移文件声明的表、列、索引与约束，与数据库目录中的实际对象逐项比对，输出缺失对象与多余对象两张清单。

对象声明 MUST 来自迁移文件中的结构化头注释，MUST NOT 由 SQL 文本推断——推断不完整会产生假阴性，而此处的假阴性等价于「验证通过」。

基线登记 MUST 仅在缺失对象清单为空时被允许。缺失清单非空时执行器 MUST 拒绝基线并逐条列出缺失对象及其来源版本，MUST NOT 无条件把历史迁移标记为已应用。基线登记对账本中已存在的版本 MUST 幂等跳过，MUST NOT 覆盖已有行。

#### Scenario: 缺失对象时拒绝基线

- **WHEN** 实测对账发现某个迁移声明的表或列在数据库中不存在
- **THEN** 基线登记被拒绝，输出缺失对象清单及其来源版本 id，账本不写入任何行

#### Scenario: 对账通过后完成基线

- **WHEN** 实测对账的缺失对象清单为空
- **THEN** 执行器把全部现有迁移以基线标记写入账本，并输出账本行数与最高版本 id

#### Scenario: 基线重复执行幂等

- **WHEN** 基线登记在已完成基线的数据库上再次执行
- **THEN** 已存在的账本行被跳过且不被覆盖

### Requirement: 数据库 DDL 只有迁移一个所有者

Cloud 运行时代码 MUST NOT 创建、修改或删除数据库对象。所有 `CREATE TABLE`、`ALTER TABLE`、`CREATE INDEX` 与等价语句 MUST 只存在于迁移文件中。

在从存储自建表迁移到单一所有者的过渡期，系统 SHALL 维护一份运行时 DDL 白名单，实际扫描到的运行时 DDL 集合 MUST 是白名单的子集；白名单 MUST 只减不增。

存储在启动时发现所需对象不存在时 MUST 报出带版本 id 的明确错误并使该能力 fail-closed 降级或拒绝启动，MUST NOT 创建对象后继续运行。启动期对象缺失与数据库连接失败 MUST 被区分并分别报出，MUST NOT 合并为同一条通用告警。

#### Scenario: 新增运行时建表被机械拦下

- **WHEN** 某次改动在 `src/` 下新增一条不在白名单中的 `CREATE TABLE`
- **THEN** DDL 所有者验收用例失败，并提示 DDL 只能加在迁移目录

#### Scenario: 对象缺失时诚实降级而非自建

- **WHEN** 某个存储在启动时探测到其所需的表不存在
- **THEN** 系统报出带缺失对象与来源版本 id 的错误，该能力 fail-closed，且不执行任何建表语句

#### Scenario: 连不上库与缺对象被分别报出

- **WHEN** 启动期存储初始化失败
- **THEN** 日志分别指明是数据库不可达还是所需对象缺失，不使用同一条通用告警覆盖两种原因

### Requirement: 启动期必须校验 schema 版本，不匹配一律拒绝启动

Cloud 构建 SHALL 声明其所需的最低迁移版本与其认识的最高迁移版本。启动时系统 SHALL 读取账本中的最大已应用版本并按复合版本序比较，MUST NOT 使用字符串比较。

账本最高版本低于所需版本时，系统 MUST 拒绝启动并报出 `schema_behind_code` 与缺失版本清单。账本最高版本高于本构建认识的最高版本时（典型场景为回滚到旧版本代码），系统 MUST 默认拒绝启动并报出 `schema_ahead_of_code` 与超前版本清单，MUST NOT 创建任何表、MUST NOT 降级继续运行。

该校验 MUST 在任何存储初始化之前执行，MUST NOT 被 `try/catch` 吞掉。读取账本本身失败（账本表不存在或数据库不可达）时同样 MUST 拒绝启动，理由是无法证明 schema 正确。

超前放行通道 MUST 要求填写具体的最高放行版本 id；布尔值、空值或通配值 MUST 一律视为未放行。放行生效时 MUST 在启动日志与告警通道各记录一条，含被放行的版本区间与操作者。系统 MUST NOT 提供一次开启即永久生效的放行形态。

#### Scenario: 回滚旧代码时拒绝启动而非重建空表

- **WHEN** 数据库账本最高版本高于当前构建认识的最高版本
- **THEN** 系统拒绝启动并报出 `schema_ahead_of_code` 与超前版本清单
- **AND** 本次启动过程中没有执行任何建表语句

#### Scenario: 迁移未跑时拒绝启动

- **WHEN** 账本最高版本低于本构建声明的所需最低版本
- **THEN** 系统拒绝启动并报出 `schema_behind_code` 与缺失版本清单，提示补跑迁移

#### Scenario: 账本不可读同样拒绝启动

- **WHEN** 启动时账本表不存在或数据库不可达
- **THEN** 系统拒绝启动并报出无法证明 schema 正确，不进入任何存储初始化

#### Scenario: 放行通道必须写具体版本

- **WHEN** 超前放行通道被设为布尔真值或空字符串
- **THEN** 系统视其为未放行并按 `schema_ahead_of_code` 拒绝启动

#### Scenario: 告警模式与拒绝模式判定一致

- **WHEN** 契约门运行在只告警模式且检测到版本不匹配
- **THEN** 输出的判定结论与版本清单与拒绝模式完全一致，不使用模糊提示

### Requirement: 迁移期只扩张不收缩

每个迁移文件 MUST 在头部声明类别为扩张或收缩，缺声明 MUST 被执行器拒绝应用。扩张指新增表、新增列、新增索引、新增未验证约束、数据回填与新增触发器，其判定标准是旧版本代码在该迁移之后仍能正常读写；收缩指删表、删列、重命名、类型收窄、加非空约束、删索引与约束收紧，其判定标准是旧版本代码在该迁移之后会失效。

dev 与 ol 共用同一个数据库期间，执行器 MUST 默认拒绝应用收缩类迁移，仅在显式授权参数下应用，并 MUST 把授权者记入账本。

重命名 MUST NOT 使用 `ALTER … RENAME`；MUST 改写为新增目标列、双写、影子读比对、切读、以及一次独立的收缩变更删除旧列。收缩变更 MUST 是独立的 OpenSpec change、独立部署、可单独回滚，MUST NOT 与任何扩张迁移在同一批交付。

#### Scenario: 缺类别声明的迁移被拒绝

- **WHEN** 一个迁移文件没有类别声明头
- **THEN** 执行器拒绝应用该迁移并提示补充类别声明

#### Scenario: 共库期收缩默认被拒

- **WHEN** 待应用集合中包含一条收缩类迁移且未提供显式授权参数
- **THEN** 执行器拒绝整批并提示收缩需要显式授权

#### Scenario: 标为扩张却含破坏性语句被拦下

- **WHEN** 一个声明为扩张的迁移文件中出现删列、重命名、类型收窄或加非空约束
- **THEN** 迁移纪律验收用例失败并提示改标为收缩

### Requirement: 表所有权迁移必须走可回退的六步模板

任何一次把表或列的写入所有权从一处移到另一处的变更 SHALL 按准备、双写、影子读对账、切读、停旧写、收缩六个步骤推进，每一步 MUST 有可观测的验收信号与明确的回退动作。

双写期间新目标写失败 MUST 计数并告警，MUST NOT 静默吞掉，MUST NOT 因目标写失败而阻断原权威写。

影子读对账 MUST 同时上报差异条数与已比对行数。已比对行数为 0 时结论 MUST 是「未验证」，MUST NOT 被报告为「一致」或「通过」。

切读步骤 MUST 可通过开关即时切回读旧路径且不产生数据动作。停旧写步骤的验收信号 MUST 是旧对象在观察期内确实不再有写入发生，而不是代码里已经删掉调用。

收缩步骤 MUST 被明确标注为不可逆，其回退方式 MUST 记为从备份恢复；文档与变更说明 MUST NOT 把该步描述为可回滚。

跨进程执行双写时 MUST 使用持久命令或消息投递，MUST NOT 依赖数据库 advisory lock 或跨进程共享事务。

#### Scenario: 双写失败不被静默吞掉

- **WHEN** 双写期间对新目标的写入失败
- **THEN** 系统记录错误计数并告警，原权威写照常完成，不返回成功以外的假象

#### Scenario: 零覆盖率的对账不算通过

- **WHEN** 影子读对账器已比对行数为 0 且差异条数为 0
- **THEN** 对账结论为未验证，不得推进到切读步骤

#### Scenario: 停旧写以实际写入量为准

- **WHEN** 判定旧写入路径是否已停止
- **THEN** 验收依据是旧对象在观察期内的实际写入统计不再增长，而不是代码中已移除调用

#### Scenario: 收缩步骤诚实标注不可逆

- **WHEN** 变更文档描述收缩步骤的回退方式
- **THEN** 明确写为从备份恢复，不写为可回滚

### Requirement: 库级作用域机制必须登记并机械守护

系统 SHALL 维护一份库级作用域机制清单，逐条记录机制、位置、当前作用域、拆分 schema 后是否仍然成立、拆分数据库后是否仍然成立以及替代方案。清单 MUST 至少覆盖数据库 advisory lock、跨领域外键、跨多表的单事务清理与硬编码 schema 名的对象探测。

清单 MUST 明确声明：advisory lock 与外键均为数据库级作用域，把表搬进不同 schema 后二者依然有效，只有拆成不同数据库才失效，且失效方式是静默的——锁不再互斥、外键不再存在而业务照常运行。

清单 MUST 由源码扫描用例锁死：实际的 advisory lock 调用点集合与跨领域外键目标集合 MUST 与清单一致，新增未登记条目 MUST 使用例失败。仅有文档而无机械校验 MUST NOT 被视为满足本要求。

#### Scenario: 新增未登记的 advisory lock 被拦下

- **WHEN** 某次改动新增一处数据库 advisory lock 调用且未更新清单
- **THEN** 库级作用域验收用例失败并提示先登记该机制

#### Scenario: 清单区分拆 schema 与拆库

- **WHEN** 读者查阅清单以判断某处 advisory lock 在迁移后是否仍然有效
- **THEN** 清单明确给出「拆 schema 仍成立、拆库静默失效」的结论与替代方案，不把两种拆分混为一谈

#### Scenario: 跨多表单事务清理被标注原子性边界

- **WHEN** 清单登记跨多张表的单事务清理逻辑
- **THEN** 标注其在同库跨 schema 下仍为原子、在拆库后不再原子，并给出可重入分表方案

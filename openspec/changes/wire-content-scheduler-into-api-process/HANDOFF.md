## 3. 这个 change 在解决什么

三进程拆分后，负责「到点该发帖了」的排期器**没有任何进程在跑**：它按分工归接口服务，类也在接口仓里，但接口服务的手写入口从不构造它。今天不出事只因为还是单体在跑。真拆开那天，到点什么都不会发生，**且没有一行日志说为什么**——「队列里暂时没活」与「永远没人来处理」在外部完全同形。

同一条链的另一半也断着：自动化服务已有客户端在调「归还小时格」，接口服务压根没提供这条口。账面上标着已接线，真跑起来是跨进程 404，而 404 会被读成「对面版本落后」。

**用户 2026-08-03 裁定**：账号连着引擎才执行排期（**在线闸保留**），但**不必管是哪个浏览器环境**。dev/ol 隔离另算，是红线，保留。

## 4. ⚠️ 动手前必读

### 4.1 先去对面确认路由真被注册，再写客户端（第 3 组的头号坑）

派生服务的启动入口**各自手写、从不自动同步**，它注册的路由集合会悄悄少于单体。
**上一个 change 为此连撞五次**：客户端建得出来（构造函数只吃基址与令牌）、调用点编译得过（类型描述形状、不描述「对面有没有这条路由」）、两仓测试各自全绿 —— **只有真把两个进程一起跑起来才 404**。

而那是**跨进程**的 404：调用方读到的是「对面不支持这个方法」，一个本该留给「对面版本落后」的具名原因，被一次纯接线遗漏冒名顶替。

⇒ tasks 3.1 要求**在写任何客户端之前**先去自动化侧的 `main()` 里逐条确认。**别信「通道已就位 / 路由已注册」这类记载**——实测它们指的往往是「**单体**里注册了」，而单体那处通常带模式守卫、三进程下根本不跑那一支。

**还有一层**：路由对了，**令牌也可能是错的**。发布授权那族路由挂的是专用令牌、与通用令牌不互相回落，拿错了每次都判未授权，而编译过、两仓测试全绿。

### 4.2 别加投机性强转——本 change 已经靠它兜住一次

第 1 组按符号 grep 出四处环境绑定落点，自认为查全了。删完之后**编译器点出第五处**：同一个归属结构在共享层还有一份、名字不同（`ScheduledExecutionAttribution`）。

**符号 grep 看不见改了名的第二份。** 所以「不加强转、让编译器说话」在这里不是风格偏好，是普查的兜底。收尾 `grep 'as never\|as unknown as'` 应为 0。

### 4.3 「闸恒真通过」＝「闸消失了」——第 4 组全靠变异实测

判断一旦在生产路径上不可达，**没有任何机械手段能证明它还在不在**。

第 1 组做过一次、可照办：把保留下来的部署目标闸改成 `if (true)`，**恰好一条**用例红（「其它 target 的自动排期稿在授权读取和 Edge 写入前被跳过」）。这才叫证明它承重。

**还原用 `cp` 不用 `mv`**：`mv` 保留旧 mtime，带缓存的构建会跳过重编，于是你测的是变异产物。

第 4 组的每条失败方向都要这么验，**且要逐条说出是哪条用例抓住的**。没红的那条说明用例是空的——上一个 change 实测过「桩把陈旧态置了空，而真实现会保留上一份，于是那条用例什么都没测」。

### 4.4 失败方向按「哪边更严」判，不按「哪边更像缺省」判

这是第 4 组的全部内容，规格里已逐条写死：

| 依赖 | 问不到时 | 为什么 |
| --- | --- | --- |
| 在线账号清单 | **整个心跳跳过** | 回空数组＝「没人在线」，与真的没人在线完全同形，全员静默停摆且看着正常 |
| 风控状态 | 跳过该账号 | 回 `normal` 就是放行 |
| 三个「是否在跑」 | **判为在跑** | 回「不忙」是放行；这道闸就是防重复触发的，**失败开闸＝双发** |
| 委托任务占用 | 判为占用 | 同上，且委托是人主动发起的 |
| 发帖素材可用数 | 判为 0 | 与既有实现同向 |

**「未注入」与「问不到」必须分得开**：前者是既定零回归跳过，后者是具名失败。两者今天在外部同形。

### 4.5 迁移的耦合单元是五处，但本批只中四处

`0109` 已按 ① 迁移文件 ② `KNOWN_MAX_SCHEMA_VERSION` ③ 该常量上方那段逐迁移追加的 JSDoc ⑤ schema 测试里**第二次写死**的那个常量 —— 四处办完。

**④ `table-ownership.json` 本批不用改**（不新增表，该表早已登记 owner=api）。下一批若新增表，④ 必须补。

⑤ 那处最阴：一处从目录**算**最大版本、一处**逐字写死**，改完前者会以为完事了。它自己的注释就写着「每加一条迁移都要在这里同步抬」。

### 4.6 运行期建表是只减不增的棘轮，新增 DDL 只能落到迁移

第 1 组踩过：为了绕开「代码硬依赖迁移」，我给存储的启动 DDL 加了同一句 `DROP NOT NULL`，被 `AC-SCHEMA-DDL-OWNER-01/02` 当场拦下，**断言里直接写着正确动作**。

**那道闸是对的**：绕过硬依赖的代价是把 schema 真相分散回运行期。撤掉兜底后硬依赖恢复成立，REQUIRED 照抬。

### 4.7 部署顺序是硬的（第 8 组）

本批带迁移且 REQUIRED 抬到 0109 ⇒ **rsync → `migrate status`（确认待应用条数、不盲目 apply）→ `migrate up` → 重启 → healthcheck**。

倒过来做的后果实测过链路：schema 门在 enforce 下抛出 → 进程 exit 1 → systemd 每 5 秒静默重启的崩溃循环、**零告警**，且 `behind` 这一档**没有豁免通道**。

补迁移**只能用 `migrate up`**：另一个执行器执行 SQL 但不写账本，用它补完会出现「表明明建好了、门还判落后」，最费时间。

### 4.8 并发纪律

- 代码**只在 worktree 里**改，canonical checkout 永远停在默认分支。
- 提交**只显式列文件，绝不 `git add -A`** —— 控制仓当前就有别的 session 在编的目录（`recognize-facebook-french-reel-controls/`），扫进来就把别人的活提交走了。
- push 遇 non-ff 一律 rebase 后重来，**绝不 force**。
- 事实源仓被并发推进后，派生仓会漂而**没有任何信号**（六仓测试各自照样全绿）。第 8 组同步前先跑一次对账。

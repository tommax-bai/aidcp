## Context

内容排期调度器是个每分钟醒一次的命令式触发器：遍历账号，逐道闸判「这一格该不该发」，该发就触发发布 / 评论 / 加群管线，并对每次触发回一张诚实结果卡。

它的依赖今天全是**同进程直调**。拆成三个服务后，依赖散在两侧：

- **接口侧现成**：排期配置现读、小时格原子占位、账号平台、已发数与在途自主草稿数、周历掩码。
- **在自动化侧**：在线账号清单、风控状态、发布 / 评论 / 加群三类触发、三个「在跑吗」单飞判定、委托任务占用判定。
- **在内容侧**：Facebook 发帖素材可用数。

调度器类本身已经把全部依赖收在**一个依赖接口**里，实现可换。所以主体工作不是改调度器，而是**为接口进程写一套跨进程的依赖实现**，并逐个回答一件事：**这一跳问不到的时候算什么**。

单体形态必须逐位不变——同一个类同时服务两种装配，差别只在喂给它的依赖实现。

## Goals / Non-Goals

**Goals:**

- 接口进程真正构造并启动调度器；缺部署目标即不启动（fail-closed）。
- 「排期名额回程」在接口进程有真落点，且与本进程调度器共用同一个方法。
- 每一条跨进程依赖都有明确的失败方向，且方向按「哪边更严」定。
- 去掉自动发帖的浏览器环境绑定（三处），保留在线闸与部署目标隔离。
- 单体行为逐位不变。

**Non-Goals:**

- **不**改成「只看排期表、不看在线」。用户 2026-08-03 裁定保留在线闸。
- **不**动评论 / 加群管线本身的编排，只改「谁来喊它开工」。
- **不**迁移历史稿件里已冻结的环境标识（保持可读、不再参与判定）。
- **不**在本 change 里给三进程建 systemd 单元——那属真跑批次。

## Decisions

### 一、同一个类、两套依赖实现；接缝就是那个依赖接口

调度器类不感知自己跑在单体还是接口进程。接口进程的装配提供一套 HTTP 背后的依赖实现，单体保持直调实现。

**替代方案（否决）**：给调度器加一个「模式」开关，内部分支。否决理由——那会把两种装配的差异散进调度逻辑里，而调度逻辑正是最不该有分支的地方；依赖接口本来就是为此存在的接缝。

### 二、几个同步签名的依赖必须放宽成「同步或异步」，并逐个定失败方向

在线账号清单、三个单飞判定今天是**同步**签名，跨进程拿不到。放宽成同步或异步（风控状态与委托占用判定**已经**是这个形态，照它办，不发明第二种）。

**失败方向逐条定死，判据是「哪边更严」，不是「哪边更像缺省」**：

| 依赖 | 问不到时 | 为什么是这个方向 |
| --- | --- | --- |
| 在线账号清单 | **整个 tick 跳过**，具名记一行 | 回空数组＝「没人在线」，与真的没人在线完全同形，会让全员静默停摆且看着正常 |
| 风控状态 | **跳过该账号** | 回 `normal` 就是放行；风控闸的全部意义就是拦住非 normal |
| 三个「在跑吗」 | **判为在跑、跳过本槽** | 回「不忙」是放行；这道闸就是防重复触发的，失败开闸＝双发 |
| 委托任务占用 | **判为占用、跳过本槽** | 同上，且委托是人主动发起的、优先级更高 |
| 发帖素材可用数 | 判为 0、跳过 | 与既有实现同向（今天就是 `catch → 0`） |
| 三类触发 | 如实回「未受理」并留痕 | 触发失败不能被读成「触发了但没结果」 |

**「未注入」与「问不到」必须分得开**：可选依赖没注入 ⇒ 该动作整体跳过（既有零回归约定，保留）；跨进程问不到 ⇒ **具名失败**。两者今天在外部同形，正是本项目反复点名的静默假成功形态。

### 三、跨进程触发的回执语义改成「受不受理」，结果卡由持有结局的一侧发

今天三类触发返回的 promise 在**生成完成或失败时**才 settle，调度器挂个 finally。跨进程不能这么办——一次 HTTP 挂住整条生成链，既占连接又把超时语义搅进业务结局。

改成：跨进程调用**在受理时即返回**（受理 / 未受理 + 具名原因）。

由此推出一条必须同批办的事：**终态结果卡由自动化侧发**，因为结局在它那儿。调度器只对「未受理」这一类回卡。

**为什么不让调度器等结局再发卡**：那要么把 HTTP 挂到生成结束（不可接受），要么让调度器去轮询结局（新造一套状态机）。更重要的是——两侧都发卡会让运营**分不出是哪条路径放行的**，这个形态在拆仓过程里已经咬过一次（免审通知的来源在透传后丢失，两种授权发出同一种卡）。

**单飞窗口因此变短**（受理即释放，而非结局即释放），但不构成漏洞：账号粒度单飞的真态由「在跑吗」那道闸向自动化现问，不靠调度器自己的内存标志兜底。

### 四、去掉环境绑定：三处同批，部署目标判断原样保留

- 调度器：删掉「解析不出环境身份就跳过发帖」那道跳过。
- 下发前形状校验：环境标识退出校验项；**部署目标必须是 dev 或 ol 且等于本机**这条**原样保留**——它管的是「这稿子属于哪台机器」，两套环境长期共用一个数据库，拿掉会串数据。
- 下发时环境匹配：整条删掉。

**幂等不受影响**：小时格占位那张表的唯一键是「账号 + 动作」，环境标识只是记录列。

**历史稿件不迁移**：已落库的环境标识保持可读、不再参与判定。

**这条是生产行为变更，且方向是放松**（原先跳过的稿件现在会发），所以它单列任务、单独可回退。

### 五、接口进程的「排期名额回程」照单体那个形态办

单体注册的是一个**转发器**：读一个晚绑定槽，缺席时**响亮抛具名错误**。接口进程照办，理由不变——回 false 读作「调度器看过了、没接管」，与「这个进程根本没有调度器」完全同形，而后者是配置问题、必须有人去修。

落点与本进程调度器**共用同一个方法**：小时格账本只有调度器自己那一本，第二条路径就是第二本账。

## Risks / Trade-offs

- **接了客户端但对面没注册路由** → 编译过、两仓测试各自全绿，只有真跑两个进程才 404，而 404 会被读成「对面版本落后」。**Mitigation**：每接一个跨进程客户端，先去对面启动入口里确认那条路由真被注册；并配一条只许下降的路由清单闸（内容侧已有同形先例）。这条坑本项目连撞五次，不靠自觉。
- **同一个定时器在两个服务里各跑一份** → 同一格被触发两次。**Mitigation**：小时格数据库原子占位仍在（唯一键「账号 + 动作」），跨进程与重启同格都拦得住；另配结构断言钉住「自动化侧不构造这个调度器」。
- **失败方向写反** → 闸失败时开闸，表现是双发或越过风控，而这类路径最少被真跑到。**Mitigation**：上表逐条写进规格并各配一条喂失败输入的用例；**MUST 做变异实测**——把某条方向改反，确认有用例当场红。
- **去掉环境绑定后，稿件从另一个环境发出** → 若某账号真的同时在两个环境在线，投递环境变得不确定。**Mitigation**：这是用户明确裁定接受的；下发时仍走账号在线判定与单飞，且日志如实记录实际投递环境，便于事后对账。
- **调度器搬进接口进程后，接口进程多了一个每分钟的定时器** → 与面板请求争资源。**Mitigation**：心跳重入护栏已在（上轮未完即跳过本轮）；跨进程调用只在命中分钟错峰后才付出成本，既有实现已是这个顺序。
- **文档事实源与本裁定相左** → 后人照文档改回去。**Mitigation**：同批更正 §4.6.5 第 12 项，写明裁定日期与理由，不留两份互斥的权威。

## Migration Plan

1. 事实源仓先落改动 → 机械派生到接口 / 自动化两仓 → **逐仓编译**（对账只比文件，不管编不编得过）。
2. 单体形态零回归验证：单体下调度器仍由原路径构造，行为逐位不变。
3. dev 部署按既有安全序列；**本批不含新迁移**（环境列退化为记录列，不改表结构）。
4. **回退**：环境绑定那三处是纯放松，回退＝把三处判断加回来，无数据面残留；调度器接线回退＝接口进程不构造它，回到今天的状态（单体照常）。

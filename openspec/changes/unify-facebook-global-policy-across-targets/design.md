## Context

三张表当前按运行目标分行存放，每个进程按自己的 `AIDCP_DEPLOY_ENV` 只读自己那一行：

| 表 | 分行键 | 现状 |
|---|---|---|
| `facebook_operation_global_policy`（+ `_audit`） | `execution_target` 主键，CHECK `dev\|ol` | dev revision 4（冷启动 5 天 / 5 行曲线）、ol revision 3（7 天 / 7 行） |
| `facebook_group_comment_policy` | `execution_target` 主键，同 CHECK | 只有 `ol` 一行（72 小时）；dev 无行 → 回落默认 |
| `facebook_environment_slow_start_completion` | 键含 `execution_target` | dev 46 行 / ol 21 行，互不相认 |

与之对照，同一件事的其余事实**本来就是共享的**：环境本身与冷启动起点（`client_environments`，无目标列）、安全限额（`quota_config`，无目标列）、镜像版本表（`config_mirror_version`，只按 `mirror_key`）。所以今天的隔离是切了一半的，本变更把剩下这一半也切掉、方向取"共享"。

两个关键的既有事实，决定了本设计能不能成立：

1. **dev 与 ol 当前共用同一个 PostgreSQL 的同一个 `aidcp_api` 库**（从两台机器分别连过去看到的是同一批行）。"合成一份"目前就是靠这个事实。
2. 而 `deployment-environments` 规格明确要求 `ol` 最终使用独立生产库、MUST NOT 与 dev 静默共享可变运行态。**这两条是冲突的**，本设计必须把冲突显式化，不能让"单份"靠一个规格上迟早要消失的默认悄悄成立。

## Goals / Non-Goals

**Goals:**

- Facebook 全局运营策略与冷启动完成事实在所有运行目标间只有**一份**，一次写入两边同时生效。
- 迁移基准可复核、可回滚，且不把"某一侧没有行"误当成"那一侧配了默认值"。
- 合并抹掉的那条安全性质（dev 可随便试参数）在界面上被明确补偿。
- 把"单份依赖共库"这条前提写进规格，交给未来的迁库变更去承接。

**Non-Goals:**

- 不解决 `ol` 迁往独立库之后如何维持单份（本变更只留具名前提与判据）。
- 不合并任何**运行态**（会话、任务、认领、风控计数），那些按目标隔离的理由与本变更无关，一条都不动。
- 不改冷启动起点、安全限额、同群复评冷却这三样 —— 它们本来就是共享的或不在库里。
- 不顺手修客户端"读不到曲线"与后台"群组评论时序未知"，那两条各有归属。

## Decisions

### D1：删分行键，而不是"固定一个常量目标"

策略表与完成表**删掉 `execution_target` 列**，策略表改为单行约束（固定主键），完成表主键改为 `env_key`。

- 备选一（保留列、固定写 `'all'`）：列还在，下一个读代码的人会认为"这里还能按目标分"，而唯一拦着的是一个约定。本仓已有过同形状的教训——一个还留着的维度迟早会被重新用起来。
- 备选二（保留两行、指定一行权威 + 另一行同步）：两个事实源，正是本变更要消灭的东西。

**审计表相反：保留 `execution_target` 列**。它是历史，历史本来就发生在某个目标上，重写它等于伪造记录。做法是放宽 CHECK 允许一个新取值（表示"全目标"），新行一律写该值，旧行原样不动。

### D2：合并基准是"逐项显式选定"，不是"取某一行整搬"

- 五项取 dev 现值（用户裁定）。
- 入群后首次评论等待取 **ol 的 72 小时**：dev 侧**没有行**。"没有行"在读取语义里会回落到默认 24 小时，但它**不是**一个被运营写下的值 —— 把它当成 dev 现值搬过去，就是把运营手写过的窗口悄悄改回默认。**合并规则：缺席的一侧不参与取值。** 这条规则要写进 spec，而不是只在这次迁移脚本里体现。

### D3：revision 序列从两侧历史之上重新开始

新的单一序列起点取 `max(dev.revision, ol.revision) + 1`。审计表唯一约束 `(execution_target, new_revision)` 原样保留：新行都落在新的"全目标"分组里，与历史两组天然不冲突，无需重写任何历史行。

后台的写入用的是 `expectedRevision` 比较交换，序列跳号不影响它 —— 它比的是"我读到的那个数还在不在"，不是连续性。

### D4：完成标记按环境取**更早**的完成时刻

同一环境两侧都有记录时取 `min(completed_at)`。理由是方向安全：完成是"这个号已经毕业"的事实，取更早的一条最多让一个号早一点走安全限额；取更晚的则可能把一个**已经在按毕业档跑**的号重新关回冷启动，那是对既成事实的否认。

### D5：两个接口进程从此互为对方写入的消费者 —— 这条通道必须被证明存在

合并前，dev 写 dev 行、ol 写 ol 行，两个接口进程永不互相影响。合并后，**在 dev 后台按下保存，OL 那个进程必须看到**。

现状是：接口进程在向自动化发布同步读快照前会先 `refreshFromAuthority()` 重读库，于是另一侧的写会被**周期性地捎带**刷进来。这是副作用，不是为此设计的通道 —— 而 `config_mirror_version` 的消费者名册里，这个镜像键的消费者只登记了自动化进程，没有登记"另一个接口进程"。

**决定**：实装时必须先坐实那条周期的实际上限，并把它写成规格里的可验收界（"另一目标 MUST 在 N 内读到新值"）。若该周期不可接受或不可证明，则把接口进程自己补进该镜像键的消费者名册，走既有失效通道。**MUST NOT** 就这么依赖一个没人写下来的副作用：它现在能跑，是因为没人需要它跑；一旦有人为别的原因改了发布节奏，"两边同时生效"会静默退化成"另一边等重启"，而且不报错。

### D6：迁库之后如何维持单份 —— 留具名前提，不留默认

规格里写清：本能力的"单份"当前**成立于两个目标共用同一属主库**这一事实。`ol` 迁往独立库的那个变更 MUST 一并处理本能力（指定一侧为属主 + 另一侧经既有跨进程同步读消费，或显式接受重新分成两份并撤销本变更的承诺）。不写这条的后果不是报错，而是迁库当天悄悄回到今天的状态 —— 两边各一份、各自都不报错、只有逐格比对才发现。

### D7：合并抹掉的安全性质必须在界面上补偿

后台该页 MUST 明示"本页配置对 dev 与 OL 同时生效"，写入确认里同样带上。这不是文案润色：合并前误改的代价是"试坏了一个测试环境"，合并后是"改到了线上"。界面不讲，下一次误改一定会发生。

## Risks / Trade-offs

- **[OL 上处于第 7 天的 10 个环境在迁移瞬间毕业]** → 它们的当日上限会从冷启动第 7 天（浏览 70 / 点赞 18 / 评论 5 / 关注 5 / 加群 3）跳到安全限额，是一次**放宽**。迁移安排在低峰时段，迁移当天盯这批账号的实际用量；这批环境键在迁移记录里逐个列出，便于事后核对。
- **[消费模式"确认点赞→加群"由 5 收到 2，加群频率翻倍以上]** → 这是"整套取 dev"的顺带结果，不是本变更的目的。该格在迁移记录里**单列**，一旦观察到加群过频，可只回滚这一格而不必回滚整次合并。
- **[迁移期间两个接口进程各持旧缓存]** → 迁移后两侧都重启（或确证已过一个刷新周期）再做验收，否则会看到"库里已合并、界面还是旧值"，并把它误判成迁移失败。
- **[两个后台并发写同一份配置]** → 既有 `expectedRevision` 比较交换会拦（409，前端已有"revision 已变化"文案）。但这是合并后才可能出现的情形，必须补一条验收，不能假定它天然成立。
- **[回滚窗口是有限的]** → 回滚＝恢复分行键 + 从备份还原两行。一旦运营在合并后改过配置，回滚只能还原到备份那一刻的两份值，中间的编辑会丢。因此回滚窗口要在迁移记录里写清，过期后只能"向前修"。
- **[与 `deployment-environments` 的既有隔离要求冲突]** → 本变更在该规格上补一条具名例外并写清依赖；MUST NOT 靠"反正现在共库"默默成立。

## Migration Plan

1. **迁移前备份**：三张表全量导出（含 `_audit`），落到与本次变更同名的备份文件，记录导出时刻。
2. **一个事务里完成**：DDL（删分行键 / 放宽审计 CHECK / 重设主键）＋数据合并（策略按 D2 逐项选定、完成标记按 D4 取更早、revision 按 D3 起新序列）。事务失败即整体回退。
3. **两个接口进程重启**，确保各自缓存重新从库装载。
4. **验收**（缺一不可）：两边后台读到逐格相同的一份；OL 上原第 7 天的环境显示已完成且当日上限等于安全限额；在一侧后台改一格，另一侧在约定时限内读到新值；两侧并发写触发 409 而不是互相覆盖。
5. **回滚**：恢复 `execution_target` 分行键，从第 1 步备份还原两行，重启两个进程。回滚窗口见上文风险条。

### D8：一次迁移全量切换，不分阶段 —— 归因靠分开观察，不靠分开上线

用户已裁定一步到位：六项配置与完成事实在同一次迁移里全部合并，不先切冷启动、再切消费与 Reel 节奏。

代价必须写明：合并当天 OL 上会**同时**出现两个方向相同（都是放宽）的变化 —— 一批账号立即毕业改走安全限额，以及消费模式的加群阈值由 5 收到 2。若当天观察到异常放量，"是毕业那批放的量，还是加群那格放的量"在总量上分不开。

**因此归因必须在观察面上解决，而不是在上线节奏上解决**：迁移记录 MUST 把两批受影响对象分开列（立即毕业的环境键清单 / 处于消费模式的账号清单），观察时也分开看 —— 毕业那批看当日各动作总量是否顶到安全限额，消费那批只看加群次数。两批若有交集，MUST 单独标出，它们是唯一无法靠观察面区分的样本。

## Open Questions

- 入群后首次评论等待取 ol 的 72 小时是按 D2 的"缺席不参与取值"推出的；若运营本意就是 24 小时，需明确改口径。
- D5 那条周期的实际上限是多少、够不够格写成规格里的可验收界 —— 实装第一步就要坐实，它决定是"沿用副作用"还是"补消费者名册"。

## Why

Facebook 的全局运营节奏配置（普通人设 Reel 节奏、规则模式、消费模式、冷启动天数、冷启动每日动作上限、入群后首次评论等待）与冷启动「完成」标记，目前都**按运行目标各存一份**（`dev` 一行、`ol` 一行）。管理后台按主机各部署一套且页面上不标注当前目标，运营看到的是一张"全局配置"页，实际只改了自己连的那一边。

这已经造成一次真实事故：运营在 dev 后台把冷启动周期改成 5 天并重排了曲线，OL 侧仍是 7 天 —— OL 上处于第 6/7 天的账号一直显示"未完成"，配额继续被冷启动曲线夹住，走不到安全限额。两边各自都在如实汇报自己那份配置算出来的结果，因此没有任何一处报错，只有对着两个后台逐格比对才能发现。

更根本的问题是**隔离切得不齐**：同一个环境的冷启动**起点**（`client_environments.slow_start_since`）与**安全限额**（`quota_config`）本来就是两边共享的，而**总天数**与**完成标记**却各存两份。于是同一个账号"起点只有一个、天数有两个、完成状态有两个"，这个不自洽本身就是缺陷来源。用户已裁定：这些节奏配置不再区分 dev/ol，两边节奏完全一致。

## What Changes

- **BREAKING**（对既有部署的运行行为）：Facebook 全局运营策略收成**跨运行目标唯一一份**。写入任一后台即同时改变 dev 与 OL 的生产行为。涉及后台那一页的全部六项：普通人设 Reel 节奏、规则模式、消费模式、冷启动、每日动作上限、入群后评论延迟（独立保存）。
- **BREAKING**：冷启动「标记完成」事实收成唯一一份，不再按运行目标各记一套（当前 dev 46 行 / ol 21 行互不相认）。
- 迁移基准按用户裁定：**整套取 dev 现值**；唯一例外是**入群后首次评论等待取 OL 的 72 小时** —— dev 侧根本没有行、会回落到默认 24 小时，照搬 dev 等于把运营手写过的窗口悄悄改回默认（现行代码注释已就此点名警告）。
- 完成标记按环境合并：同一环境在两侧都有记录时取**更早**的完成时刻。
- **补偿性要求**：后台在该页明确标注"本页配置对 dev 与 OL 同时生效"，并在写入确认里带上同样的告知。合并抹掉了"dev 是可以随便试参数的地方"这条既有安全性质，若不在界面上讲明，下一次误改的代价只会更大 —— 因为现在会一次改到线上。
- 审计表保留历史行上的运行目标字段**仅供追溯**，不再作为分行键。

### 合并后 OL 生产行为的即时变化（本变更的主要风险面）

| 项 | OL 现值 | 合并后 |
|---|---|---|
| 冷启动总天数 | 7 | **5**（当前处在第 7 天的 10 个环境立即毕业、改走安全限额） |
| 冷启动逐日曲线 | 7 行 | **dev 那张 5 行表**：搜索全天归零（原 1/1/2/2/3）、第 1 天点赞 2→0 关注 1→0、第 2 天点赞 3→2 关注 1→0、第 3 天评论 1→0 关注 2→3、第 4 天关注 2→3、第 5 天搜索 3→0 |
| 冷启动 Reel 浏览→点赞 | 7 | **8** |
| 消费模式 浏览→点赞 | 7 | **5** |
| 消费模式 确认点赞→加群 | 5 | **2**（加群频率明显放宽，是最需要复核的一格） |
| 入群后首次评论等待 | 72 小时 | **72 小时**（不变，见上文例外） |
| 冷启动完成标记 | 21 行 | 与 dev 46 行按环境合并 |

## Capabilities

### New Capabilities

- `facebook-global-policy-single-scope`: Facebook 全局运营策略与冷启动完成事实在所有运行目标间只有一份的归属规则 —— 单份的读写语义、迁移与合并基准、后台必须明示的"同时生效"告知，以及一旦 `ol` 迁往独立数据库时这份"唯一"如何继续成立。

### Modified Capabilities

- `facebook-reel-mode-cadence`: 六个 Reel 节奏值由"target-global"（每个运行目标一份全局值）改为跨目标唯一一份全局值；全局写路由的 revision 与审计语义随之改为单一序列。
- `client-facebook-slow-start-progress`: 进度写入不再"按 `completed` 原子新增或删除**当前 execution target** 的完成事实"，改为写唯一一份完成事实；`totalDays` 的权威来源同样收成单份。
- `deployment-environments`: 在"dev 与 ol 运行态必须隔离"之上补一条**具名例外**：运营节奏类配置为刻意跨目标共享，并写清该例外当前依赖"两个目标共用同一 PostgreSQL"这一事实 —— 该 spec 同时要求 `ol` 最终使用独立生产库，两者必须在此显式对账，不能靠默认共库悄悄成立。

## Impact

- **aidcp-cloud / aidcp-api（属主域 api）**：`facebook_operation_global_policy`（+ `_audit`）、`facebook_group_comment_policy`、`facebook_environment_slow_start_completion` 三张表的运行目标分行键；对应的策略存储、面板读写路由、客户鉴权侧慢启动进度读写。
- **aidcp-automation**：经同步读镜像消费该策略（曲线、总天数、消费节奏）。镜像载荷本就是"一份"，预期零改动，但必须验证不因属主侧去掉目标过滤而漂移。
- **aidcp-console**：Facebook 全局策略页新增"对 dev 与 OL 同时生效"的明示与写入确认。
- **数据迁移**：三张表的一次性合并，需迁移前备份两边现值；回滚＝恢复分行键与两行。迁移会立即改变 OL 生产行为（见上表），MUST 作为一次有意的线上变更执行，不能混在常规部署里悄悄带上去。
- **不在本变更范围**（同期存在、各自独立处理）：客户端"暂时读不到当前曲线限额"＝曲线下发改动只部署到 dev、OL 未部署，属部署问题；后台"群组评论时序状态未知"与"配额页·热帖引流"打不开＝接口进程漏构造两个存储，修复已落在 `aidcp-api` 主干（`restore-panel-capability-wiring`，`02e2237` / `e09079b`）但尚未部署。

## Why

`aidcp-automation` 每次重启都卡在优雅关停、90 秒后被 systemd 超时 SIGKILL。2026-08-05 dev 上一小时内四次，次次如此（12:56 / 15:33 / 15:36 / 15:43 / 16:01）。

根因是**关停时没有人去断开在线的边缘连接**：

- 关停顺序里第一个真正会阻塞的 await 是「关闭边-云连接入口」。它调 `ws` 库的 `close()`。
- 那个方法只做两件事——不再接受新连接、等**现有连接全部结束**才回调。**它一条已建立的连接都不碰**（`ws` 8.21.1 实测：有一条客户端连着时回调 3 秒不触发，客户端一断开 3 毫秒内触发）。
- 边缘客户端只会一直心跳，没人通知它下线，它就一直连着。于是回调永远不触发。
- systemd 单元没写 `TimeoutStopSec`，用默认 90 秒，到点整个 cgroup 被 SIGKILL。

证据是闭合的：journal 里每次都有 `shutdown_begin`、从来没有 `shutdown_complete` 或 `shutdown_failed`（说明卡在关停**内部**，不是关完之后没退出）；api / content 用**同一套关停外壳**、同样有内部 HTTP 服务端，两个都在同一秒停干净——唯一的结构差异就是 automation 多一个边缘 WebSocket 服务端。

**代价不只是等 90 秒。** 关停被打断在第一步，后面的步骤一个都没跑：模型用量缓冲的最后一次提交没做（那段代码写明「失败即丢、不重投」，所以每次强杀都是实打实的用量少记）、委托任务的执行泵没收敛、边缘那侧收不到任何下线通知、风控写者锁没有显式归还（只能靠进程死亡后数据库那侧发现连接断了才释放）。

同一条路径上还有两个独立缺陷，今天不是主因，但会让排查走错方向：

1. **关停即使走完，进程也不会退出**。api / content 关完都显式退 0；automation 的入口只打一行「关停完成」，没有人调退出。api 那份代码的注释写明了为什么必须显式退 0——否则要么不退，要么以 143 结束、systemd 把一次干净停机记成 `failed`。
2. **逃生口是死的**。启动外壳的设计是「收到信号先把自己摘掉，第二个信号落回 Node 默认处置、当场结束」，专门用于关停卡死时不必去找 `kill -9`。但 automation 的入口文件**另外挂了一个从不摘掉的信号处理器**，第二个信号被它吞成一行「重复信号」就返回了。所以发多少个 SIGTERM 都杀不掉它。api / content 没有这个双挂（它们的入口就是外壳本身）。

## What Changes

- 关闭边-云连接入口时**主动断开在线的边缘连接**（关闭码 1001「服务端下线」，边缘据此正常重连），再等服务端回调；并给一个**有界兜底**：超时未收到对端关闭帧的连接直接掐掉，避免一条卡死的连接把关停重新拖住。
- automation 入口在关停干净后**显式退 0**，与 api / content 同形。
- 摘掉 automation 入口里那个重复且从不摘除的信号处理器，让「第二个信号立刻结束」的逃生口恢复生效。
- 把上述三条收紧成 `cloud-automation-production-runtime` 上可机械验证的关停要求。

## Capabilities

### Modified Capabilities

- `cloud-automation-production-runtime`：新增「关停 SHALL 在有界时间内真正结束进程」要求，覆盖主动断连、有界兜底、显式退出码、以及第二个信号的逃生口。

## Impact

- `aidcp-cloud/src/comm/ws-server.ts` 的 `close()`——**事实源在 cloud**，`aidcp-automation` 的同名文件是 `scripts/sync-split-repos` 的派生物，只在 cloud 改、再同步下来（只改 automation 那份会被下一次同步原样覆盖）。
- `aidcp-automation/src/server.ts` 的入口关停段——组装根，`sync-split-repos` 对它只报不改，直接在 automation 仓改。
- 不改协议、不改边缘、不改风控与配额、不动就绪闸与业务入口的启动顺序。
- **单体 `aidcp-cloud` 不因此被部署**（CLAUDE.md §8.0）：它在这里只作为事实源与整图验证仓。

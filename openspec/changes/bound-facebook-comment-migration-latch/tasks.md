## 1. aidcp-cloud — 消费准入与清闩时机（①，与 §2 必须同批）

- [ ] 1.1 把消费分支改成「先读闩 → 先判相关性（noteId 匹配）→ 相关才取出并清 → 再判落地」。**清闩不得先于判定**（design D1）
- [ ] 1.2 不相关的开帖回执：闩原样不动、不产生本次迁移的失败归因、**交还给后续正常路径处理这条回执**（不得就地吞掉）
- [ ] 1.3 相关性与落地判据**分开**：相关性只判「是不是在说本次迁移那条笔记」，落地判 `ok` 与观测面。相关但导航失败的仍须被消费并判失败，**不得因失败而被当成不相关留在闩上**（design D2）
- [ ] 1.4 抢占分支（开帖时清闩的那一处）与消费分支的相关性判定尽量共用一个判定函数，避免两处分叉；实读后若确不宜共用，在此写明理由

## 2. aidcp-cloud — 有界终局扩到每一次已批准交付（②，与 §1 必须同批）

> **两者不可只做一半**：只做 §1 会把「错误地清掉闩」换成「永远不清」，是更糟的形态（design 风险首条）。

- [ ] 2.1 去掉武装函数里 `if (!trace) return` 的守卫，让**每一次已批准交付**都武装有界超时
- [ ] 2.2 到期回报按有无审批 trace 分口径：有 trace 走既有的强制评论结局上报，无 trace 走既有的「已批准未送达」上报。**照抄消费分支现有写法，不新造上报语义**（design D5）
- [ ] 2.3 到期同时 emit 终局事件，确保评论支线时钟解冻（与消费分支同口径）
- [ ] 2.4 **改名**：武装 / 清除 / 定时器字段这一组不再只管免审强制评论一支，一并改成反映真实职责的名字。**改名与行为改动分成两次提交**（design D3 / 风险条）
- [ ] 2.5 武装时若闩已被占：如实回报，**不得静默覆盖**（design 风险「单槽假设」；这是低成本诚实兜底，不引入队列）

## Context

### 起点

用户在审阅 Cloud→Edge 命令说明书（46 条）时提出两个观察，经核实全部坐实且同根因：

1. **`page.scroll` 该不该分成 `feed.scroll` / `search.scroll` / `group.scroll`？** 查实：这个区分**已经存在**，落在 `PageScrollPayload.reason?: string` 一个裸字符串字段加一句注释里（`aidcp-cloud/src/comm/protocol.ts:1492`）——不是联合类型，写错了两边都编译得过。
2. **救援清单那七条「和其他的不在一个维度上」。** 查实：`identity.read_*`（翻译层）、`captcha.assist.*`（环境层）、`edge.task.acquire/release`、`session.end`（执行权与编排）全登记为 `page_automation`，唯一共同点是**都需要浏览器**。分类被「怎么执行」污染，身份闸只好手工挖六个洞（救援清单）当补丁。

统一诊断：**命令词汇没有语法**。同样「原语 / 面 / 目标 / 意图」四维，存量有四种编码（`page.scroll` 只有原语；`note.scroll_comments` 原语+面；点赞/评论点赞按目标展开成两条；`note.open` 原语+参数面+参数意图）；「surface」在协议里三处三义，其中一处不得不加注释「不是那个 surface」。

### 业界对照：OpenCLI（`github.com/jackwener/OpenCLI`）

两层设计：语义层 `opencli <站点> <命令>`（站点是命名空间，页面不出现在任何一级）+ 原语层 `opencli browser <动作>`（click/scroll/state…，完全无页面维度）。同一动作跨页面靠 **reactive snapshot-and-act**：每步动作前 `state` 拿一次带元素引用的快照，页面一变引用失效再拿。

**可学的**：语义命令与原语命令分层，不混在一个命名空间平级（我们今天混着）。
**不可抄的**：无页面建模成立的前提是**决策者在现场**（人或本地 agent 每步看得到快照）；我们的决策者在云端，命令名 + 回执是它的全部输入。它能纯本地也因为它只有前两层、账号层是空的（"账号"就是用户本人，无额度/风控/记账）。

## Goals / Non-Goals

**Goals:**

- 确立六条命令设计规则，作为**新增** Cloud→Edge 命令时的裁决依据
- 四个判例示范用法（两正、一反、一混合），三条撤回结论防重走弯路
- 登记本判据暴露出的三个后续缺口（观察命令 / 七条归类根治 / page.scroll 收敛），不在本 change 内做

**Non-Goals:**

- 不重命名、不重分类任何存量命令（理由见决策五）
- 不实装观察命令（state 类）
- 不动身份闸、不动救援清单（`close-account-layer-operation-manual` 正在给它上断言）
- 不产生任何新的命令清单 / 归属表——逐命令声明的唯一落点仍是操作说明书

## Decisions

### 决策一：期望执行面进命令词汇；理由是「推定开环」，不是「云端看不到」

**撤回的第一版论证**：「云端隔着连接看不到页面，所以面必须编进命令名」。用户驳倒：云端基于自己发过的命令**能推定**当前页（`group.open` 成功 ⇒ 在群组页 ⇒ 可发 `group.join`），因果链成立。

**站得住的论证**：云端有的是**推定**，不是事实，而推定是**开环**的——中间任何一次非云端发起的跳转（平台自跳、弹层、重定向、断连重上、人碰了一下）都会让推定与现实脱节，且脱节无人上报。这不是假想：边缘侧同形态的状态漂已出过事（浏览面开场钉一次、之后静默回落信息流，新号整场 11 次进不了 Reels，三条早退路径全不打日志）。

**面进命令词汇的真实作用：把云端的推定变成每条命令自带的一次可证伪声明。** 发 `group.scroll` = 声明「我认为你在群组页」，边缘不在就能当场拒绝并如实回报；发 `page.scroll` 则边缘无从判断命令是否发错了地方，只能照滚再报成功——正是静默假成功的形态。成本为零（不占往返、不加延时）。

**完整形态是三段，缺一段都不成立**（第三段是用户补的）：

```
① 命令带期望（名字或必填参数）   ← 让边缘有得可比；没有①，②永不发生
② 不符如实报错，三态分开         ← 「确认到不在」≠「没能确认在哪」
③ 云端以观察命令问真相、重规划   ← 没有③，报错之后没有出路
```

②的三态是红线的既有要求；③所需的「问现在在哪个面」命令今天**不存在**（46 条里最近的是读登录身份——问的是登着谁，不是在哪页），登记为后续缺口。

### 决策二：拆分判据四条（下限）+ 外观不冒泡（上限）

**任一命中 ⇒ MUST 拆成不同命令**：

| # | 判据 | 典型例 |
| --- | --- | --- |
| ① | **回执语义不同**：同一结果让云端做不同决定 | 信息流滚到底⇒该刷新换批；搜索页滚到底⇒这个词穷尽了该换词 |
| ② | **失败原因集合不同** | 群组页有「未加入看不到」，信息流没有；合并则要么丢原因要么进兜底桶（明令禁止） |
| ③ | **平台留痕 / 可重放性不同** | 合并只能按最坏一档，安全的那面被白白锁死 |
| ④ | **决定权落点不同**：边缘必须自己判断上下文才知道怎么做 | 决策下沉到边缘，违反边轻云重；Reels 点赞分叉即此 |

**四条全同、只是页面长得不一样（选择器 / 布局）⇒ MUST NOT 冒泡到协议**，差异留在引擎平台适配层——否则每接一个平台就复制一整套命令。

**防爆炸的闸不是「少建命令」，是「无语义差异的组合不许建」**：条目按「每个面下真正不同的能力」线性增长，且平表可枚举可穷举检查；会爆炸的是不问差异的面×原语笛卡尔积。

### 决策三：执行层不做决定；「简洁 = 职责单一」，不是条数少

**撤回的两版论证**（都记入文档防重走）：

- 「CLI 宽容文化（默认值 / 猜意图）在我们这儿危险，因为错了会留痕」——**拿后果定归属**，与 addressing-layers 判例二同一错误形态。对错的账全在云端（风控 / 配额 / 人审 / 绝不重投），执行层不背也背不动。
- 「简洁与清晰冲突，简洁是上限」——把简洁错当**条数少**。`page.scroll` 一条打天下不是简洁：四个面的分支没有消失,只是挪进了命令实现内部（说明书按消息类型给声明，一行给不了四种）、挪到了边缘的隐式状态机（会漂,已出过事）、挪出了可枚举可检查的平表。**命令表少一条，边缘多一个隐式状态机，净亏。**

**站得住的表述**：

- **执行层不做决定**：命令必须参数齐全；执行层不补任何一个空——「没说在哪个面就用当前的」里,「用当前的」是执行层在替发令方决定。拒收参数不完整的命令不是防御,是拒绝替上层做决定,与「未登记命令直接拒收、绝不猜」同族（fail-closed）。
- **期望进命令服务的是发令方自己的可调试性**：不带期望,上层给错 → 照执行 → 报成功 → 上层永远不知道自己错了;带期望,给错 → 当场报错 → 上层拿着报错查自己。
- 边缘侧核对不是负担:「你让我滚群组页,我找不到群组页」与「你让我点赞,我找不到那张卡」是同一件事——**合同履行不了,如实说**（`no_target` 的既有形态）。

### 决策四：类别按「在编址什么」分，不按「怎么执行」分

七条归错类的判例（详表见 `close-account-layer-operation-manual` design 的修正节）坐实：按执行载体（要不要浏览器）归类,会把翻译层的身份读取、环境层的验证码协助、编排层的租约与收尾全塞进「页面自动化」,身份闸按类别一拦全拦,只好手工打洞。**救援清单的存在本身就是分类错误的补丁。**

重新归类会改变身份闸实际拦什么,属行为变更 ⇒ 不在本 change,且 MUST 等本语法立起来后再做——否则改完仍无判据挡住下一次归错（该依赖已登记在 `close-account-layer-operation-manual` tasks 9.0）。

### 决策五：只约束新增；存量机会式收敛

不批量重命名存量：每条重命名都触协议四处同步 + 边缘改动要出包才生效（当前已有两条 change 因出包门槛收不了尾）,批量动 46 条是把整个协议置于长期半新半旧态。**存量与语法的偏离在触碰该命令的 change 里顺带收敛,或显式记录豁免**;`browse.next` / `browse.scroll` 的 `@deprecated` 先例证明存量收敛有既定路径。

### 决策六：interaction 按「对象类型」拆,不按「位置」拆

用户第 4 层的纠结,按判据二裁决:

- 赞帖子 / 赞视频 / 赞评论——**对象类型不同 ⇒ 拆**（回执、失败原因、策略都不同;系统里已有「视频按概率随机赞」这种按对象类型的策略）
- 详情页赞 vs 信息流赞同一张卡——效果全同,只是位置 ⇒ **不拆**,位置差异走决策一的期望面
- **判断口诀:不问「点的位置一样吗」,问「云端要不要因此做不同的决定」**

Reels 点赞今天的形态是判据④的活判例:云端下发同一条点赞命令不说在哪个面,边缘靠自维护的会话状态分叉两套实现（`facebook-session.ts:982`）,该状态漂过,回执又只在信息流面挂独立见证、云端归账仲裁只在那个面激活——「在哪个面」已经在影响云端记账,却是事后从回执里读到的,而它本该是下发时指定的。

## Risks / Trade-offs

- **[被读成重命名工程]** → 决策五写死:只约束新增;验收项含「未改任何存量命令名」。
- **[判据被机械套用产生笛卡尔积]** → 决策二的上限条 + 「无语义差异的组合不许建」写进规格。
- **[「期望面」被实装成边缘侧默认值]** → 决策三:参数不完整拒收,与未登记同族 fail-closed;规格给出反例场景。
- **[观察命令被顺手实装]** → Non-Goals 写死;它需要协议四处同步 + 出包,值得独立 change。
- **[判例随实现漂移]** → 全部标注为 2026-08-06 快照,引用前重核（与 addressing-layers 同口径）。

## Open Questions

- **观察命令的形态**:独立的「问在哪个面」,还是并进既有身份读取做一条「问现状」（面 + 身份一起回）?倾向后者（一次往返拿全恢复所需事实）,留给实装它的 change 定。
- **期望面进名字还是进必填参数**:两者在「能报错」上等价;判据二四条全同才允许参数形态。逐命令裁决,不一刀切。

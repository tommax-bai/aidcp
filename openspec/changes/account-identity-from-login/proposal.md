## Why

`multi-account-node-support`（已部署）让每个 edge 节点在握手时声明账号身份，但身份来源是**启动器外部指派的环境变量标签**（`AIDCP_ACCOUNT_ID`），缺失即被诚实闸拒绝握手。这有两个弱点：

- **标签与真实登录解耦**：运营声明 `accountId=A` 却在该节点的浏览器里登了账号 B，系统无从察觉——人设、风控配额、归因全都挂在错误的账号上（错配是静默的）。
- **要求运营预先管理标签、且漏设即被拒**：节点启动器不显式写 `AIDCP_ACCOUNT_ID` 就被新门禁拒握手（仅 `dev-run.sh` / 多节点启动器声明了；`npm start` / Electron 应用不声明 → 下次启动即被拒）。

更稳的模型：**账号身份应来自「实际登录进去的那个账号」**，由边缘在登录后从登录态读出，而不是外部贴标签。这把"我是谁"与"谁真的登录了"绑死，错配从根上消失，运营也不必管标签——只需"起一个节点、扫码登想用的账号"。

本 change 据此**重定义节点生命周期的登录前/登录后边界**，并把身份来源从「启动器标签」改为「登录态读出的真实账号稳定 id」。这是对 `multi-account-node-support` 决策 D4 的设计迭代：复用其**已部署**的诚实人设就绪闸 + 飞书通知 + 按账号风控/去重，只换"身份从哪来"。

## What Changes

- **节点生命周期按「身份是否确立」分三态**（概念地基，见 design）：
  1. **无身份态**（账号无关，绝不替任何账号做事）——内含两件本质不同的事：**节点初始化**（一次性：拉浏览器 / 分配端口 / 用户数据目录 / 连传输）与**身份确立**（可反复发生的态：进站 → 登录 → 读出稳定账号 id）。
  2. **已确立身份 · 就绪闸**（知道是谁了 → 过人设绑定闸，default 豁免；未绑停手 + 飞书，已绑放行）。
  3. **运行态**（账号作用域操作，按人设驱动、受风控/配额/去重约束）。
- **身份来源改为登录态读出的稳定 id**（小红书 userid 类，**非昵称**）：边缘当前时序已是"登录在前、握手在后"，本 change 让边缘在登录后**读出真实账号稳定 id、用它当握手身份**，取代环境变量标签。**握手消息字段不变、云端门禁逻辑不变**——只换身份的产生方式。
- **身份确立必须诚实**：读不出稳定 id → 诚实失败、停手，绝不猜、绝不回落 `default`（守住"绝不静默以默认账号/默认人设跑"红线）。
- **身份可翻转、要持续校验**：登出 / session 过期 / profile 换登别的号 → 节点退回**无身份态**重新"身份确立"，但**不重跑节点初始化**（浏览器不重启、端口目录不重分）。身份不是握手时定死一次。
- **启动器与目录命名简化**：多节点启动器只分配**节点槽位**（端口 / 用户数据目录 / `edgeId`），**不再分配 accountId**；用户数据目录按节点槽位命名（`node-<n>`），账号是"谁登进这个槽位"的产物。
- **顺带消除一个运营风险**：身份从登录态推导 → 永不缺失 → 不再有"运营漏设环境变量即被新门禁拒握手"的问题。
- 兼容：保留"启动器环境变量显式覆盖身份"为**可选**逃生阀（预置 / 特殊场景），默认走登录推导（取舍见 design 开放问题）。

## Capabilities

### New Capabilities
- `account-identity-resolution`：节点生命周期的**身份维度**模型——以「身份是否确立」为登录前/后的分界；定义无身份态（节点初始化 + 身份确立两件事）、身份确立为可反复的态、身份从登录态读出稳定 id（非昵称、读不出即诚实失败）、身份可翻转则退回无身份态重新确立而不重跑节点初始化。

- `accounts-master-data`：账号以**登录态读出的真实稳定 id** 为主表主键自动登记（不再用运营外部标签）；昵称仅作显示名（与 `account-real-nickname` 协调：昵称=显示，稳定 id=主键）。

> 注：`persona-gated-session-start` / `chrome-instance-isolation` 的相关行为也被本 change 修订（身份来源、启动器只分配节点槽位），但这两个 capability 来自**尚未归档**的 `multi-account-node-support`（其 spec 未并入基线），故无法对它们写 delta。这部分修订**由新增的 `account-identity-resolution` capability 承载**（其需求即新行为、取代 env 标签那部分），待 `multi-account-node-support` 归档后由后续迭代正式对齐。

## Impact

- **aidcp-edge（主体）**：新增"登录后读出稳定账号 id"的能力（CDP 读页面，与现有登录态探测同手法）；`main.ts` 身份来源从 `process.env.AIDCP_ACCOUNT_ID` 改为登录后读出（环境变量降级为可选覆盖）；握手时序保持"登录在前、握手在后"，握手身份字段不变；身份失效检测 → 退回无身份态重新确立；多节点启动器 `scripts/launch-multinode.ts` 改为只分配节点槽位、用户数据目录按 `node-<n>`。
- **aidcp-cloud（零改）**：经查实 `accountId` 在云端全程是**不透明字符串、无格式校验**，换源对整条云端透明——握手建运行时 + 就绪闸 + 风控/人设/主表全原样消费（**已部署、逻辑复用**）。**唯一需验证**："同 edgeId 不同账号重连"（profile 换号）经已部署顶替机制正确重绑。**不动边-云协议**（`HelloPayload.accountId` 字段早已存在）。
- **成败手 / 须先验证**：能否在登录后可靠读出**稳定** id（userid 类，非昵称）——apply 第一项技术任务实地验证小红书把 userid 放在哪（页面状态 / 个人主页链接 / cookie）；读不出即诚实失败。
- **依赖 / 关系**：迭代 `multi-account-node-support` 的 D4（复用其已部署门禁/通知/风控）；与 `account-real-nickname`（未启动）正交协调（昵称=显示名，稳定 id=主键）。
- **非目标**：不动边-云协议；不引入指纹浏览器；不改云端按连接多租户/风控/去重内核（仅换身份来源）。

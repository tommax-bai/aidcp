## Context

「实时工作过程」面板活在小红书环境价值首页，取数模型只有创作侧三种证据（`content-workspace.js:777-815`）。账号的日常主路径——浏览、找灵感、点赞——从不进入该模型，因此一个正在跑的账号在面板上恒为空态。

证据其实已经躺在客户端里：核心进程 stdout 经 `ui-events.cjs` 翻译成条目 `{ts, type, sentence, loopStage?}`，`main.cjs:3314 broadcastActivity` 补上 `envId` 后经 `ui:activity` 广播，`preload.cjs` 暴露 `onActivity`，运行面板 `renderer.js:5058 routeActivity` 已按 envId 存入 `fleetView.buffers`（上限 `STREAM_MAX`）并上屏。内容工作区是一个独立模块（`window.ContentWorkspace.create`），由 `renderer.js` 单向喂 `setEnvironment` / `setRuntime`，从未接过这条流。

约束来自本能力已有规格与仓内红线：面板总高 ≤255px、不得伪造推理、声称执行层动作必须有执行层证据、未知与已确认为空不得压成一态。另有一条来自 `ui-events.cjs` 自陈的性质：那张兜底映射表是**无保障的手工耦合**（核心改一句日志措辞，条目会静默消失而测试全绿），任何设计都不能把「一定有条目」当作前提。

## Goals / Non-Goals

**Goals:**
- 没有创作任务时，面板用当前环境真实发生过的活动记录呈现工作过程。
- 活动记录只表达「发生过」，不被翻译成阶段进度、完成度或当前动作。
- 面板把「暂时读不到」「确认没有任务且无活动」「没有任务但有活动」三种结论分开表达。
- 不新增跨进程通道、不改活动流的产生与广播规则。

**Non-Goals:**
- 不为活动流补充新的事件类型或改核心侧措辞（那是发射器侧的事，见 `ui-events.cjs` 的覆盖纪律）。
- 不把面板扩展到 Facebook / 视频号环境——该面板本就只在小红书环境出现。
- 不引入云端「浏览进度」接口：本变更只消费已在本机的证据。
- 不改动运行面板（旧 UI）的活动流呈现。

## Decisions

### D1：活动条目由 `renderer.js` 单点转发，内容工作区不自己订阅

`renderer.js` 已是活动流的唯一路由点，持有 envId 归属判断、环形缓冲与上限。内容工作区新增 `pushActivity(entry)`（增量）与 `setActivities(list)`（切环境时整体补发），由 `routeActivity` 与环境切换处调用。

*备选*：内容工作区直接 `api.onActivity(...)` 订阅。否决——同一广播会被两处各存一份，两边裁剪时机与环境切换语义不同步，日后必然漂移；且订阅方多一处就多一处「切环境忘了清」的路径。

### D2：活动记录是独立的视图模型，不复用 `stages`

现有 `stages` 自带 `done / current` 与「阶段完成 / 阶段中」文案，把活动条目塞进去等于凭条数合成进度——正是规格禁止的那件事。新增 `kind: 'activity'` 视图模型，条目只携带 `ts` 与 `sentence`，渲染时显示真实相对时间与句子本身，不显示阶段名、不显示完成勾。

*备选*：把活动条目映射成 stages 并按 `loopStage` 归类。否决——`loopStage` 表达的是「当前处在浏览循环的哪一段」，不是「哪几段已完成」，据此画进度条会凭空造出并不存在的完成度。

### D3：图标一律中性，不用完成勾

活动流里既有成功事件，也有阻断浮层、失败提示一类条目。统一用中性圆点标记，避免把「发生过」渲染成「成功了」。这与 `ui-events.cjs` 的计数纪律同向：只有 ✓ 成功行才计数，展示层不得替它加语义。

### D4：进行中语义只由运行态授权

只有 `browseActivity().proven`（即 `automationState === 'running'`，判据与诊断面板同源）为真时，最新一条活动才带进行中标记与逐字效果；其余八档下所有条目一律按历史呈现，无动效。这条直接落实规格「执行层未跑起来时不声称正在浏览」，也覆盖「已停止但留有历史活动记录」。

### D5：三态判定的输入是来源状态，不是数据是否为空

面板依赖两个来源：创作队列（`state.publishQueue.kind`）与待审稿（`state.homeDrafts.kind`）。任一为 `error` → 面板呈现「暂时读不到当前进度」并给重试（复用 `refreshHome`）；两者仍在首轮 `loading` 且无既有数据 → 呈现读取中；两者均 `ready` 且无任务时，才按「有无活动记录」二选一呈现。**判定 MUST NOT 以 `data` 是否为 null 作为唯一依据**——那正是当前把三态压成一态的写法。

### D6：时间按真实 `ts` 渲染，不走独立时钟

条目显示相对时间（由现有 `uiLogic.relTime` 计算）。面板本就随状态心跳与首页轮询重渲染，无需为它新开计时器；重渲染时按原始 `ts` 重算，绝不因刷新把旧条目改写成「刚刚」。

### D7：条数有界，顺序与现有过程区一致

面板内保留最近若干条（取值与面板 255px 高度上限相称，超出部分由现有 `overflow:auto` 承载），按时间正序、最新在底，与现有过程条目渲染方向及自动滚到底的行为一致。

## Risks / Trade-offs

- **活动流是无保障的手工耦合，核心改措辞会让条目静默消失** → 面板不依赖任何具体措辞或类型白名单：有条目就按条目呈现，没有条目就回到诚实空态（而不是造进度）。缺失表现为「面板显示空闲」，不会表现为错误内容。
- **活动记录只有本次会话、且只在客户端内存** → 切换环境或重启客户端后历史不完整。面板 MUST NOT 因此宣称「今天没做过事」：无活动记录时的文案只说明当前没有可展示的过程，不下达已确认空态的历史结论。
- **面板同时承载两类语义（任务投影 / 活动记录），有被误读为同一进度的风险** → 两类模型渲染上明确区分：任务投影保留阶段名与完成勾，活动记录只有时间与句子、中性标记。
- **旧 UI 与面板并存同一条流，可能被质疑重复** → 二者受众不同（运行面板面向排障，价值首页面向账号主）；共用单一路由点转发，不产生第二份状态。

## Migration Plan

纯客户端渲染层改动：无协议、无云端、无数据库、无迁移。落地即随桌面客户端代码生效；回滚为还原对应提交。是否出安装包由用户显式触发（本仓 §6 长期授权口径）。

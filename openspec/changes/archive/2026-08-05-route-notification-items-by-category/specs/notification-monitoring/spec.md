## MODIFIED Requirements

### Requirement: 通知巡视——评论/@ 通知，忽略赞/藏/关注

系统 SHALL 在检测到"消息"有未读时，暂停浏览、去通知页**逐类查看以清零未读**：评论/@ MUST 提取来源用户名与内容并发飞书通知；点赞、收藏、新增关注 MUST 被"忽略"——此处"忽略"指 **MUST NOT 发飞书**，而非不看：为把平台未读清零，这两类 SHALL 仍「看一眼」（已真机验证看一眼即清该类未读）。检测由边缘后台监测体完成（只读、只上报、不操作页面）；抽取 MUST 产出**原始结构化**通知项（用户名 / 内容 / 关联笔记标题 / 稳定 itemKey），是否值得通知由云端判定，边缘 MUST NOT 在「评论和@」tab 之外做分类决策。「评论和@」的浏览 MUST 覆盖到该类未读清零（滚到底 / 直到不再有新项或角标清零），MUST NOT 因固定滚动屏数不足而遗留未清的评论未读。

**「忽略」这条禁令 MUST 按类别机械成立，MUST NOT 由对通知正文的文案识别来承担。** 巡视是云端**自己点名**去看哪一栏的（分诊选中某类 → 下发该类的浏览命令），因此「这批到达的通知条目来自哪一栏」是云端的**既有事实**，MUST 由云端自身状态回答。判据如下：

- **定性依据 MUST 是云端本趟自己选中的分类**：该分类 MUST 记录在巡视状态里、由分诊在选中时**单点写入**，并随巡视开始 / 结束清空。系统 MUST NOT 把「某批条目属于评论和@」这一判断建立在条目正文长成什么样上——正文识别是内容层防御（防抽取残留 / 占位串），MUST NOT 兼任类别路由。
- **只有选中分类为「评论和@」时，到达的条目批次才准进入评论管线**（分类 → 去重 → 发飞书 → 该类收尾）。选中分类为「赞和收藏」/「新增关注」，或本趟尚未选中任何分类时，该批次 MUST NOT 进入评论管线：MUST NOT 被分类、MUST NOT 被去重、MUST NOT 发飞书、MUST NOT 产生「评论和@ 已处理」的收尾事件。
- **被拒进评论管线的批次 MUST 仍照常到达**：这些条目对通知联系人名册是有用产物（见能力 `notification-contact-registry`），拒的是「进评论管线」，不是「到达」。MUST NOT 在到达口把它们丢弃，MUST NOT 因此让名册少一份增量。
- **条目自带的类型字段只作交叉校验纵深，MUST NOT 作唯一判据**：该字段由执行端推导（现网实现按云端下发的命令类别推导，仅「赞 vs 收藏」用行内文案），与云端选中类同源、且可能猜错。两个判据不一致时 MUST 以**云端自己选中的分类**为准，且 MUST 留下具名记录——不一致本身是值得看见的信号，MUST NOT 静默取其一。
- **三态 MUST NOT 压成一态**：「评论和@ 栏确实一条都没有（或全部已通知过）」MUST 仍照常收尾该类，使分诊回首页并进入下一轮；「这批条目根本不是评论和@ 栏来的」MUST 一条收尾事件都不产生。二者在日志与事件上 MUST 可区分。
- **每一类的收尾 MUST 由该类自己的证据产生**：赞和收藏 / 新增关注 MUST 各自凭其**浏览命令的成功回执**收尾，MUST NOT 依赖旁路条目上报来收尾；同一类在一轮内 MUST NOT 被收尾两次（重复收尾会多下发一条返回通知首页的导航命令）。去掉重复收尾后，每一类 MUST 仍恰好收尾一次。

#### Scenario: 评论/@ 触发飞书
- **WHEN** 通知页「评论和@」有新的评论或 @ 项
- **THEN** 边缘抽取其用户名与内容上报云端，云端对评论/@ 发飞书通知

#### Scenario: 赞/藏/关注看一眼清未读但不发飞书
- **WHEN** 未读来自点赞、收藏或新增关注
- **THEN** 巡视看一眼对应分类以清该类未读，但不发任何飞书，正常恢复浏览

#### Scenario: 评论/@ 浏览覆盖到清零
- **WHEN** 「评论和@」未读条数多于一屏窗口
- **THEN** 浏览滚到底 / 直到不再有新项或角标清零，不因固定屏数遗留未清未读

#### Scenario: 赞/收藏栏的旁路条目不进评论管线
- **WHEN** 巡视选中的是「赞和收藏」，执行端在清未读回执之外顺带回传了一批发送者条目
- **THEN** 该批条目 MUST NOT 被分类、MUST NOT 被去重、MUST NOT 发飞书
- **AND** MUST NOT 产生「评论和@ 已处理」的收尾事件，因而 MUST NOT 多下发一条返回通知首页的导航命令
- **AND** 这些条目 MUST 仍到达联系人名册通路，不被丢弃

#### Scenario: 类别判据不依赖正文文案
- **WHEN** 某条赞 / 收藏 / 关注通知的正文不是已知的固定说法（平台改文案、多语言、正文位取到了笔记标题）
- **THEN** 它仍 MUST NOT 被当成评论推送飞书
- **AND** 拦住它的 MUST 是「本趟选中的不是评论和@ 栏」，MUST NOT 只是正文文案识别

#### Scenario: 评论栏空批次仍正常收尾该类
- **WHEN** 巡视选中「评论和@」，执行端上报的条目批次为空或其中的项全部已通知过
- **THEN** 系统 MUST 仍产生「评论和@ 已处理」的收尾事件，使分诊回首页并进入下一轮
- **AND** 该态 MUST 与「这批条目不是评论和@ 栏来的」在日志与事件上可区分

#### Scenario: 赞/关注两类各自凭自己的回执收尾
- **WHEN** 巡视看过「赞和收藏」或「新增关注」，该类浏览命令回执成功
- **THEN** 该类 MUST 凭该回执收尾并返回通知首页
- **AND** 去掉旁路条目造成的重复收尾后，该类 MUST 仍恰好收尾一次，MUST NOT 一次都收不了尾

#### Scenario: 两个判据不一致时以云端选中类为准并留痕
- **WHEN** 云端选中「评论和@」但该批条目里没有任何评论/@ 类型，或云端选中的不是评论类却出现了评论/@ 类型
- **THEN** 系统 MUST 按云端自己选中的分类处置
- **AND** MUST 留下具名记录使该不一致可被发现，MUST NOT 静默取其一

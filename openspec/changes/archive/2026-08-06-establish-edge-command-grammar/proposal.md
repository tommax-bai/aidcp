## Why

云端对边缘的命令词汇今天没有语法：什么时候一个动作该拆成两条命令、什么信息必须进命令名、什么差异该留在引擎内部，每次新增全凭当时那个人的手感，而手感不能被检查。后果已经在代码里：同样「原语 / 面 / 目标 / 意图」四个维度，存量命令有四种编码方式；「面」这个概念在协议里三处三义；`page.scroll` 的面区分早已存在、却落成一个裸字符串注释；七条根本不是页面动作的命令因为「都需要浏览器」被归进页面自动化，身份闸只好手工挖六个洞当补丁。

刚归档的 `establish-edge-addressing-layers` 回答了「这件事该归本地还是云端」；本 change 回答它的下一问——**归了账号层（云端决策）之后，命令这门语言本身怎么设计**。这也是「新增浏览器操作时该在哪个维度加什么能力」的裁决依据（用户 2026-08-06 定为重要规则：后续每次新增操作必须按此讨论）。

## What Changes

- 新增判据文档 `docs/edge-command-grammar.md`：六条规则 + 四个判例 + 撤回结论清单（防重走弯路）。
- 新增**目标词汇蓝图**（判据文档附录）：46 条存量 + 观察命令逐条映射到目标形态（保留 / 改名 / 拆分 / 墓碑），充分借鉴 OpenCLI 的两层分离与命名空间化（用户 2026-08-06 定调：核心目标是 CLI 层功能清晰，OpenCLI 非常值得借鉴、要充分参考）。蓝图是迁移设计产物，MUST NOT 成为第二张运行时表。
- 新增规格 `edge-command-grammar`：约束**整个** Cloud→Edge 命令词汇——新增即时生效，存量按蓝图分批迁移收敛（出包与非原子升级两项迁移成本，用户均裁定可接受；核心目标是功能清晰）。
- `docs/architecture.md` 加指针（与 addressing-layers 指针并列）。
- **本 change 仍零源码改动**：蓝图落纸；分批迁移由后续 change 按命名空间成批执行（协议热点单写区，批次串行）。观察命令与七条归类根治并入蓝图后的迁移序列。

六条规则（全文见 design）：

1. **类别按编址单位分**（宿主 / 环境 / 翻译 / 账号），不按要不要浏览器分
2. **命令是发令方写下的完整意图**，含期望执行面；执行层不补全任何一个空——补空即决策，决策归上层
3. **语义差异才冒泡成新命令**：回执语义 / 失败原因集合 / 平台留痕 / 决定权落点，任一不同 ⇒ 拆；只是页面长相不同 ⇒ 留在引擎平台适配层
4. **同族同编码**：同一语义维度在同族命令里用同一种编码；协议词汇一词一义
5. **三段对账**：命令带期望 → 履行不了如实报错（「确认到不对」与「没能确认」分开）→ 云端以观察命令问真相、重新规划
6. **责任分置**：对错的账全在云端（风控 / 配额 / 人审 / 重放）；执行层只欠照做与如实回报

## Capabilities

### New Capabilities
- `edge-command-grammar`: 云端→边缘命令词汇的设计语法——新增命令时怎么判「拆不拆、什么进名字、什么进参数、归哪一类」，以及执行层对不完整命令与期望不符的诚实处置。

### Modified Capabilities
（无——本 change 不改任何既有命令的行为或登记；`client-core-browser-executor-separation` 的登记表仍是逐命令声明的唯一落点，本语法不产生第二张表。）

## Context

手动 / 批量启动一个 Facebook 指纹浏览器环境的现有顺序是：

```
并发计数闸 → 错峰串行链 → 运行时与内核准备 → 代理预检 → 串行启动队列 → spawn 核心
                                              ↑
                                    失败即终结，环境从未入队
```

预检**在进队之前**，所以「失败后排到队尾」在今天不成立——失败的环境不是排在队尾，而是被挡在门外、原地消失，没有任何东西会来接它。手动启动要人再点一次。

冷待机唤醒是另一条路，顺序相反：先进串行启动队列，轮到它时**在队内**做预检，失败后按 1 / 2 / 5 分钟退避重新入队。它本身已具备自愈形态，但退避的第一跳（60s）落在预检结论 120s 的缓存有效期内，会复用旧失败结论而不发新探测——那一跳是空的。

约束来自 `docs/stop-or-continue.md` §Q2：同一步重来可能得到不同结果 ⇒ 非结构性 ⇒ **MUST** 留带上限的自愈通道、**MUST NOT** 落终态；同时 §「加闸准入」要求重试通道必须有界，不得以无限排队掩盖真实故障。

## Goals / Non-Goals

**Goals:**

- 让链路瞬时不通的预检失败进入**有界**重排重试，而不是当场终结本次启动。
- 让每一次以重试为目的的重新探测都**真的发出探测**，而不是复用正被重试所针对的那个旧失败。
- 重排在排队语义上与普通启动请求完全等价：受同样的闸、排同样的队尾、不享任何优先级。
- 重排全过程可被运营看懂：既不伪装成正常启动，也不提前宣告死亡。

**Non-Goals:**

- 不改探测本身的实现（仍是单发 + 25s 窗口，本次不加探测内重试）。
- 不改串行启动队列、槽位 FIFO、并发计数闸三者自身的实现。
- 不扩展预检的平台覆盖（仍只有 Facebook + AdsPower + 浏览器未运行）。
- 不处理运行期（浏览器已跑起来后）的代理抖动识别与归因——那是完全独立的一段空白。

## Decisions

### 决策一：重排 = 延迟重入既有启动入口，不新建重试队列

启动入口本身已经带了三件我们正好需要的东西：幂等闸（同一环境不会并行两条启动流）、并发计数闸的准入、以及出栈时归还排队容量的 `finally`。因此重排只需要**等当前这条启动流出栈之后，重新调用同一个入口**。

这样得到的排队语义是免费且正确的：重新入场时它和任何新来的启动请求走同一条路，自然排到队尾、自然重新受闸、自然不可能插队。规格里「重排 SHALL 排队而非插队」这条不需要额外代码去保证，它是这个落点的结构性后果。

必须延迟到出栈之后，是因为当前启动流仍持有幂等标志与排队名额；在栈上直接重入会被幂等闸挡掉，什么都不会发生。

**备选方案（否决）**：往串行启动队列里塞一个重试项。否决理由是它要求预检先于入队的关系被倒过来，牵动的远不止失败分支；而且那条队列带优先级，塞进去反而要额外写代码去**阻止**重试项插队。

### 决策二：失败原因二分类，未识别默认可恢复

只有「重来可能不同」的才配消费重排预算：

| 类别 | 原因 | 处置 |
| --- | --- | --- |
| **可恢复** | 探测超时、连接被拒、主机解析失败、代理连接建立失败、未归类的请求失败 | 重排 |
| **可恢复** | 受管中继端口被占、启动过慢、提前退出、孤儿清理失败 | 重排 |
| **不可恢复** | 代理配置不完整、代理类型配错（协议不匹配）、认证不通过 | 立即终结 |
| **不可恢复** | 系统前置代理未配置 / 类型不受支持 / PAC 与自动发现、系统代理与环境代理重复 | 立即终结 |
| **不可恢复** | 环境代理权威读不到、权威格式无效、权威版本已变 | 立即终结 |

认证不通过归入不可恢复，是因为它指向凭据本身：重排三次同样不会通过，只会反复打代理商的认证。中继类失败归入可恢复，是因为端口占用和启动过慢都是本机瞬时状态。

**未识别的新原因一律按可恢复处置**。反过来做就是本仓明令禁止的兜底桶——把没认出来的原因折进终局，等于让一个谁也没做过的决定变成「这件事做不到」。代价是对称的但不对等：错判成可恢复只是多探两次，错判成不可恢复是把一个能起来的环境判死。

### 决策三：预算 2 次重排，间隔 20s / 60s

一次探测最坏吃满 25s 窗口，所以最坏路径是 `25 + 20 + 25 + 60 + 25 ≈ 2.5 分钟`后终结。

这个数量级的选择理由：它要盖住的是「抖动」——秒级到十几秒的链路波动，两跳重试足够；真正的代理故障是分钟级以上的，多试也没用，而每多一档都要乘上批量启动的环境数。间隔递增而非固定，是为了让第二跳落在一个和第一跳明显不同的时间点上，避免两次都撞在同一个波谷里。

**上限通过环境变量可调，默认 2，设为 0 即逐字退回今天的行为**——本仓惯例的秒级回滚旋钮（对照冷启动爬坡那一个）。

### 决策四：冷待机唤醒不接重排通道，只修缓存作废

唤醒那条路已经有自己的退避重试（1 / 2 / 5 分钟，且失败后一定把待机定时器还回去）。再叠一层重排，两套重试会互相触发，节奏无法推理。

所以唤醒路径只做一处改动：**退避重试到点、真正重探之前，先作废该环境的旧结论**。改完之后 60s 那一跳才是一次真的探测。这一处同时覆盖了「排队已满」触发的退避重试——对那个场景多探一次无害。

### 决策五：重排计数的生命周期

计数挂在环境句柄上，随环境的生命周期代次作废（暂停 / 移出 / 停止会换代次，旧代次的重排回调一律作废，不会把一个已被叫停的环境重新拉起来）。另外两个清零点：预检成功，以及用户手动点击启动——后者是人的显式重试意图，不该继承机器上一轮用掉的预算。

### 决策六：三态文案必须可区分

- 重排等待中（预算未尽）：代理不通 + 已重排第 N 次 → 既非「启动中」，也非失败。
- 预算耗尽终结：写明**重试预算耗尽**。
- 不可恢复终结：写明具体配置原因。

第二态与第三态必须用不同措辞。压成一句「代理不可用」，运营就无法区分「试了三次都不通，可能是网络在抖」和「密码配错了，再试也没用」——而这两者的下一步动作完全不同。

## Risks / Trade-offs

- **批量启动时整体网络中断 → N 个环境各重排 2 次** → 探测总量变成 3N，分散在 2.5 分钟内，且错峰串行链本身有间隔；每次重排还会各打一次 AdsPower 本地查询接口。缓解：上限固定为 2 且可一键设 0；本地查询接口的调用量仍在既有错峰约束内。
- **一个环境的重排占着并发计数闸的名额** → 在它重排等待期间，其它环境可用的入场额度少一个。缓解：重排是延迟重入，等待期间**不持有**排队名额（当前启动流出栈时已归还），只在真正重新入场的那一刻才重新占用。
- **重排让失败反馈变慢**（最坏从当场变成 2.5 分钟后） → 这是本变更主动接受的交换：用一点反馈延迟换掉「一次抖动 = 一次人工干预」。缓解是第六条的文案要求——等待期间界面一直说得清它在等什么、已经等了第几次。
- **认证不通过被归入不可恢复，可能误伤代理商偶发 407** → 承认这是一处有意的取舍，登记在案。若真机上观察到偶发 407，把它移入可恢复类即可，分类表是单点。

## Migration Plan

纯客户端改动，不涉及云端、协议与数据库，无迁移。随下一次桌面客户端出包生效。回滚：把重排上限环境变量设为 0，行为逐字回到今天（确定失败立即终结）；缓存作废那一处是纯增益，不随开关回退。

## Open Questions

- 重排等待期间是否需要向云端上报一个可区分的在途状态？当前倾向不报——环境此刻既没连上云端也没占浏览器，云端侧没有据此可做的决策。留待真机观察后再定。

## Context

`unify-facebook-global-policy-across-targets`（迁移 `0110`）把 Facebook 全局策略与冷启动完成事实收成一份，做法是**放宽 + 写合并行 + 切读**，不是删维度。当前实测状态（2026-08-06）：

| 表 | 现有分行 | 主键 |
| --- | --- | --- |
| `facebook_operation_global_policy` | `all` / `dev` / `ol` 各 1 行 | `(execution_target)` |
| `facebook_group_comment_policy` | `all` / `ol` 各 1 行（dev 侧本就无行） | `(execution_target)` |
| `facebook_environment_slow_start_completion` | `all` 49 / `dev` 46 / `ol` 27 行 | `(env_key, execution_target)` |

代码侧只读 `all`（作用域常量在 api / cloud 两侧共 5 个文件被引用），dev 与 OL 的接口进程均已跑该版本。

## Goals / Non-Goals

**Goals:**

- 让「同时存在两份 Facebook 全局策略」在**库层面不可表示**，而不是靠约定只写一行。
- 删掉那条没人读、却谁都能写且写了不报错的旁路。
- 把回滚语义从「看起来还能回滚」改成一句写下来的实话。

**Non-Goals:**

- **不碰审计表。** 两张 `*_audit` 的 `execution_target`、CHECK 与唯一约束全部保留原样。
- 不改视图里 `executionTarget` 那一格的语义（它表示「通过哪个目标的接口读」，面板对它有 `['dev','ol']` 硬闸）。
- 不改任何策略数值，本 change 零生产行为变化。
- 不合并 `facebook_primary_browse_surface_policy` 等其它按 `env_key` 分行的表——它们本来就不按运行目标分行。

## Decisions

### D1. 单行怎么保证：显式单行约束，不是「约定只插一行」

删列之后两张策略表没有主键。**MUST NOT 就这么放着**——一张没有唯一性约束的配置表，插入第二行不会报错，而读路径拿到的是「某一行」，于是同一次部署里两个进程可能读到不同值，且没有任何一处报错。

采用固定值单例列：加一列 `singleton boolean NOT NULL DEFAULT true`，`PRIMARY KEY (singleton)` + `CHECK (singleton)`。取值集合只有一个元素，故第二行在库层面插不进去。

**为什么不用「删列后不加约束、靠代码只写一行」**：那正是本条链路一直在付代价的那种保证——靠人记得，不靠机器拦。

**为什么不复用 `execution_target` 只留一个合法值**：那等于把分行维度改名留下，下一个人照样能往里加值。要消除的就是这个维度本身。

### D2. 冷启动完成表主键改 `(env_key)`，先删旧行再改键

顺序不可颠倒：`(env_key)` 在删除非 `all` 行之前不成立（同一 `env_key` 在 dev 与 ol 各有一行）。

三条前置在迁移里 MUST 逐条断言、任一不成立即整条失败回滚（实测当前全为 0，但**执行时必须重测，不得引用实测快照**）：

1. `all` 未覆盖的 `env_key` 数 = 0 —— 否则删旧行会丢掉一条毕业事实，把一个已按毕业档运行的账号重新关回冷启动曲线。
2. `all` 行内 `env_key` 重复数 = 0 —— 否则改主键会失败。
3. `all` 的完成时刻晚于任一旧行的环境数 = 0 —— 这是对 `0110` 「取更早」那条规则的**事后复核**；不为 0 说明合并当时取错了方向，此时删旧行等于把证据一起删掉。

### D3. 审计表整个不动（含唯一约束不得收紧）

直觉上「revision 已是一条序列 ⇒ 唯一约束应改成只按 `new_revision`」。**实测否掉了它**：`facebook_operation_global_policy_audit` 现有 9 行只有 6 个不同 `new_revision`（1 / 2 / 3 各出现两次，dev 与 ol 各一次），收紧会在现有数据上直接失败。

而保留原约束**对新行同样成立**：新行作用域一律 `all`，`(all, N)` 的唯一性就是「每个 revision 至多一条审计」。所以不动它既不是妥协也不是欠债，是正确解。

历史行上的 `dev` / `ol` 保留为追溯字段——**这也是删主表旧行之后，「合并前两边各是什么」唯一的留存处**。

### D4. 回滚语义必须改写，并写进迁移记录

删列是收缩：此后任何按运行目标过滤的构建都起不来，**回滚代码救不了**。本 change 的退路只有一条——迁移前备份。

因此备份不是流程装饰：三张表的迁移前导出 MUST 在同一次操作里完成并留下时刻与文件位置，且 MUST 写进迁移记录。这一点与 `0110` 时的处境正好相反（那次旧行还在，代码回滚就能退），**不得照抄那次的回滚说明**。

### D5. 上线顺序：先确认全部进程已切读，再执行迁移

contract 迁移的前置是「没有任何在跑的进程还依赖被删的东西」。判据是实测两侧 `aidcp-api` 都跑着切读合并行的构建（作用域常量存在且被引用），**不是**读台账。

顺带：本 change 上线后若有人从更早的发布分支往 OL 发一次版，那个构建会因为按目标过滤而读不到策略 —— 这与 `0110` 之后 OL 接口进程「一重启即死」是同一类事故，只是原因从 schema 门换成了缺列。**发布分支必须先带上本 change**，这条要写进部署任务。

## Risks / Trade-offs

- **风险：删列后旧构建不可用，且不会优雅降级。** 缓解＝上线前实测全部进程已切读（D5）+ 发布分支准入 + 迁移前备份（D4）。这是收缩段的固有代价，不是可以设计掉的。
- **风险：三条数据前置在执行时不再成立。** 缓解＝写进迁移本体逐条断言、任一不成立整条回滚，而不是靠执行前人工看一眼。
- **权衡：加一列 `singleton` 换掉分行列，列数没少。** 接受——目的不是少一列，是把「至多一份」从约定变成库层面不可表示。
- **权衡：审计表留着 `dev` / `ol`，看起来与「去掉分行维度」不一致。** 接受且刻意：审计是历史事实，改写历史比留一个不参与分行的追溯字段糟得多；且实测证明收紧唯一约束会当场失败。
- **已知不在本 change 内**：策略表当前 revision 序列是从合并行继承来的，本 change 不动 revision 语义；两侧并发写仍靠 CAS 拦，与本 change 无关。

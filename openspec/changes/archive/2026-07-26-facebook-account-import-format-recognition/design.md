## Context

Facebook 单建和批量建环境共用主进程 `parseFacebookAccountImport`，渲染层只把一次性文本交给主进程，主进程在任何 AdsPower `user/create` 前完成整批解析。当前代码根据最先出现的 `----` 或 `|` 直接选择一个位置固定的解析函数，只支持 `email----password----2FA----cookie` 与 `uid|password|cookie|access_token|email|timestamp`。新的实际输入为 `uid|password|2FA|email|cookie|access_token`；若继续按分隔符直接选旧规则，会把 2FA 当 Cookie、把 Cookie 当邮箱。

密码没有可依赖的通用正则，Cookie 值还可能包含记录分隔符，因此本设计不能通过任意字段全排列或简单 `split` 猜测账号资料。账号凭据继续只在创建链路内存中短暂存在，错误、日志和回执不得包含原文。

## Goals / Non-Goals

**Goals:**

- 让每行输入经过一组可扩展、独立测试的格式规则，并自动选择唯一合法候选。
- 在不破坏现有两种格式的前提下支持 `uid|password|2FA|email|cookie|access_token`。
- 复用 Cookie 规范化、必需字段校验与 UID/`c_user` 一致性校验，失败时保持整批零创建。
- 让未来增加新供应方字段布局时只新增规则和测试，不复制 AdsPower 创建逻辑。

**Non-Goals:**

- 不宣称可识别任意未知格式，不用概率评分或模型推断密码字段。
- 不验证 Access Token、邮箱、密码或 2FA 的在线有效性，不调用 Facebook API。
- 不保存 UID、Access Token、时间戳或原始导入文本，不增加凭据预览或历史记录。
- 不改变代理分配、指纹、慢启动、串行创建、部分成功回执或 AdsPower API。

## Decisions

### 1. 以候选规则注册表替代单一分隔符分派

每个规则接收完整行并返回“不匹配”“合法候选”或“结构匹配但字段非法”。第一版注册三条规则：既有四字段 `----`、既有六字段竖线、新的 UID/密码/2FA/邮箱/Cookie/Token 竖线格式。解析入口运行所有适用规则；恰好一个候选通过才接受，零个或多个候选均按行号安全拒绝。

选择确定性规则而不是“给每个字段打分并取最高分”，因为错误账号绑定的代价高于少接受一种输入。规则数组为后续兼容提供单点扩展，但每种新布局仍必须有明确边界和测试。

### 2. 规则负责边界，公共构造器负责语义校验

规则只提取 `username`、`password`、可选 `fakey`、`rawCookie`、可选 `expectedUserId` 以及需要丢弃的边界字段。公共校验统一确认邮箱基本形态、密码非空、2FA 为 Base32 密钥、Cookie 可规范化且含 `c_user`/`xs`，并在存在 UID 时校验其为数字且等于 Cookie `c_user`。

Access Token 和时间戳只帮助特定规则确定边界，规则返回对象不包含这些值。原有四字段格式继续兼容既有 2FA 行为，不对历史输入新增破坏性限制；严格的 2FA 特征用于新规则与其他竖线规则消歧。

### 3. 从规则两端定位可变 Cookie 区段

既有竖线格式继续从左侧取 UID/密码、从右侧取 Token/邮箱/时间，中间重组为 Cookie。新竖线格式从左侧取 UID/密码/2FA/邮箱、从右侧取 Token，中间重组为 Cookie。这样 Cookie 值含 `|` 时仍保持完整，也不会把 Access Token 当 2FA。

不增加对冒号或分号等高冲突分隔符的通用切分；这些字符常见于密码、Cookie 名值和时间。未来格式若使用它们，必须以明确的转义或外层结构规则接入。

### 4. 保持主进程权威、整批预校验和脱敏错误

识别只在主进程共用入口实现，渲染层不复制正则。单建和批量自动获得相同行为。任一行未知、歧义、字段缺失或身份不一致时，错误仅包含行号和安全原因，返回空创建计划；原始凭据不进入日志、设置或 UI 回执。

导入区文案列出当前直接支持的三种布局，并说明会自动识别、Token 不导入。文案不承诺“任意格式”。

## Risks / Trade-offs

- [密码或 Cookie 含未转义的外层分隔符] → 已知竖线规则从两端定位 Cookie；密码、邮箱或 Token 内含未转义 `|` 仍明确拒绝。
- [两条规则都能构造候选] → 必须唯一匹配，否则失败关闭并提示行号，不按规则顺序静默选取。
- [过严的字段正则拒绝少数合法输入] → 既有四字段保持兼容；新增布局使用保守特征，后续根据真实样本以新规则扩展。
- [错误信息泄露凭据] → 测试断言错误只含行号/字段原因，不包含邮箱、密码、2FA、Cookie、UID 或 Token 原文。

## Migration Plan

1. 在 Edge 工作树先补解析器测试，再实现规则注册表和第三种布局，更新 UI 说明。
2. 运行聚焦 Electron 测试、完整测试与 typecheck；OpenSpec strict validation 通过后集成默认分支。
3. 这是桌面源代码行为更新，不涉及数据库或配置迁移，也不按本任务打包安装器。

回滚只需回退 Edge 和 OpenSpec 提交；没有持久化数据需要修复。

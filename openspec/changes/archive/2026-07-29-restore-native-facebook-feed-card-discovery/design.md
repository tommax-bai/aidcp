## Context

Native 引擎的注入脚本按文件名顺序拼成**同一个函数体**（`00-shared.js` → `05` → `08` → `10` → `20` → …）。找卡的唯一入口是 `00-shared.js:277-280` 的 `topArticles()`：

```js
const topArticles=()=>{
  const nodes=all('[role="article"],article').filter(visible);
  return nodes.filter((node)=>!node.parentElement||!node.parentElement.closest('[role="article"],article'));
};
```

它有 9 处消费方：点赞精确定位（`10-feed-like.js:39`）、卡片上报与列表态（`20-feed.js:23/43`）、物理卡计数（`20-feed.js:228`）、Reels 序号（`30-reels.js:23`）、诊断与首帖候选（`90-dispatch.js:39/190`）、首帖定位（`00-shared.js:469`）。

退役 TS 的对应入口 `fbFeedTopCards`（`src/facebook/post-identity.ts:135-150`）是三路合并。2026-07-29 真机实测（Xu Nu 越南语首页）证实：该版式上语义路恒零，回落路可得 5 张真卡。

## Goals / Non-Goals

**Goals:**

- 让 `topArticles()` 在没有语义化 Feed 结构的版式上也能找到卡。
- 让「有物理卡」的判定以水合证据为准，空壳不再冒充。
- 已有语义化版式行为逐位不变。
- 只改注入脚本，不动 Rust、协议、cloud。

**Non-Goals:**

- 不搬视频路（②）。见 proposal「非目标」：其准入依赖 `08-reaction-semantics.js` 的控件语义，跨文件取用引入隐式加载顺序耦合；实测该页面收益 ≤1 张卡。
- 不做时间戳诱饵链接的悬停取值（新能力，另起 change）。
- 不改 `closestArticle()` / `targetScopeRoot()` 等以 `role="article"` 为语义边界的定位辅助——它们服务的是「从某个元素回溯到卡」，不是「发现卡」，语义不同。
- 不调任何超时、轮次、阈值。

## Decisions

### D1：合并而非替换，语义路优先

`topArticles()` 返回「语义路 ∪ 回落路」，按包含关系去重（外层胜），按文档顺序排序。

- **为什么不替换**：语义化版式今天工作正常，替换等于拿一个已验证的路径去赌一个新路径。合并让新版式得救、旧版式零回归。
- **为什么外层胜**：分享 / 引用帖会让内层也命中正文标记；只保留最外层，避免一帖两卡与跨卡误归因（退役实现同判据）。
- **备选（已否决）**：只在语义路为空时才启用回落路。否决理由——真机上出现过「背景 feed 有语义卡 + 前景 permalink 卡无语义结构」的混合态，退役实现正是为此做的是合并而非二选一（`post-identity.ts:141-145`）。二选一会在混合态下漏掉一半。

### D2：回落路的边界判据逐条照抄退役实现

种子 = 帖子正文标记；从种子向上走，遇到「自身之外、且内部含作者链接」的祖先即停，该祖先为卡边界；走到 body / documentElement 仍未命中则**不成卡**。种子若已在 `div[role="feed"]` 内则跳过（交语义路）。

- **为什么不自己设计**：这条判据在退役实现里经过真机探针钉死，且本次实测在同一页面上直接复现出 5 张正确的卡（作者、正文都对得上）。重新设计等于把已验证的东西再赌一次。
- **红线**：找不到作者证据就不成卡。绝不回落到 body / `[role="main"]` —— 那会把整页当成一张卡，是典型的静默假成功。

### D3：水合过滤只作用于「物理卡计数」，不作用于「卡发现」

`articleCount` 改为只数含作者链接或正文标记的卡；`topArticles()` 本身不加水合过滤。

- **为什么分开**：发现阶段宁可宽——未水合的壳后续轮次可能水合，过早丢弃会让虚拟化列表少扫一批。计数阶段必须严——它是「present-but-unreportable ⇒ 授权切 Reels」的准入证据，宽了就是拿空壳换一次面别切换。
- **与既有 change 的关系**：`restore-native-facebook-feed-scroll-continuation` 的兜底阶梯读的正是这个计数。本 change 让它的依据从「有 2 个空壳」变成「确有 N 张水合卡但读不出身份」——结论可能不变，但依据从假变真。

### D4：验证以真机注入为准，不以桩为准

本机有一个已登录该账号的 AdsPower 浏览器在跑。改后的发现逻辑直接注入实页，与本次基线（语义路 0 / 回落路 5）逐条比对。

- **理由**：这套逻辑的全部风险都在「真实 DOM 长什么样」，桩只能验证我对 DOM 的假设、验证不了假设本身。真机比对是这里唯一有意义的证据。
- 注入脚本没有 JS 层单测夹具；Rust 侧单测覆盖不到注入脚本内部。因此本 change 的验收以真机比对 + 既有 Rust/TS 全量回归不破为准，并把跨版式复核登记真机 backlog。

## Risks / Trade-offs

- **[回落路在别的版式上误抓容器]** → 判据要求祖先内含作者链接，且只保留最外层、跳过语义 feed 内的种子。真机比对时须逐张核对卡边界高度与作者名是否一一对应，不能只看数量对。
- **[候选集变大导致点赞定位歧义]** → 消费方都按 permalink 精确匹配 + 要求唯一命中；合并去重保证同帖不重复。真机须复核：同一 permalink 不会同时命中语义卡与回落卡。
- **[水合过滤把「真有卡但作者链接尚未渲染」误判成零]** → 判据是「作者链接**或**正文标记」，两者取或，且 settle 会等满预算再判（`restore-native-facebook-feed-scroll-continuation` 已落）。
- **[只做 2/3 条路，覆盖仍不完整]** → 已在 proposal / tasks 显式登记视频路为后续，并写明实测收益与推迟理由，不留「以为做完了」的错觉。
- **[改完仍读不到首页]** → 本 change 只解决「找不到卡」。冷启动、零指针事件复测：4 张水合卡**可上报 0 张**——该版式上所有时间戳 href 都是诱饵。**预期收益是「发现 0 → 5 张真卡、物理卡证据由假转真」，可上报卡仍为 0。** 验收按这个口径对，别指望首页当场可读。
- **[首轮测量被自身干扰污染]** → 首轮得到「2 张可上报」，实为调查中我自己悬停过那 2 张所致。教训写进 tasks 的验证步骤：**任何取值测量必须在重载后、用纯程序化滚动（不产生指针事件）复测**，否则调查动作会把结论做成自己想要的样子。

## Migration Plan

1. 改注入脚本 → `cargo test` + `npm run typecheck` + `npm run test:acceptance` + `npm test` 全过。
2. 把改后的发现逻辑注入本机在跑的 Xu Nu 实页，与基线比对：语义路仍 0；合并后卡数 ≥5；每张卡有作者与正文；带可接受 permalink 的 ≥2；同一 permalink 不重复。
3. 合入 master。本 change 改的是被编入 Rust 二进制的注入脚本，**必须重新编译边缘产物才生效**，仅 push 不改变运营机行为。
4. 回滚：纯脚本改动、无 schema / 无协议变更，回退提交并重打包即可。

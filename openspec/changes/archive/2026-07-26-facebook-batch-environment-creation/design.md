## Context

Electron 客户端的新建环境链路已经具备三块可复用能力：渲染层收集平台/模板/代理；主进程逐次签发客户归属创建意图并串行调用 AdsPower `user/create`；Facebook 账号资料解析器把每行 `email----password----2FA----cookie` 转成一次性 `accountImport`。现有 Facebook 多行输入会创建多个环境，但仍把一个手选模板和一条代理复用于所有账号，也没有显式批量模式。

该链路同时受以下约束：主进程创建单飞、AdsPower 本地 API 串行限速、整机模板必须通过 OS/UA/字体/renderer 一致性护栏、账号和代理凭据不得持久化或进入回执/日志、已成功创建的环境不得为了模拟事务而自动批量删除。

## Goals / Non-Goals

**Goals:**

- 为 Facebook 提供清晰的单个/批量新建模式，其他平台保持单建。
- 在发出第一条写请求前完成整批账号、代理、模板池和剩余账号容量校验。
- 为每个账号独立随机选择一套现有整机模板，并按稳定轮询规则分配代理。
- 复用现有创建意图、预置分组、AdsPower 写客户端、归属确认和花名册加入链路。
- 对中途失败、部分成功和归属未确认给出不泄密的真实回执。

**Non-Goals:**

- 不新增云端批量创建 API、数据库表或本地凭据台账。
- 不并行调用 AdsPower，不追求批量创建吞吐量。
- 不自动启动新环境，不自动登录后验证账号状态。
- 不为失败批次自动删除已经创建的环境，也不提供批量删除。
- 不打包或发布 Electron 安装器；该动作需另行明确要求。

## Decisions

### 1. 批量模式作为显式 IPC 意图，而非从换行数隐式推断

渲染层仅在平台为 Facebook 时展示创建方式，批量调用显式携带 `creationMode: 'batch'`、`facebookAccountImport`、`batchProxyType` 和 `facebookProxyBatch`。主进程再次校验 `platform === 'facebook'`，从而避免仅靠隐藏 UI 做权限边界。单建继续携带一个模板和现有结构化代理。

选择显式模式是因为“一行账号资料”既可能是带导入资料的单建，也可能是只有一个条目的批量；按换行数推断会让模板可选性和回执语义不稳定。

### 2. 多行代理先解析为统一结构，再生成完整创建计划

批量代理每行接受 `host:port` 或 `host:port:username:password`；同时兼容与账号输入一致的 `host----port----username----password` 分隔形式。代理类型 `http`/`https`/`socks5` 只选一次并注入每一行，密码包含额外冒号时归入密码尾部。选择 `no_proxy` 时代理列表必须为空；选择实际类型时至少一条代理，所有行复用既有代理归一层校验。

主进程的纯函数一次性产出 `[{ accountImport, templateKey, proxy }]`。第 `i` 个账号使用 `proxies[i % proxies.length]`；因此每一轮先覆盖全部代理，再从第一条开始下一轮。解析错误只返回安全的行号和字段原因，不带原始行。

备选方案是把多行原文逐次交给现有创建流边建边验；这会在后面的坏行出现前已产生环境，无法满足整批预校验，故不采用。

### 3. 随机单位是现有整机模板 key

批量模式隐藏并忽略渲染层模板值。主进程从 `adsFingerprint.DEVICE_TEMPLATES` 的 key 列表为每个账号独立抽取一个 key，再由现有 `buildFingerprintConfig` 做完整护栏校验。实现接受可注入随机函数以便单元测试固定抽样边界。

不随机拼装模板字段，因为那会破坏 OS/UA/字体/renderer 一致性；也不做简单顺序轮换，因为需求明确要求随机分配。

### 4. 顺序执行并保留部分成功真相

完整计划通过校验且不超过剩余账号容量后，主进程沿用单飞锁，逐项执行“创建意图 → `user/create` → 云端归属确认/花名册回读”。任何一项失败即停止后续项，返回失败行号、已创建安全摘要与 `createdCount`；渲染层刷新环境列表，但保留输入以便运营修正/核对。全部成功才清空一次性账号与代理文本。

不做补偿删除，因为既有规范禁止自动/批量删除，且 AdsPower 创建成功后是否已经产生可用登录态不可用事务回滚表达。

## Risks / Trade-offs

- [同一代理用于多账号可能带来平台关联风险] → UI 明示轮询规则和重复使用事实，不把“分配成功”表述为“风控安全”。
- [随机抽样可能连续命中同一模板] → 独立随机允许重复，测试只证明每项来自合法模板池；不伪装成均匀分布。
- [批次较大时创建耗时较长] → 继续串行遵守 AdsPower 限速，并在按钮在途时禁用；不以并发换速度。
- [中途失败会留下部分环境] → 返回真实已建数量/摘要并刷新列表，保留输入；不自动删除或假称整批失败无副作用。
- [凭据从渲染层进入 IPC] → 只保存在表单和本次内存调用中，成功后清空；错误、日志和回执只携带行号/计数，不携带原文。

## Migration Plan

1. 先加入纯解析/计划模块及单元测试，再接入主进程批量分支。
2. 更新 Facebook 新建表单和渲染层回执，保留现有单建默认路径。
3. 运行聚焦 Electron 测试、完整测试和 typecheck，并严格校验 OpenSpec。
4. 集成到 `aidcp-edge/master` 后推送源码；不自动构建安装器。

回滚只需回退该源码提交；无数据库、设置格式或持久化数据迁移。

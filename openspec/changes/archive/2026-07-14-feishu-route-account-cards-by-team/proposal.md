## Why

按团队分发飞书通知的机制在 `feishu-per-team-notification-routing` 已建齐（账号 → `group_label` → `group_route.chat_id`，未命中回落默认群 + config-gap 日志），但**只接了一个调用点**：通知巡视产出的账号入站「评论 / @」消息。其余全部飞书出口仍调用无账号参数的默认群解析——**从不读团队路由表**。

后果是运营侧的真实困惑（2026-07-14 dev 实测）：账号「工程师大白」的 `group_label=tom`、后台已把 `tom` 绑到「Tom.A」群，但它的排期发帖 / 排期评论结果卡仍然只落默认群「AI运营」。这些卡的正文里明明渲染了「账号：工程师大白」，闭包里 `accountId` 也现成——却结构性地不可能路由到该账号的团队群。后台页面主标题写着「按团队分发飞书通知」，运营按字面理解去配是合理的，实现范围却只覆盖一类通知：**产品表达与实际行为不一致**。

## What Changes

- **账号维度的业务结果卡改走账号路由**：凡是卡片承载 `accountId`（且语义为「该账号的运营结果」）的飞书卡，SHALL 经账号级解析投递到其团队群；未绑定 / 读失败仍回落默认群、绝不静默丢。涉及 6 个出口（均在 `aidcp-cloud/src/server.ts`）：
  - 排期评论 / 排期联系评论 **免审通知卡**
  - 评论**终态结果卡**（含自动排期与人工 `/comment`）
  - **排期发帖结果卡**
  - **排期评论触发回执**
  - **排期联系评论触发回执**
  - **参照创作结果卡**
- **审批卡与运维告警维持默认（管理）群不变**：评论人审卡、发布审批卡、离线 / CDP 不健康 / 熔断 / 验证码 / 边缘握手 config-error 告警——客户外部群不该让客户点授权、也不该看内部运维流量。这条边界不动。
- **收口一处统一 helper**：云端新增 `resolveAccountChatId(accountId)`，把账号存储 / 路由存储 / 默认群存储 / `FEISHU_CHAT_ID` 的注入内聚一处。逐处手工注入时**漏传路由存储 = 静默回落默认群**，正是本 bug 的同类失败模式，用一处注入结构性消除。
- **不做但记录的已知边界**（留后续 change）：`comm/handler.ts` 与 `publish-agent/roles/publish-executor.ts` 各自内联了默认群解析链、绕过统一解析器；console 通知路由页缺「哪些通知类型走此路由」的可视化。

## Capabilities

### New Capabilities
（无）

### Modified Capabilities
- `feishu-notification-routing`: 「账号入站平台通知按账号路由，面向运营方的卡片 / 告警不按账号路由」这条要求的**分界线右移**——账号维度的业务结果卡从「面向运营方、留默认群」重新归类为「账号作用域、按团队路由」；审批卡与运维 / 配置 / 验证码告警仍留默认（管理）群。新增一条要求约束账号级解析的**统一注入**（禁止逐处手工注入导致漏传路由存储）。

## Impact

- `aidcp-cloud/src/server.ts`：新增 `resolveAccountChatId` helper；6 处卡片出口从默认群解析切到账号级解析。
- 无 schema / 协议 / 角色 / 风控改动；无 console 改动；无边缘改动。
- **行为影响面**：`group_route` 表为空时行为逐字不变（解析器空表等价默认群）。dev 现有 3 条映射（`tom` / `ninghao` / `YY`）会立即生效——`tom` 与 `YY` 的账号业务卡将从「AI运营」群改投各自团队群；`ninghao` 已映射到默认群本身，无可观察变化。
- **风险**：团队群若为客户外部群，这些卡的正文（失败原因、素材判定、评论预览）将对客户可见。已由用户确认接受该范围；审批与运维流量仍不外流。

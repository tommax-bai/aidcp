## Context

`feishu-per-team-notification-routing`（2026-07-08 归档）把「账号 → 团队 → 群」的解析器、`group_route` 表、面板 API 与 console 配置页全部建齐，但**出站只接了一个调用点**。当时的显式设计边界写在代码注释里：「其余审批卡 / 运维告警仍走默认群（面向运营方）」——顾虑是团队群可能是客户外部群，不该让客户点审批、看运维。

这个边界画得过宽：它把「排期发帖结果」「排期评论结果」这类**账号自己的运营结果**一并归入了「面向运营方的命令回执」，于是这些卡即使闭包里有 `accountId`、卡片正文也渲染了账号名，仍然硬绑默认群。运营在后台配了团队路由却发现不生效，且**无法从现象上区分「配错了」和「压根没接线」**——因为解析器根本没被调用，那条 config-gap 告警永远不会打。

现状（`aidcp-cloud` master）：
- 账号级解析器 `resolveChatIdForAccount`（`src/feishu/chat-target.ts:47`）：账号 → `group_label` → `group_route` → 命中即用；每层读各自 try/catch、失败向下穿透；未命中打 config-gap 日志后落默认群。**全仓仅 1 处调用**（`src/server.ts:2053`，通知巡视）。
- 默认群解析器 `resolveDefaultChatId`（`chat-target.ts:18`）：只查 `bot_chats.is_default` → `FEISHU_CHAT_ID` → 空串，**无账号参数**。`src/server.ts` 内 11 处调用。
- 另有两条**内联的**默认群解析链绕过上述两个解析器：`src/comm/handler.ts`（边缘发起的发布人审卡）、`src/publish-agent/roles/publish-executor.ts`（发布审批卡）。二者都是审批类、本次不动。

## Goals / Non-Goals

**Goals**
- 账号维度的业务结果卡（6 处）按账号路由到团队群；未绑定 / 依赖缺失一律回落默认群，绝不静默丢。
- 消除「逐处手工注入依赖」这一静默失败源：统一一处 helper。
- `group_route` 为空时行为逐字不变（零回归）。

**Non-Goals**
- 不动审批卡与运维告警的目标（仍默认群）。
- 不收口 `comm/handler.ts` / `publish-executor.ts` 的内联默认群链（审批类，边界不变；留作后续 change）。
- 不改 console（「哪些通知类型走此路由」的可视化留后续）。
- 不改 schema、协议、角色注册、风控。

## Decisions

### 决策一：以「卡片是否承载 accountId 且语义为账号运营结果」划线，而非以「自动 / 人工触发」划线

**取**：6 处出口一律按账号路由，含人工 `/comment` 的终态结果卡。

**舍**：曾考虑按触发来源分流——自动排期走团队群、人工 `/comment` 回执留管理群（「谁问谁得答案」）。放弃原因：
1. 评论终态结果卡的 `source` 参数并非在所有调用路径上都填（Facebook 加群 / 评论链的几处不传 `source`），按它分流会产生一张**语义不确定**的分流表；
2. 人工 `/comment` 的结果同样是该账号的运营结果，团队看到它是合理的；命令的**受理回执**与**审批卡**仍在管理群，操作员的命令闭环不断；
3. 真正「谁问谁得答案」的正解是把发起群 `chatId` 一路透传到结果卡——那是更大的改动（命令路由 → 评论调度器 → 结果卡），本次不做，留作后续。

**代价（已知、可接受）**：运营在管理群下 `/comment <账号>` 后，终态结果卡会出现在该账号的团队群而非管理群。若后续证明碍事，回退面只有一处（该出口改回默认群解析）。

### 决策二：统一 helper 而非逐处复制依赖注入

新增 `resolveAccountChatId(accountId?: string): Promise<string>`，内聚 `accountStore` / `groupRouteStore` / `botChatStore` / `FEISHU_CHAT_ID` / `logger`。

理由不是「少写几行」，而是**堵一类静默失败**：逐处手工注入时，漏传 `groupRouteStore` 会让解析器合法地判定「无团队路由」→ 回落默认群 → 投递成功、无异常、无 config-gap 日志。这与「未接线」在现象上完全不可区分，正是本次 bug 的同类。统一注入让「漏传依赖」在类型层面不可表达。

现有唯一调用点（通知巡视）一并切到该 helper，消除两套注入写法并存。

### 决策三：保持解析器本身不动

解析器的容错语义（逐层 try/catch、失败向下穿透、绝不抛入投递闭包、未命中打 config-gap）已满足红线，本次**不改 `chat-target.ts` 一行**。改动面收敛在 `server.ts` 的调用侧，回退成本 = 6 处 revert。

## Risks / Trade-offs

- **跨客户信息面扩大**：团队群若是客户外部群，业务结果卡正文（失败原因、素材判定、评论预览）对客户可见。用户已确认接受此范围；审批与运维流量仍不外流。缓解：解析器只做**精确相等**匹配，不模糊匹配——错映射（跨客户 PII 泄漏）在机制上被排除，配不上时安全地落默认内部群。
- **dev 现有映射会立即生效**：`tom` / `YY` 的账号业务卡将从「AI运营」群改投各自团队群（`ninghao` 映射到默认群本身，无可观察变化）。这是预期效果，但部署后运营会看到通知去向变化，需知会。
- **回退**：清空 `group_route` 表即可让全体账号回到默认群（解析器空表等价默认群）；代码回退为 6 处 revert。

# Design

## 1. 三道闸的位置与性质

规则模式今天被三处拦住，性质各不相同，不能用同一种手法处理。

**第一道，会话启动闸**（`aidcp-cloud/src/orchestrator/role-dispatcher.ts:2175`）。它用独立于人设解析器的判据看账号有没有人设行，未绑即在角色重订阅之前短路为 `needs_persona_setup`。这是纯前置拦截，与规则模式要做的事没有任何因果关系，直接开例外即可。

**第二道，模式裁决闸**（`aidcp-cloud/src/orchestrator/facebook-rule-mode.ts:29-34`）。它在慢启动优先权判完之后、规则模式准入之前再查一次人设三态。同样是纯拦截，开例外。注意顺序不能动：慢启动的绝对优先权与 fail-closed 判据必须仍在人设例外之前生效。

**第三道，评论触发口**（`aidcp-cloud/src/comment-agent/comment-scheduler.ts:439`）。这一道**不能简单开例外**，因为它下游分两条路：模板正文完全不读人设，生成式正文要调模型撰写、必须有人设。所以这一道要改成按有效正文方案分流，而不是无条件放行。

## 2. 为什么模板正文这条路是干净的

`facebook-global-group-regional-comment-templates` 已经把正文来源解析定成四种情形：账号显式生成 → 生成器；账号显式模板且模板非空 → 账号模板；账号显式模板但模板为空 → 目标群区域通用模板；**账号没有显式方案 → 默认按模板并使用区域通用模板**。

也就是说系统的默认路径本来就不调用生成器。代码里模板分支直接取模板文本（`aidcp-cloud/src/comment-agent/comment-scheduler.ts:859-874,1004`），不经过撰写角色，也不经过人设口吻改写；只有显式生成方案才走 `CommentComposer`，而它以 `getSoul(accountId)` 为输入（`:1285`）。

所以规则模式免人设的完整条件就一句话：**有效正文方案必须是模板**。这不是新造机制，是把已有的默认路径设成规则模式的硬约束。

## 3. 生成方案账号怎么处理

不静默改写方案，也不静默跳过。规则批次在调用评论编排之前先解析一次有效正文方案：

- 方案为模板（含未显式选择的默认）→ 评论段照常执行。
- 方案为显式生成 → 该批次评论段以具名原因收敛为不可执行，浏览与点赞照常，批次如实呈现为部分完成。

之所以不回落成模板：显式生成是运营的明确选择，`facebook-global-group-regional-comment-templates` 已经写明「显式 `generated` MUST NOT 被区域模板覆盖」。规则模式没有理由推翻它。

之所以不整批阻断：浏览与点赞本来就不需要人设也不需要正文，因它们无关的评论配置停掉是过度收紧。

## 4. 例外的边界必须写死

这是对一条安全不变量开口子，所以边界要逐条钉死，避免日后被当成通用豁免引用：

- 例外**只在** Facebook、**只在**该环境已启用规则模式、**只在**规则批次自身的浏览/点赞/加群/模板评论四个动作上成立。
- 普通浏览、发布、飞书手工评论、排期评论、mandatory 评论的人设闸逐字不变；同一账号若被这些路径触发，仍以 `no_persona` 诚实拒绝。
- 系统仍不存在默认或兜底人设。例外的含义是「这条路不需要人设」，不是「缺人设时用一份替代的」。人设解析器的行为一个字不改。
- 风控、配额、去重、目标复核、平台确认、正文安全校验、审批策略与真实终态记录全部照旧。

## 5. 呈现口径

未绑人设的规则模式账号会同时满足「没有人设行」和「正在正常运行」，今天的界面没有这种态。必须新增一种如实说法：按规则运行、未绑人设。既不能沿用待补人设的引导（会让运营去做无用功，也会误导成没跑起来），也不能伪装成已绑。

## 6. 交付顺序

1. 会话启动闸与模式裁决闸的规则模式旁路（两处纯拦截，可同批）。
2. 规则批次评论段的正文方案预解析与不可执行终态。
3. 评论触发口按来源与方案分流放行。
4. Console 与 Edge 的呈现口径。
5. 回归：普通浏览、发布与其它评论来源的人设闸逐条未变。

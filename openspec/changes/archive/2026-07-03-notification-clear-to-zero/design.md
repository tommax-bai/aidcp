## Context

通知巡视当前由两件事共同决定行为：边缘「边沿触发」（未读「无→有」翻转才上报一次，`epoch` 此时 +1）+ 云端分诊「看一眼、标记已处理、≤N 轮、不回头」。这套是「奔着收尾去」：每类点一下就算处理过。问题在于它**不保证把平台未读真清零**（赞/关注只看一眼、评论固定滚 3 屏、被判不值得通知的评论仍占未读），而边沿触发又只认「无→有」——于是只要某趟没清零，未读永久为真、再无翻转、边缘不再上报，机器人对后续通知装聋。

真机探针（`aidcp-edge/scripts/notification-clear-probe.ts`）已坐实「看一眼某分类能让平台服务端把该类未读清零」（赞收藏/新增关注探针验证、评论/@ 人工确认，重载后服务端三栏与入口红点均归零，生产 tab 选择器命中）。本设计据此把巡视从「奔着收尾」改为「奔着清零」。

约束：沿用现有 `notification.*` / `browse_notification_*` 协议通道，不新增消息类型；安全红线不变（诚实失败不静默假成功、风控/发布闸不漂移）；边缘只执行不决策。

## Goals / Non-Goals

**Goals:**
- 巡视把通知首页三栏未读**真扫到零**（赞/关注看一眼即清、评论/@ 滚到底覆盖到清零）。
- 「真有新消息就处理」：去掉「已处理过（epoch）」准入闸，按未读「无→有」翻转再触发。
- 循环有界 + 诚实放弃：清不掉就记日志停手，不空转、不假成功。
- 明确区分并保留「飞书通知去重」（`notifiedItemKeys`），只删「巡视触发去重」。

**Non-Goals:**
- 不改 cloud↔edge 协议消息集；不引入指纹/多浏览器。
- 不为赞/关注发飞书（仍只评论/@ 通知）。
- 不改硬暂停（验证码/人工接管）与风控状态机。
- 不默认改边缘触发模型为「计数增量触发」（仅作某栏被证实不可清时的兜底，见 Decisions）。

## Decisions

**D1 — 分诊「循环到零」取代「≤N 轮标记已处理」。** 每处理完一类**重读**三栏计数，任一 > 0 就继续，直到全 0 或达上限。理由：清零是巡视的真实目标，也是边沿触发下一次「无→有」的前提；旧的「标记已处理不回头」是为了**保证终止**，但代价是「一眼没清干净就遗留未读」。终止性改由「最大尝试上限」保证（见 D4）。
- 备选：保留 ≤N 轮但 N 调大 —— 仍是「次数兜底」而非「清零兜底」，治标不治本，弃。

**D2 — 保留边沿触发（无→有），不默认改计数增量触发。** 理由：探针证明清零可靠，则「清零→下一次无→有」即天然且正确的再触发节律，无需在边缘维护「上次处理到第几条」的水位（那正是用户不想要的「已处理过」同类物）。把「按计数增量触发」留作**仅某栏将来被证实不可清**时的兜底（该栏退化方案），默认优先清零。
- 备选：改计数增量触发 —— 重新引入 per-栏 watermark、复杂且与「真有新消息就处理」的简洁性相悖，非默认。

**D3 — 去掉准入第三道闸（epoch「已处理过」/`lastHandledEpoch`），保留前两道（硬暂停、正在处理中）。** 理由：一旦清零可靠，epoch 水位只剩「防同一波重放」的 belt-and-suspenders；而「真有新消息就处理」要求不能因处理过而拒绝新波。**「正在处理中」闸（`excursionActive`）必须保留**——它承担「巡视途中又来新一波（更大 epoch）时不开并发第二趟」，这是 epoch 水位拦不住的窗口；新波由正在跑的清零循环重读计数时自然吸收。
- 备选：保留 epoch 水位 —— 与「有新消息就处理」冲突、且清零后已无重放风险，删。

**D4 — 终止性 = 最大尝试上限 + 诚实放弃。** 循环每趟设上限；到顶仍有栏未清 → 记原因停手，不空转、不假报已清。理由：替代旧 ≤N 轮提供的「必然终止」安全，同时不掩盖「清不掉」这一真问题（红线：不静默假成功）。

**D5 — 飞书通知去重水位（`notifiedItemKeys`）保留，与触发去重解耦。** 理由：扫得更勤 → 同一条评论会被反复看到，必须靠 itemKey 水位防重复打扰。删的是「巡视是否触发」的去重（epoch），留的是「是否再次推飞书」的去重（itemKey）——两个维度，勿连带误删。

**D6 — 评论/@ 浏览滚到底 / 直到不再有新项或角标清零，替代固定 3 屏。** 理由：未读多于一屏时固定滚屏会遗留未清，破坏 D1 的清零前提。赞/关注「看一眼即清」已验证，保持。

## Risks / Trade-offs

- 某栏将来被证实「看一眼/滚到底也清不掉」 → 由 D4 有界放弃保证不卡死；并以 D2 的 per-栏「计数增量触发」兜底，使该栏仍能响应新增（不致永久装聋）。
- 清零循环因某栏计数抖动（>0 反复）空转 → D4 最大尝试上限硬兜底 + 诚实日志，绝不无限循环。
- 扫得更勤导致飞书重复推送 → D5 itemKey 去重水位保留（仅成功上报后推进水位）。
- 去 epoch 后出现「巡视风暴」（反复重开） → 由「正在处理中」闸（D3）+ 边沿触发「无→有」（D2）共同抑制；清零使下一次触发是真正的新一波，而非同波反复。
- 入口红点 count 与首页三栏求和口径不一致（探针实测入口 4 vs 三栏 2）→ 低优先校准两处扫描判据，确保「清零」终止信号（首页三栏=0）与「再触发」信号（入口无→有）一致归零；当前两者最终都归 0，故非阻塞。

## Migration Plan

- 部署：cloud 按既有全量 master rsync 快照部署（先备份→rsync→重启 `aidcp-cloud.service`→healthcheck），edge 本地跑连云端；部署前先 dry-run 暴露随附的 master 增量范围。无数据迁移（仅清理 `lastHandledEpoch` 字段，无表变更）。
- 回滚：还原上一份 cloud 备份 + 还原 edge 代码即可；行为退回「≤N 轮 + epoch 闸」。
- 顺序依赖：`notification-monitoring` 能力由 `notification-monitor` change 引入、尚未合并；本 change 的 spec delta 逻辑上在其归档后叠加。

## Open Questions

- 最大尝试上限取值（轮次数 / 总时长）——与现有巡视总超时兜底如何对齐。
- 评论/@「滚到底」的终止判据：以「连续 K 次无新项」还是「角标清零」为准（或两者取先到）。
- 是否需要在「滚到底仍未清零」时进一步逐条打开评论项来强制清——探针未显示需要，默认不做，留作 D2 兜底触发前的可选加强。

## Context

**取证结论（2026-08-06 实读代码，立项前完成）：**

| 事 | 结论 |
| --- | --- |
| 现成的边缘→云端浏览器真态通道能不能复用 | **不能。** 它只接受 `absent` / `ready` 两个值；诊断字段明写「不参与云端会话状态判定」；云端处理函数**第一行就是「状态没变直接返回」**。让位被拒时浏览器一直是 `ready` ⇒ 状态没变 ⇒ 整条消息连同诊断字段被丢弃 |
| 有没有别的通用遥测通道 | **没有。** 已把整张消息类型表扫过一遍，边缘→云端全部是业务语义消息，无通用诊断/遥测道 |
| 有没有非协议旁路 | **有，但不推荐。** 桌面外壳里有一个带鉴权的 HTTP 客户端可直接调云端（customer-auth 出口）。**否决理由**：那套接口两端是手工维护的双份契约、**零路径级测试、已经断过两次**；且它是**客户侧**接口，拿来送运维遥测是层次错位 |
| 决策在哪个进程做 | **Electron 外壳**（准入判据模块由外壳引入并调用） |
| 云端连接在哪个进程 | **核心子进程**。⇒ 上报必须走「外壳 → 核心 → 云端」三跳，**没有捷径** |
| 外壳→核心有没有现成通道 | **有。** 外壳用本地消息把窄生命周期意图送给核心；核心侧用**逐类具名解析器**分发（不是通配转发） |
| 协议副本有几份 | **三份**（edge / cloud / automation），跨仓对账门逐字比对。**不是文档里常写的两份** |

## Goals / Non-Goals

**Goals:**

- 宿主层的每一次让位判决对云端可见：让了 / 没让、**为什么**没让、**连续**多少次、卡了多久。
- 让「一台机器上某个环境卡了半小时」这件事**在另一处就能看出来**。
- 把「可见 ≠ 可否决」这条边界写进规格，防止下一轮有人把它接成第二道闸。

**Non-Goals:**

- **不给云端任何槽位决策权。** 不新增否决通道、不让云端参与准入。
- 不动等待门槛的权威归属（那是后一个 change）。
- 不动云端那道验证码否决（按分层判据它放对了地方）。
- 不做历史留档 / 报表。本 change 只做「当前态可读」。

## Decisions

### D1 · 新增协议消息，不复用现有通道、不走 HTTP 旁路

三个候选都实读过（见 Context）：现成通道会静默吞掉载荷；HTTP 旁路是手工双份契约、
零路径级测试且层次错位。**新增一条消息是三者中唯一不引入静默失败面的。**

代价诚实记账：三份 `protocol.ts` 逐字同步 + 文档表 + 热点文件串行。**这个代价是本 change 的主要成本。**

### D2 · 上报按**判决变化**发，不按提示节拍发

云端提示每 60 秒一跳。若每跳都回执，一个卡住的环境会产生几百条等价消息。

规则与本地日志节流**保持同一套**（首次 + 原因变化 + 此后每 N 次），理由是
**两处不一致会让「日志里有几条」和「云端收到几条」对不上，排障时反而制造矛盾证据**。

**由拒转让、由让转拒 MUST 立即发**——那是状态迁移，不受节流约束。

### D3 · 载荷是**事实**，不是判决词

字段承载：判决结果、具名原因、连续次数、首次拒绝时刻、对应提示的标识。
**MUST NOT** 出现任何形如「云端应该怎么做」的字段——那会把遥测悄悄变成协商。

**对应提示的标识是必需的**：没有它，云端无法区分「拒绝的是刚推的那条提示」与
「拒绝的是三跳之前那条、新提示还没到」。缺了它，连续拒绝次数就无法归因。

### D4 · 云端必须有真实消费方，否则本 change 等于没做

新增消息若只被接收后丢弃，就复刻了它要修的那个病（有事实、无人可见）。
**验收判据是「在另一处能看出某台机器上的环境卡住了」**，不是「消息发出去了」。

因此云端侧 MUST 落地两件：按环境/账号留存最近一次判决与连续拒绝态；面板侧可读。

### D5 · 能力位协商，且现有字段一个都不减

边缘对待机提示做**格式先验**：「是否够格让位」不是布尔、或「门槛值」小于 1 秒 ⇒
**整条提示当场判无效丢弃**。⇒ 云端侧任何字段删减都会让**所有在跑的客户端集体停止让位**。

**且不能靠版本号灰度**：客户端会被从源码重新编译装机而不抬版本号（2026-08-06 实证），
版本号认不出装的是哪份代码。**唯一安全的开关是握手能力位。**

### D6 · 只报宿主层这一层的判决，不合并核心侧的待机失败

「外壳判定不该让位」与「核心执行进入待机时失败」是两件事，前者是判决、后者是执行结果，
**且后者已有自己的本地回执通道**（`lifecycle.standby_refused`，含「浏览器是否原样未动」）。
合并会把两种不同的可恢复性压成一种——正是本仓反复付过代价的那类压缩。

本 change 只报前者；后者是否也要上报，留给需要时另立。

## Risks / Trade-offs

- **[R1] 新增协议消息 = 三份副本 + 文档 + 串行开工** → 已在 proposal 的 Impact 记账；
  立项时已核协议热点当前空闲。**开工前 MUST 重核一次**（fleet 高度活跃）。
- **[R2] 遥测被误用成闸** → 由规格条款 + 结构断言双管：云端消费方 MUST NOT 出现在任何
  下发决策路径上。**这是本 change 最需要防的失败模式**，因为它「看起来只是多读一个字段」。
- **[R3] 三跳链路任一跳静默丢失** → 外壳→核心那跳是**逐类具名解析器**、不是通配转发，
  漏加解析分支的表现是「静默不转发」。MUST 有一条端到端断言覆盖三跳，
  MUST NOT 只测外壳发出这一段。
- **[R4] 节流把关键状态迁移吃掉** → D2 已规定迁移不受节流约束；须有定向回归。
- **[R5] 云端消费方只落库不呈现** → 由 D4 的验收判据挡住：验的是「另一处能看出来」。

## Migration Plan

- **上线路径**：三仓协议同步 → 云端先上（能接收、能留存、能呈现）→ 边缘随客户端重新编译装机后开始上报。
  **顺序不可反**：边缘先发而云端不认，消息会被当未知类型丢弃。
- **能力位缺席即静默**：旧客户端不声明该能力 ⇒ 不上报，云端不期待，无任何报错。
- **回滚**：云端侧停止消费即可；协议消息保留无害（边缘发、云端忽略）。
  **MUST NOT** 靠删字段回滚（见 D5）。

## Open Questions

- **云端呈现落在哪个界面位置**（环境列表的告警位 / 环境详情 / 单独的诊断视图）——
  不阻塞协议与边缘侧开工，实装到云端呈现那一步时定；判据是 D4 的「在另一处能看出来」。

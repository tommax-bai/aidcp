## Context

`native-locating-gates` 已经把「每条写命令都必须校验其效果」这条保证的**读法**定死了：它不是运行时的整体属性，只能按逐面盘点表读；未列出的面会被读成已覆盖；一个面在被记为达标之前，这条保证不得被引用在它身上。

盘点表（`native/page-engine/command-postconditions.json`）与常驻门禁（`test/native-page-engine/command-postconditions.test.ts`）都已存在。门禁今天强制四件事：

1. 表恰好覆盖引擎命令类型里 `may_write` 为真的全部命令（键集机械相等）；
2. unread 条数 ≤ `unreadBudget`；
3. `unreadBudget` 恰等于 unread 实际条数（不留空位）；
4. below_bar 必须有 `evidence`，not_applicable 必须写明「不得因此默认成功」。

**第 2、3 条只锁住了 unread 一个方向。** below_bar 既无预算、也无处置字段，因此 unread → below_bar 是一条能让门禁变绿、而命令的实际风险一点不变的合法路径。棘轮的经典失效方式在本仓已被点名过（留空位给新违规回填）；这里是另一种：**给它开第二个出口。**

现存 3 条 below_bar 都不带「谁来消除、什么时候」，等于已经停在那个出口上。

## Goals / Non-Goals

**Goals:**

- 把 16 条 unread 逐条读完并分类，`unreadBudget` 归零。
- 给 below_bar 补上与 unread 同规格的单调预算，并要求逐条具名处置。
- 修可修的已知不达标项；不可修的（真机标定前置）转成**带具名处置的 below_bar**，而不是留在原地。
- 让盘点表从「一份状态快照」变成「一份只能向前走的账本」。

**Non-Goals:**

- **不把命令统一改走共享的 resolve–act–validate 编排。** 规格明写合规是逐条后置条件的属性，不是模块归属的属性。改走编排是逐条的实现选择。
- 不改任何命令的协议形状、回执字段或云端消费面。
- 不新增写命令、不改命令词表。
- 不做真机标定（`publish_add_with_candidate` 三支的结构信号属真机项，backlog 簇 123.34）。

## Decisions

### D1. 先读后修，读的结果不预判

16 条 unread 的第一步是**读**，不是修。规格对 unread 的定义是「没人核过」，不是「已知有问题」。读完可能有相当一部分直接落 confirmed。

**这条要写下来是因为存在一个具体的坏做法**：为了让分类看起来漂亮，把判据往松了写、或者把「读不到」记成「达标」。那会把一份可信账本变成一份说谎的账本，比 unread 更糟 —— unread 至少诚实地说了「不知道」。

**顺序**：逐条读 → 记结论与证据 → 落 below_bar 的再排修复。修复不与分类混在一次提交里，便于事后分辨「哪些是读出来的、哪些是改出来的」。

### D2. below_bar 补棘轮，形态与 unread 一致

新增 `belowBarBudget`，断言三条与 unread 完全同构：条数 ≤ 预算、预算恰等于实际条数、只许下降。

**同构是刻意的**：两个不同形态的棘轮会让人记不住哪个是哪个，也让「哪个方向被锁住了」变成需要读代码才知道的事。

### D3. below_bar 每条 MUST 带具名处置

新增必填字段：消除动作，或**具名例外**（理由 + 前置 + 谁来解）。今天的 `evidence` 只说「差在哪」，不说「怎么办、谁办」。

**没有处置的 below_bar 与 confirmed 的区别只存在于读者的记忆里** —— 而这张表存在的全部理由，就是不再依赖任何人的记忆。三条现存条目正好各是一种处置形态，可以当模板：属主待核（搜索输入）、可直接修（上传配图）、真机前置（候选项三支）。

### D4. `unreadBudget` 归零后不得再抬起

门禁今天只断言「不许上调」，但预算归零后语义更强：**新增写命令不得默认落进 unread**（表自己的不变量已经这么写了，门禁没强制）。归零后把「预算恒为 0」变成硬断言，让这条不变量从注释升级成机械约束。

### D5. 搜索输入那条先核属主，不预设归属

它此前登记的两个去处：「并入会话守卫流」——该 change 已于 2026-08-01 归档，此路已断；「另起 change」——即本 change。另一条主张是「实现点在单写区属主处」，那个属主是否仍活着**必须当场查**，不能照抄登记。

**这条单独写出来是因为本仓刚为它付过代价**：拟人化线有一条任务挂着「须与某属主对齐」，而那个属主 change 前一天已经归档 —— 单写区主张随之失效，却没人回头查，任务因此空卡了很久。

### D6. 上传配图：判据必须绑定「本次」

现判据是「该序号位置存在预览图」。上一次残留的预览同样满足 —— 这是**证据与本次动作无绑定**，与「读回自己刚写的东西」同族：都只证明了页面上有东西，没证明这次动作产生了它。

改法方向是按本次上传的标识回读；具体标识取什么由实现期实读决定，但判据必须能区分「本次产生的」与「之前就在的」，否则不算达标。

### D7. 候选项三支：标定前只能是 below_bar

提及 / 地点 / 合集三支走注入路由，判据是自证。达标形态需要各自的结构接受信号，而那要真机标定。

**在标定完成前，它们只能记为带具名处置的 below_bar** —— 不能记 confirmed（没有证据），也不能记 not_applicable（它们结构上**有**可读回的业务结果，只是还没测出信号在哪；记成 not_applicable 等于用「读不出来」冒充「本来就没有」）。

## Risks / Trade-offs

- **[改动面读完才知道]** 16 条读完之前无法穷举实现点 → 本 change 如实不预列，tasks 分成「读」与「按结果修」两段；修的那段在读完后就地展开，不预写虚假的具体任务。
- **[为了数字好看而放松判据]** 分类由同一个人做、又由同一个人定判据强度 → D1 明写禁止；每条分类必须带**可复核的证据**（指向具体判据代码），而不只是一个结论词。
- **[热点文件串行]** `engine.rs` / `facebook/auth.rs` 是并行开发点名的热点 → 本 change 期间与触碰这两个文件的流串行；开工前 `openspec list` 核对有无并行流压着。
- **[below_bar 变成新的停车场]** 补了预算但每条都写「具名例外」→ 处置字段要求写清**前置与解法**，而不只是理由；真机前置类必须指到具体 backlog 簇号，可被追踪。
- **[Facebook 登录面动不得]** 7 条 FB 登录写动作若读出来不达标，修它们要动登录链 → 登录链有独立的稳定性历史；若修复面过大，按 D3 转成带具名处置的 below_bar 并单独立项，**不在本 change 里硬做**。

## Migration Plan

无数据迁移、无协议变更。盘点表与门禁都是仓内文件，改动随 edge 主干走。表的分类结论不影响运行时行为；实现层的判据修复按各自命令面独立生效。

回滚粒度＝逐条判据修复各自可回滚；表与门禁的棘轮改动是纯约束增强，回滚只会让约束变松、不影响运行。

## Open Questions

- 16 条读完后落 below_bar 的比例未知。若比例很高（比如过半），说明这张表在建表时的 confirmed 判定标准与实读标准有系统性差异，那时应回头复核已记 confirmed 的 22 条，而不是只处理新读的这批。
- Facebook 登录面的 7 条是否应整体转给一条专门的登录链 change，取决于读的结果；本 change 不预判。

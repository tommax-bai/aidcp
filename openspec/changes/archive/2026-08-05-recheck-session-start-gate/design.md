## Context

会话启动闸活在自动化段的角色调度器里，入口有四条：边缘握手、浏览器状态转好、续场休息结束、面板显式启动。四条最终都汇到同一个带副作用的裁决方法；该方法已经拆出一份**无副作用的纯判据**（因为约 60 秒一跳的只读裁决链会调它，不能每分钟刷告警脉冲）。这两支的分工是本设计能干净落地的前提——复判必须走纯判据那一支。

拒绝结论目前有五种：平台无浏览能力、未绑人设、人设副本陈旧、配置镜像陈旧、调度开关关闭。除「调度开关关闭」是静默返回外，其余四种都会打日志并触发「会话被拒」回调，**然后 return，不留任何后续动作**。

现状的关键事实：

1. 「绑定人设后就地开跑」的方法**已经存在且实现完整**（起会话 + 补一条重驱唤醒干等的边端）。缺的只是调用它的人——单体时代由接口侧的人设写入回调触发，云端三等分后接口进程拿不到自动化段的句柄，那条线断了。
2. 自动化进程的人设事实来自一份**同步读只读副本**，由一条失效信号中继 + 2 秒兜底轮询刷新。副本追上是秒级的、且不需要任何新通道。
3. 所以「复判」不需要任何跨进程通信：**答案自己会变好，只是没人再问一遍。**

## Goals / Non-Goals

**Goals:**

- 被可恢复原因挡住的连接，在同一连接内自动恢复开跑，不需要运营重连环境。
- 消除「新账号第一次接入必然踩中人设竞态」这一必然失效。
- 复判 MUST NOT 制造告警脉冲、MUST NOT 重复触发「会话被拒」回调、MUST NOT 产生任何 I/O 或命令。
- 放行时的回执要能看出「这是复判救回来的」，而不是伪装成一次普通启动。

**Non-Goals:**

- 不做接口进程→自动化进程的跨进程叫醒通道（另立 change）。本 change 落地后它只把「≤60 秒」变成「立刻」。
- 不改人设三态语义、不改各态的用户可见文案与告警口径、不改 Facebook 规则模式豁免。
- 不改协议、不改数据库、不改边缘、不改接口进程。
- 不为「全局调度开关关闭」提供自动解除（见下方决策四）。
- 不开任何「未绑人设也以默认人设开跑」的口子。

## Decisions

### 决策一：复判驱动方式选「连接内定时退避」，不选「订阅副本变更」

**选择**：在角色调度器内部起一个每连接私有的退避计时器，到点重跑纯判据。

**为什么不选订阅副本变更（事件驱动）**：单体与派生仓两条装配路径上，人设事实源是**两个不同的对象**（单体读进程内人设存储，派生自动化读同步读副本层）。要做成事件驱动，得让这两个各自长出「变更通知」并一路注入到调度器——那是两处新接线、两份新契约，而收益只是把 ≤60 秒缩短到秒级。本仓已有明确判例：同一份判断被两处实现，行为测试原理上看不见第二份。为一个纯内存读做这套接线不划算（YAGNI）。

**为什么不选复用既有的约 60 秒只读裁决链**：那条链的存活条件是「待机提示在场」，与本问题无关；把恢复挂在一条为别的目的而活的链上，等于把两件事的生死绑一起——那条链哪天因为别的原因不起了，账号又会静默睡死。这正是档案里反复出现的失效形状。

**代价**：秒级而非毫秒级恢复。竞态窗口实测 0.1~0.8 秒，首跳 2 秒即可覆盖；运营手动补人设的场景最坏等 60 秒。可接受。

### 决策二：复判 MUST 走纯判据，只有转「可启动」那一刻才允许走带副作用的路径

带副作用的裁决方法会打日志 + 触发「会话被拒」回调。复判每跳若走它，就会变成每分钟一次告警脉冲和一次「被拒」回调——既有代码里为这件事专门拆过一次纯判据，本 change MUST NOT 把它撤回去。

因此：每跳只读纯判据；结论仍是同一个可恢复原因 → 静默排下一跳；结论变成可启动 → 才调用既有的「绑定人设后就地开跑」方法（它内部会过一次带副作用的裁决，但此时结论已是放行，不产生任何告警）。

### 决策三：退避节奏 2s → 5s → 10s → 30s → 60s → 稳定 60s；上限绑在**连接**上而非时间上

**节奏**：首跳 2 秒覆盖自动补人设的竞态（实测窗口 0.1~0.8 秒，2 秒有数量级余量）；随后拉开，最终稳定在 60 秒，与既有只读裁决链同量级。

**为什么不设时间上限**（这是本设计最需要交代的一条）：本仓红线要求自愈通道「带上限」，其立意是**不要在结构性失败上无限重试**。这里的判据不同——每跳只是一次纯内存读，无 I/O、无命令、无日志、无落库；计时器一连接一个，随连接拆除即解除，不存在无界增长。而给它加一个时间上限，会**原样重新制造本 change 要消灭的那个缺陷**：运营在上限之后才补人设，账号照样静默不动，而且这一次还带着「我们已经放弃了」的假象。

所以本设计的「上限」是**资源上限而非时间上限**：一连接一个计时器、跳与跳之间无累积状态、连接一断即消失。这一条 MUST 写进规格，免得日后被当成「忘了加上限」而补一个回来。

### 决策四：可恢复集合只收「事实会自己变好」的三条，运营意志类不纳入

- 未绑人设 → 纳入（人设可能正在被补、或运营正在客户端里设）。
- 人设副本陈旧 → 纳入（副本会自己追上）。
- 配置镜像陈旧 → 纳入（同上）。
- 平台无浏览能力 → **不纳入**。这是真结构性：该平台就是没有这个能力，重来一万次也一样。
- 全局调度开关关闭 → **不纳入**。它不是「读早了」，是运营的显式停机；且已有专门的恢复入口（面板显式启动）。纳入它等于让全局停机在任一连接上被自动解除，那是另一件事，超出本 change 的问题域。

### 决策五：武装点放在带副作用的裁决方法内部，解除点放在会话真起来与会话结束两处

**武装点**：放在裁决方法返回 false 的那几个可恢复分支里（不是放在四个调用入口里）。理由是四个入口迟早会变成五个，逐个入口武装必然漏掉新加的那个——本仓已有同形状的前科（新增命令忘了进白名单，静默丢弃）。放在唯一的裁决收口处，新入口自动获得该行为。

**解除点**：
- 会话真正激活时解除（复判的使命完成）。
- 会话结束时解除（与既有的休息计时器 / 窗口唤醒计时器同处，且 MUST 在「会话本来就不活跃就提前返回」那一行**之前**——连接拆除走的正是这条路，漏在后面就会让计时器活过连接）。

**为什么解除点必须覆盖连接拆除**：计时器若活过连接，到点会对着一条已断的连接起会话、发命令。这是比原缺陷更坏的结果，MUST 有回归用例钉住。

### 决策六：放行回执必须自证是复判救回来的

复判成功开跑时打一条独立日志，写明「此前被哪一个闸挡住、复判后放行」。若沿用普通启动日志，档案里就再也看不出竞态发生过——而这正是这次能定位到根因的唯一线索来源。

## Risks / Trade-offs

- **[计时器活过连接，对死连接起会话发命令]** → 解除点放在会话结束流程的最前段（早于「不活跃就返回」的短路），并加回归用例断言连接拆除后计时器不再触发。这是本 change 唯一可能造成**新的对外动作**的路径，优先级最高。

- **[复判与续场休息计时器同时武装，重复起会话]** → 「就地开跑」方法首行即有「已在跑则直接返回」的守卫，重启会话方法本身也会先拆旧订阅。两者叠加不会双跑；回归用例覆盖「两个计时器同窗口触发」。

- **[复判把一个刚被风控/活跃时段挡住的会话强行拉起]** → 不会。复判只判启动闸（调度开关 + 平台能力 + 人设/镜像），风控状态、活跃时段窗口、每日上限属于续场闸，且重启会话方法内部还有一道活跃时段的防御性拦截。复判过闸后若被这些拦住，会话不激活，计时器保持武装、继续等——行为正确。

- **[每连接一个 60 秒计时器的开销]** → 一跳是一次纯内存读（副本查表 + 几个布尔）。按当前边缘规模，稳态开销可忽略。若未来连接数进入千级需重新评估，届时正是接跨进程叫醒通道、把定时复判降级为兜底的时机。

- **[「不设时间上限」被后人当成疏漏补回来]** → 已在决策三写明理由，并在规格里写成显式要求（上限是资源上限而非时间上限），而不是只留在实现注释里。

- **[全局调度开关关闭不自愈，运营开关后仍需重连]** → 这是本 change 的显式取舍，非疏漏。已在决策四交代理由；若日后确认需要，单独立项并连同「全局停机的恢复语义」一起设计。

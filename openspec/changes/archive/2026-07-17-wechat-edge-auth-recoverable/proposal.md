# 边缘授权态与端点熔断可恢复

## Why

视频号边缘端把「现在暂时不行」实现成了「永远不行」：一次限流或一次网络超时会把授权态打到 `degraded`，而 `degraded` 让全部能力翻 false、定时同步直接静默 return —— 不再发请求，就不再有新的失败，也就没有任何东西能把它拨回来。加密会话本身完好、根本没过期，客户却必须在客户端点「重新登录」、重开浏览器重扫二维码才能恢复。同一台机器上的端点熔断器同样只有开、没有关：一次 WAF 拦截页（HTTP 200 返回 HTML）就能把某个能力熔断到进程结束，后台切开关也无效。

此外，探针把限流、网络抖动、账号还没发过帖这三类完全不同的情况统统对外压成「接口改版」，真实原因被算出来后写进一个从无人读的字段。运营据此会去重新抓包校准端点，而真相可能只是这个账号是新号、一篇帖子都还没发。零发帖账号会被永久误判为平台改版。

不修的代价是：视频号评论与私信收件箱会因为一次上游抖动永久停摆，且对外给出误导性的原因码，把运营引向错误的排查方向。

## What Changes

- **临时性失败不再终局化**：限流与网络抖动进入降级后 MUST 安排有限退避的恢复尝试（限流优先遵循平台给的 `retryAfterMs`），恢复尝试成功即自动回到正常运行态，无需客户重新登录。
- **每个降级态都要回答「什么把它拨回来」**：为四类降级原因各规定恢复路径与退避区间；权限拒绝与接口改版用长间隔慢探，恢复通道永不归零。恢复尝试 MUST NOT 自动反复打开浏览器（沿用既有冻结契约）。
- **结构性 vs 临时性划清**：只有身份不匹配（会话属于别的账号）与运营显式停用属于「不自动恢复」，且两者各自都有明确的人工恢复入口；其余类别一律带自愈通道。
- **探针原因诚实分类**：探针返回结构化结果而非裸 boolean，按错误类别映射到既有的授权原因码（不新增协议枚举），真实原因直达云端与客户端。
- **零可探范围不是失败**：账号一篇帖子都没发时，MUST NOT 判为接口改版、MUST NOT 降级；授权态保持正常，相关能力按 fail-closed 保持关闭，待账号有帖后由周期性重探自动放行。
- **端点熔断可复位**：熔断带 TTL 自动过期（无需任何外部接线的兜底恢复通道），探针对该端点成功即立刻复位。
- **非 schema 原因不再触发熔断**：HTTP 200 返回非 JSON（WAF/故障页）与响应超限改判为可重试的临时上游故障，不再打开熔断器。

## Capabilities

### Modified Capabilities

- `wechat-channels-interaction`: 授权降级与端点熔断必须可恢复——规定每个不可用态的回拨路径、退避区间，以及哪些错误类别根本不该进入不可恢复态。

## 并行与协调

本 change 不触碰 CLAUDE.md 列的四个热点文件（两份 `protocol.ts`、command-bridge 动作映射、`RoleName`+role-catalog、`risk-state-machine.ts`），故可与本批其余 change 全并行开发；集成仍串行（合回前 rebase + `test:acceptance` + `typecheck`）。

**跨 change 协调项**（并行的 `wechat-edge-runtime-honesty` 拥有 `runtime.ts`）：

- 本 change **不改** `auth.clear()` / `auth.initialize()` 的签名，两者的调用点归对方；本 change 只在其内部补恢复计时器的取消逻辑。
- 本 change 改 `WechatAuthCoordinatorOptions.probeEnabledReads` 的**返回类型**（`Promise<boolean>` → `Promise<WechatProbeOutcome>`）。`runtime.ts:83` 是纯透传箭头函数、`runtime.ts:223` 的结果被丢弃，**两处均预期无需改动即可通过 typecheck**；若对方的改动使其不再透传，则由后集成的一方在 rebase 时对齐（改动量为一行）。
- 本 change 需在 `api-client.ts` 改两处 throw 的错误类别（约 3 行）。该文件在本批中无其他 owner；若集成时发现冲突，以「非 schema 原因不得判 schema_changed」为准语义合并。

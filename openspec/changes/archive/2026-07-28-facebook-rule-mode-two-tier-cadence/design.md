## Context

Facebook 规则模式今天是单轴节奏。云端把确认浏览事实按「账号 + 部署目标 + 规则定义号 + 定义版本 + 收集序号 + 内容键」落进去重账本，计数到第 10 条时在同一个事务里关掉当前收集集合、创建**一个批次行**、把收集序号推进一位。批次行把点赞、加群、评论三个动作状态焊在同一行，串行执行：点赞先做，点赞到达任一终态后无条件调用加群联系评论编排器，编排器返回后写入终态并释放账号的逻辑单飞占用。

三条与本设计强相关的现状约束：

1. **节奏数字是规则身份的一部分**。定义号字符串本身编码了「浏览 10 / 点赞 1 / 加群联系评论 1」，而定义号 + 定义版本是进度表主键、去重账本主键与批次唯一约束的组成部分，另有四张表用 CHECK 把它钉成字面量。
2. **加群与联系评论在代码里是同一个动作**，没有独立的「只加群」步骤；它的唯一入口在点赞状态机之后，且入口开头有幂等守卫，所有点赞终态分支都汇入这一个漏斗。
3. **释放单飞占用的唯一正常路径是批次终结写入**。进度行的活跃批次指针只在批次被标记为终态时清空；活跃批次指针非空时，确认浏览事实在写入去重账本**之前**就被短路，既不计数也不落账。

约束还包括：既有迁移已入 DEV 账本，磁盘内容一旦变化即触发校验和不匹配、整批拒绝；规则模式配置表没有部署目标列而 DEV/OL 长期共库；配置回读当前直接返回代码常量、不读库中定义号。

## Goals / Non-Goals

**Goals:**

- 把「浏览→点赞」与「点赞轮次→加群联系评论」拆成两级独立节奏，一级 5、二级 2，使加群频率维持每 10 条浏览一次。
- 让「本轮按节奏不做加群」成为数据与界面上可辨识的诚实事实，既不借用失败态，也不让轮次停在非终态。
- 在不新增计数事实、不新增表的前提下实现二级节奏，把改动收敛在既有数据模型内。
- 保持联系评论发布链零改动，保持点赞被抑制仍推进节奏的现行语义。

**Non-Goals:**

- 不改联系评论的选群、正文来源、联系方式注入、审批模式、去重与风控记账。
- 不改缺联系方式时的 fail-closed 行为（另一变更承接）。
- 不改人设准入、慢启动优先级、活跃时段、平台能力与安全闸。
- 不把节奏做成可配置项。两级节奏仍是固定定义，运营的唯一选择仍是开或关。
- 不改规则模式配置的持久化主键归属（环境级迁移由另一变更承接）。

## Decisions

### D1：二级节奏按「轮次序号」判定，不新增点赞计数事实

**选择**：用轮次序号的奇偶决定本轮是否包含加群联系评论。轮次序号由进度行的收集序号单调递增派生，建轮次时的冲突处理保证并发只成一个轮次，序号稠密无洞，可直接作为周期判据。

**备选（否决）**：新增持久化点赞计数列或点赞事实表，按「真正点成功的赞」计数。否决理由有三：

- 语义歧义无解。点赞终态里「已经赞过」「提交后结果不明」「回执模糊」三种既不算失败也不算新点赞，仓内没有先例可循，任何裁定都是新造口径。
- **会静默停掉加群**。只数成功点赞时，点赞日配额、分钟突发或冷却一旦耗尽，二级计数永远推不动，加群与联系评论随之完全停止，而界面上看不出任何异常——这正是「静默假成功」红线的镜像形态。
- 新增表或列会同时触发三道机械门禁：运行时代码不得含建表语句、属主表清单是生成物必须重新生成、组装根跨段清点需登记新属主。成本与收益不成比例。

**代价**：轮次序号推进不依赖点赞是否成功，因此「点赞被风控抑制的轮次」仍计入周期。这与现行行为一致（今天点赞被抑制也照样做加群），并在规格里显式写明，不作为隐含约定。

### D2：换新定义号并把版本抬到 2，不复用旧号

**选择**：定义号换成编码新两级节奏的新串，定义版本抬到 2。

**理由**：定义号是进度、去重账本与轮次三张表的键组成部分。若沿用旧号，同一个号下会混进「10 浏览一批」与「5 浏览一轮」两套语义的历史行，任何按号查询都无法分辨记录属于哪套节奏，重启恢复与对账都会读到混合语义。换号让新节奏从零重新收集，是正确语义而非副作用。

**代价与时机（2026-07-28 实装期实测修正）**：换号后旧进度、旧去重事实与旧轮次在新定义下不可见。

母变更 `facebook-rule-mode-cadence` 的实装记录写的是「DEV 配置行与运行时行均为 0」——那是它上一日部署当刻的真态，**到本变更实装时已过期**。部署前实测 DEV：配置 **22 行（21 行已开启）**、进度 11 行、去重事实 418 行、批次 38 行。因此：

- **配置行必须随定义身份一起迁移**（见 D2.1）。不迁的话 21 行配置停在旧定义、运行时按新定义跑，配置权威与实际行为长期对不上，运营还得逐个重开开关。
- **运行时三张表不迁**：它们答的是「这个账号在这套节奏下做到哪了」，换节奏从零重收才是正确语义；旧行留作历史、新定义查不到。代价上限是每个账号丢至多 4 条已累计浏览。
- 旧定义下残留的非终态批次由存储层的重启恢复统一终结（该恢复按部署目标扫描、不按定义号）。

**教训（登记于此）**：母变更部署记录里的数据量是**当刻快照**，MUST NOT 当作实装期的现状引用；涉及换身份 / 回填的改动，部署前必须重新实测。

### D2.1：配置回填只动身份，不动开关与审计字段

回填 `UPDATE` 只写 `definition_id` / `definition_version`。**MUST NOT** 改 `enabled`——开关表达的是「这个账号要不要跑规则模式」，与节奏版本正交；也 **MUST NOT** 改 `updated_by` / `updated_at`——迁移不是运营动作，冒充操作人会污染审计。合同测试逐条守住这三点。

**配套修正**：配置回读当前无视库中定义号、直接返回代码常量，因此换号后任何存量配置行都会在接口、后台与客户端被谎报成新定义，没有任何机械手段能发现漂移。本变更 MUST 把回读改为读库中真值，并对库值与代码常量不匹配的行显式报出，不得继续以代码常量冒充事实。

### D3：新增「本轮按节奏不适用」动作终态，不复用既有取值

**选择**：动作状态枚举新增一个明确表示「按节奏本轮不执行」的取值，只点赞的轮次把加群与评论两格写成该值。

**理由**：现有取值里最接近的两个语义都不对——「未开始」表示本该做却没起来（模式被抢占、编排器没接管），「结构性跳过」表示目标结构上做不到。用它们表达「节奏规定本轮不做」，会让运营无法区分「按设计不做」和「该做没做成」。而后台是无条件渲染三个动作标签的，一半轮次会被渲染成两个假失败——这是「不静默假报」红线的镜像形态。

**连带**：新枚举值需要放宽轮次表三个状态列的 CHECK，并同步后台的状态中文映射与配色（那是穷举映射，漏改会 TypeScript 编译失败；若绕过则整页白屏）。

### D4：判据内移到加群入口，五个点赞终态调用点不动

**选择**：把「本轮是否加群」的判据放在加群联系评论入口的幂等守卫之后。本轮不加群时，直接写入终态（两格写 D3 的新取值、标记终态）并按既有的「未启动加群」分支续跑浏览。

**理由**：加群联系评论入口开头已有幂等守卫，所有点赞终态分支都汇入这一个漏斗；判据内移即可覆盖全部路径，五个调用点无需改动。终结路径也已存在——既有终结函数在「未启动加群联系评论」时走的正是继续浏览的分支，行为正确。

**硬约束**：本轮不加群时**必须**走到终结写入。若漏掉，活跃批次指针永不清空，该账号后续所有确认浏览在写入去重账本之前就被短路，点赞与加群双双永久停摆——这是活锁，不是精度问题。实装必须为此补回归断言。

### D5：本轮不加群时不覆写点赞阶段的阻断原因

轮次表的阻断原因是三个阶段共用一列，写入语义是后写覆盖先写。若「本轮不加群」也写一个原因，会把点赞阶段的抑制原因抹掉。**选择**：本轮不加群时不写阻断原因，保留点赞阶段已写入的值；「本轮不加群」这件事由 D3 的动作终态承载，不占用阻断原因这一列。

### D6：迁移形态为 expand，且必须动态查约束名

四张表对定义号与定义版本的 CHECK、轮次表三个状态列的 CHECK，一律从「等于旧值」放宽为「属于新旧集合」。放宽既有 CHECK 属 expand，不需要收缩授权。

**必须动态查名**：这些 CHECK 是表级内联匿名约束，名字由数据库自动生成、不可靠猜。仓内既有两种删除模式，其中「固定名 + 若存在则删」只适用于名字可推导的列级约束。本迁移 MUST 走「先查系统目录拿到真名、再动态删除」的模式。若用猜名 + 若存在则删，名字不符会**静默跳过**，随后新增的更宽 CHECK 与旧 CHECK 取合取，迁移报成功而运行期写入仍被拒——迁移层的静默假成功。

**副产品（有利）**：放宽成「新旧集合」意味着旧定义号仍被接受，因此回滚只需把代码常量改回旧值，不需要反向迁移。

### D7：进度投影新增二级节奏轴

除既有的浏览进度（现为 `0..4/5`）外，投影新增「当前轮次在两轮周期中的位置」与「本轮是否包含加群」。后台需据此展示第二级进度，并把「本轮不加群」渲染成中性说明而非进行中或失败。既有的浏览阈值投影字段是字面量类型，需一并调整以容纳新值。

## Risks / Trade-offs

- **[停表窗口出现次数翻倍]** 活跃轮次在飞期间，确认浏览在写入去重账本之前就被短路，既不计数也不落账。一级阈值从 10 降到 5 使建轮次频率翻倍，撞上「点赞已下发但回执永不到达」的卡死窗口次数随之翻倍。→ 缓解：只点赞的轮次终结极快（只等点赞回执，不进加群与审批），总阻塞时长预期不增甚至下降；既有的会话边界对账与进程重启恢复两条兜底不变，实装期须验证两条兜底对「只点赞轮次」同样生效。
- **[DEV/OL 两套节奏并存且无暴露]** 规则模式配置表没有部署目标列而两侧共库，进度三表则按目标隔离。若只部署一侧，同一批已开启账号会在两侧按不同定义号各自维护进度，双方都自称权威。叠加配置回读不读库值这一点，漂移没有任何机械手段能发现。→ 缓解：D2 的回读修正是必做项；部署策略（是否要求两侧同步）在实装期显式裁定并记入实装记录。
- **[旧进度不可见]** 换定义号后存量进度归零。→ 缓解：当前两侧实测均为 0 行，代价为零；必须在实装记录里具名登记，并在此后视为不可回收的一次性窗口。
- **[匿名 CHECK 的静默 no-op]** 见 D6。→ 缓解：迁移里动态查名，并为迁移形态补一条断言，守住放宽后的约束形态。
- **[规格叠层]** 规则模式能力至今不在主 spec 目录，本变更是第四层 delta。→ 缓解：把「先归档 `facebook-rule-mode-cadence`」列为硬前置，实装前核对。
- **[并行冲突]** `facebook-rule-mode-without-persona` 同改规则模式判定与调度接线。→ 缓解：按热点文件单写者纪律串行，开工前确认对方状态。
- **[版本常量的字面量断言]** 运行时所需 schema 版本与已知最高版本两个常量都有字面量断言测试，加新迁移必然打红。→ 缓解：列入任务清单，不作为意外。

## Migration Plan

1. 前置：确认 `facebook-rule-mode-cadence` 已归档、`facebook-rule-mode-without-persona` 未在同期改动同一批文件。
2. 出 expand 迁移：动态查名后放宽四表定义号/版本 CHECK 与轮次表三个状态列 CHECK。
3. 抬升运行时所需 schema 版本与已知最高版本两个常量，同步其字面量断言测试。
4. 改规则定义常量（新定义号 + 版本 2 + 一级阈值 5 + 二级周期 2），修正配置回读读库真值。
5. 接线两级节奏判定与「本轮不加群」终态，补活锁回归断言。
6. 投影与后台展示同步（含新枚举值的中文映射与配色）。
7. 云端测试全绿后部署 DEV，按部署安全序列执行，验证：规则模式账号能建轮次、只点赞轮次能正常终结并继续浏览、第 2 轮能触发加群联系评论。
8. 回滚：迁移已把旧定义号留在接受集合内，回滚只需把代码常量改回旧值并重新部署，无需反向迁移。

## Open Questions

- **真机验收**：只点赞轮次与第 2 轮加群的真实账号验收需在共享真机环境上做，是否本变更内完成或收拢进真机验收 backlog。

## Why

**小红书自 2026-07-29 起一条命令都没执行过，而系统的每一层都在说它在正常工作。**

三件事叠在一起，任何一件单独存在都不会有这个后果。

### ① 引擎准入上限漏了非 Facebook 那一条道

边缘开会话时报的时间上限是 45 秒；引擎入口对**非 Facebook 平台**的准入上限仍是 30 秒。45 > 30 ⇒ `invalid_request` ⇒ **会话在门口就开不起来**，不是某条命令失败。

实机复现（用当前发版二进制，`0.3.25`）：

| 会话超时 | 引擎回复 |
| --- | --- |
| 45_000（边缘实际下发值） | `{"ok":false,"error":{"code":"invalid_request","message":"invalid session timeout"}}` |
| 30_000 | 通过准入，进入端点连接（`endpoint_unreachable`，因探针未开浏览器） |

引入于 `aidcp-edge 70f6947`（2026-07-29，Facebook 时间预算 ×1.5）。该提交把 Facebook 那条链的六层上限全抬了，同时把**非 Facebook 的会话超时** 30_000 → 45_000，但引擎侧非 Facebook 的准入 `MAX_TIMEOUT_MS` 仍是 30_000。

**影响面不止小红书**：微信视频号的浏览器旁车走同一条非 Facebook 分支，同样被拒。

**为什么没被拦住**：该提交**同批新增了机械守卫** `test/native-page-engine/timeout-chain-contract.test.ts`，其立意正是「这类跨语言常量组 typecheck 完全无感，只有这种对账能拦住漏改一层」。但它五条断言**全部只覆盖 Facebook 那条道**——其中一条的失败信息逐字写着「否则整个 Facebook 会话开不起来」。守卫在缺陷存在的六天里**一直是绿的**。这不是守卫写错了，是**守卫的覆盖面按平台切了一刀，而缺陷正好落在没切到的那半边**。

### ② 会话启动失败被吞成一行日志

四个启动点（首次启动 / 身份重立后 / 恢复自动化 / 冷待机唤醒）全部是 `browse.start().catch((err) => console.error(...))`。失败之后：

- **不上报云端**——浏览闭环由边缘首次扫描点火，火没点着，云端连「有过一次尝试」都不知道，没有任何超时或升级会触发；
- **不改运行态**——外壳判「核心是否停摆」走一张具名白名单，这条错误信息不在白名单里，于是 `edge` 轴保持 `running`、`automationState` 落在 `ready`；
- **顺带掐死周期巡视**——`scheduleProbe()` 排在首扫之后，首扫抛出即整条自愈通路不再武装，且四个入口没有一个会再次触发。

这正是红线「停手在下游被读成什么都没发生」的形态：**边缘停了手，上游读到的是「一切正常，只是还没有内容」**。

### ③ 界面把「读不到」画成「没有」和「在跑」

现场三个计数格子的取值恰好覆盖了三种状态，而**格子本身是诚实的**（`null` 渲染为 `—`）：

```
—   精选灵感      读取失败
0   我的内容      真实空池
—   进行中        读取失败
```

但同一屏上有三处把同一批 `null` 讲成了别的东西：

1. **首页标题**：判据 `(inspiration || 0) === 0 && (drafts || 0) === 0`，`null || 0` 得 `0` ⇒ 输出「还在寻找新灵感，暂无待处理内容」。**格子说读不到，紧挨着的标题说没有。**
2. **「最值得看的灵感」**：失败分支要求**两个来源都失败**才显示（`sourceState.kind === 'error' && draftState.kind === 'error'`）。单边失败时掉进空态，向用户宣布「只有赞藏表现和内容证据完整…才会进入这个位置」——**把一次服务不可用描述成一次质量筛选结果**。
3. **「当前环境仍在浏览推荐内容」/「小萝北正在继续寻找」**：唯一判据是把 9 档运行状态压成的一个布尔量（`automationState !== 'stopped'`），**除 `stopped` 外 8 档全为真，含 `paused` 与 `error`**。真正能反映「浏览循环在不在跑」的信号在这一步被抹平。同一个 `ready`，诊断面板标注为「待任务」，内容页却讲成「正在浏览」，并配一个跳动的 live 圆点。

已上线规格 `client-xhs-content-value-home` 的「一个来源读取失败」场景写的是「**页面不得整体伪装为空**」。①②③ 中的 ③ **不是新缺陷，是现行实现违反了已上线规格**。

### 立论

①是回归，必须修。但**只修①，②③原样留着**，意味着下一次执行层出问题时，系统仍然会用同样的方式把它藏六天。①的代价是六天停摆，而**让它能藏六天的是②③**。

## What Changes

### A. 引擎准入上限按平台道对齐，守卫覆盖全部平台道

- 引擎侧非 Facebook 准入上限抬到与宿主下发的非 Facebook 会话超时一致。
- 守卫从「Facebook 那条道」扩成**逐平台道对账**：每条道都要验「请求 ≤ 边缘准入」「请求 ≤ 引擎天花板」「会话超时 ≤ 两道准入」「会话超时 ≥ 会被它夹回的天花板」。
- **新增一条元断言**：引擎准入里被特判的平台集合，必须与守卫覆盖的平台道集合逐一对应。新增一个平台特判而不加对应道，守卫 MUST 当场失败——**这是本次真正的修复**，只抬一个常量等于把同一枚地雷挪到下一个平台。

### B. 会话启动失败必须离开本进程

- 四个启动点不再各自 `catch(console.error)`，改为经一个具名的失败上报口。
- 失败按**结构性**分档：门口拒收类（准入不通过、能力不支持）判结构性 ⇒ 落终态、回执写清「为什么重来也不会变」；端点不可达、浏览器未就绪类判非结构性 ⇒ **MUST 留带上限的自愈通道，MUST NOT 落终态**。
- 无论哪一档，**MUST 上报云端**并**MUST 让外壳的运行态离开「正常」**：现状是两者都没有。
- 周期巡视的武装 **MUST NOT** 依赖首扫成功——首扫失败恰恰是最需要它的时刻。

### C. 界面 MUST NOT 把「读不到」画成「没有」或「在跑」

- 首页标题的空态判定 **MUST** 区分 `null`（未知）与 `0`（已确认为空）；任一计数未知时 MUST NOT 宣布「暂无待处理内容」。
- 「最值得看的灵感」的失败分支 **MUST** 按**自己那个来源**是否失败判定，MUST NOT 要求全部来源同时失败；单边失败 MUST NOT 落进讲质量条件的空态文案。
- 「正在浏览」这类**声称执行层在动作**的文案 **MUST** 有执行层证据（真实跑起来的信号），MUST NOT 只凭「进程活着 + 连接已建立」。无证据时 MUST 退到不声称动作的措辞。
- 账号身份行 **MUST** 标明来源（平台昵称 / 客户端环境名），与标题栏既有口径一致；MUST NOT 让一个环境备注名读起来像平台身份或人设名。

## Non-goals（本 change 明确不做）

- **不碰 `aidcp-api` 的客户端依赖接线**（精选内容 / 账号安排 / 今日进展 / 进行中 等 503）。那批属活跃 change `deploy-derived-services-to-dev`，2026-08-04 16:17 仍在提交、16:19 刚部署 dev，并发改同一组装根必撞。本 change 只保证**读取失败被如实呈现**，不负责让它读得到。
- **不动节奏系数、不动风控状态机**。握手 `tempo=1.3` 的二义（`warned` 与 `quota_level=conservative` 同值）与「`warned` 无自动回落」是独立问题，登记不修。
- **不出桌面安装包**。打包属用户显式触发动作（CLAUDE.md §6）；本 change 的收尾到提交 / 推送为止。

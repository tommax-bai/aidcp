## Context

`transcribe-textcard-image-text` 已把参考文字卡按原始顺序转写并交给 `CoverCardWriter`，但当前 `CoverCardCopy` 和渲染器只有 `title + bullets + tags`。提示词又把内页限制为 1–5 个短要点，因此即使来源是连续文章页，模型也只能产出信息框式卡片。现有渲染器随后按要点模型排版，视觉审核能识别不相似，却无法通过重做获得系统根本不支持的长文结构。

本次只改 Cloud 内部文案与确定性渲染契约。输出尺寸、字体资产、OSS、发布协议和人审流程保持不变。

## Goals / Non-Goals

**Goals:**

- 在首次文案调用中产出覆盖开头、中段和结尾的整套长文轮播。
- 让长文卡呈现为简洁的标题与短句段落，不出现通用 PPT 卡片装饰。
- 用字体度量预先验证断行、溢出和页面占用，避免下半页大面积空白。
- 保持旧要点卡输入和渲染结果向后兼容。
- 让 14 张等超出发布上限的来源卡按连续语义区间压缩到 9 张，而不是只取前 9 张。

**Non-Goals:**

- 不引入自由坐标、原图像素、图片 URL 或 OCR 原文到渲染器。
- 不让模型自由设计模板，不增加图片模型调用，不新增多套主题系统。
- 不改变视觉审核阈值、轮播部分成功语义、发布审批或 Edge 行为。
- 不为所有文字卡强制长文版式；短要点来源继续走现有布局。

## Decisions

### D1. 在现有卡片类型上增加两个明确的长文版式

`CoverCardCopy` / `TextCardCopy` 增加可选 `layoutKind: article_cover | article_page` 和 `paragraphs`。旧对象不带 `layoutKind`，继续逐字走现有要点卡布局。长文对象的 `bullets/tags` 保持空数组，使下游仍消费一个卡片类型，不新建第二条图片链路。

选择显式枚举而不是让 renderer 根据字数猜版式：生成决策必须可审计、可测试，同一输入也必须稳定走同一布局。

### D2. 用 OCR 文本结构确定是否为长文来源

只有 `all_text_card + carousel enabled + ordered transcription` 才评估长文模式。确定性分类使用转写文字的有效字符数和完整句数量：多数来源槽达到长文阈值才选择 `article_flow`；短清单、海报和缺少可靠转写的来源保持现有 `bullet_card`。

不解析视觉模型的自由文本来判断“无卡片/无网格”，避免否定词误命中和额外模型调用。

### D3. 来源卡超过发布上限时做连续分桶

长文模式读取全部成功且有对应来源图片的转写卡，按原始数组顺序分成 N 个连续桶；每个生成槽接收一个桶的合并文字和完整 `sourceArrayIndices`。这样 14→9 时仍覆盖文章结尾，同时保持顺序和来源可追溯。旧要点卡继续保持前 N 张逐槽一一对应。

计划与发布审计新增可选 `cardSourceArrayIndexGroups`；既有 `cardSourceArrayIndices` 继续记录每组首下标，兼容旧消费者。

### D4. 长文提示词只生成内容，不让模型设计版式

长文 prompt 固定输出 `cardTitle + paragraphs[]`：

- 第 1 张是 `article_cover`，承接主题和问题；
- 第 2..N 张是 `article_page`，每个 paragraph 是一个完整短句段落；
- 整套覆盖来源分桶与改写终稿的开头、中段和结尾；
- 终稿事实优先，来源 OCR 只负责信息位置，继续禁止逐字搬运。

模型不输出字号、颜色、坐标、行高、装饰或版式名。解析器根据槽位确定版式，并在现有防搬运校验之外调用共享的长文布局预检。

### D5. 排版参数固定为已验收的简洁模板

在现有 1080×1440 逻辑画布上采用与本地 V2 等价的比例：正文约 36px（输出约 58px）、常规字重、行高约 1.62、左右 96px；内页标题约 50px、粗体、按语义词组断行。正文按句号/问号/感叹号拆成短句块，块间距固定。

`article_cover` 使用单一黑色上半区、黄色标题和浅灰正文区；`article_page` 使用浅灰纸面、深灰正文、标题下细分隔线。两者都不渲染英文眉题、页码、网格、圆角框、标签胶囊、角部装饰或水印。文章模板不消费来源装饰令牌，保持实现和视觉都简洁。

### D6. 文案校验与 renderer 共用同一纯布局计算

纯布局函数负责字体覆盖、语义断行、逐句行数、内容底边和占用率。内页可接受占用率为约 0.80–0.96；低于下限视为内容不足，高于上限视为溢出。校验失败不会通过放大行高、添加装饰文字、静默截断或删除正文来伪装成功。

`CoverCardWriter` 在发出计划前运行同一计算，因此正常情况下 renderer 一次即可完成；renderer 保留相同检查作为最终安全门。长文卡视觉审核失败时不做仅改变装饰令牌的确定性重渲染，因为文章模板不消费这些令牌，重复渲染只会产出同一内容并浪费时间。

## Risks / Trade-offs

- [长文阈值误把高密度清单判成文章] → 同时要求有效字符和完整句占比；分类结果只在有序转写路径生效，旧路径不变。
- [模型输出字数波动造成占用不合格] → prompt 给出逐槽短句数量与文字预算，解析后用真实字体度量拒绝不合格集合；沿用现有至多一次收敛调用，不增加循环重做。
- [14→9 合并导致单槽上下文过长] → 连续分桶后对每桶提示摘录设上限，整套仍受现有 2000 字终稿预览和单次 LLM 调用预算约束。
- [固定简洁模板降低账号主题变化] → 仅长文文章页固定模板；旧要点卡的账号主题与参考样式路径保持不变。这里优先保证阅读质量和参考形态。
- [页面占用率不是审美评分] → 它只作为防止极端空白和溢出的机械门禁，最终视觉审核仍负责整体可用性。

## Migration Plan

1. 以现有 `AIDCP_PUBLISH_TEXTCARD_CAROUSEL` 和 `AIDCP_TEXTCARD_OCR` 为准入，不新增环境开关或数据库迁移。
2. 部署到 dev 后用“小猫 / 物欲情欲其实是在拼凑破碎的自己”执行真实内容生成验证，确认 9 张全部为确定性长文卡、顺序覆盖结尾且页面占用合格。
3. 若运行态异常，回滚 Cloud 提交即可恢复旧要点卡行为；所有新增 JSON 字段均为可选，旧发布记录和旧代码可读取。

## Open Questions

无。已确认采用 V2 的简洁长文方向，不再增加装饰或自由模板选择。

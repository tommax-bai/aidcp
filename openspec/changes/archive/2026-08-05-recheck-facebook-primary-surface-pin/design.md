## Context

云端角色调度器在会话启动时执行一次浏览面钉定（`aidcp-cloud/src/orchestrator/role-dispatcher.ts:1105`）：

```
this.sessionFacebookPrimarySurface = this.facebookRuleDecision().primarySurface ?? 'feed';
```

`facebookRuleDecision()`（同文件 `:1096`）转调注入的账号运营裁决口。生产上这个口有两份实现——单体 / 接口段在 `aidcp-cloud/src/server.ts:7236`，派生自动化进程在 `aidcp-automation/src/automation-connection-dispatcher.ts:356`——两份各有三到四条**早退分支**，早退时返回的对象里**没有** `primarySurface`：

- 连接平台非 facebook → `rule_mode_unsupported`
- 内容排期配置副本陈旧 → `facebook_operation_policy_stale`
- 属主存储未就绪（仅单体路径）→ `facebook_operation_policy_unavailable`
- 基线解析失败 → `policy.blocker`，本身有三个具名值：账号→环境绑定问不到 / 快照里没这个账号 / 该环境没有浏览面基线
- 裁决整体抛错 → `rule_projection_unavailable`（`:1096` 的 catch）

**每一条早退都已经带了具名 blocker**，问题只在于钉定那一行把它连同 `primarySurface` 一起丢掉，`?? 'feed'` 把「没问到」变成了一个看起来正常的 Feed 会话。整场此后不再重问：进 Reels 的两条路（`redriveBrowse()` `:2355`、`page.cards.arrived` 的主入口分支 `:4295`）都以钉定值为条件，剩下的只有首页空 / 到底 / 不可上报的降级通道（`:2396`），首页有卡时永不触发。

2026-08-05 dev 的 11 例全部发生在**启动闸复判通道**救起来的会话上（`:3007` `onStartGateRecheckElapsed` → `startOnPersonaBound` → `restartSession` → 钉定 → `redriveBrowse`）：新账号首次真实握手，人设副本晚到几秒，复判在 1.6~16.3 秒后放行并**就地钉定**。该通道本身是为一模一样的首次握手竞态建的，只是它只重问「能不能开工」，没有重问「在哪个入口开工」。

约束：不改协议、不改库表、不改边缘；纠正动作只能复用既有统一重驱滚动命令；`authoritative` 钉定后「配置中途改不影响本场」这条既有保证必须逐字保住。

## Goals / Non-Goals

**Goals:**

- 让「此刻问不到」与「运营选了 Feed」在会话内**结构上可区分**，并把前者的具名原因送到回执。
- 给「问不到」一条**有界**自愈通道：答案变好就地改钉并把浏览纠正到正确入口；问不到到顶则如实终结。
- 纠正路径零新增协议、零对外写入、零重复动作。

**Non-Goals:**

- 不改动裁决口本身的判据或它的任何 blocker 取值——这次只是不再把它们丢掉。
- 不追查 2026-08-05 那 11 例究竟命中哪一条早退：快照不留档，事后不可回溯。本方案的验收标准是**下一次同类故障能当场说出原因**，不是补证这一次。
- 不改「配置中途写入不影响本场」的语义；复判只对 `unresolved` 生效，且是单向的（`unresolved → authoritative`，永不反向）。
- 不引入新的任务让位 / 页面独占协调机制。

## Decisions

### D1：钉定值改为带来源的结构，让 typecheck 逼所有读取点表态

把 `private sessionFacebookPrimarySurface: 'feed' | 'reels'`（`:801`）换成一个私有结构：面值 + `resolution: 'authoritative' | 'unresolved'` + `blocker`。

- **为什么不加一个并列的布尔标志**：并列字段留着旧字段可读，漏改的读取点编译照过、行为照旧错——这正是本仓判例里「同一判断被两处用、第二份看不见」的形状。换类型后每一个 `=== 'reels'` 都会红，改的时候必须逐个表态。
- 读取点收口成一个取用方法（判「本场是不是 Reels 主入口」），避免各处各自解构结构体又长出第二份判据。

### D2：blocker 直接取裁决对象上现成的字段，不新增管道

`FacebookRuleModeDecision` 已经有 `blocker: string | null`。钉定处的判据是：**`primarySurface` 缺席即 `unresolved`，原因取同一个对象上的 `blocker`**。

- 两份裁决实现（单体 / 派生）各自的早退都已具名，故本方案**不需要改任何一份裁决实现**，只改消费端。这同时避免了「两处各算一遍」——按引用取同一个对象的两个字段，不可能错配。
- `primarySurface` 缺席而 `blocker` 也为空，是「有一条早退忘了具名」的信号：回执 MUST 打成显式的未识别值，MUST NOT 折进任何已有名字。这条是跨层翻译红线的直接落地。
- 注意反向情形必须放行：裁决可以 `mode:'blocked'` 却**带着** `primarySurface`（例如慢启动状态问不到、但基线读到了）。这类仍算 `authoritative`，不武装复判。

### D3：复判通道逐字复用启动闸复判的形状，但独立计数

启动闸复判（`:2960`~`:3042`）已经把这类通道该有的性质踩全了：只武装一次、退避表 `[2s, 5s, 10s, 30s, 60s]`、纯判据不打日志不发回调、到顶记终态收摊、会话起来即解除。新通道照抄这套形状，但用**自己的**步进与计数器。

- **为什么不挂在启动闸那条通道上**：那条的使命是「能不能开工」，会话一起来就 `cancelStartGateRecheck()`；而本通道恰恰要在会话**已经在跑**的时候继续问。共用一个计数器会让两条通道互相重置退避。
- **为什么不是每批卡片顺手重问**：那是无界的，且会把一次裁决口异常放大成每几秒一次的重试脉冲。上限 + 退避是本仓对这类通道的既有纪律。
- 武装时机：在两个会话启动方法把 `sessionActive` 置真**之后**武装，避免一跳打在还没激活的会话上。每跳先判 `sessionActive`，会话结束时解除。

### D4：纠正 = 就地改钉 + 一条既有重驱；命令被闸住不回滚改钉

问到基线后：先把钉定改成 `authoritative` + 权威面值（纯内存、无副作用），再判断是否需要纠正浏览位置。

- 纠正面与当前正在浏览的面相同 → 不发任何命令。
- 不同 → 走既有统一重驱出口发一条 `page.scroll{reason:'resume_redrive', targetSurface:<权威面>}`。该出口自带风控 / 配额 / 软暂停闸；**被闸住不回滚已改的钉定、也不消耗复判预算**：钉定已经是权威的，后续任何一次自然重驱（任务归位后的重驱、下一批首页卡片触发的主入口推进）都会用上正确的面。
- **为什么不额外做任务在途的让位判断**：重驱走的就是那个统一出口，既有闸已经覆盖了软暂停与配额；再造一套「现在方不方便打断」的判断就是第二份实现。这条命令是纯滚动，不构成对外写入，不触碰提交点红线。

### D5：回执按「每场每个不同 blocker 至多一条」去重

`unresolved` 钉定与每次复判失败都可能重复同一个原因。回执按 `(本场, blocker 值)` 去重；blocker 在可恢复类之间迁移（例如「副本问不到」→「确认没有这个环境」）时允许再出一条，因为那是新信息。到顶那一条终态回执不受去重影响，必出。

### D6：验证以「闸喂违规输入」为主，不堆端到端

裁决口是注入的，可以直接喂桩。核心用例（少而承重）：

1. 裁决缺 `primarySurface` 且带 blocker → 钉 `feed`/`unresolved`、回执具名、通道武装。
2. 裁决带 `primarySurface` 但 `mode:'blocked'` → 钉 `authoritative`、**不**武装、无回执（防止把「保守钉定」错扩成「凡 blocked 都复判」）。
3. 复判后裁决转好为 `reels` → 改钉 `authoritative`、恰好一条重驱、通道解除。
4. 复判后裁决转好为 `feed` → 改钉 `authoritative`、零重驱。
5. 到顶仍不可解析 → 一条终态回执、不再有跳、会话继续在 Feed 上跑。
6. 缺 `primarySurface` 且 blocker 为空 → 回执打显式未识别值（守 D2 那条红线，防止将来有人加早退时忘了具名）。

## Risks / Trade-offs

- **[会话内浏览面不再恒定，可能被误当成「配置中途改也会生效」]** → 复判是单向且只对 `unresolved` 生效；`authoritative` 钉定的会话不武装通道，既有场景「会话中途改配置不影响本场」的用例逐字保留在规格里，作为反向断言。
- **[纠正重驱可能落在任务在途的时刻]** → 只走既有统一命令出口，所有既有闸照旧生效；被闸住不回滚钉定，靠后续自然重驱收敛。命令是纯滚动，不产生对外写入。
- **[复判把一次裁决口异常放大成日志脉冲]** → 上限 + 退避 + 每场每原因一条的去重；到顶收摊并记终态。
- **[两份裁决实现将来漂移，新早退忘了具名]** → 消费端对「缺面值且无原因」显式报未识别值并有用例守住；这条比在两份实现里各加一次检查更难被绕过。
- **[改类型触及的读取点多]** → 这是刻意的：漏改点必须编译红，而不是运行时静默走老路。取用收口成一个方法，减少各处重复解构。

## Migration Plan

1. 改动落 `aidcp-cloud/src`（属主仓），跑 `test:acceptance` → 全量 `npm test` → `typecheck`。
2. 用 `scripts/sync-split-repos --repo aidcp-automation` 先 dry-run 对账，再 `--apply` 同步派生仓；派生仓组装根若无需改动则不动（裁决实现不在本次改动面内）。
3. 按既有安全序列部署 dev（备份 → rsync → 重启 → healthcheck）。
4. 回滚：本change 不涉及库表与协议，回滚即回退提交并按同一序列重部署。

## Open Questions

- 复判上限取几跳：退避表照抄 `[2s, 5s, 10s, 30s, 60s]` 即覆盖约 107 秒。首次握手的实测竞态窗口是 1.6~16.3 秒，故该表已足够；若实装时发现有更长的问不到窗口（例如副本整体落后），再决定是否延长末位，而不是无上限。
- 回执落哪一层：本仓既有做法是 `console` 具名行 + 已有告警存储。默认只出具名日志行；是否升格为告警留到实装时按该 blocker 是否代表「整批新账号都会中」来定。

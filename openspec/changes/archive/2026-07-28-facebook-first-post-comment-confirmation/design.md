## 3. 判据为何必然落空

`facebook-router/50-comment.js` 的确认闸是 `own && (serverId || (like && reply))`：

- `serverId` 曾要求 `/^Y29tbWVudD/` → 纯数字形态永远 false；
- `like && reply` → 回复控件不出现，永远 false；
- 更靠前的 `own`（本人身份）只认 `?id=` 与 `/people/<name>/<id>`，而群 feed 的作者链接是
  `/groups/<gid>/user/<uid>/` → **连"这是我发的"都判不出来**，后面两条根本没机会跑。

三条叠加 ⇒ 确认窗口无论开多久都不可能确认。云端再叠一层 `fastReturnToFeed: true`（自动路径写死），
连那个窗口都不进，Enter 后 500ms 直接导航回首页。

后果不是"看着像失败"：`comment-scheduler.ts` 对 `verification_ambiguous` 打去重标记，
目标帖被永久烧掉、覆盖冷却不落、当日配额不计 —— 同群首帖此后只剩 `all_deduped`。
这是"持续无法评论"而非"偶发失败"的机械原因。

## 4. 本 change 的取舍

**放宽 id 判据会不会变成假成功？** 不会，且净安全性提升：

- 客户端占位由平台自己打标记（`client:` 前缀），继续一律拒绝，并补上裸 UUID 形态；
- 同时新增「在飞否决」：行上有「发布中 / đang đăng / posting」时不确认（此前 `inFlight` 只上报、不否决）；
- 待审徽章否决、被拒终局、控件计数不可作判据这三条既有红线原样不动。

**滚动判据**改为读真正在滚的元素，仅在「文档自己不滚」时才回落到容器；窗口正常滚动时行为逐字不变
（真机复验：feed 水合完成后 `documentElement` 恢复可滚，新旧判据取到同一组数字）。

## 5. 已定位但本 change 不修（须单独决策 / 单独 change）

1. **评论模板"每行一条"语义 vs 运营意图**。后台"评论模板"框的规则是每行一条、发时随机挑一条；
   运营把整段 13 行招聘广告粘进去 ⇒ 被切成 13 条 ⇒ 每次只发其中一行（12:53 那条 26 字的
   "👉 Chuyên cần: 400.000 VNĐ" 即是）。**改成整段一条不是纯 UI 改动**：spec
   `facebook-scheduled-comment` 要求正文过联系方式校验、电话必须走 contact 通道后置注入，
   而这段广告自带 `📞 Liên hệ: 0335 610 868` ⇒ 整段作正文会被校验拒掉。需产品决策：
   正文去掉电话行 + 电话配成账号联系方式，还是另立"整段广告"投放形态。
2. **首帖绑定证据漂移**。`firstPostEvidence` 把容器内**全部**可见图片 alt 与全部链接算进指纹，
   且未像正文那样排除嵌套 article；真机实测 Enter 后 5.774s 指纹即变 ⇒ `boundFirstPostRoot` 失效。
   本轮因确认判据修好、评论行确实在容器内而未致命，但仍是定时炸弹。
3. **同群多个加群按钮**。群页页头与吸顶栏各有一个「Tham gia nhóm」（同一个群），
   实测某些群甚至 10 个（含推荐群）。引擎要求候选唯一，否则 `ambiguous_target` → `not_ready`。
   应按群 id 归一后再判唯一。
4. **评论框坐标可能在视口外**。实测编辑器 rect y≈1731 而视口高 803；引擎靠 6 轮 650px CDP 滚轮兜底，
   是否总够未验证。可信点击前应先把目标滚进视口再取坐标。
5. **`verification_ambiguous` 一个 reason 混装两种事实**：「压根没看」（快返）与「看了 9 秒没看见」。
   同一份 edge.log 里 8.49s / 11.24s / 13.52s 三次同 reason 实为两种机制。建议拆 reason。
6. **并发 `page.scroll` 被租约静默丢弃**：边端不回执，云端空等到租约释放才重发（实测 04:53:18.661 丢弃、
   04:53:27.775 重发）。丢弃应有回执或至少有可观测计数。

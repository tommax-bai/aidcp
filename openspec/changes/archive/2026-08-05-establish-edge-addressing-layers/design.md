## Context

### 起点

边缘长期被描述为「重、不好理解」。逐条盘点生产可达的多步流程后（判据＝「边缘在**决定下一个动作是什么**」，而非「一条命令内部有几步」），结论与直觉相反：

| 流程 | 规模 | 该不该上移 |
| --- | --- | --- |
| Facebook 启动登录协调（最多 4096 轮轮询，9 种信号映射 9 种动作） | 971 行 | 否 |
| 身份守卫与唤醒重立 | 1234 行 | 否 |
| 主进程生命周期（冷待机、唤醒、回收、暂停恢复） | 约 1870 行（单闭包） | 否 |
| 浏览器槽位调度 | 外壳内一部分 | 否 |
| 视频号定时同步 | 336 行 | 是（已后置：尚无真实应用） |
| 周期阻断观测 | 约 200 行 | 部分（决策上移、能力留下） |

**真正该上移的约 500 行，该留但该划清边界的约 4000 行。** 所以「把边缘变薄」是错误目标；「把层的界划出来」才是。

历史上最典型的一条边缘编排 `ensureFeed`（"不在目标页就整页导航过去"）现在只存在于三个**已退役**文件里——Native 迁移已经消化掉了。这也印证：减重空间比想象中小。

### 为什么需要一把尺子而不是一张表

控制仓已有 change `split-classic-client-edge-host`（分支 `codex/split-classic-client-edge-host`，未合 main，故 `openspec list` 看不到）已完成：

- 82 条运行时通道全部归属，零遗漏、零重复、零冲突
- 230 块行段清单，覆盖 1–7396 行**无空洞**
- 一份推导出的宿主公开面，其中已自带「资源协调（机器级）」分组

**边缘不缺归属表，缺的是裁决依据。** 已经出现用错判据的实例（见 §4 判例二）。

## Goals / Non-Goals

**Goals:**

- 确立四层编址模型与权威归属，作为边缘一切归属决策的裁决依据
- 给出四条可机械套用的判据，以及三个已裁决判例作为用法示范
- 明确本判据与既有「产品侧 / 引擎宿主」拆分的**正交关系与不重叠边界**
- 用一条禁令挡住最可能的失败模式：派生出第二张互不校验的归属表

**Non-Goals:**

- 不新建任何边缘归属表、归属清单、目录规则文件或门禁
- 不改 `aidcp-edge` / `aidcp-cloud` / `aidcp-console` 任何源码
- 不动 `split-classic-client-edge-host` 的 worktree、台账与结论
- 不解决「四层今天混在同一个闭包里」这件事本身——那是后续 change 的对象，本 change 只提供判断它的依据
- 不涉及边云协议、风控配额口径、部署与打包

## Decisions

### 决策一：按「编址单位」分层，而不是按「观测 / 动作」或「读 / 写」分

| 层 | 编址单位 | 权威 | 典型内容 |
| --- | --- | --- | --- |
| **宿主层** | 机器 | 本地 | 槽位调度、可用内存推算、有界启动队列、进程生死与回收 |
| **环境层** | 分身 | 本地 | 浏览器开关与待机、Facebook 启动登录协调、指纹、代理、阻断检测 |
| **翻译层** | 环境 → 账号 | 本地 | 身份首读与确立、身份守卫复核、身份翻转后重立 |
| **账号层** | 账号 | **云端** | 浏览、互动、发布、风控、配额、人审、记账 |

**核心论据（已对 `aidcp-edge/src/main.ts` 实测）**：主进程的实际顺序是

```
① 浏览器起来（环境）
② 引擎建立
③ Facebook 登录协调        ← 进度与失败只报桌面外壳，不报云端
④ 读登录态 → 账号身份确立（约 :670）
⑤ 才 new EdgeClient({ accountId })（约 :682）   ← accountId 是构造参数
⑥ 才 connect()（约 :1414）
```

登录协调执行时，云端客户端对象**尚不存在**；且身份翻转的处理是「断开 → 换账号 → 重连」，即**一条云端连接绑死一个账号**。

因此：**云端不是「来不及说话」，是「没有可说的对象」**——它的整套权威（额度、风控、审批、归属）全部按账号编址，一个还没有账号的环境在它的概念体系里不存在。

**为什么不用其他分法**：按「观测 / 动作」分会把周期观测整块判错（它跨层）；按「读 / 写」分解释不了槽位调度为什么必须本地（它既不读页面也不写平台）。编址分法是唯一能同时正确裁决这三例的。

### 决策二：四条判据

| # | 判据 | 问什么 |
| --- | --- | --- |
| ① | **事实归属** | 决策依赖的事实**只有谁知道**（本机可用内存 vs 账号级额度） |
| ② | **时序** | 它是否发生在**云端到场之前**；断连时是否**仍须工作** |
| ③ | **后果** | 判错了会不会**在平台上留痕**（可逆 vs 不可逆对外写入） |
| ④ | **性质** | 决定「**何时能开始**」还是「**开始之后做什么**」 |

四条互相印证。四条全中 ⇒ 铁定本地；全不中 ⇒ 铁定账号层。中间态按 §4 判例三的方式**拆开处理**，而不是整块二选一。

**为什么是这四条而不是一条**：单用①会把登录协调判错（页面信号确实只有本机知道，但那不足以说明它该自主决策）；单用③会把它判成"混合体"（见判例二）。四条一起用才能定位到"它是环境层"这个结论。

### 决策三：本判据 MUST NOT 派生第二张归属表

这是本 change 的立身之本，写成硬约束。

- 边缘一旦出现两张互不校验的归属表，就是这套系统反复付过代价的那个形态。
- `aidcp-cloud/boundaries/ownership-rules.json` 已就同类形态记过教训：**绝不能拿生成物顶替人工裁定的名册**，否则判据退化成「是否已经在生成物里」，手工塞一条 + 目录默认层就能全绿。
- 既有归属台账（82 通道 / 230 行段）是本判据的**消费方**：它回答「这块归谁」，本判据回答「凭什么」。

### 决策四：与 `split-classic-client-edge-host` 的关系是正交，不是替代

| | 那条 change | 本判据 |
| --- | --- | --- |
| 切什么 | **产品侧 / 引擎宿主** | 引擎宿主**内部**的四层 |
| 回答什么 | 这块代码归哪个仓 | 同在宿主里的两件事，为什么一个必须留本地、另一个能上移 |
| 产出 | 归属台账、宿主公开面 | 裁决依据 |

那条 change 的宿主公开面里已自带「资源协调（机器级）」分组——即本判据的宿主层。本判据把这个已被局部发现的结构**命名并补全**，特别是补上**环境层与账号层的分界**，那是既有拆分未回答、而后续每一次上移决策都必须回答的。

**边界写死**：本 change 不修改那条 change 的任何产物；那条 change 是否引用本判据由其 owner 决定。

## 已裁决判例（文档的用法示范）

### 判例一 · 浏览器槽位调度 ⇒ 宿主层，铁定本地

| 判据 | 结论 |
| --- | --- |
| ① 事实归属 | 容量按**本机启动时可用内存**推算——云端问都问不到 ✓ |
| ② 时序 | 浏览器得先开起来才能连云端；断连时仍须工作，否则本机连自救都做不了 ✓ |
| ③ 后果 | 判错了最坏是本机卡住，**平台上一个字都不会多发** ✓ |
| ④ 性质 | 准入排队，不决定行为 ✓ |

四条全中。这也解释了它为什么天然不需要人审、额度、"已派发未确认"那一整套。

### 判例二 · Facebook 启动登录协调 ⇒ 环境层，留本地

**曾被误判为「混合体、建议先别碰」，本 change 撤回该判断。**

误判原因：拿「登录失败会打到账号头上（触发风控、安全检查点）」当归属判据。**那是后果，不是归属**——执行的时候账号还不存在（见决策一的启动顺序）。

**用后果去定归属，方向反了。** 这条判例作为反面示范写进文档。

### 判例三 · 周期阻断观测 ⇒ 跨层，拆开处理

- **看页面**（探测有没有被拦住）＝ 环境层能力 ⇒ 留本地
- **看到了要怎么办**（置风控态、停发命令、通知人）＝ 账号层决策 ⇒ 可上移

正解不是整块搬走，而是**能力留下、决策上移**，并保留一条环境层的自我保护兜底（「发现被平台拦住就地停手」）——断连期间继续瞎点是所有情况里最坏的一种。

## Risks / Trade-offs

- **[判据被当成表用，有人照它新建一份边缘归属清单]** → 决策三写成 MUST NOT，并在文档开头与架构文档指针处各重复一次；验收项显式检查「未产生任何新的归属清单文件」。
- **[与 `split-classic-client-edge-host` 的结论打架]** → 本 change 不修改那条的任何产物，只声明正交关系；若将来发现真冲突，走控制仓 change 修订本判据，而非在两处各改一半。
- **[四层划分被当成"必须物理拆成四个模块"]** → 文档明确：这是**裁决依据**，不是目录结构要求；如何落到代码结构由后续 change 决定。
- **[判例随实现漂移]** → 三个判例均附代码位置与实测依据；文档注明这些是**核对当日快照**，引用前应重核（与仓内既有文档的一贯口径一致）。
- **[本判据只覆盖边缘，云端侧另有一套分层（api/content/automation/kernel）]** → 两者编址单位不同、适用范围不重叠；文档中显式声明本判据**不适用于云端拆仓归属**，避免被误用。

## Open Questions

- 翻译层是否应独立成一个明确的模块？（今天散在身份首读、身份守卫、身份翻转三处；收拢后「云端在跟谁说话」会有唯一出处。）**本 change 不决定，只在文档中登记为待决。**
- 后续「划分层边界」若要落到代码，粒度是「每模块标注所属层 + 门禁禁止跨层直调」还是物理拆分？**由后续 change 决定；本 change 只提供判断依据。**

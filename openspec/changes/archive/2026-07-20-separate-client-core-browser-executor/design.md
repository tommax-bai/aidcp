## Context

当前桌面端以“环境子进程是否启动”同时代表三件不同的事：客户端是否能处理该环境、是否已连接 Cloud、是否拥有可执行页面自动化的浏览器。这个合并模型使渲染层把 `handle.child`、登录态或 Cloud 连接态当成非自动化操作的共同前置，也使重连、Cloud 切换、offboard 清理等控制操作可能复用浏览器启动队列。

浏览器槽位调度解决的是昂贵页面执行器的并发与内存约束，不应成为客户端核心或 Cloud 业务操作的容量模型。本设计把每个可信绑定环境的客户端核心定义为客户登录后的正常常驻单元，把浏览器定义为核心按需取得和释放的执行器。现有 `browser-slot-scheduling` 的排队、公平性、内存准入与回收语义继续存在，但只位于浏览器执行域。

实现横跨 `aidcp-edge` Electron 主进程、每环境 Edge core、渲染层状态模型和 `aidcp-cloud` 客户鉴权/控制协议。安全边界保持不变：历史绑定足以授权账号归属范围内的 Cloud 操作，但绝不能代替页面读写前的真实平台身份复核。

## Goals / Non-Goals

**Goals:**

- 客户登录并解析出可信环境归属后，为每个可用环境自动建立浏览器无关的客户端核心与 Cloud 控制连接。
- 用显式操作分类决定路由和前置条件；浏览器槽位只约束真实页面自动化。
- 让人设、内容预览、待审稿编辑、审批受理、配置和 API-only 平台操作在浏览器关闭、CDP 缺席、AdsPower 不可用或槽位为零时仍可工作。
- 把核心、Cloud、自动化和浏览器四条状态轴独立呈现并独立恢复。
- 浏览器按需启动后仍执行槽位准入、CDP 附着、页面身份复核和页面任务租约，保持发布与互动安全红线。
- Cloud 切换、核心重连和 offboard 清理不得隐式拉起浏览器。

**Non-Goals:**

- 不取消或放宽浏览器槽位、内存准入、页面任务租约和页面身份复核。
- 不把页面自动化迁移到 Cloud，也不让 Cloud 直接控制本机浏览器。
- 不把每环境核心拆成新的独立产品、微服务或第二套可执行程序。
- 不把“审批已受理”表述为“平台已发布”；实际发布仍由后续浏览器执行确认。
- 不在本 change 中提高浏览器并发上限、改变槽位公平性或重写平台自动化实现。
- 不把渲染层暴露给客户令牌、`accountId` 或通用网络访问能力。

## Decisions

### 1. 同一每环境 core 以浏览器无关形态正常启动

客户登录成功、环境列表刷新并完成可信绑定解析后，Electron 主进程以有界并发启动或恢复每个可用环境的 Edge core。core 初始进入 `browser=closed`，建立控制连接和可用的平台 API 会话，但不调用 AdsPower 启动接口、不启动浏览器、不附着 CDP、不申请浏览器槽位。

选择复用同一 core 进程而不是新建“轻量控制面”二进制，是为了保留现有协议、账号隔离、日志与监督边界，避免两套进程争夺同一环境身份。这里的浏览器无关形态是正常状态，不叫降级、冷备或无槽位 fallback。

客户退出登录后，客户态 Cloud 操作停止；是否保留本地只读 UI 由现有缓存合同决定。环境被解除归属或绑定冲突时，core 必须 fail-closed 停止对应客户业务能力，不猜账号，也不通过启动浏览器尝试恢复身份。

### 2. 建立集中式操作分类注册表

每个客户端动作或 Cloud→Edge 命令必须在单一注册表中声明类别、所需身份事实和允许的传输，不允许由散落的 `child != null`、`cloud === connected`、CDP 或槽位状态隐式推断。

| 类别 | 典型操作 | 允许的执行面 | 浏览器要求 |
|---|---|---|---|
| `local` | 本地显示设置、通知、昵称缓存 | Electron 主进程/本地存储 | 禁止启动 |
| `cloud` | 人设、内容状态、草稿编辑、审批受理、客户配置 | 客户鉴权 HTTP 或浏览器无关 core 控制连接 | 禁止启动 |
| `platform_api` | 已具备持久凭据的平台 API 同步/回复 | 浏览器无关 Edge core | 默认禁止；仅显式鉴权恢复可转入浏览器生命周期 |
| `browser_lifecycle` | 打开、关闭、显示、隐藏、人工登录/验证 | Electron 浏览器监督器 | 可申请槽位，但不要求预先存在 CDP |
| `page_automation` | DOM 读取、发帖、评论、页面身份敏感写入 | Edge core + 浏览器执行器 | 必须申请槽位并通过全部页面准入 |

注册表未知项必须以 `operation_unclassified` fail-closed，不能为了兼容默认归入 `page_automation` 后误拉浏览器，也不能默认归入 `cloud` 绕过页面安全链。协议 v2 新命令或既有命令改类时，两端类型、Cloud 映射、Edge 路由和协议文档必须同步。

### 3. 非自动化操作按权威身份事实选择传输

纯 Cloud 操作由 Electron 主进程以客户鉴权令牌和服务器解析的 `envKey` 直接调用 customer-auth HTTP：人设生成/确认、待审配图删除、审批通过/驳回及同类可撤销业务写。渲染层只调用窄 IPC；令牌、权威 `accountId` 和通用请求能力不进入 renderer。Cloud 必须逐请求解析“客户拥有环境 + 环境当前可信绑定账号”，客户端自报的 `accountId` 不具权威性。

必须依赖本地平台凭据或长期 API 会话的 `platform_api` 操作继续经浏览器无关 core 和 Edge↔Cloud 协议执行。这样不会为了去掉浏览器依赖而把平台凭据搬到 Cloud。

不选择“所有非自动化都经 Edge WS”，因为客户已登录但 core 正在恢复时会把 Cloud 原生操作重新绑到本机在线；也不选择“所有操作都走 HTTP”，因为平台 API 凭据和本地设备执行边界仍属于 Edge。

### 4. 浏览器是按需取得的执行器

`page_automation` 动作先在控制面被诚实受理或排队；准备执行时按以下固定顺序取得执行器：

1. Electron 浏览器调度器申请环境槽位并经过内存准入；
2. 启动对应 provider 浏览器；
3. core 附着 CDP；
4. 从真实页面重新读取平台身份并与预期绑定比对；
5. 如页面账号变化，先重建权威绑定/握手，不沿用旧账号上下文；
6. 取得页面任务租约后执行；
7. 结束或空闲回收时释放页面租约、CDP 与槽位，core 和 Cloud 会话继续在线。

浏览器、provider 或 CDP 故障只能使执行器进入 `error/closed` 并让对应页面任务诚实失败或重排，不能终止 core 或伪造 Cloud 离线。槽位为零或已满时，`cloud`/`platform_api` 操作完全绕过该队列。

### 5. 四条状态轴和四类用户意图独立

客户端每环境状态至少拆为：

- core：`starting | online | restarting | error | stopped`
- Cloud：`connecting | connected | reconnecting | offline`
- 自动化：`stopped | queued | running | paused | error`
- 浏览器：`closed | queued | starting | ready | releasing | error`

主操作拆为“开始自动化 / 暂停自动化”和“打开浏览器 / 关闭浏览器”。客户登录后的 core 在线不再由“启动环境”表达；浏览器关闭、自动化暂停都不是断线。人设、草稿和配置入口只显示其真实前置，例如绑定未解析或 Cloud 请求失败，不再提示“请先启动浏览器”或“等待槽位”。

### 6. Cloud 切换只重绑控制连接

保存目标 Cloud 后，客户端对各 core 发出显式控制传输重绑，而不是调用普通“全部重启”。有在途页面任务时先到安全边界并停止旧 Cloud 接受新任务，然后关闭旧连接、用新地址重新握手。切换前浏览器关闭则保持关闭；已打开则保持打开但空闲，不能因切换申请或释放槽位。

若某环境重绑失败，UI 同时显示该环境“实际 Cloud”和“目标 Cloud/失败原因”，不把部分完成冒充全量成功。回滚是将目标重新设为原 Cloud 并执行同一重绑流程，而不是重启浏览器。

### 7. offboard 清理使用受限清理会话

Cloud 为 offboard 操作签发短期、单用途、绑定 `offboardId/envKey/accountId/edgeId` 的不透明清理凭证。Electron 可持久化未完成清理意图并启动浏览器无关的受限 core 会话；该会话只能领取和回报指定清理命令，不能注册普通任务能力、不能恢复一般客户会话、不能启动浏览器。

不再复用 `queueStartEnv` 做清理恢复，因为它混入正常自动化启动语义。凭证过期、归属变化或命令不匹配时诚实失败并进入人工处理，不扩大权限。

### 8. 能力协商和渐进兼容

新客户端在 hello/能力协商中声明可选能力 `client_core_browser_executor_v1`。Cloud 只向声明该能力的客户端使用分离后的生命周期和命令；旧客户端继续按旧启动语义工作。既有 `browser_absent_v1` 只作为过渡兼容信号，不再作为产品状态或“无槽位降级”判断。

部署顺序采用 Cloud additive-first，再部署 Edge 源码。协议新增字段保持可选；在旧客户端占比未清零前，Cloud 同时保留旧路径。兼容窗口结束另行提出移除 change，不在本 change 直接删除旧协议。

### 9. 常驻 core 使用独立资源与重起预算

core bootstrap 使用有界并发、指数退避和抖动，预算与浏览器槽位队列完全独立。监督器记录每环境 core RSS、重连次数和稳定在线时间；同一环境达到熔断阈值时停在 `core=error` 等待显式恢复，不形成全环境重起风暴。

实现验收需要覆盖目标上限环境数（当前桌面支持口径）的浏览器关闭常驻内存；若实测不满足资源预算，应优化 core 而不是重新借用浏览器槽位限制 core 数量。

## Risks / Trade-offs

- [常驻 core 增加桌面内存与进程数] → 有界 bootstrap、独立退避/熔断、按环境观测 RSS，并以真实多环境验收数据决定优化。
- [历史绑定被误当作页面当前身份] → Cloud 操作只授权账号归属；任何页面读写仍在 CDP 后读取真实身份并 fail-closed 比对。
- [同一操作同时存在 HTTP 与 WS 两条写路径] → 复用 Cloud 同一领域方法和幂等/CAS 闸，只让传输适配层不同，审计记录实际调用身份。
- [Cloud 切换时产生裂脑] → 先停止旧连接受理、逐环境回报实际目标、失败不伪装全成功，并提供可逆的重绑回滚。
- [旧客户端和新客户端语义分叉] → 可选能力位、Cloud additive-first、保留旧路径和专门兼容测试。
- [错误分类绕过浏览器安全链或误拉浏览器] → 集中注册表、未知项 fail-closed、协议漂移测试覆盖每个命令的唯一类别。
- [浏览器崩溃连带 core] → 独立故障状态与监督策略，验收明确断言 Cloud/非自动化能力继续在线。
- [offboard 清理凭证扩大权限] → 单用途、短期、强绑定、最小命令集、使用后作废和全链路审计。

## Migration Plan

1. Cloud 先增加可选能力协商、customer-auth 环境级窄接口、共用领域方法、清理凭证和旧/新双路径，不改变旧客户端行为。
2. Edge 增加集中式操作分类、浏览器无关 core bootstrap、独立状态模型和控制传输重绑；保持浏览器槽位调度的现有自动化语义。
3. 依次迁移人设、待审编辑、审批受理和 API-only 操作，删除这些入口对 `handle.child`、CDP、浏览器登录态或槽位的准入依赖。
4. 拆分 UI 操作与文案，移除非自动化入口的“启动浏览器”引导；保留绑定未解析、Cloud 失败和页面执行排队的真实差异。
5. 在 Edge/Cloud 执行协议漂移、安全、幂等/CAS、页面任务租约、槽位与多环境监督测试；先部署 Cloud `dev`，再部署 Edge 源码进行 dev 联调。除非用户另行明确要求，不构建或发布桌面安装包。
6. 真机覆盖浏览器关闭、槽位为零/满、AdsPower 不可用、CDP 缺席、浏览器崩溃、Cloud 切换、offboard 清理和旧客户端兼容；无法自动完成的部分记录到真实机器验收 backlog。
7. 回滚时先让 Cloud 停止向新客户端下发分离命令，再回退 Edge；保留 additive 接口直到所有新客户端安全回退。不得通过强开浏览器掩盖回滚后的控制面失败。

## Open Questions

当前架构决策已封闭。实现过程中若发现某项操作同时包含 Cloud 决策和页面执行，必须拆成“受理/排队”与“平台执行/确认”两个阶段，并在 spec delta 中补齐状态语义；不得临时把整个操作归为浏览器前置。

## Context

Native 引擎与页面之间的分工是硬边界：

- **只有引擎能下发可信输入**（`Input.dispatchMouseEvent`）。注入脚本一次求值内发出的合成事件，Facebook 不认（实测 0/8）。
- **只有页面能看见 DOM**。引擎必须通过求值表达式向页面提问。

今天的扫卡是**一次求值**：`probe_facebook_feed` 跑一遍注入脚本，把整屏卡一次性带回（`facebook/feed.rs`）。这在「地址本来就在 DOM 里」的年代成立。现在地址要交互才出现，于是取身份这件事**同时需要边界两侧的能力**，一次求值无法完成。

引擎里已有同形状的多轮编排范例：`facebook/feed_like.rs` 的 `execute_facebook_feed_like_inner`——探测目标（求值）→ 下发可信指针（引擎）→ 复探验证（求值），且带轮次上限与超时。本 change 照该房规走，不新造机制。

## Goals / Non-Goals

**Goals:**

- 在有界开销内，把「找得到但读不出」的卡转成「可上报」。
- 采集失败时保持今天的诚实终态，不降低任何既有诚实度。
- 指针移动只做移动，不产生任何平台可见的写操作。
- cloud / 协议零改动。

**Non-Goals:**

- 不改上报口径。没有地址的卡今天就不上报（页面侧 `cardOf` 取不到地址即返回 null），本 change **不**改这条，也不新增「半成品卡」这种东西。
- 不改 `present_unreportable` 与 Reels 兜底的语义。采集之后仍然一张都没解析出来时，走的还是今天那条路。
- 不做键盘 / 点击等其他交互手段。实测 `focus()` 3/25 不可靠，点击会产生真实写操作（打开帖子），都不在范围内。
- 不改滚动轮次、判稳预算、懒加载阈值（分属另外两条已落地的 change）。
- 不为「时间戳文字被打散」做还原。我们不需要读懂它，只需要知道哪个元素是它。

## Decisions

### D1：采集回合插在「本轮扫卡之后、判定终态之前」

一轮滚动的顺序变为：滚动 → 判稳扫卡 → **身份采集回合** → 用采集后的卡列表判定终态（有新卡则上报，否则落原有原因码阶梯）。

- **为什么不在滚动前**：滚动会让卡换位，先采集等于给一批马上要滚走的卡做无用功。
- **为什么不在终态判定之后**：终态一旦判成「读不出来」就会触发 Reels 兜底授权，采集必须在这之前有机会翻盘。
- **为什么不单独做成一条命令**：会新增协议消息与云端归宿，违背「不新增原因码 / 字段」的约束，也会让云端多一次往返。

### D2：命中判据用「重扫卡列表」，不用「按序号回读那一个链接」

每次指针移动后，重跑既有的扫卡求值；若卡列表中出现了新的有地址卡，即视为命中。

- **为什么不按链接序号回读**：序号会因虚拟化重渲染而错位。调查期实测踩过这个坑——先扫一遍记下坐标 / 序号、十几秒后再用，命中率从 5/5 掉到 0/4，全是过期所致。
- **代价**：每次移动后多一次全量扫卡求值。可接受：该求值本就是每轮都要跑的，且纯读。
- **附带好处**：命中即得到完整卡（作者 / 正文 / 地址），不需要再拼装。

### D3：候选按形状筛，且**筛不出就不试**

候选必须同时满足：地址指向站点根路径、可见、位于视口内、**有文字内容**、**不含图标元素**、**无无障碍标签**、宽高比呈扁长。

- **依据**：实测同卡两个候选——时间戳 124×15 / 有文字 / 无图标 / 无标签 / 悬停后变；「隐藏此帖」36×36 / 无文字 / 含图标 / 有标签 / 悬停后不变。后者是用链接实现的按钮，**本就没有目的地**，试它是纯浪费。
- **为什么「筛不出就不试」**：宁可少解析一张卡，也不要为了多试几下把一轮时间拖长、把指针在无意义的控件上乱移（那反而不像真人）。
- 具体阈值（宽高比、上部占比）实装时用真机标定，以具名常量声明，不留裸字面量。

### D4：只移动，不按下

采集只下发 `mouseMoved`。**MUST NOT** 出现 `mousePressed` / `mouseReleased`。

- 按下会打开帖子或触发按钮，那是平台可见的写操作，且会把账号带离列表面。
- 这条要有测试断言守住：采集路径下发的输入类型集合只允许包含移动。

### D5：三重上限，触顶即停、不重试

每张卡候选上限、每轮采集卡数上限、整轮采集墙钟上限，任一触顶即结束采集回合，用当前已得结果继续。

- **为什么不重试**：地址持久（实测挪走鼠标 / 再悬停 / 滚走滚回都还在），所以「这轮没拿到」的卡下一轮滚回来还有机会，不必在本轮死磕。
- 墙钟上限必须显著小于云端闲置看门狗 240 秒；把这条结论写进代码注释，避免后人调大。

### D6：已解析的卡不参与采集

地址持久 ⇒ 已有地址的卡直接跳过。

- 这条同时是性能优化与拟人考虑：真人不会反复把光标移到同一条已读帖子上。

## Risks / Trade-offs

- **[单轮变慢]** → 最坏约 30 秒（现约 10 秒）。只发生在「有卡待解析」路径；正常有卡时不触发。远小于 240 秒看门狗。
- **[坐标过期导致空移]** → D2 的「移动前现取坐标 + 移动后重扫」结构性消除。调查期已证实这是最容易踩的坑。
- **[候选筛选把时间戳也筛掉]** → 阈值需真机标定；标定前先取宽松值，并在采集回合记录「筛出候选数 / 命中数」以便观察。若某版式时间戳形状不同，宁可漏筛（多试一次）也不误筛（永远试不到）。
- **[指针轨迹反成为指纹]** → 引擎已有拟人轨迹能力。本 change 先用直接移动 + 有界停留；是否叠加轨迹作为后续可调项，不在本轮拍板。
- **[Facebook 改变机制]** → 该行为是平台侧的、可能随时变。采集失败必须无声降级回今天的行为（Reels 兜底），不得因采集不到而让整条滚动失败。这条要有测试断言。
- **[改完首页仍读不出]** → 可能存在「悬停也不换地址」的卡型（调查中未遇到，但样本有限）。采集回合会如实记录命中率，真机验收按实际命中率对，不预设 100%。

## Migration Plan

1. 实装 → `cargo test` + `npm run typecheck` + `npm run test:acceptance` + `npm test` 全过。
2. 真机验证：在本机已登录 Xu Nu 的环境上，冷启动 + 纯程序化滚动建立基线（当前可上报 0 张），再跑改后逻辑，对比可上报卡数与单轮耗时。
3. 合入 master。**本 change 改的是编入 Rust 二进制的引擎与注入脚本，必须重打边缘客户端包才生效。**
4. 回滚：纯边缘改动、无 schema / 无协议变更，回退提交并重打包即可。

## Context

Facebook 软阻断的识别是**纯文字匹配**，落在两处、两仓各一份、无共享模块：

- 边缘 `aidcp-edge/src/facebook/overlay.ts:40` `classifyFacebookOverlayFromSignals()` —— 读整页文字（截 4000 字）分类；命中限流判据（`:86`）返回阻断态并经既有遮罩上报通道上报。
- 云端 `aidcp-automation/src/comm/facebook-throttle-signals.ts:16` `FB_THROTTLE_PHRASES` + `isFacebookThrottleText()` —— 收到上报后匹配证据文案，命中则把风控信号从 `light` 升为 `confirmed`（`captcha-coordinator.ts:122`）。

**现状（已用现役模块实证，非复刻）**：两侧词条集合只含英文与中文短语，法语零命中 ⇒ 边缘判 `none` ⇒ 连上报都不发 ⇒ 云端全静默。

**分级现状（本 change 刻意不动，查证结论）**：`risk-state-machine.ts:101/104` 显示两条路径分级不同且各有其理——

| 路径 | 信号 | 迁移 |
| --- | --- | --- |
| 限流词库命中 | `confirmed` | `normal` → `restricted`（一次刹车） |
| 安全检查 / checkpoint | `light` | `normal` → `warned` → `restricted`（两轮） |

checkpoint 只是 Facebook 的通用安全路由，可能只是身份确认或设备确认，两轮确认是**为了不误伤**的刻意设计（边缘 `overlay.ts:67` 注释明载）。本 change 的目标是让法语走上英文今天已走的那条路，**两条路径的分级各自维持原样**。

**约束**：误报使账号迁入 `restricted`、钉住恢复窗、不自动回滚、只能人工恢复；漏报仅维持现状。代价严重不对称。

## Goals / Non-Goals

**Goals:**
- 法语版软阻断弹窗的识别行为与其英文版**逐字等价**（同判定、同分级、同上报）。
- 消解拉丁语系文字的变音符转录差异，使词条书写有唯一确定形式。
- 两仓词条集合的漂移由测试而非人眼拦截。

**Non-Goals:**
- 不改任何分级、协议、状态机、告警、快照阈值、DB。
- 不预先填充其他语种词条。
- 不解决跨语言脆性本身（属 L4 模型兜底，另一 change 量级）。

## Decisions

### 决策 1：归一化补「去变音符」，而非在词条里写重音字面

**选择**：在两仓的文本归一化中补一步 `normalize('NFD')` + 剥离组合用变音符（`U+0300–U+036F`），与既有的小写化、去撇号、折叠空白并列；词条一律以**纯 ASCII 归一形式**书写。

**否决的替代方案**：词条直接写带重音的法语字面（`contrôle de sécurité est requis`）。

**理由**：带重音的字面有三种失配路径，且都无法在代码评审中看出来——

1. **Unicode 等价形式**：`é` 可以是预组合的 `U+00E9`，也可以是 `e` + `U+0301` 的组合序列。页面 `innerText` 用哪种不受我们控制，两者字面比较不相等。
2. **转录差异**：本 change 的文案来自用户截图转录，重音已在转录中丢失（`fonctionnalite`、`contrale`、`securite`）。真实 DOM 一定带重音，但**将来的每一次文案取证都会再经历一次这种损耗**，去重音归一使取证与词条之间不再有这条缝。
3. **地区变体**：同一措辞在不同地区可能重音标注不同。

**为何不引入回归**：既有词条全部是英文与中文，两者均不含变音符，去变音符对它们是恒等变换。对**输入文本**，去变音符只会使匹配更宽容（`áction blocked` → `action blocked`），而更宽容的方向落在既有的英文长短语上，不构成新的误报类别。中日韩文字不含 `U+0300–U+036F` 区间的组合记号，不受影响。

**代价**（接受）：理论上存在「两个不同拉丁词去重音后同形」而造成误命中的可能。因词条均为长句片段而非单词，该风险可忽略。

### 决策 2：只取两条词条，且显式排除申诉话术

**选择**：
- `controle de securite est requis`
- `cette fonctionnalite nest pas disponible`

**显式排除**：`ne va pas a lencontre des standards de la communaute`（「如果你认为这不违反社群规范，告诉我们」）。

**理由**：第三句是 Facebook 的**申诉入口话术**，附在一切违规告知之后，包括通知中心里的**陈年**内容删除通知。把它做成判据，则一条几个月前的旧通知就能把账号打进 `restricted`。这与云端删除 `we removed your` 的判断完全同源（见 `facebook-throttle-signals.ts:32` 的注释）——措辞过泛，误报代价不可承受。

**两条入选词条的专属性论证**：
- `est requis` 是第一条的必需限定。裸的 `contrôle de sécurité` 在 Facebook 法语安全设置页里是**功能名**，广泛出现；加上「是必需的」之后，语义从「这里有个功能」变为「平台要求你现在做」，只出现在阻断语境。
- 第二条的英文对等条目（`this feature is not available`）今天已在词库内，本条不引入新的风险类别，只是补齐同一语义的法语面。口径一致优于逐条重新评估。

**关于撇号**：`n'est` 经去撇号归一后为 `nest`，故词条写作 `nest pas disponible`。这与既有英文词条 `youre temporarily blocked`、`you cant use this feature right now` 的写法一致（同样是去撇号后的形式）。

**关于未真机逐字坐实**：沿用中文那次的定案理由——**失败方向是安全的**。词条不命中即回落今天的静默行为，不误伤；要防的只有反向误报，而误报由词条构造（长句片段 + 排除申诉话术）对冲，不由等待真机对冲。

### 决策 3：边缘侧新增独立集合常量，不改既有正则

**选择**：在边缘新增 `FB_THROTTLE_FR_PHRASES` 常量数组 + 一个归一函数，接入既有阻断判据分支（`overlay.ts:84` 的 `if`），与既有正则并列为 OR 条件。

**否决的替代方案**：把法语短语塞进 `:86` 那条既有大正则。

**理由**：既有正则跑在**未做撇号 / 变音符归一**的 `textLower` 上；把归一化引入那条正则会改变全部既有英文与中文判据的输入面，风险远超收益。独立集合 + 独立归一是中文那次（`FB_THROTTLE_ZH_FREQUENCY_PHRASES`）已验证的模式，照用。

**两仓归一函数刻意保持行为一致**（小写 → 去撇号 → 去变音符 → 折叠空白），使两侧词条可以逐字相同、可互为断言对象。

### 决策 4：漂移由两侧单测各锁一份集合拦截

沿用既有模式（无跨仓共享基建，成本 > 收益）。两侧测试各自把法语词条集合作为字面量断言；任一侧新增或删除而另一侧未同步 ⇒ 该侧测试失败。

**这一条不是形式主义**：云端词库注释（`:32`）记录过一条真实的死代码——某短语只在云端存在，边缘不认故永不上报，云端永远收不到能命中它的文本。词条集合的两侧对齐是使判据**可达**的前提。

## Risks / Trade-offs

- **[词条误报 → 账号停摆至恢复窗结束且需人工恢复]** → 两条词条均为长专属句片段；显式排除申诉话术；`est requis` 限定使其脱离设置页语境。失败方向安全（不命中 = 回落现状）。
- **[未经真机 CDP 逐字坐实，法语原文可能与转录不完全一致]** → 去变音符归一已消解重音一路的差异；撇号由既有去撇号归一消解；剩余风险是**用词本身不同**（例如 FB 实际用 `Une vérification de sécurité` 而非 `Un contrôle de sécurité`），后果是两条词条空转、回落今天的静默行为，不误伤。登记为真机验收项，不阻塞码级实装。
- **[去变音符使匹配更宽容，理论上扩大误报面]** → 既有词条不含变音符，恒等变换；宽容方向只作用于输入文本，且落在长句片段上。评估为可忽略。
- **[本 change 只治一张卡片，下一个语种仍会静默]** → 已在 Non-Goals 显式承认，不假装解决；去变音符归一为拉丁语系留了干净的扩展缝，彻底解法属 L4 模型兜底。

## Migration Plan

无 DB 迁移、无协议改动、无配置项。两仓各改一个纯函数模块 + 各补一份单测。

- **部署**：edge 随客户端发版（代码改动默认收尾只到 commit / push，出安装包属用户显式触发）；automation 按既有安全序列部署 `dev`。
- **回滚**：删除新增词条即回落今天的行为；无状态、无数据残留。已迁入 `restricted` 的账号按既有人工恢复流程处理（本 change 不改恢复语义）。

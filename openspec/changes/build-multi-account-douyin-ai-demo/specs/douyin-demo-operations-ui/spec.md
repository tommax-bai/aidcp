## ADDED Requirements

### Requirement: The operations UI uses the operator authorization boundary
The operations UI SHALL require the configured operator token before loading account, QR, timeline, automation, source-health, or delivery state. UI mutation requests and live-event subscriptions MUST use the same authorization boundary as the HTTP API. The UI MUST NOT embed the token in links, QR payloads, browser history, screenshots generated by the service, or server-rendered state, and an authorization failure MUST clear previously rendered sensitive account state.

#### Scenario: Operator session is unauthorized
- **WHEN** the UI loads or refreshes with a missing or invalid operator token
- **THEN** it renders an authorization prompt or failure and no account or timeline data

#### Scenario: Live subscription loses authorization
- **WHEN** the authenticated live-event subscription is rejected or closed for authorization failure
- **THEN** the UI stops applying live events and requires reauthorization before fetching current state

### Requirement: Platform mode and experimental boundaries are always visible
The UI SHALL display the process platform mode and write gate on every account and write-capable view as fixture, real read-only, or real writes enabled. Fixture mode MUST be labeled as deterministic simulation with no Douyin activity. Real mode MUST be labeled experimental and dependent on undocumented web interfaces except where an official capability is explicitly selected. The UI MUST NOT infer write enablement from health or successful reads, and MUST NOT describe the demo as fully browserless when QR authorization or a configured comment reply requires headed Chromium.

#### Scenario: Fixture mode is active
- **WHEN** an operator views the dashboard in fixture mode
- **THEN** the UI visibly states that accounts, inbound events, and receipts are simulated and no platform action occurs

#### Scenario: Real mode is read-only
- **WHEN** real mode is selected without process-level real-write enablement
- **THEN** the UI visibly states real read-only and does not imply that an available account capability can currently dispatch

#### Scenario: Chromium comment capability is selected
- **WHEN** a real account uses chromium_worker comment delivery
- **THEN** the account view states that Chromium starts transiently for QR authorization and eligible comment writes

### Requirement: Account and QR states reflect server evidence
The UI SHALL project each account's stable sanitized identity, authorization state, runtime state, and last current evidence separately. QR views SHALL distinguish starting, ready, scanned, confirming, authorized, expired, canceled, challenge, identity-mismatch, and failed states where applicable, and SHALL display expiry without treating scan alone as authorization. Account status MUST NOT become authorized until encrypted session persistence, identity binding, and the required post-login probe are confirmed. Reauthorization and logout actions MUST target one explicit account or attempt.

#### Scenario: QR code has been scanned only
- **WHEN** the platform reports a scan but has not confirmed login and identity
- **THEN** the UI displays scanned or confirming and does not display the account as authorized

#### Scenario: First-party QR creation is still pending
- **WHEN** the operator has requested a real QR but the official Creator page has not returned the QR challenge
- **THEN** the UI immediately shows that Douyin is preparing the QR with the observed 5–20 second range and does not claim that the code was scanned

#### Scenario: Restored account needs reauthorization
- **WHEN** the server rejects a restored session during its identity or read-capability probe
- **THEN** the UI shows reauthorization-required with the sanitized reason and offers an explicit new QR attempt

### Requirement: Official secondary verification stays bounded and operator authenticated
When a pending real authorization requires Douyin's official secondary verification, the UI SHALL display only a current element-only image of the single admitted official Verify Center surface from that same bounded browser context after operator authentication. That surface may be the exact allowlisted Verify Center iframe, the exact structurally verified same-document official second-validation dialog, or the deepest iframe leaf of one verified nested dialog/iframe tree; it MUST NOT be the Creator viewport. The UI MAY submit an exact-account click, one-shot drag, bounded scroll, at-most-64-character temporary text, or allowlisted key through same-origin requests carrying both the snapshot revision used to fetch the image and the one-use frame identity returned with that image. It SHALL validate the server-returned absolute expiry and bounded remaining lifetime, derive a local deadline, enable controls only after that exact JPEG decodes and the remaining safety window is recomputed, keep the current operable frame stable, and hard-disable and replace it before expiry even if timers were throttled or a pointer/wheel gesture was unfinished. Pointer and accumulated-wheel gestures SHALL remain bound to the revision and frame on which they started but MAY be canceled at that hard cutoff. The UI SHALL invalidate the image and clear temporary text before every input, accept at most one input from one frame, and wait for a fresh JPEG before enabling another input. It SHALL parse only bounded sanitized error codes: a missing, ambiguous, pending-UC-renderer, or unsupported-UC surface retries only the frame read with truthful copy, a stale frame fetches a fresh frame, and only an actual stale revision or ended verification blocks that revision and refreshes the account snapshot. It SHALL NOT automatically replay an input rejected by a stale revision or frame identity, and SHALL stop polling, disable controls, clear temporary text, and revoke local frame URLs when the account changes, the console locks, verification completes, or the attempt terminates. It MUST NOT place the operator token in the frame URL, persist frame identities, screenshots or temporary input, or expose Cookies, QR tokens, decision configuration, dynamic renderer URLs, browser endpoints, clipboard, upload, download, arbitrary navigation, Escape, DevTools, or script execution. Completion of the visible verification SHALL remain authorizing until the server confirms stable identity, IM bootstrap, and a structurally valid Douyin-scoped Cookie set.

#### Scenario: Operator completes a slider in the official verification view
- **WHEN** the authenticated operator drags once across the decoded current verification frame with that frame's account revision and one-use frame identity
- **THEN** the service applies one bounded drag to the same pending page, stores neither the frame nor coordinates, and waits for the official QR status and later identity/session proofs

#### Scenario: Verification input is stale
- **WHEN** the account revision changes or the decoded frame identity expires, is consumed, or is replaced before a click, drag, text, scroll, or key request is admitted
- **THEN** the server applies no input, returns a conflict, and the UI refreshes without automatically replaying that action

#### Scenario: Verification surface is temporarily unavailable
- **WHEN** a frame read reports a sanitized missing or ambiguous official surface while the same account revision remains current
- **THEN** the UI states the actual temporary condition, keeps controls disabled, retries only the frame read, and does not claim that authorization state changed

### Requirement: Source health is projected independently and honestly
For each account, the UI SHALL display direct-message and comment source state, last successful evidence time, last sanitized error, and baseline state independently. A TCP or WebSocket connection opening MUST NOT be shown as direct-message healthy before protocol subscription acknowledgement, and a completed HTTP request MUST NOT be shown as comment healthy when its schema is invalid. A healthy source MUST NOT hide another source's degraded, reconnecting, baselining, stopped, or reauthorization-required state.

#### Scenario: Direct messages are healthy and comments are degraded
- **WHEN** the server reports an acknowledged direct-message subscription and a comment schema-drift failure
- **THEN** the UI displays direct messages healthy and comments degraded with separate evidence timestamps

#### Scenario: Comment baseline is still running
- **WHEN** an account has started comment reads but has not durably completed its historical baseline
- **THEN** the UI displays baselining and does not imply that observed comments are eligible for auto-reply

### Requirement: Reply capability and transient browser use are explicit
The account view SHALL display exactly one comment capability state: official_api, chromium_worker, or unavailable, together with its current admission reason. It MUST NOT imply that comment writes will fall back to another route. While a bounded headed Chromium comment worker exists, the UI SHALL show its account, one target-safe work item, and lifecycle state without exposing selectors, browser endpoints, cookies, or raw target content; after closure it SHALL return to idle with the terminal delivery outcome.

#### Scenario: Official route is misconfigured
- **WHEN** the server reports official_api selected but required permission is not verified
- **THEN** the UI shows official_api unavailable for writes and does not advertise a Chromium fallback

#### Scenario: Comment worker closes with uncertainty
- **WHEN** a headed Chromium worker closes after dispatch without a verifiable receipt
- **THEN** the UI shows the worker idle and the delivery submitted_unknown rather than failed or confirmed

### Requirement: Timeline preserves baseline, deduplication, generation, and delivery truth
The UI SHALL render a sanitized durable timeline that correlates one normalized inbound identity with baseline or new classification, eligibility, generation ownership and outcome, delivery identity, route, dispatch evidence, and terminal state. Replayed deduplicated events MUST NOT appear as new reply work. confirmed, rejected, failed_not_submitted, submitted_unknown, and blocked MUST be visually and semantically distinct, and submitted_unknown MUST NOT increment confirmed counts or expose a retry action for the same delivery identity.

#### Scenario: Replayed inbound event is deduplicated
- **WHEN** the server reports a replay of an already stored platform event
- **THEN** the timeline retains one inbound item and no second generation or send row appears

#### Scenario: Delivery remains submitted unknown
- **WHEN** a delivery terminal state is submitted_unknown
- **THEN** the timeline shows that the write may have occurred, excludes it from success totals, and offers no same-identity retry

### Requirement: Automation controls expose current ownership and configuration
The UI SHALL provide explicit account-scoped stop and resume controls and SHALL display the authoritative server automation state, configuration revision, held item count, current generation owner, and current delivery owner when present. A button click or accepted HTTP request MUST NOT alone be shown as completed state; the UI MUST converge from the subsequent authoritative read or event. Stopping generation MUST NOT relabel an already dispatched delivery or hide its terminal uncertainty.

#### Scenario: Stop is accepted while a generation is active
- **WHEN** the operator requests stop and the server reports the generation canceled before dispatch
- **THEN** the UI shows automation stopped, no active generation owner, and the canceled or held item disposition

#### Scenario: Stop occurs after dispatch
- **WHEN** the operator stops automation after a delivery has already been dispatched
- **THEN** the UI preserves the delivery's confirmed, rejected, or submitted_unknown outcome independently of the stopped automation state

### Requirement: Mutations are exact-target and revision checked
Every account, QR, automation, and reply mutation SHALL include the exact server-issued target identity and its current revision. The server MUST reject a stale or mismatched revision with a conflict and MUST NOT apply the action to a replacement account, inbound item, authorization attempt, or delivery. The UI SHALL refresh authoritative state after a conflict rather than silently resubmitting against a newer target.

#### Scenario: Account revision changed before logout
- **WHEN** an operator submits logout with a revision older than the current account projection
- **THEN** the server rejects the mutation as stale, logs out no account, and the UI refreshes the current state

### Requirement: Secrets and private protocol data are never rendered
The operations UI SHALL consume sanitized view models only. It MUST NOT render or make downloadable platform cookies, session tokens, QR payload internals, request signatures, raw WebSocket frames, chat-llm credentials, encryption keys, browser debug endpoints, or unredacted protocol error bodies. Diagnostic views SHALL expose bounded reason codes, timestamps, correlation identities, adapter mode, and schema versions sufficient for operation without credential disclosure.

#### Scenario: Real adapter returns a raw error body
- **WHEN** a Douyin adapter failure contains cookies, signatures, or personal payload fields
- **THEN** the UI receives only the sanitized reason code and bounded diagnostic metadata
